# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Scoped to `apps/osionos/app`. The repo-root `/CLAUDE.md` (monorepo topology, grobase BaaS, lifecycle Makefile) is the parent authority and is always in context — this file only adds app-specific detail. The hard rules in §Conventions override defaults.

## What this is

**osionos** (npm name `osionos-playground`) is a Notion-style **block editor that grew into a full collaborative workspace**: React 19 + Vite 6 + TypeScript, served at `https://localhost:3001`. Beyond the document/"Second Brain" editor it ships chat channels & DMs, live-database views (charts/maps/equations), self-hosted video rooms, and an in-app BaaS tenant console — see **§Shipped capabilities beyond the editor**. It is one frontend of the `ft_transcendence` monorepo and reaches the **grobase BaaS through a Node bridge**, never directly. Source is **feature-sliced**; it embeds a force-graph engine workspace package and two large vendored sub-repos.

## Commands — Docker-first, never run Node on the host

**Every** `package.json` script (except `lighthouse`) is a thin shim: it calls `scripts/docker-run.sh <target>` (or `docker-dev.sh`), which on the **host** spins up an ephemeral `docker compose -f docker-compose.base.yml -f docker-compose.dev.yml run --rm --no-deps <service>` and re-execs **the same script inside the container** (the `/.dockerenv` / `OSIONOS_IN_DOCKER=1` check is the fork). So run scripts normally — they self-Dockerize. There is no host `node_modules`; host `node` is absent on purpose. **Exceptions to the `run --rm` shape:** `dev` (and `bridge-api`) use `up -d --build` for a *long-running* container, not an ephemeral run; `dev` also boots the notion-database-sys Mongo contract server (on 27017; the playground's own Mongo publishes on 27018) before Vite.

```sh
npm run dev          # docker-dev.sh: starts the notion-database-sys Mongo contract server, then Vite HMR on :3001
npm run build        # graph-engine tsc → root tsc → vite build  (typecheck-gated)  → ./build
npm run test:quality # THE gate: graph-engine tsc → root tsc → eslint src/ packages/ --max-warnings=0
npm run typecheck    # the two tsc passes only        npm run lint[:fix]  # eslint only
npm run test:e2e     # Playwright (service: browser-tests). :serial (--workers=1), :smoke (tests/e2e/smoke)
npm run test:canvas  # block-editor model/serialization/transaction tests (node --test, service: playground)
npm run test:bridge  # website→editor auth-handoff tests   npm run test:doctor  # validate Playwright env
bash scripts/check-style-tokens.sh   # style-token guard (also runs as the final step of test:quality)
```

- **Two compose services**, deliberately separate node_modules volumes: `playground` (build/typecheck/lint/quality/canvas/bridge/dev) vs `browser-tests` (e2e/doctor/bench).
- **Run a single test:** `npm run test:e2e -- -g "pattern"` or `npm run test:e2e -- tests/e2e/functional/<file>.spec.mjs` (args after `--` pass through to playwright). **e2e specs are `.mjs`** (under `tests/e2e/{functional,smoke,persistence,visual}`, plus a few loose graph-engine/benchmark specs at the `tests/e2e/` root; shared helpers in `tests/e2e/support/`), **not** `.spec.ts`; canvas tests are `.test.ts` under `tests/canvas/` (run with node `--experimental-strip-types`); `tests/browser/` is a separate JSX-harness tree (see its `COVERAGE_MATRIX.md`).
- From the **repo root** the equivalent is `docker compose exec osionos-app npm run <script>` (needs the long-running service up via `docker compose up -d --build osionos-app`).
- **`npm run lighthouse`** is the only host script (there is no `docker-run.sh lighthouse` host arm — it falls through to Usage). **`bridge-api`** is special: it `cd`s to the monorepo root and builds the `osionos-bridge` service there. Other `docker-run.sh` targets not shown above: `build-offline` (blanks `VITE_API_URL`/all `VITE_BAAS_*` — the offline prod build matching the Playwright env), `preview`, `bench-layout` (the `graph-bench`/`pane-resize-bench`/`dashboard-bench` scripts have **no** target — run them directly), and `mcp-claude` = `npm run mcp:claude` (the in-Docker MCP server). `test:setup` aliases `test:doctor`; plain `npm run test` aliases `test:e2e`.

## Architecture (the big picture)

**Feature-sliced, dependency points downward:** `app → pages → widgets → features → entities → shared` — but **honor-system: the only enforced import firewall is on `packages/graph-engine/src/core/**`, not the app slices** (a widget importing a page lints clean; rely on review). A **feature** is one capability slice (21 total — editor/core: `block-editor`, `auth`, `second-brain`, `baas-console`, `raw-mode`, `slash-commands`, `page-management`, `ui-orchestrator`, `settings`, `theme`, `share`; collab/social: `chat`, `group-chat`, `collab`, `communities`, `connections`, `connectors`, `search`; plus `marketplace`, `template-designer`, and the flag-gated `automations`); a **widget** is a page-level UI assembly wiring features+entities+`shared/ui` into a mountable region (23 total: `sidebar`, `top-bar`, `page-renderer`, the routing-critical `workspace-grid`, `graph-explorer`, `database-view`, `page-toc`, `home-variants`, `admin-space`, `embed-app`, plus the collab widgets `channel-list`/`channel-messages`/`chat-shell`/`messages-view`/`dm-list`/`contact-dock`/`collab-browse`/`notifications`/`activity-rail`/`profile-page`/`people-search`/`video-room`/`agent-conversation`). Older slices expose a barrel `index.ts`, but there is **no barrel at slice roots** and ~20 slices have none — all the chat/collab/communities/connections features plus `widgets/page-toc`, `people-search`, `profile-page`, `messages-view`, `notifications`, `contact-dock`, `embed-app`, and `features/settings`/`theme`/`ui-orchestrator` — import those by deep path.

**No react-router.** "Routing" is a VSCode-style **tab/pane layout tree** in the `useWorkspaceLayout` zustand store — a 7-file module under `src/widgets/workspace-grid/model/` (`workspaceLayout.ts` store, `layoutTree.ts` types, `layoutMutations.ts`, `layoutPersist.ts` [localStorage key `osionos.workspace.layout.v1`], `layoutSync.ts`, `pageToTab.ts`, `paneDropZone.ts`). The real view dispatch is the **`if (tab.kind === …)` guard chain** (NOT a `switch` — grepping for `switch (tab.kind)` finds nothing) in `widgets/page-renderer/ui/PaneContent.tsx` (`PaneContentImpl`): kinds `home`/`folder`/`trash`/`database`/`profile`/`console`/`admin`/`chat`/`messages`/`collab`/`community`/`channel`|`group`/`embed`, default → editable `PageTabView`. URL is used only for deep-links (`?home=`, `?view=`, `bridge_token`, dev `/__styleguide`). **Two sources of truth for "open page"** — the layout store and the legacy `pageStore.activePage` — are kept in sync in **both directions but by two different seams**: tab → `activePage` via `layoutSync.ts:mirrorActiveTab` (from `workspaceLayout.commit`), and `activePage` → tab via `workspaceLayout.syncFromActivePage` + `pageToTab.ts:activePageToTab` (committed with `mirror=false` so it does **not** loop back). Edit one side without its mirror — or make the reverse sync mirror back — and the header/graph/session-restore desync.

**Performance is a first-class design concern.** Surfaces are code-split via `React.lazy` using **deep import paths, never widget barrels** (importing `@/widgets/page-renderer` staples the whole ~1.1MB editor onto the warm chunk). `src/app/lazyAppRegions.tsx` splits the app **shell**; the per-pane editor/database/channel/console splits live in `src/widgets/page-renderer/ui/lazyViews.tsx`. **Every pane mounts its own live editable editor** (`LazyOsionosPage` keyed by `pageId`; the pane passes `activePageRef` so it does **not** subscribe to the global `activePage` — typing in one pane doesn't re-render the others). Background panes stay cheap via `widgets/workspace-grid/ui/PaneView.tsx`: a shared **serial idle queue** mounts one deferred pane per idle tick (opening 8 panes costs ~1 up front) + `contain: layout paint` per-pane isolation. (The old focused-pane/`PageBlocksRenderer`-preview switch is gone; `PageBlocksRenderer` survives as the read-only renderer for hovers/marketplace/profile.) Lazy views export **named** components adapted to default (`.then(m => ({ default: m.X }))`). Perf tooling: `src/shared/lib/perf/` is a built-in profiler harness (React-commit/event-timing ring buffers capped at 5k) — on in Vite dev, elsewhere via `localStorage.setItem('osio:perf','1')`; console globals `__perfSeed(n)`/`__perfType(n)`/`__perfEditorType(n)`/`__perfRun()` seed synthetic pages and drive typing benchmarks (see its README). `ANALYZE=1` on a build emits `build/stats-chunks.json` — a dependency-free per-chunk module-size breakdown (plugin in `vite.config.ts`) for hunting warm-chunk bloat.

**Feature flags & the editor selection/keyboard layer** — app-level flags live in `src/shared/config/featureFlags.ts` (6 as of this branch — default **ON**: `osio.canvas.v2`, `osio.blockselect`, `osio.automations`, `osio.db.server`; default **OFF**: `osio.profile.template`, `osio.collab.shared`; each toggles via `?<flag>=1` URL param, a localStorage key of the same name, or a `VITE_*` env — distinct from the second-brain-local `featureFlag.ts` and from the vendored notion-database-sys *view* automations). Three shipped systems ride them: (1) **`osio.blockselect`** — a cross-cutting selection layer in `features/block-editor/model/`: `blockSelectionStore.ts` (zustand single source of truth for selected block ids, keyed by surface `sourceKey` so background panes never see a stale selection), `useSurfaceMarquee`/`marqueeGeometry` (full-page rubber-band select), `editorCommandBus.ts` (registry of the active editor's imperative handle), `blockClipboard.ts` + `services/page-actions/blockClipboardSerialize.ts`, and the right-click menu `usePageContextMenu`/`pageContextMenuSections` — all wired in `BlockEditorSurface.tsx`. (2) **`osio.automations`** — `features/automations`: a data-driven VSCode-style shortcut manager (each shortcut is a keyboard-trigger → command record; commands in `model/commands/`, defaults + zustand-persisted user overrides with JSON export/import in `useAutomationStore`); its document-level `useAutomationDispatcher` (reads the selection store + command bus, owns the bound chords when ON) mounts **once in `App.tsx`**. (3) **`osio.db.server`** — server-side persistence for user-created object databases (the inline `/database` blocks, `source=adapter`): schema, views AND records live in Postgres owner-isolated via the bridge; localStorage stays a write-through offline cache (the offline/Playwright build has no bridge URL, so sync no-ops there).

**State / page store** (`src/store/`): `usePageStore` is the central client cache of the workspace page tree. It is split — `usePageStore.ts` (assembler) + `pageStore.helpers.ts` (pure recursive block-tree ops + localStorage cache) + `pageStore.actions.ts` (async/network) + `pageStore.persistence.ts` (**deliberate no-op seam** — do not "fix" the empty stubs) — to isolate pure logic from network/persistence (combined ~2200 lines: 489/831/808/44 — only the no-op `persistence.ts` is actually within the ≤200 convention; the others are still refactor targets). Two parallel persistence layers: (1) localStorage page cache, (2) **BaaS sync via an offline-first outbox/ledger** (`src/store/sync/` + `src/shared/sync/outboxLedger.ts`). **BaaS is the source of truth; store+localStorage are a cache** (last-write-wins by `updatedAt`). Sync invariants: ledger advances **only on server confirm**; a transient failure stops the whole batch (anti-429-storm); content is lazy and `pageStamp` uses a `CONTENT_UNLOADED` sentinel + `pageOutbox` omits `content` when unloaded so an unloaded page never wipes the server copy. Page sync mounts once at `App.tsx` (`usePageSync`, hydrate-then-outbox, debounce 800ms, retry 15s→120s). A **second, parallel** outbox/ledger engine exists for second-brain notes (`src/features/second-brain/sync/noteSyncLedger.ts`, key `osio-sb-synced-notes`) that — despite `outboxLedger.ts`'s "engine-agnostic" docstring — does **not** reuse the shared primitive; change both if you touch ledger semantics.

**Data / bridge** (`src/shared/api/`, `scripts/bridge-api.mjs`): **two separate transports to grobase, do not conflate them.** (1) Page/workspace data → the **bridge** at `VITE_API_URL` (`https://localhost:4000`, `scripts/bridge-api.mjs`) — the trust boundary holding the BaaS service-role key and proxying PostgREST/Kong. The bridge is **modular**: `bridge-api.mjs` mounts 15 sibling modules (`bridge-chat`/`-feed`/`-profile`/`-perms`/`-rtc`/`-graph`/`-graph-data`/`-collab`/`-communities`/`-connector`/`-records`/`-notify`/`-oauth`/`-agent`/`-social`; shared plumbing in `bridge-social-core.mjs`/`bridge-storage-core.mjs`; `bridge-chat.mjs` itself mounts second-level helpers `bridge-chat-media`/`-search`/`-threads` + shared `bridge-ratelimit`; Node built-ins only, ~7.6k LoC across 23 `scripts/bridge-*.mjs`, one of which is the `bridge-rtc.test.mjs` test), so it also serves chat, feed, profiles, ABAC perms, and `POST /api/rtc/token` LiveKit grants, and publishes realtime events **server-side** to the Rust gateway at `REALTIME_PUBLISH_URL` (`mini-baas-realtime:4000`, best-effort). (2) Realtime (chat/feed/live-DB) → **Kong directly** at `VITE_BAAS_URL` (`:8000`, `/realtime/v1/ws`), gated by `VITE_CHAT_WS`/credential, degrading to 15s polling without a token. `shared/api/baas-client.ts` (direct `/query/v1`) is **dead** (`VITE_BAAS_ENABLED=false`). Auth carries an opaque **`osionos_v1.` app-session token** (HMAC, distinct from gotrue JWTs — `pageApiJwtFromSessionToken` vs `apiJwtFromSessionToken`; wrong one silently skips the fetch). The user store publishes itself to **`globalThis.__playgroundUserStore`** — a load-bearing decoupling seam read by the api client (`shared/api/client.ts`), the page-access ACL layer (`shared/lib/auth/pageAccess.ts`), and vendored realtime/feed code; not a hack to remove. Realtime credential resolution reads the app JWT off this same global (`activePageJwt()`/`activeJwt()`) when `VITE_BAAS_REALTIME_TOKEN` is unset — so a missing/expired app session knocks realtime down to the poll, the same root cause as a skipped page fetch.

**Graph engine** — `packages/graph-engine/` (`@osionos/graph-engine`), the Second-Brain force graph: Canvas2D + Web-Worker d3-force, "aurora-glass" visual language. **Framework-agnostic, consumed like an installed plugin**: host builds a `GraphModel` (pure backend-agnostic projection with O(1) indexes; `NodeId == BaaS global id` so layout stays stable across rebuilds) and hands it to the thin React adapter; the engine never fetches. Resolves via vite/tsconfig alias, **not** node_modules; ships as TS source (no build step) so consumers import CSS explicitly. **ESLint import firewall** (`eslint.config.js`): `packages/graph-engine/src/core/**` may not import `@/*` or `react`/`react-dom` — a `no-restricted-imports` **error** rule (the *only* import boundary in the repo), so a violation still type-checks but fails the eslint/`test:quality` gate. Worker falls back to an in-process engine when `Worker` is undefined (tests/SSR; `layoutBridge.ts:createWorker`); the tick-driver `core/layout/layoutEngine.ts` (wrapping the d3-force sim in `forceLayout.ts`) is imported verbatim by both worker and fallback, so physics is never duplicated. The engine is framework-agnostic but **not** visually self-contained — its theme resolves the host's `--osio-*` tokens (`global.css`, "Warm Constellation" block) at runtime, so renaming those tokens silently changes graph colors.

**Vendored sub-repos** under `src/shared/` — large, with their own toolchains; **do not edit as ordinary app code.** They are excluded from app **ESLint** (ignored in `eslint.config.js`) but only **partially from tsc**: `tsconfig.json` excludes only `notion-database-sys/{packages,playground,examples,vendor}`, so `notion-database-sys/src/` (the `@notion-db` alias target) and **all of `lib/markengine`** are in the app compile graph — a type error there can break `test:quality` (`skipLibCheck` softens but doesn't remove this).
- `notion-database-sys/` (the "object database"; **a registered git submodule** — `.gitmodules`, `git@github.com:Univers42/notion-database-sys.git`, currently checked out dirty so `git status` shows it `?`; commit inside it first, then the parent records the SHA) → wired via `@notion-db/*` aliases. Exact mapping (must stay identical in **both** `vite.config.ts` and `tsconfig.json`): `@notion-db/object-database` → `…/src/component/index.ts`, `@notion-db/contract-types` → `…/packages/contract-types/src/index.ts`, theme/styles css → `…/src/index.css`.
- `lib/markengine/` (Markdown↔block AST: `parseMarkdownToBlocks`, `parseInlineMarkdown`, `detectBlockType`) → **no alias**; imported as `@/shared/lib/markengine` via the generic `@ → src` alias, so it is invisible to package-name tooling.

**Styling** — token values live in **exactly one file**, `src/app/styles/global.css` (~1600 lines; `--osio-*` custom properties across three orthogonal axes: light + `[data-theme=dark]`, ×7 `[data-palette=…]` color palettes (`contrast`/`maximal`/`midnight`/`mono`/`nord`/`rose`/`solarized`) mirrored from `src/shared/config/palettes.generated.ts` (the 7 non-default entries; `light`/`dark` map to `[data-theme]`, not `[data-palette]`), plus motion/elevation/density design tokens). **Tailwind v4 CSS-first — there is no `tailwind.config.js`/postcss config**; the `@theme` block maps utilities onto tokens. SCSS `$`-vars alias `var(--osio-*)` from `src/app/styles/base/tokens/` (`_colors`/`_spacing`/`_typography.scss`; mixins in `abstracts/`) — a few layout-dimension `$`-vars like `$sidebar-width: 260px` are literal pixel constants; components read tokens, never branch on theme in JS. `scripts/check-style-tokens.sh` (dependency-free) forbids raw color literals across **all** app CSS/SCSS (excluding the `src/app/styles/**` token files + vendored trees) and **runs as the final step of `test:quality`**.

## Shipped capabilities beyond the editor

osionos is a full workspace, not just a doc editor — these surfaces are real and sidebar-reachable, each opening as a `tab.kind` pane (see `PaneContent.tsx`):

- **Collaboration / social** — chat `channel-list`/`channel-messages` (model split into per-concern hooks: `useChannelHistory`/`useChannelLive`/`useChannelActions`/`useChannelInfo`, plus `useThread`/`useMessageSearch`/`useAttachmentUpload`/`useVoiceRecorder`/`useChannelReceipts`/`useComposerDraft`), `dm-list` direct messages, `profile-page`, `people-search`, a feed, and `agent-conversation`. Backed by the modular bridge (`bridge-chat`/`bridge-feed`/`bridge-profile`) + the `services/realtime-messages` WS service. Cross-user delivery is gated by `VITE_CHAT_WS` (default ON when a realtime token resolves); a same-tab `BroadcastChannel` echo always runs underneath (additive, never replaced).
- **Video rooms** — `widgets/video-room` = self-hosted **LiveKit** (`livekit-client`): grant from `POST /api/rtc/token` (`bridge-rtc`), connect to the `livekit` compose service at `ws://127.0.0.1:7880` (loopback ws is mixed-content-exempt). Also embeds as an in-channel `CallPanel` via a deep lazy import to keep `livekit-client` out of the warm chunk.
- **Database plane** — `widgets/database-view`: Notion-style DB blocks with **live-DB adapters** (`liveDatabaseAdapter`/`liveMountTables`/`dataSourceProvider`) + an object-database adapter, plus per-tenant view presets (gourmand/agency/commerce/opsActivity). Chart/map/equation rendering lives mostly **inside the `notion-database-sys` submodule** (echarts/recharts/leaflet/katex/mermaid) — the app-level `echarts`/`recharts`/`leaflet`/`katex`/`mermaid`/`pdf-lib` deps exist for these blocks. Opens on `tab.kind === 'database'`; tests are `tests/canvas/live-*.test.ts`.
- **BaaS tenant console** — `features/baas-console` (`tab.kind === 'console'`): API-key CRUD, usage metering, plan, tenant account — the osionos-side UI for grobase's flag-gated **Track-B** managed-cloud metering/billing.
- **page-toc / `PageOutlineRail`** — a hover TOC minimap pinned right of the reading column. Purely presentational: scans `heading_1..3` blocks from the **rendered editor DOM** (`MutationObserver` + `IntersectionObserver` scroll-spy), never fetches; mounted in `pages/notion-page/ui/NotionPage.tsx` only when the page has no full-page layout and ≥2 headings (else returns `null`). No `index.ts` barrel — import by deep path.
- **second-brain is partly live, not purely planned** — `features/second-brain/baas/` is an **implemented** BaaS txn/graph client (`baasTxnClient`, `buildNoteTxn`, `baasGraphClient`, …) gated by `featureFlag.ts`, distinct from the aspirational `docs/second-brain/*`. **raw-mode** (`features/raw-mode`) is a split-pane markdown-source editor reconciling edits back into the block tree via `markengine`. **Passkeys** (WebAuthn, `@simplewebauthn/browser`) are managed in settings (`store/settings/useAccountPasskeysStore.ts`).

## Conventions, gates & gotchas

- **Hard rules (from repo-root CLAUDE.md — authoritative):** commit message `"updated"`; **no auto-push** (changes are reviewed first); **no `Co-Authored-By`/"Generated with" trailer**. File-size convention **≤200 lines / ≤5 functions** is **honor-system** (no eslint rule; ~60 app+graph-engine files already exceed it — the vendored trees far more — the biggest are refactor targets, e.g. `usePlaygroundBlockEditor.ts` ~2000, `src/components/blocks/EditableContent.tsx` ~1700 (the contenteditable core, stranded in the legacy pre-slice `src/components/` dir yet imported by every block-editor UI), `block-editor/ui/canvas/LayoutBlockEditor.tsx` ~1450 — its pure layout logic is already extracted to sibling `layout.constants.ts`/`layout.helpers.ts`/`layout.types.ts`, so extend those rather than growing the component; `global.css` ~1600 is the deliberate single token file). Do not treat existing violations as license to add more.
- **Branching:** osionos work **branches from `develop`** (per `docs/CONTRIBUTING.md`); never commit to `develop`/`main` directly — open a short-lived feature branch (`feat/…`). Commit/push discipline still follows repo-root CLAUDE.md: message `"updated"`, **no auto-push** (reviewed first), no trailer.
- **Quality gate order matters:** graph-engine `tsc` runs **first** (fail-fast on the decoupled package), then root `tsc`, then `eslint --max-warnings=0`. Build duplicates the two tsc passes — change `docker-run.sh` build/typecheck/quality together.
- **Playwright runs fully offline:** its config spawns its **own** Vite on `:3004` in `--mode test` with `VITE_API_URL=`/`VITE_ALLOW_OFFLINE_MODE=true`/`VITE_REQUIRE_BRIDGE_SESSION=false` — not the `:3001` dev server.
- **Env:** only vars in `vite.config.ts`'s `define` are statically inlined (`VITE_API_URL`, `VITE_AUTH_MODE`, `VITE_REQUIRE_BRIDGE_SESSION`, `VITE_ALLOW_OFFLINE_MODE`, `VITE_BAAS_URL`, plus `VITE_OBJECT_DATABASE_DISABLE_WASM` inlined as the `__OBJECT_DATABASE_DISABLE_WASM__` global); others reach code via `import.meta.env` and must be present at build/serve time. `VITE_API_URL`=bridge (`https://localhost:4000`), `VITE_BAAS_URL`=Kong (`:8000`). **Heads-up:** `.env.example` still ships `VITE_BAAS_URL=http://localhost:3000` (legacy port) while the active `.env` uses `:8000` — fix it after copying or realtime points at the wrong port.
- **The bridge images COPY modules by name — in TWO Dockerfiles:** both `infrastructure/docker/osionos/bridge.Dockerfile` (monorepo root, local container) and `deploy/bridge-fly/Dockerfile` (fly.io) enumerate every `bridge-*.mjs` in an explicit `COPY` list — a new bridge module works under `npm run bridge:api` but is **silently absent from both built containers** until added to each list.
- **Production deploy config lives in-app** (the one place the Docker-first rule doesn't apply — Vercel CI runs pnpm directly): `vercel.json` builds the frontend with `pnpm exec vite build` → `build/` and rewrites `/api/*` → `https://grobase-stack.fly.dev/api/*` (plus HSTS/nosniff/frame-deny headers); `deploy/bridge-fly/` (Dockerfile + `fly.toml`) deploys the bridge as fly app **`osionos-bridge`** (region `cdg`, co-located with `grobase-stack`; secrets via `flyctl secrets set`). Prod URLs and the localhost-vs-prod health matrix are in the root CLAUDE.md (`make check_health_apps`).
- **Supply chain is locked down:** 7-day release-age hold — `minimum-release-age=10080` in `.npmrc` (kebab-case) and `minimumReleaseAge: 10080` in `pnpm-workspace.yaml` (the otherwise-empty workspace file exists only for this pnpm-only knob). `.npmrc` also sets `prefer-frozen-lockfile=true`; `pnpm.onlyBuiltDependencies` is a 5-entry allowlist (`@tailwindcss/oxide`, `esbuild`, `playwright`, `protobufjs`, `sass-embedded`) — a dep needing a postinstall but not on the list silently won't build. Regenerate the lockfile inside Docker.
- **Aspirational docs:** `docs/dossier-project-dylan/*` (block normalization, Node/Mongo module layering) and the prose in `docs/second-brain/*` describe **future** state — their code samples are plans, not the current codebase. The real backend is grobase/Kong; the BaaS contract pointers in `docs/second-brain/*` now resolve to `apps/grobase/wiki/*`.
- **42-school header comment blocks** are present on JS/TS config files (`vite.config.ts`, `eslint.config.js`, `scripts/*.sh`) — preserve them when editing. JSON and `.md` files don't carry them.
- `.mcp.json` routes the stdio MCP server through `scripts/docker-run.sh mcp-claude` (Docker-first; same as `npm run mcp:claude`), so `scripts/osionos-mcp-server.mjs` (`@modelcontextprotocol/sdk` + zod) runs **inside the playground container** with `OSIONOS_MCP_BRIDGE_URL`/`_API_URL` defaulted to `host.docker.internal:4000` — no host node path.
