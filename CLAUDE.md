# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Scoped to `apps/osionos/app`. The repo-root `/CLAUDE.md` (monorepo topology, grobase BaaS, lifecycle Makefile) is the parent authority and is always in context — this file only adds app-specific detail. The hard rules in §Conventions override defaults.

## What this is

**osionos** (npm name `osionos-playground`) is a Notion-style **block editor that grew into a full collaborative workspace**: React 19 + Vite 6 + TypeScript, served at `https://localhost:3001`. Beyond the document editor it ships chat/DMs, live-database views, video rooms, a browser IDE backed by per-user sandbox containers, and an in-app BaaS tenant console — see **§Shipped capabilities**. It is one frontend of the `ft_transcendence` monorepo and reaches the **grobase BaaS through a Node bridge**, never directly. Source is **feature-sliced** (`src/`), with reusable engines split out as workspace packages under `packages/`.

## Commands — Docker-first, never run Node on the host

**Every** `package.json` script (except `lighthouse`) is a shim: it calls `scripts/docker-run.sh <target>` (or `docker-dev.sh`), which on the **host** runs `docker compose -f docker-compose.base.yml -f docker-compose.dev.yml run --rm --no-deps <service>` and re-execs **the same script inside the container** (the `/.dockerenv` / `OSIONOS_IN_DOCKER=1` check is the fork). Host `node` is absent on purpose; the root-owned, empty `node_modules/` at the app root is a volume mount point, not an install. `dev` and `bridge-api` use `up -d --build` (long-running) instead of `run --rm`; `dev` first boots the notion-database-sys Mongo contract server (27017; the playground's own Mongo publishes on 27018) before Vite.

```sh
npm run dev           # docker-dev.sh: notion-database-sys contract server, then Vite HMR on :3001
npm run build         # graph-engine tsc → markdown-engine tsc → root tsc → vite build → ./build
npm run test:quality  # THE gate: the 3 tsc passes → eslint src/ packages/ scripts/ --max-warnings=0 →
                      #   check-markdown-engine-boundary.sh → check-ui-token-contract.sh →
                      #   check-token-refs.mjs → build-tokens.mjs --check → check-style-tokens.sh
npm run typecheck     # the 3 tsc passes only          npm run lint[:fix]   # eslint only
npm run tokens        # regenerate colour tokens from scripts/tokens/
npm run test:e2e      # Playwright (service browser-tests); :smoke = tests/e2e/smoke, :serial = --workers=1
npm run test:e2e:perf # PLAYWRIGHT_PERF=1, tests/e2e/perf, one worker (excluded from the normal suite)
npm run test:canvas   # tests/canvas/*.test.ts via node --test --experimental-strip-types
npm run test:bridge   # tests/bridge/*.test.mjs — the whole bridge suite (bridge-* and ide-* modules)
npm run test:bench    # tests/bench/*.bench.ts (node --expose-gc); pass file paths to run a subset
npm run test:doctor   # validate the Playwright env (alias: test:setup; plain `npm test` = test:e2e)
```

- **Single test:** `npm run test:e2e -- -g "pattern"` or `npm run test:e2e -- tests/e2e/functional/<file>.spec.mjs`; `npm run test:canvas -- tests/canvas/<file>.test.ts`; `npm run test:bridge -- tests/bridge/<file>.test.mjs`. Args after `--` pass straight through.
- **e2e layout:** specs are mostly `.spec.mjs` under `tests/e2e/{functional,smoke,persistence,visual,perf,graph-studio-off}` (helpers in `tests/e2e/support/`), plus a few loose specs at the `tests/e2e/` root (some `.spec.ts`). `tests/browser/` is a separate JSX-harness tree (`COVERAGE_MATRIX.md`).
- **Playwright runs fully offline** on its **own** Vite at `:3004` (`--mode test`, `VITE_API_URL=`, `VITE_ALLOW_OFFLINE_MODE=true`, `VITE_REQUIRE_BRIDGE_SESSION=false`), not the `:3001` dev server. Workers default to **1** (`TEST_WORKERS` overrides). Spec routing is build-dependent: a default build ignores the `LEGACY_ON_SPECS` list in `playwright.config.ts` and runs `graph-studio-off/`; `VITE_LEGACY_SECOND_BRAIN=true` flips it.
- **Two compose services** with deliberately separate node_modules volumes: `playground` (build/typecheck/lint/quality/canvas/bridge/bench/dev) vs `browser-tests` (e2e/doctor/bench-layout). The app-local `Makefile` wraps the same flow (`make up`, `make quality`, `make test-canvas`, `make pnpm-lock`, `make sonar`).
- From the **repo root**: `docker compose exec osionos-app npm run <script>` (needs `docker compose up -d --build osionos-app`). The full website→app login flow needs the whole stack: sign in at `https://localhost:4322` and the website hands off into osionos; direct app loads require a bridge session unless `VITE_REQUIRE_BRIDGE_SESSION` is off.
- Other `docker-run.sh` targets: `build-offline` (blanks `VITE_API_URL`/`VITE_BAAS_*` — the prod build matching the Playwright env), `preview`, `bench-layout`, `mcp-claude`. `scripts/{dashboard,pane-resize,legacy-graph}-bench.mjs` have **no** target — run them directly. `npm run lighthouse` is the only host script.

## Architecture (the big picture)

**Feature-sliced, dependency points downward:** `app → pages → widgets → features → entities → shared` — **honor-system for app slices** (a widget importing a page lints clean; rely on review). A **feature** is one capability slice, a **widget** a page-level UI assembly; list them with `ls src/features src/widgets`. About half the slices have **no `index.ts` barrel** — check before importing and use the deep path when there is none. `src/components/` is a legacy pre-slice dir still imported by the editor (`components/blocks/EditableContent.tsx` is the contenteditable core).

**Workspace packages** (`packages/`, all consumed as **TS source** through aliases, no build step, no node_modules resolution): `legacy-graph-engine`, `markdown-engine`, `outbox-ledger`, `perf-probe`, `feature-flags`, `http-gate`, `osionos-ui` (`@osionos/ui`). **All but `legacy-graph-engine` are git submodules**, as are `src/shared/notion-database-sys` and `vendor/scripts` (`.gitmodules`) — commit inside the submodule first, then the parent records the SHA. Every alias must stay identical in **both** `vite.config.ts` and `tsconfig.json`; in Vite the `@osionos/markdown-engine/*` subpaths must stay **above** the `@` catch-all or they rewrite to `<root>/srcosionos/…`. Package boundaries are enforced, unlike app slices:
- `legacy-graph-engine/src/core/**` may not import `@/*` or `react`/`react-dom`; `osionos-ui/src/**` may not import `@/*`; `http-gate/src/**` keeps React behind its `./react` entry — all ESLint `no-restricted-imports` **errors** (`eslint.config.js`), so a violation type-checks but fails the gate.
- `markdown-engine` is **ESLint-ignored entirely**; its boundary is its own tsc pass (`tsconfig.markdown-engine.json`) plus `scripts/check-markdown-engine-boundary.sh` (the lexical half: tsc can't see a real node_modules import).

**No react-router.** "Routing" is a VSCode-style **tab/pane layout tree** in the `useWorkspaceLayout` zustand store (`src/widgets/workspace-grid/model/`: `workspaceLayout.ts` store, `layoutTree.ts` types incl. the `TabKind` union, `layoutMutations.ts`, `layoutPersist.ts` [localStorage `osionos.workspace.layout.v2`, migrates the `v1` prefix and legacy tabs], `layoutSync.ts`, `pageToTab.ts`, `paneZoom.ts`, …). The shell region is `widgets/workbench` (workspace grid over a resizable dock + status bar; rail and top bar stay in `App`). View dispatch is an **`if (tab.kind === …)` guard chain** (not a `switch`) in `widgets/page-renderer/ui/PaneContent.tsx`; the default `PageTabView` then branches on **`page.surface`** (`agent` → agent conversation, `code` → Monaco `CodeFileView`, else the block editor). URL is used only for deep-links (`?home=`, `?view=`, `bridge_token`, dev `/__styleguide`). **Two sources of truth for "open page"** — the layout store and the legacy `pageStore.activePage` — sync both ways through two seams: tab → `activePage` via `layoutSync.ts:mirrorActiveTab` (from `workspaceLayout.commit`), and `activePage` → tab via `workspaceLayout.syncFromActivePage` + `pageToTab.ts:activePageToTab` (committed with `mirror=false` so it does **not** loop). Edit one side without its mirror — or let the reverse sync mirror back — and header/graph/session-restore desync.

**Performance is a design constraint.** Surfaces are code-split with `React.lazy` via **deep import paths, never widget barrels** (importing `@/widgets/page-renderer` staples the ~1.1MB editor onto the warm chunk). `src/app/lazyAppRegions.tsx` splits the shell; per-pane splits live in `widgets/page-renderer/ui/lazyViews.tsx` (named exports adapted with `.then(m => ({ default: m.X }))`). **Every pane mounts its own live editor** keyed by `pageId`, fed `activePageRef` so it does **not** subscribe to the global `activePage`. Background panes stay cheap via `workspace-grid/ui/PaneView.tsx`: a shared **serial idle queue** mounts one deferred pane per idle tick, plus `contain: layout paint`. `PageBlocksRenderer` is the read-only renderer for hovers/marketplace/profile. Profiler harness: `src/shared/lib/perf/` (+ `@osionos/perf-probe`) — on in Vite dev, elsewhere via `localStorage.setItem('osio:perf','1')`; console globals `__perfSeed`/`__perfType`/`__perfEditorType`/`__perfRun` (its README). `ANALYZE=1` on a build emits `build/stats-chunks.json` (per-chunk module sizes).

**Feature flags** live in `src/shared/config/featureFlags.ts` (on `@osionos/feature-flags`) — one exported `is…Enabled()` per flag with its default and docstring; each toggles via `?<flag>=1|0`, a same-named localStorage key, or a `VITE_OSIO_*` env. Distinct from the build-time gate `src/shared/config/legacySecondBrain.ts` (`VITE_LEGACY_SECOND_BRAIN`, deliberately not URL/localStorage-flippable) and from notion-database-sys *view* automations. Three default-ON systems worth knowing: (1) **`osio.blockselect`** — the cross-cutting selection layer in `features/block-editor/model/`: `blockSelectionStore.ts` (selected ids keyed by surface `sourceKey`, so background panes never see a stale selection), `useSurfaceMarquee`, `editorCommandBus.ts` (the active editor's imperative handle), `blockClipboard.ts`, the context menu `usePageContextMenu` — wired in `BlockEditorSurface.tsx`. (2) **`osio.automations`** — `features/automations`: data-driven shortcut manager (keyboard trigger → command record, commands in `model/commands/`, persisted user overrides in `useAutomationStore`); its `useAutomationDispatcher` mounts **once in `App.tsx`**. (3) **`osio.db.server`** — inline `/database` blocks (`source=adapter`): schema, views and records persist owner-isolated in Postgres via the bridge; localStorage is a write-through offline cache (no-op in the offline build).

**State / page store** (`src/store/`): `usePageStore` is the client cache of the page tree, split into `usePageStore.ts` (assembler) + `pageStore.helpers.ts` (pure block-tree ops + localStorage cache) + `pageStore.actions.ts` (network) + `pageStore.persistence.ts` (**deliberate no-op seam** kept for call sites — do not "fix" the stubs). **BaaS is the source of truth; store + localStorage are a cache** (last-write-wins by `updatedAt`). Writes go through an offline-first outbox (`src/store/sync/`, on `@osionos/outbox-ledger`; `usePageSync` mounts once in `App.tsx`, hydrate-then-outbox, debounce 800ms, retry 15s→120s). Invariants: the ledger advances **only on server confirm**; a transient failure stops the whole batch (anti-429-storm); content is lazy, so `pageStamp` uses the `CONTENT_UNLOADED` sentinel and `pageOutbox` omits `content` when unloaded — an unloaded page never wipes the server copy. Second-brain notes run a second ledger (`features/legacy-second-brain/sync/noteSyncLedger.ts`, key `osio-sb-synced-notes`) on the same package — change ledger semantics in the package, then check both consumers.

**Data / bridge** (`src/shared/api/`, `scripts/bridge-*.mjs`): **two transports to grobase — do not conflate them.**
1. Page/workspace data → the **bridge** at `VITE_API_URL` (`https://localhost:4000`), the trust boundary holding the service-role key and proxying PostgREST/Kong. `scripts/bridge-api.mjs` mounts ~40 sibling `bridge-*.mjs` modules plus `ide-*.mjs` helpers (Node built-ins only, ~12.7k LoC): chat, feed, profiles, ABAC perms, workspace invites, LiveKit grants (`POST /api/rtc/token`), the IDE sandbox broker, and more. It publishes realtime events **server-side** (`REALTIME_PUBLISH_URL`, best-effort; `bridge-realtime-socket.mjs` publishes over the gateway WS where POST is refused).
2. Realtime (chat/feed/live-DB) → **Kong directly** at `VITE_BAAS_URL` (`:8000`, `/realtime/v1/ws`) via `src/services/realtime-messages/`. Credential: the baked `VITE_BAAS_REALTIME_TOKEN`, else a subscribe-only token per topic minted by the bridge (`POST /api/realtime/token`, `mintedTopicSocket.ts` — one socket per topic, never multiplexed, because the gateway replaces a socket's claims on re-AUTH). `VITE_CHAT_WS` opts out; a same-tab `BroadcastChannel` echo always runs underneath.

`shared/api/baas-client.ts` (direct `/query/v1`) is **dead** (`VITE_BAAS_ENABLED` unset). Auth carries an opaque **`osionos_v1.` app-session token** (HMAC, distinct from gotrue JWTs — `pageApiJwtFromSessionToken` vs `apiJwtFromSessionToken` in `features/auth/model/userStore.helpers.ts`; the wrong one silently skips the fetch). The user store publishes itself to **`globalThis.__playgroundUserStore`**, a load-bearing seam read by `shared/api/client.ts`, `shared/lib/auth/pageAccess.ts` and vendored live-DB code — not a hack to remove. A missing/expired app session therefore both skips page fetches and blocks token minting, knocking realtime down to polling.

**Graph** — two engines. `packages/legacy-graph-engine` (`@osionos/legacy-graph-engine`) is the Second-Brain force graph (Canvas2D + Web-Worker d3-force), framework-agnostic: the host builds a `GraphModel` (`NodeId == BaaS global id`, so layout is stable across rebuilds) and hands it to a thin React adapter; the engine never fetches. The worker falls back in-process when `Worker` is undefined (`core/layout/layoutBridge.ts:createWorker`); both paths import `core/layout/layoutEngine.ts` verbatim, so physics is never duplicated. Its theme reads the host's `--osio-*` tokens at runtime, so renaming those silently recolours the graph. `features/graph-studio` + `widgets/graph-studio-view` instead load graph_render's `<graph-studio>` web-component pack, which is **not in this bundle**: the groot osionos-app image serves it under `/graph-studio/<sha>/` and names the base in `<meta name="graph-studio-base">`; without it the view says so instead of drawing.

**Vendored `src/shared/notion-database-sys/`** (the "object database", git submodule pinned on a `groot-pin` tag) has its own toolchain — **do not edit it as app code**. ESLint ignores it entirely, but tsc only excludes its `packages/`, `playground/`, `examples/`, `vendor/` and `src/vite.config.ts`, so `notion-database-sys/src/` (the `@notion-db/object-database` alias target) is in the app compile graph and a type error there breaks `test:quality`. Most chart/map/equation rendering (echarts/recharts/leaflet/katex/mermaid) lives inside it.

**Styling** — colours are **generated, never hand-edited**: `scripts/build-tokens.mjs` (`npm run tokens`) grows the seeds and pins in `scripts/tokens/` into `src/app/styles/{tokens,accents,database-bridge}.generated.css` and `src/shared/config/{palettes,accents}.generated.ts`; `--check` (stale output, contrast, unmapped vendored colour) runs in the gate. Nine palettes (`warm` = "Calm" default) × light/dark. Three tiers: **ramp** (`--osio-n-*`, `--osio-a-*`; components never read them), **semantic** (`--osio-bg-*`/`fg-*`/`accent*`, same names in every palette), **component** (`--osio-{overlay,control,field,chip,tooltip}-*`, also read by `@osionos/ui`). Never rename an existing `--osio-*` token. `src/app/styles/`: `global.css` (palette-independent geometry/type/motion/`@theme`), `shell.css`, `type.css` (`osio-h1..h4`), `recipes.css` (component tokens, `osio-*` utilities), `appearance.css`. The database bridge CSS and `database-overrides.css` are imported by the components that render `ObjectDatabase`, so they ship in the lazy database chunk. Appearance is `<html>` attributes (`data-theme`, `data-palette`, `data-accent`, `data-density`, `data-radius`, `data-ui-scale`, inline `--osio-accent-hue`) written by `src/shared/config/theme.ts` and mirrored by `index.html` before first paint. **Tailwind v4 CSS-first — no `tailwind.config.js`/postcss config**; stock keys (`--text-*`, `--spacing`, `--radius-*`, `--font-*`) are mapped in the **unlayered** `:root` block, because notion-database-sys imports Tailwind itself and its later `@layer theme` silently beats a stock-key override in `@theme`. UI font size is set on `body`, never `html` (it would redefine `1rem`). ESLint rejects `text-[Npx]`, stock shadows, bare `rounded`, raw hex outside `HEX_ALLOWLIST` and ramp tokens; `scripts/check-style-tokens.sh` forbids raw colours in app CSS/SCSS outside `src/app/styles/**`. Both are text matches — blind spots and how to add a palette/accent are in `src/app/styles/README.md`.

## Shipped capabilities

Each opens as a `tab.kind` pane (see `PaneContent.tsx`) or a page `surface`:

- **Collaboration / social** — channels (`widgets/channel-list`/`channel-messages`, model split into per-concern hooks `useChannelHistory`/`useChannelLive`/`useChannelActions`/…), DMs, profiles, people search, feed, notifications, communities, agent conversations. Backed by the bridge chat/feed/profile/social modules + the realtime service above.
- **Video rooms** — `widgets/video-room`, self-hosted **LiveKit** (`livekit-client`): grant from `POST /api/rtc/token`, connect to the `livekit` compose service at `ws://127.0.0.1:7880` (loopback ws is mixed-content-exempt). Also an in-channel `CallPanel` via a deep lazy import that keeps `livekit-client` off the warm chunk.
- **IDE** — `features/ide` (Monaco editor, xterm terminal, explorer, run/debug/problems/source-control panels) inside the workbench dock. A code file is a `surface: "code"` page storing the whole file as **one `code` block** in `page.content` (`model/codeFile.ts`), so it rides the normal page sync. The runtime is a persistent per-(user, workspace) container brokered by `scripts/bridge-ide-sandbox.mjs`: double-gated (`OSIONOS_IDE_SANDBOX=1` **and** `OSIONOS_IDE_DOCKER_HOST`, else 404), auth before any docker call, docker reached only through an allowlisting socket-proxy (`infrastructure/docker/osionos/ide-*` at the monorepo root).
- **Database plane** — `widgets/database-view`: Notion-style DB blocks with live-DB adapters (`liveDatabaseAdapter`/`liveMountTables`/`dataSourceProvider`) + an object-database adapter; tests are `tests/canvas/live-*.test.ts`.
- **BaaS tenant console** — `features/baas-console` (`tab.kind === 'console'`): API keys, usage metering, plan — the osionos UI for grobase's flag-gated Track-B metering/billing.
- **Whiteboard** (built-in app `osionos.whiteboard`) — always on, no install: availability is `isWhiteboardReady()` (`features/whiteboard/model/whiteboardAvailability.ts`) = the `osio.whiteboard` kill-switch plus a non-blank `whiteboardAppUrl()` (`shared/config/appUrls.ts`, dev default `https://localhost:3007`, the drawnosaurus app). There is no native draw tool: `draw` survives only as a legacy block (`LegacyDrawNotice`, "Import as whiteboard" accepted only when the PUT is 2xx **and** the live element count equals the count sent). Only `/whiteboard [name]` creates a board (`requiresApp: "osionos.whiteboard"`, enforced at list, selection and dispatch). `BUILT_IN_APP_IDENTIFIERS`/`STATIC_APP_IDENTIFIERS` (`features/marketplace/model/installedAppLauncher.ts`) stop an installed `osionos.whiteboard`/`osionos.draw` adding a second rail icon; old installs and `draw` tabs are migrated (`installedMigrations.ts`, `layoutPersist.ts:migrateLegacyTabs`); `scripts/seed-marketplace.mjs` retires `osionos.draw` via `RETIRED`.
- **Flag-gated, default OFF** — SQL runner (`osio.sqlrun`), comments (`osio.comments`), public publish to `/p/:token` (`osio.publish`, also needs `OSIONOS_PUBLISH_ENABLED` on the bridge), push (`osio.push`), shared collab (`osio.collab.shared`); tasks, quick capture, unified search, favorites and backlinks are flagged default ON.
- **Smaller surfaces** — `page-toc` (`PageOutlineRail`, a hover TOC built from the rendered editor DOM, mounted in `pages/notion-page/ui/NotionPage.tsx` only with ≥2 headings and no full-page layout); `raw-mode` (split-pane markdown source reconciled into the block tree via `@osionos/markdown-engine`); `legacy-second-brain/baas/` (an implemented BaaS txn/graph client, reachable only behind `VITE_LEGACY_SECOND_BRAIN`); passkeys (`@simplewebauthn/browser`, `store/settings/useAccountPasskeysStore.ts`).

## Conventions, gates & gotchas

- **Hard rules:** conventional commit messages, `type(scope): what` (e.g. `fix(settings): …`) — this overrides the repo-root `"updated"` rule for this app; **no auto-push** (changes are reviewed first); **no `Co-Authored-By`/"Generated with" trailer**. Branch from `develop` into a short-lived `feat/…` branch — never commit to `develop`/`main` directly (`docs/CONTRIBUTING.md`).
- **File size ≤200 lines / ≤5 functions is honor-system** (no eslint rule) and widely violated — the biggest refactor targets are `features/block-editor/model/usePlaygroundBlockEditor.ts` (~2200), `components/blocks/EditableContent.tsx` (~1750), `block-editor/ui/canvas/LayoutBlockEditor.tsx` (~1480; its pure logic is already in sibling `layout.{constants,helpers,types}.ts` — extend those), and `store/pageStore.{actions,helpers}.ts` (~1050/~900). Existing violations are not licence to add more.
- **Gate order matters:** graph-engine tsc → markdown-engine tsc → root tsc → eslint. `build`, `typecheck` and `quality` each repeat the tsc chain in `scripts/docker-run.sh` — change them together.
- **Env:** only vars in `vite.config.ts`'s `define` are statically inlined (`VITE_API_URL`, `VITE_AUTH_MODE`, `VITE_REQUIRE_BRIDGE_SESSION`, `VITE_ALLOW_OFFLINE_MODE`, `VITE_BAAS_URL`, plus `VITE_OBJECT_DATABASE_DISABLE_WASM` as `__OBJECT_DATABASE_DISABLE_WASM__`); the rest reach code via `import.meta.env` and must exist at build/serve time. **`.env.example` still ships `VITE_BAAS_URL=http://localhost:3000`** (legacy port) while the real value is Kong on `:8000` — fix it after copying or realtime points at the wrong port.
- **Bridge images:** the monorepo-root `infrastructure/docker/osionos/bridge.Dockerfile` copies by glob (`scripts/bridge-*.mjs scripts/ide-*.mjs`), so a new module **must** follow that naming. `deploy/bridge-fly/Dockerfile` still lists every module **by name** — add a new one there too; `tests/bridge/bridge-dockerfile-closure.test.mjs` fails when the fly list misses a module `bridge-api.mjs` imports.
- **Production deploy config lives in-app** (the one place the Docker-first rule doesn't apply — Vercel CI runs pnpm directly): `vercel.json` builds with `pnpm exec vite build` → `build/` and rewrites `/api/*` → `https://grobase-stack.fly.dev/api/*` (plus HSTS/nosniff/frame-deny); `deploy/bridge-fly/` deploys the bridge as fly app **`osionos-bridge`** (region `cdg`, co-located with `grobase-stack`; secrets via `flyctl secrets set`).
- **Supply chain is locked down:** 7-day release-age hold — `minimum-release-age=10080` in `.npmrc` and `minimumReleaseAge: 10080` in `pnpm-workspace.yaml` (that file exists only for this knob). `.npmrc` also sets `prefer-frozen-lockfile=true` and store-integrity checks; `pnpm.onlyBuiltDependencies` is a 5-entry allowlist (`@tailwindcss/oxide`, `esbuild`, `playwright`, `protobufjs`, `sass-embedded`) — a dep needing a postinstall but absent from it silently won't build. Regenerate the lockfile inside Docker (`make pnpm-lock`).
- **Aspirational docs:** `docs/dossier-project-dylan/*` and the prose in `docs/legacy-second-brain/*` describe **future** state — their code samples are plans. The real backend is grobase/Kong; BaaS contract pointers resolve to `apps/grobase/wiki/*`.
- **42-school header blocks** sit atop JS/TS/shell sources (`vite.config.ts`, `eslint.config.js`, `scripts/*`, many `src/` files) — preserve them when editing; JSON and `.md` files don't carry them.
- `.mcp.json` routes the stdio MCP server through `scripts/docker-run.sh mcp-claude`, so `scripts/osionos-mcp-server.mjs` runs **inside the playground container** with `OSIONOS_MCP_BRIDGE_URL`/`_API_URL` defaulting to `host.docker.internal:4000`.
