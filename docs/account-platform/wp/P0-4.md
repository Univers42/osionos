# P0-4 👹 — session rows, per-session revocation, shared handoff

Repo: osionos app (`apps/osionos/app`), branch `feat/acct-P0-4` from `feat/account-platform` **after
P0-3 merges**. Depends on: P0-1 (the `osionos_sessions` table, root repo), P0-2 (`bridge-pg.mjs`,
`bridge-paging.mjs`), P0-3 (`bridge-kv.mjs`, `bridge-redis.mjs`, `bridge-guard.mjs`).

## Why
Every app session is an HMAC token (`signAppSessionToken`, `scripts/bridge-api.mjs:423`) that
nobody can end one device at a time: the only revocation is the per-user cutoff (ADR 0025,
`bridge-session-cutoff.mjs`), which ends *every* session. Handoff tokens and replay markers live in
per-process `Map`s (`bridge-api.mjs:4223-4224`), so on two replicas a handoff minted on A and
consumed on B fails, and a replayed gateway request accepted by A is accepted again by B.

## Decisions (the devil rules on these)
1. **A session row is written when the session is delivered**, not when it is minted: at the two
   handoff consumers, `handleBridgeConsume` (`:4000-4005`, browser) and `handleAuthProxy` (consume at
   `:4074`, browser login/register). Those are the requests whose client metadata is the user's;
   the mint (`createBridgeHandoff` `:1632`) is a server-to-server call from the gateway.
   `id` = the token `jti`, so the primary key is also a second single-use guard.
   **Fail closed:** if the row cannot be written the consume answers 503
   `session_record_unavailable` and returns no token (the handoff is already spent — the user
   signs in again). **One off state covers recording, enforcement and the routes**, entered by
   `OSIONOS_SESSION_RECORDS=off` or by a missing service key / BaaS URL — the same reasons as
   `sessionCutoffsFromConfig` (`bridge-session-cutoff.mjs:161-165`); the boot line says which.
   While off, `GET`/`DELETE /api/account/sessions*` answer 503 `session_records_off` — never a 204
   for a revoke nobody enforces. A duplicate `id` on insert (23505) is 409 and logged, not 503.
2. **Revocations are polled, like cutoffs.** A tracker reloads every revoked, unexpired session id
   (`revoked_at IS NOT NULL AND expires_at > now()`) every 10 s and `verifyAppSessionToken` checks
   it synchronously right after the cutoff check (`:479`): a revoked `jti` → 401 `session_revoked`;
   a stale or never-loaded set → 503 `session_revocations_unavailable` (same states and thresholds
   as `SessionCutoffs`: off | loading | fresh | stale, `STALE_AFTER_MS`). A revoke on this replica
   applies locally at once and must survive a reload that was already in flight (the cutoff
   tracker's `localWrites`/`writeSequence` solve exactly this — reuse them).
   **Do not copy the cutoff machinery.** Extract what the two trackers share (state, freshness,
   announce-once, paged full reload, local writes, poller loop) so both use one implementation; the
   three cutoff suites must pass with their assertions unchanged.
3. **Handoff and replay move to the kv store** (`createKv`, P0-3):
   - handoff: lookup key `handoff:` + hex(HKDF-SHA256(token, info `osb:handoff:key`)); the value is
     the JSON record sealed with AES-256-GCM under a second HKDF output (info `osb:handoff:seal`),
     so Redis never holds a usable session token. TTL = `handoffTtlMs + 60_000`; the record keeps
     `expiresAt`, so an expired-but-present handoff is still 410 and an unknown one 404 (today's
     contract, `:1652-1667`). Consume is `getDel` (single use across replicas).
   - replay: `verifyBridgeRequest` stays synchronous and does authentication only; AFTER the HMAC
     check passes (`:408-415`) the caller claims the jti with an awaited
     `setNx('replay:' + jti, '1', 2 × timestampSkewMs)`; false → 409. A bad signature never burns a
     jti. The marker must live `2 × skew`: a timestamp up to `+skew` in the future is accepted
     (`:407`); today's marker lives `1 × skew` (`:419`).
   - `kv` is created once in `createBridgeServer` (`options.kv` for tests). **`required` =
     a Redis URL is configured** (`OSIONOS_BRIDGE_REDIS_URL`): a configured Redis that is down
     fails closed; no URL means memory and the boot line warns "single replica only". No separate
     "required" knob. **Capability probe, not `INFO`** (a least-privilege ACL user gets `NOPERM` on
     `INFO` while the data commands work — measured on redis 7.4.11): inside the handshake
     (`bridge-redis.mjs` `#handshake`, before it marks ready) and on every reconnect, run
     `SET osb:probe:<random> 1 PX 5000 NX`, `PEXPIRE … 5000 NX`, `GETDEL`; any error → logged once,
     treated as not connected (required mode 503s).
4. **Owners read their sessions through `asUser`** (ADR 0001); **writes are `asService`**, which
   ADR 0003 (`docs/account-platform/adr/0003-session-rows-are-written-by-the-bridge.md`) records as
   an amendment to ADR 0001: the role may never write its own session rows (P0-1 grants it SELECT on
   nine columns only). Both writes live in ONE function in `bridge-sessions.mjs` that takes the user
   id only from the verified session, never from the request.

## Contracts
`scripts/bridge-sessions.mjs` (new):
- `recordSession(pg, { accessToken, authMethod, meta })` — **takes `jti`, `sub`, `iat_ms` and `exp`
  only by decoding the access token it is about to deliver.** Trap: `createBridgeHandoff`
  overwrites the record's `expiresAt` with the *handoff* expiry, now + 90 s (`bridge-api.mjs:1637-1639`,
  `:98`), and `consumeHandoffToken` returns that (`:1664`); a row built from it would leave the
  polled revocation set after 90 s and the revoked token would work again. POST `osionos_sessions`
  with `id` (= jti), `user_id` (= sub), `created_at` (= `iat_ms`, so the row orders the way the cutoff
  compares tokens), `expires_at` (= `exp`), `auth_method, ip_prefix, ip_hash, user_agent`.
  `meta` = `clientMeta(request, { ipHeader, hashSecret })` from P0-3 **only when
  `OSIONOS_BRIDGE_CLIENT_IP_HEADER` is set**; otherwise `ip_prefix`/`ip_hash` are NULL (without the
  header the socket peer is the proxy, so every row would record the proxy's /24).
  `auth_method`: `'password'` for `handleAuthProxy`, `'handoff'` for `handleBridgeConsume`.
- Routes (behind `verifySession`):
  - `GET /api/account/sessions` → `asUser`, `select=id,created_at,expires_at,last_seen_at,auth_method,ip_prefix,user_agent`,
    `revoked_at=is.null&expires_at=gt.<now>`, `order=created_at.desc`, `limit=50`; drop rows the
    user's cutoff already ended; mark `current` (`id === session.raw.jti`). Response
    `{ sessions: [{ id, createdAt, expiresAt, lastSeenAt, authMethod, ipPrefix, userAgent, current }] }`.
  - `DELETE /api/account/sessions/:id` → uuid check (422); `rateLimit(kv, ['session-revoke', userId], { limit: 30, windowMs: 60_000 })`;
    `writeAudit(pg, { session, meta, eventType: 'session_revoke', details: { sessionId } })` BEFORE
    the write; `asService` PATCH `osionos_sessions?id=eq.<id>&user_id=eq.<me>&revoked_at=is.null`
    body `{ revoked_at, revoked_reason: 'user' }`, `return=representation`, `select=id,expires_at`;
    zero rows → 404 `session_not_found` (not yours and already-revoked look the same); else apply
    locally **using the id and `expires_at` from the PATCH response rows, never the path id**, and
    204. Revoking the current session is allowed. Audit `details` name it an attempt.
    Caveat to state: `limit=50` has no paging — a user with more live sessions sees the newest 50.
- No `last_seen_at` writes (a write per request is the P0-5 problem). No reaper (follow-up).

`scripts/bridge-account-mounts.mjs` (new): **the one seam** account modules mount through —
`createAccountHandler(deps)` tries each account route module in order and returns true when one
handled the request. `bridge-api.mjs` gets one `account:` entry in the `social` object
(`:4237-4259`) and one dispatch line (`:4170-4190`). Later packages append to this file's list and
do not touch `bridge-api.mjs`.

`bridge-api.mjs` — seams only, net growth ≤ 40 lines (the file is 4293 lines; logic goes in the
new modules): `createUserSession` passes an explicit `jti` and returns it as `sessionId`; the
handoff/replay `Map`s become the kv calls above; `consumeHandoffToken` becomes async and its two
callers await it and then `recordSession`; the revocation check in `verifyAppSessionToken`; the
mount; health gains `kv` (`required ? (connected ? 'redis' : 'unavailable') : 'memory'` — never
`backend()` alone, it says `memory` in required mode) and the revocation tracker state.
Env (names): `OSIONOS_BRIDGE_REDIS_URL`, `OSIONOS_SESSION_RECORDS`, `OSIONOS_BRIDGE_CLIENT_IP_HEADER`,
`OSIONOS_BRIDGE_IP_HASH_SECRET` (blank → `ip_hash` NULL, P0-3 rule 5).

## Acceptance (each is a test in `tests/bridge/`)
1. A consume writes exactly one row with the fields above (`id` = the token's `jti`, `expires_at` =
   its `exp`, `created_at` = its `iat_ms`); `handleAuthProxy` writes `auth_method='password'`.
   Revoke a session, move the clock past `handoffTtlMs`, run a reload: the token still answers 401
   (kills the "row stores the 90 s handoff expiry" mutant). No IP header configured → NULL IP columns.
2. Two `createBridgeServer` instances sharing one kv: a handoff minted on A is consumed on B (200)
   and then refused on A (404); a gateway request replayed from A to B → 409 on B; a request with a
   bad signature does not burn its jti (the same jti, correctly signed, then succeeds); a timestamp
   of now + skew is accepted and its replay at now + 1.5 × skew is 409.
3. Insert failure → 503 `session_record_unavailable`, no `accessToken` in the body.
4. Off (by the env switch, and separately by a missing service key) → no insert, no revocation
   check, the session routes 503 `session_records_off`, the boot line names the reason.
5. One user, two sessions, revoke one: the other still answers 200; the revoked one answers 401 on
   A **immediately (no tick)** and on B after one reload (drive the poller, no real 10 s sleep) —
   kills a mutant that keys the set by `sub`. Revocation set stale → 503; never loaded → 503; a
   revoke that raced an in-flight reload survives it.
6. The fake PostgREST **applies the filters**. Revoking user B's session id as A → 404, the PATCH
   carried `user_id=eq.<A>`, B's row is still unrevoked, and B's token still verifies **on the same
   replica with no tick** (kills "apply the path id locally before checking the row count"). Audit
   failure → 503 and no PATCH sent; 31st revoke in a minute → 429; a 23505 on insert → 409.
7. `GET /api/account/sessions` uses `asUser`, lists only the caller's live sessions, marks
   `current`, omits sessions the cutoff ended.
8. Handoff seal: flipping one ciphertext byte → 404 (not 200, not 500); the stored key differs
   from the seal key and contains no part of the token; the stored value contains neither the
   access token nor the persona email **after base64/hex decoding attempts**; an expired-but-present
   handoff → 410, an unknown one → 404 (no test pins 410 today). A fake Redis answering `ERR` to
   `PEXPIRE NX` in the probe → required mode 503.
9. Every existing suite stays green. Allowed edits to existing tests, and only these: sync →
   `await`; `assert.throws` → `assert.rejects`; read the handoff token from `redirectUrl` instead
   of `handoffStore.keys()`; replace `.size` checks with "no `osb:handoff:*` key in the kv". Each
   test's meaning must survive (e.g. `bridge-handoff-persistence.test.mjs:56` "a failed mint stores
   nothing"). Files: `bridge-api.test.mjs:221,245-251,363,374-382`, `bridge-admin-verified.test.mjs:45-56`,
   `bridge-handoff-persistence.test.mjs:32-56`, `bridge-gateway-forwarded-for.test.mjs:37-50`,
   `bridge-subject-case.test.mjs:61`, `support/signin-world.mjs:150-153`; unchanged: logout,
   session-cutoff, session-cutoff-poller, signin-claims, dockerfile-closure.

## What a revoke does not end (state it in ADR 0003)
Derived credentials outlive it: the IDE token (15 min, `ide-server.mjs:14`), the account JWT (120 s),
LiveKit grants (up to 6 h, ADR 0025:80). Tokens minted before this deploy or while records were off
have no row — they are neither listed nor revocable one by one (the cutoff still ends them).
