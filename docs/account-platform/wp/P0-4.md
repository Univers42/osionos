# P0-4 👹 — session rows, per-session revocation, shared handoff

Repo: osionos app (`apps/osionos/app`), branch `feat/acct-P0-4` from `feat/account-platform` **after
P0-3 merges**. Depends on: P0-1 (the `osionos_sessions` table, root repo), P0-2 (`bridge-pg.mjs`,
`bridge-paging.mjs`), P0-3 (`bridge-kv.mjs`, `bridge-redis.mjs`, `bridge-guard.mjs`).

## Why
Every app session is an HMAC token (`signAppSessionToken`, `scripts/bridge-api.mjs:423`) that
nobody can end one device at a time: the only revocation is the per-user cutoff (ADR 0025,
`bridge-session-cutoff.mjs`), which ends *every* session. Handoff tokens and replay markers live in
per-process `Map`s (`bridge-api.mjs:4223-4224`), so on two replicas a handoff minted on A and
consumed on B fails, and a replayed gateway request accepted by A is accepted again by B.

## Decisions (the devil rules on these)
1. **A session row is written when the session is delivered**, not when it is minted: at the two
   handoff consumers, `handleBridgeConsume` (`:4000-4005`, browser) and `handleAuthProxy` (consume at
   `:4074`, browser login/register). Those are the requests whose client metadata is the user's;
   the mint (`createBridgeHandoff` `:1632`) is a server-to-server call from the gateway.
   `id` = the token `jti`, so the primary key is also a second single-use guard.
   **Fail closed:** if the row cannot be written the consume answers 503
   `session_record_unavailable` and returns no token (the handoff is already spent — the user
   signs in again). Off switch `OSIONOS_SESSION_RECORDS=off`, mirroring `OSIONOS_SESSION_CUTOFFS`
   (`:189`): it disables recording AND revocation enforcement, and the boot line says so.
2. **Revocations are polled, like cutoffs.** A tracker reloads every revoked, unexpired session id
   (`revoked_at IS NOT NULL AND expires_at > now()`) every 10 s and `verifyAppSessionToken` checks
   it synchronously right after the cutoff check (`:479`): a revoked `jti` → 401 `session_revoked`;
   a stale or never-loaded set → 503 `session_revocations_unavailable` (same states and thresholds
   as `SessionCutoffs`: off | loading | fresh | stale, `STALE_AFTER_MS`). A revoke on this replica
   applies locally at once and must survive a reload that was already in flight (the cutoff
   tracker's `localWrites`/`writeSequence` solve exactly this — reuse them).
   **Do not copy the cutoff machinery.** Extract what the two trackers share (state, freshness,
   announce-once, paged full reload, local writes, poller loop) so both use one implementation; the
   three cutoff suites must pass with their assertions unchanged.
3. **Handoff and replay move to the kv store** (`createKv`, P0-3):
   - handoff: lookup key `handoff:` + hex(HKDF-SHA256(token, info `osb:handoff:key`)); the value is
     the JSON record sealed with AES-256-GCM under a second HKDF output (info `osb:handoff:seal`),
     so Redis never holds a usable session token. TTL = `handoffTtlMs + 60_000`; the record keeps
     `expiresAt`, so an expired-but-present handoff is still 410 and an unknown one 404 (today's
     contract, `:1652-1667`). Consume is `getDel` (single use across replicas).
   - replay: `setNx('replay:' + jti, '1', 2 × timestampSkewMs)`; false → 409. The marker must live
     `2 × skew`: a timestamp up to `+skew` in the future is accepted (`:407`).
   - `kv` is created once in `createBridgeServer` (`options.kv` for tests). **`required` =
     a Redis URL is configured** (`OSIONOS_BRIDGE_REDIS_URL`): a configured Redis that is down
     fails closed; no URL means memory and the boot line warns "single replica only". No separate
     "required" knob. On connect, `INFO server` must report `redis_version` ≥ 7.0 (`PEXPIRE NX`);
     a lower version is logged once and treated as not connected (so required mode 503s).
4. **Owners read their sessions through `asUser`** (ADR 0001); **writes are `asService`** with an
   explicit `user_id=eq.` filter — `osionos_account_user` has only SELECT on nine columns (P0-1).
   The insert and the revoke PATCH are the only writers of `osionos_sessions`.

## Contracts
`scripts/bridge-sessions.mjs` (new):
- `recordSession(pg, { sessionId, userId, issuedAtMs, expiresAt, authMethod, meta })` — POST
  `osionos_sessions` with `id, user_id, created_at` (= `issuedAtMs`, so the row orders the same way
  the cutoff compares tokens), `expires_at, auth_method, ip_prefix, ip_hash, user_agent`
  (`meta` = `clientMeta(request, { ipHeader, hashSecret })` from P0-3). `auth_method`: `'password'`
  for `handleAuthProxy`, `'handoff'` for `handleBridgeConsume`.
- Routes (behind `verifySession`):
  - `GET /api/account/sessions` → `asUser`, `select=id,created_at,expires_at,last_seen_at,auth_method,ip_prefix,user_agent`,
    `revoked_at=is.null&expires_at=gt.<now>`, `order=created_at.desc`, `limit=50`; drop rows the
    user's cutoff already ended; mark `current` (`id === session.raw.jti`). Response
    `{ sessions: [{ id, createdAt, expiresAt, lastSeenAt, authMethod, ipPrefix, userAgent, current }] }`.
  - `DELETE /api/account/sessions/:id` → uuid check (422); `rateLimit(kv, ['session-revoke', userId], { limit: 30, windowMs: 60_000 })`;
    `writeAudit(pg, { session, meta, eventType: 'session_revoke', details: { sessionId } })` BEFORE
    the write; `asService` PATCH `osionos_sessions?id=eq.<id>&user_id=eq.<me>&revoked_at=is.null`
    body `{ revoked_at, revoked_reason: 'user' }`, `return=representation`, `select=id,expires_at`;
    zero rows → 404 `session_not_found` (not yours and already-revoked look the same); else apply
    locally and 204. Revoking the current session is allowed.
- No `last_seen_at` writes (a write per request is the P0-5 problem). No reaper (follow-up).

`scripts/bridge-account-mounts.mjs` (new): **the one seam** account modules mount through —
`createAccountHandler(deps)` tries each account route module in order and returns true when one
handled the request. `bridge-api.mjs` gets one `account:` entry in the `social` object
(`:4237-4259`) and one dispatch line (`:4170-4190`). Later packages append to this file's list and
do not touch `bridge-api.mjs`.

`bridge-api.mjs` — seams only, net growth ≤ 40 lines (the file is 4293 lines; logic goes in the
new modules): `createUserSession` passes an explicit `jti` and returns it as `sessionId`; the
handoff/replay `Map`s become the kv calls above; `consumeHandoffToken` becomes async and its two
callers await it and then `recordSession`; the revocation check in `verifyAppSessionToken`; the
mount; health gains `kv` (`required ? (connected ? 'redis' : 'unavailable') : 'memory'` — never
`backend()` alone, it says `memory` in required mode) and the revocation tracker state.
Env (names): `OSIONOS_BRIDGE_REDIS_URL`, `OSIONOS_SESSION_RECORDS`, `OSIONOS_BRIDGE_CLIENT_IP_HEADER`,
`OSIONOS_BRIDGE_IP_HASH_SECRET` (blank → `ip_hash` NULL, P0-3 rule 5).

- Never put raw user text in audit `details` (a NUL makes the insert fail → 503).

## Acceptance (each is a test in `tests/bridge/`)
1. A consume writes exactly one row with the fields above (`id` = the token's `jti`, `expires_at` =
   its `exp`, `created_at` = its `iat_ms`); `handleAuthProxy` writes `auth_method='password'`.
2. Two `createBridgeServer` instances sharing one kv: a handoff minted on A is consumed on B (200)
   and then refused on A (404); a gateway request replayed from A to B → 409 on B.
3. Insert failure → 503 `session_record_unavailable`, no `accessToken` in the body.
4. `OSIONOS_SESSION_RECORDS=off` → no insert, no revocation check, boot line says off.
5. Revoke on A → B answers 401 `session_revoked` after one reload (drive the poller, no real 10 s
   sleep); revocation set stale → 503; a revoke that raced an in-flight reload survives it.
6. Revoking another user's session id → 404 and the PATCH carried `user_id=eq.<caller>`; audit
   failure → 503 and no PATCH sent; 31st revoke in a minute → 429.
7. `GET /api/account/sessions` uses `asUser`, lists only the caller's live sessions, marks
   `current`, omits sessions the cutoff ended.
8. The kv value for a handoff contains neither the access token nor the persona email (inspect
   the stored string); Redis `< 7.0` in `INFO` → required mode 503.
9. Every existing suite stays green with its assertions unchanged except where a `Map` was
   injected (those now inject a memory kv): logout, session-cutoff, session-cutoff-poller,
   handoff-persistence, gateway-forwarded-for, subject-case, signin-claims, dockerfile-closure.
