## Why
- **Follow/unfollow does not exist.** The social graph has connections (`osionos_connections`) and blocks, but no asymmetric follow graph. The plan calls for `osionos_follows` (root) with an idempotent follow/unfollow API, follower/following counts from **one RPC** (never N queries, P0-5's `feed_page_counts` pattern), and keyset-paginated lists via `bridge-paging.mjs` cursors.
- **Friends are already connections.** `friends = accepted connections` (`osionos_connections.status = 'accepted'`). The existing `GET /api/connections?status=accepted` is the friends list; reuse it, never a parallel store.
- **Presence is binary (online/offline).** `bridge-presence.mjs` writes a heartbeat key and a 10-min database column. The plan needs four states: `online | away | DND | invisible` on a new `osionos_presence` table (root) plus the existing KV. `invisible` shows `offline` to others. At most **1 Postgres write per user per 10 min** (P0-5's pattern, `PRESENCE_PG_TTL_MS`).
- **No user-set status.** GitHub-style status (emoji + text + expiry + "busy") is missing. Owner-set, shown on hovercards and the profile. Needs columns on `osionos_profiles` (root): `status_emoji`, `status_text`, `status_expires_at`, `status_busy`.
- **Hovercards are a preference but not wired.** P1-7 added `hovercards: 'on' | 'off'` in `Appearance` and `useHovercardsEnabled()` (`src/shared/config/useAppearance.ts:44-50`). The preference is read but **no component opens a card on hover** of mentions/avatars. Extend the existing `PeoplePeek.tsx` (`src/features/settings/people/PeoplePeek.tsx:51`) rather than adding a new component.
- **Blocking (P5-4-a) wins.** A blocked user cannot follow you. Blocks hide presence and status. The existing `blockedViewerBy` (`bridge-social-core.mjs:235-254`) is the single source of truth — reuse it everywhere.
- **Inventory first.** Existing files to extend:
  - `scripts/bridge-social.mjs` (routes), `bridge-social-core.mjs` (helpers), `bridge-presence.mjs` (presence core), `bridge-profile.mjs` (profile routes), `bridge-paging.mjs` (cursors)
  - `src/features/settings/people/PeoplePeek.tsx` (hovercard UI), `PeopleDatabasePanel.tsx` (source adapter)
  - `src/store/settings/useUserPreferencesStore.ts` (preferences), `useAppearance.ts` (hovercards hook)
  - Root models: `/home/dlesieur/Documents/groot-wt/root-integration/models/osionos-social-migration.sql`, `osionos-account-profiles-migration.sql`

## Contract

### 1. Root SQL sub-package (feat/acct-P2-3-root)
1.1 **`osionos_follows` table**
```sql
CREATE TABLE public.osionos_follows (
  follower_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  followee_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (follower_id, followee_id),
  CHECK (follower_id <> followee_id)
);
CREATE INDEX osionos_follows_followee_idx ON public.osionos_follows (followee_id, created_at DESC);
-- RLS: service_role FOR ALL; osionos_account_user SELECT own follows/followers
```

1.2 **`osionos_presence` table**
```sql
CREATE TABLE public.osionos_presence (
  user_id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  state TEXT NOT NULL DEFAULT 'invisible' CHECK (state IN ('online','away','dnd','invisible')),
  custom_text TEXT CHECK (custom_text IS NULL OR char_length(custom_text) <= 120),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- RLS: service_role FOR ALL; osionos_account_user SELECT/UPDATE own row
```

1.3 **Status columns on `osionos_profiles`** (P1-1 table)
```sql
ALTER TABLE public.osionos_profiles
  ADD COLUMN IF NOT EXISTS status_emoji TEXT CHECK (status_emoji IS NULL OR char_length(status_emoji) <= 8),
  ADD COLUMN IF NOT EXISTS status_text TEXT CHECK (status_text IS NULL OR char_length(status_text) <= 120),
  ADD COLUMN IF NOT EXISTS status_expires_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS status_busy BOOLEAN NOT NULL DEFAULT false;
-- RLS: osionos_account_user UPDATE own status columns; SELECT by everyone (directory view includes them)
```

1.4 **RPC: `osionos_follow_counts(followee uuid, viewer uuid)`** — returns follower_count, following_count, viewer_follows (bool). One call, index-only scans on both indexes. **Never a sequential scan on 10K rows.**

1.5 **Trigger: block check on follow insert** — `BEFORE INSERT ON osionos_follows` calls `blockedViewerBy` logic (recreate in SQL or reuse `osionos_user_blocks`): if `followee` blocked `follower`, raise 23514 `follow_blocked`.

### 2. Bridge routes (scripts/bridge-social.mjs — extend in place)
2.1 **`POST /api/social/follow`** — body `{ followeeId: UUID }`. Idempotent: re-following after unfollow re-inserts; following twice is 200 (no-op). Block-aware: if target blocked caller → 403 `follow_blocked`. Returns `{ ok: true, following: true }`.

2.2 **`DELETE /api/social/follow/:followeeId`** — idempotent unfollow. Returns `{ ok: true, following: false }`.

2.3 **`GET /api/social/followers/:userId?cursor&limit`** — keyset-paginated (cursor = `[created_at, follower_id]`, order `created_at DESC, follower_id DESC`). Each item: `{ id, name, avatar, headline, online, following }` (viewer follows them?). Uses `bridge-paging.mjs` `keyset` + `pageOf`.

2.4 **`GET /api/social/following/:userId?cursor&limit`** — same shape, cursor on `created_at, followee_id`.

2.5 **`GET /api/social/follow-counts/:userId`** — calls RPC `osionos_follow_counts(userId, viewerId)`. Returns `{ ok: true, followerCount, followingCount, viewerFollows }`. **One HTTP request.**

### 3. Presence states (scripts/bridge-presence.mjs — extend in place)
3.1 **New exported constants:**
```js
export const PRESENCE_STATES = ['online', 'away', 'dnd', 'invisible'] as const;
export const PRESENCE_PG_TTL_MS = 600_000; // already exists, reuse
```

3.2 **`recordHeartbeat` extended:** body may carry `{ state?: 'online'|'away'|'dnd'|'invisible', customText?: string }`. Writes to KV `presence:${userId}` = `{ ts, state, customText }`. DB write (`osionos_presence`) at most once per 10 min via existing `presence-pg:` key.

3.3 **`onlineAmong` extended:** reads KV, returns `Map<userId, { online: boolean, state: 'online'|'away'|'dnd', customText? }>`. If `state === 'invisible'` → `online: false` for **other viewers**; the user themselves sees their true state.

3.4 **`GET /api/profile/heartbeat`** (in `bridge-profile.mjs`) accepts the extended body and forwards to `recordHeartbeat`.

3.5 **`GET /api/profile/:userId`** includes `presence: { state, customText }` (respects invisible).

### 4. User status (scripts/bridge-profile.mjs — extend in place)
4.1 **`PATCH /api/account/profile/status`** — body `{ emoji?, text?, expiresAt?, busy? }`. Owner only (uses `pg.asUser`). Validates: emoji ≤ 8 chars, text ≤ 120, expiresAt future ISO string or null, busy boolean. Clears on `null`/`''`. Returns updated status fields + ETag (profile `version`).

4.2 **`GET /api/profile/:userId`** and `GET /api/users/:username` include status fields when not blocked and not opted out.

## Open questions
1. **Mention renderer location** — where exactly in `src/features/block-editor/` does `@handle` render? Need to wrap it with `PeopleHovercard`. (Search didn't find a single file; may be in `usePlaygroundBlockEditor.ts` or a Mention component.)
2. **Presence KV shape** — currently `presence:${userId}` = timestamp string. Changing to JSON `{ ts, state, customText }` is a breaking format change. Should we version the key (`presence:v2:`) or migrate in place? The KV is per-replica, so a rolling deploy can tolerate a format sniff.
3. **Status expiry cleanup** — who clears expired status? A cron? The next profile read? Spec says "expiry + busy" but no cleanup mechanism. Recommendation: lazy clear on read (compare `status_expires_at` < now).
4. **Follow counts RPC signature** — `osionos_follow_counts(followee uuid, viewer uuid)` or `follow_counts(user_id uuid, viewer_id uuid)`? The plan says "counts come from one RPC" but doesn't name the function. Using `followee`/`viewer` matches the pattern of "who am I looking at".
5. **`away` vs `idle`** — the plan says "online/away/DND/invisible". Is `away` auto-set after inactivity (client-side) or only manual? Current heartbeat has no idle detection. Recommendation: manual only in this package; auto-away is a follow-up.

## Orchestrator rulings (2026-10-23). These override the draft above wherever they differ.
1. **Sub-packages:**
   - **P2-3-root:** one migration file, `models/osionos-social-follow-presence-migration.sql`, holding follows, presence, the status columns, the counts RPC and the block trigger. It sits in ORDERED_LAST and adds checks in `scripts/verify/models-grants/`.
   - **P2-3-a (app, bridge):** follow routes, the counts RPC call, presence states, the status PATCH, and the blocking projections.
   - **P2-3-b (app, UI):** a `PeopleHovercard` built on `PeoplePeek`, the follow button and counts, the status editor, and the presence badge.
   - Order: root → a → b.
2. **Presence default is `online`, not `invisible`.** The row is created on the first heartbeat. `invisible` happens only when the user picks it; a default of invisible would hide everyone.
3. **Presence KV key is `presence:v2:<userId>`** holding `{ts, state, customText}`. For one release, readers fall back to the old `presence:<userId>` timestamp and read it as `online` (open question 2).
4. **Status expiry is lazy.** Any read where `status_expires_at < now()` returns no status. No cron (open question 3).
5. **`away` is set by hand only**; auto-away is a follow-up (open question 5).
6. **The RPC** is `osionos_follow_counts(p_user uuid, p_viewer uuid)`, returning one row `(follower_count, following_count, viewer_follows)`. It runs as SECURITY INVOKER with service-role EXECUTE only, and its counts use index-only scans (an EXPLAIN check in models-grants).
7. **The block trigger** checks `osionos_user_blocks` in BOTH directions. It raises SQLSTATE 23514 with message `follow_blocked`, which the bridge maps to 403 `follow_blocked`.
8. **Canvas tests run under `node:test`**, the repo's runner, not Vitest.
9. **Mention hovercards:** find the mention renderer before wrapping it. If it lives inside `usePlaygroundBlockEditor.ts` (about 2200 lines), wrap at the smallest render seam and don't grow that file. If no seam exists, ship people-list and avatar hovercards in P2-3-b and log mention hovercards as a follow-up.
