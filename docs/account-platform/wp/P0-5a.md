## Why (app repo `apps/osionos/app`, file:line)
- `GET /api/connections` writes: `listConnections` (`scripts/bridge-social.mjs:89-104`) reads every
  co-member of the caller through one nested embed — up to `SHARED_WORKSPACES_LIMIT = 200` ×
  `COMEMBERS_PER_WORKSPACE_LIMIT = 500` = 100 000 rows (`bridge-social-core.mjs:226-245`) — and POSTs
  up to `COLLEAGUE_INSERT_CAP = 500` `accepted`/`colleague` edges (`:294-304`), on every call. No SQL

- Feed counts are fetched as rows and counted in JS, 3–4 queries per post card: likes
  (`bridge-feed.mjs:145-153`), comments (`:174-180`, its own note says to switch), shares (`:307-309`).

## Changes
1. **Colleague edges are created when a member joins**, in the database, where every join path
   (invite accept, admin add, the sign-in upsert RPC) passes. AFTER INSERT trigger on
   `public.osionos_workspace_members`: insert `osionos_connections` rows between `NEW.user_id` and each
   other member of `NEW.workspace_id` **when that workspace has ≤ 200 members** (counted inside the
   trigger), with `ON CONFLICT (pair_key) DO NOTHING`. **Mirror exactly what the bridge inserts
   today** — read `bridge-social-core.mjs:226-310` (which workspaces count, requester/addressee
   orientation, `status`, `source`, `intro_message`, whether blocked pairs are skipped) and say in a
   comment which line each rule comes from. Never an edge to self. The trigger **never fails the
   join**: its body runs in an inner `BEGIN … EXCEPTION WHEN OTHERS THEN RAISE WARNING … END` (a
   colleague edge is a convenience; a join is not), `SET search_path = pg_catalog, public`, SECURITY
   INVOKER (only `service_role` inserts members — verify with the grants and say so).
   Caveat to state: the 200-member threshold is counted at join time, so a workspace that later
   grows past it keeps the edges it already made.
   **Devil conditions (D-P0-5, 2026-10-22), each one binding:**
   - Name it `osionos_workspace_members_colleague_edges_trg` (function
     `osionos_colleague_edges_on_join()`); the backfill guard and the `checks.sql` row test
     `tgrelid = 'public.osionos_workspace_members'::regclass AND tgname = …`, not mere existence.
   - **Semantics delta, write it in the file header:** the bridge today pairs up to 500 co-members
     per workspace across up to 200 of the caller's workspaces; the trigger is per workspace, so it
     cannot reproduce the per-caller 200-workspace cap, and it skips workspaces above 200 members
     (201–500 lose auto-edges). This is deliberate: one join stays ≤ 199 inserts.
   - **Blocked pairs get an edge**, exactly like `insertColleagueEdges` (`bridge-social-core.mjs:294-304`
     inserts for every unpaired peer; `bridge-social.mjs:107-110` hides blocked rows at read). Same
     columns as the bridge: `requester_id = NEW.user_id`, `addressee_id = peer`, `status 'accepted'`,
     `source 'colleague'`, `responded_at = now()`, no `intro_message`.
   - **One set-based `INSERT … SELECT … ON CONFLICT (pair_key) DO NOTHING`**, never a per-peer loop.
   - **The exception block is narrow:** catch `unique_violation`, `foreign_key_violation`,
     `check_violation`, `not_null_violation` only, `RAISE WARNING` naming the SQLSTATE and the
     workspace id; anything else propagates (a broken trigger must be loud, not silent forever).
     The "a failing edge insert" test uses a CHECK, so it lands in the caught set.
2. **One-time backfill**, guarded so it runs only on the boot that first creates the trigger
   (test `pg_trigger` before `CREATE TRIGGER`): for every workspace with ≤ 200 members, every
   missing pair, `ON CONFLICT DO NOTHING`, one NOTICE with the row count. A replay inserts nothing.
   Backfill orientation (it has no caller): `requester_id` = the member who joined later
   (`osionos_workspace_members.created_at`, ties broken by the greater `user_id`) — the one whose
   join would have fired the trigger. State it in a comment.
3. **`public.osionos_feed_page_counts(p_page_id uuid, p_viewer uuid)`** `RETURNS TABLE (likes bigint,
   liked_by_viewer boolean, comments bigint, shares bigint)`, `LANGUAGE sql STABLE`, SECURITY
   INVOKER, `REVOKE EXECUTE … FROM PUBLIC`, `GRANT EXECUTE … TO service_role`. Each count must use an
   index on `page_id` — add a named `IF NOT EXISTS` index for any of `osionos_feed_likes`,
   `osionos_feed_comments`, `osionos_feed_shares` that lacks one (`osionos_feed_shares_page_idx`
   exists, `models/osionos-feed-engagement-migration.sql:41`; check the others).

## Locks
The trigger makes a join take `osionos_workspace_members` then `osionos_connections`. The migration
must take them in that order on replay: `SET LOCAL lock_timeout = '5s'` (with a Caveat), then
`LOCK TABLE public.osionos_workspace_members, public.osionos_connections IN SHARE ROW EXCLUSIVE MODE`
before creating anything. Prove it: a join racing a replay of the file, 20 runs, no `40P01`.
`5s` matches the P0-1 foundation (`osionos-account-foundation-migration.sql:58`); its Caveat says a
replay behind a longer-held lock fails the boot loudly rather than queueing every join behind it.
