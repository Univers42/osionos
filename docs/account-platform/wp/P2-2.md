## Contract

### Which fields are bindable

Exactly the public projection, camel-cased, minus the identifiers and the images, in this order (labels are the picker's copy):

| key | label | value |
|---|---|---|
| `displayName` | Name | text |
| `username` | Username | text |
| `pronouns` | Pronouns | text |
| `headline` | Headline | text |
| `bio` | Bio | text |
| `location` | Location | text |
| `company` | Company | text |
| `website` | Website | text |
| `links` | Links | list, rendered joined with `", "` |
| `timezone` | Time zone | text |
| `orcid` | ORCID | text |
| `patreon` | Patreon | text |
| `profession` | Profession | text (the id, e.g. `student`; see open question 3) |

Not bindable: `userId`/`id`, `avatarUrl`, `bannerUrl` (images, not text; open question 2), every `custom:<key>`, and every field outside `CARD_COLUMNS` (`email`, `directoryOptOut`, `readmePageId`, `version`, `role`, `online`, `lastSeenAt`, `joinedAt`, `status`, the settings). The list is one constant, `README_FIELDS`, in `src/entities/block/model/binding.ts`, with `isReadmeField(key)`. The bridge module in P2-2-b holds the matching list; a parity test (below) fails when they differ or when `CARD_COLUMNS` gains a field the lists do not decide on.

### How a binding is stored

A bound README block is the block the admin templates already store, nothing new in the schema:

```
{ id, type: "paragraph" | "heading_1" | "heading_2" | "heading_3", content: "",
  recordRef: "$record", fieldBind: "<README_FIELDS key>", headingLevel?: 1|2|3 }
```

- Built by `bound(blockId, fieldBind, headingLevel?)` (`templateBlocks.ts:39`). The editor writes `$record`, never the legacy `$viewedUser`, never `collectionRef`, never a `custom:` key.
- It rides the normal page content sync (outbox, `pageFileCodec` overlay); no migration, no schema change.
- `content` stays `""`: the value is never copied into the block. A reader always sees the **current** profile value, resolved at render from the record they are allowed to see.
- Unbinding deletes `recordRef`, `fieldBind` and `headingLevel`-as-bound and leaves an empty paragraph (nothing the viewer saw is kept as text).

### The README record (what a binding can resolve against)

`toReadmeRecord(profile)` in `src/widgets/profile-page/model/binding.tsx` returns `{ id, ...picked }` where `picked` has **only** the `README_FIELDS` keys whose value is non-null, non-empty (an empty array counts as empty). It copies by an explicit key list, never by spread. `ReadmeBlocks` takes this record and wraps the projected blocks in `BindingProvider`. The admin-template record (`toBoundRecord`) is **unchanged**.

`resolveBoundField` is hardened for every caller: `custom:` keys and plain keys read an **own** property only (`Object.hasOwn`), so `constructor`, `__proto__`, `toString` resolve to `undefined`.

`BoundFieldReadOnly`: when the record has no own property for the key (not allowlisted, empty, or `custom:` missing) it renders **nothing** (`null`); the existing "—" stays only for a key that is present. For the README record this means empty and denied are both invisible to the reader. Outside a provider it still shows the italic name.

### The slash item

- Entry in `slashMenuCatalog.tsx`, section `advanced`: id `advanced:profile-field` (exported as `PROFILE_FIELD_COMMAND_ID`), label "Profile field", aliases `["profile", "field", "bind", "bio", "name", "headline"]`, description "Show a field of your public profile — always current", `kind: "profile-field"` (new union member in `types.ts`).
- Visible only when the editor's page is the owner's README: `pageId === useAccountProfileStore.getState().profile?.readmePageId` (a `usePageStore`-style selector in `SlashCommandMenu.tsx`, beside the `isTemplatePage` filter at `:86-89`). Hidden on every other page, template or not.
- The gate is **re-checked at dispatch** (as `useSlashWhiteboardSelect` does): a stale row does nothing.
- Behaviour (new file `useSlashProfileFieldSelect.ts`, shaped like `useSlashWhiteboardSelect.ts`): close the menu, strip the slash query from the source block; if the source block is then empty, bind it in place (`updateBlock` with `recordRef`, `fieldBind`), else `insertBlock` a new bound block after it. Default field `displayName`, paragraph. Then dispatch `osionos:profile-field-settings` for that block so the inspector opens at once.

### The inspector

A popover anchored to the bound block, opened by (1) the slash item, (2) a "Profile field" section in the block context menu: "Bind to profile field…" on a plain `paragraph`/`heading_1..3` of a README page, "Profile field settings" on an already bound block, (3) clicking the bound block's chip. It is mounted by the editable editor only, like the button popover, and writes through `onUpdateBlock`.

Controls (all labelled, keyboard reachable, Escape closes, focus returns to the block, `--osio-*` tokens only):

| Control | Behaviour |
|---|---|
| Field | A `role="listbox"`/native `<select>` of the 13 `README_FIELDS` with their labels; the change writes `fieldBind` at once. A stored value outside the list (hand-edited page) shows "Unknown field" selected and the list; saving any choice replaces it. |
| Style | Text / Heading 1 / 2 / 3. Writes `type` and `headingLevel` together (`heading_N` + `headingLevel: N`, or `paragraph` and no level), the same pairs `bound()` writes. |
| Preview | The current value of the chosen field from the owner's own profile, as a reader would see it. |
| Remove binding | Unbinds (see above) and closes. |

States (the four):

- **Loading** — `useAccountProfileStore.status` is `idle`/`loading`: field and style are usable, the preview says "Loading your profile…".
- **Empty** — the field is empty on the profile: preview "Empty on your profile — readers see nothing here." plus a button "Edit public profile" → `openSettings("profile", "public-profile")`.
- **Error / unavailable** — status `error`/`unavailable`: "Could not load your profile, so there is no preview. The binding still works." with a Retry that calls `hydrate()`.
- **Loaded** — the value, truncated to 120 characters with the full text in a `title`.

The editor's own view of a bound block (P2-2-c): a non-editable chip "Profile field: <label>" with the live preview value dimmed beside it; the block is a normal selectable block (drag, delete, the block menu). Typing into it does nothing; Enter below it creates the next block.

### Security edge

A binding can never reach a field outside the public projection, on four independent layers: (1) **picker** — the inspector offers only `README_FIELDS`, and the slash item writes only a key from it; (2) **record** — `toReadmeRecord` copies an explicit allowlist, so `email`, `directoryOptOut`, `readmePageId`, `version`, `role`, `online`, `lastSeenAt`, `joinedAt`, `customFields` and the settings are not in the object the README resolves against, whatever `fieldBind` says; (3) **resolver** — own-property reads only, so prototype keys and `custom:` resolve to nothing; (4) **bridge** — `projectReadme` drops `recordRef`/`fieldBind` from any block whose key is not allowlisted before the card leaves the server, so a hostile owner who PATCHes a page directly never gets a non-allowlisted binding in the response, and a stale client cannot be made to resolve one. An owner-only field (`email`, the opt-out flag, the README page id, the version) is in no layer, so another viewer sees nothing for it: not the value, not a dash, not the field name. A reduced card (opted-out or blocked viewer) has no README at all (`bridge-account-profile.mjs:280`), so the viewer sees no bound block. The picker never binds a field the owner has hidden with the directory opt-out: the opt-out removes the whole card for others, not field by field. The owner still sees their own preview in the inspector (read from `GET /api/account/profile`, which only the owner can call).

## Acceptance checks

1. A bound README block shows the owner's current public value to another viewer; changing the profile changes it with no edit of the page.
2. `fieldBind` of `email`, `directoryOptOut`, `readmePageId`, `version`, `role`, `online`, `custom:x`, `constructor`, `__proto__` renders nothing for any viewer, and the bridge response contains no binding for them.
3. An empty allowlisted field renders nothing in the README (not a dash); the inspector says so to the owner.
4. `/profile` offers "Profile field" on the owner's README page and on no other page (a template page, an ordinary page, someone else's README all lack it); firing the command on a stale menu elsewhere inserts nothing.
5. The inspector changes field and style, removes the binding, closes on Escape with focus back on the block, and shows all four states.
6. A bound block survives a reload and a page-file round trip unchanged (`{recordRef:"$record", fieldBind}`), and is never stored with the value in `content`.
7. Admin templates and professions render exactly as before (`tests/canvas/profession-templates.test.ts` unchanged and green).

## Decisions (reviewer, 2026-10-24) — binding on every part

1. **Empty value:** a README shows nothing for an empty or absent bound field. Admin templates **keep "—"**. The look is chosen by the provider, not by `BoundFieldReadOnly` on its own. Part a adds one small context next to `BoundRecordContext` in `entities/block/model/binding.ts`, `BoundFieldEmptyText`, whose default is `"—"`. `ReadmeBlocks` provides `null`, and `BoundFieldReadOnly` renders `null` when the value is missing and that context is `null`. Today a missing `custom:<key>` in an admin template shows "—", and it still does after this package (acceptance 7; add a canvas case for it). Contract §"The README record" is amended accordingly.

3. **`profession` shows its label.** `toReadmeRecord` maps the id to its label through `src/data/professions/professions.ts`, with an unknown id kept as is. `entities/block` imports nothing new. Add a test case for it.
4. **README only.** Other owner pages are not in this package.
