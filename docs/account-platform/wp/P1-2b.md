# P1-2b 👹 — sudo by emailed code; username change and account deletion request behind it

Repo: osionos app, branch `feat/acct-P1-2b` from `feat/account-platform` **after P1-2a merges**
(it mounts beside P1-2a's modules). Bridge only; no gateway or grobase change. Facts are from
research R-P1-2 (2026-10-22) and a read of `apps/opposite-osiris/scripts/auth/otp-client.mjs`.

## Why
- Nothing proves a recent authentication.
  - `grantSudo`/`requireSudo` exist (`scripts/bridge-guard.mjs:186-200`: kv key `sudo:<jti>`,
    10 min) but nothing grants it.
  - The gateway has no re-auth route; its email-OTP routes need an in-progress password-login
    ticket (R-P1-2 §1).
  - A password re-check through GoTrue creates a session, sends a sign-in alert and moves the
    lockout counters (§3), and OAuth-only users have no password (§4).
  - Passkeys are grobase-side and flag-gated (§5).
- P1-6's danger zone needs a username change and a deletion request. Both must sit behind a sudo
  proof, and P1-1 gave them tables (`osionos_username_history` with the 90-day hold,
  `osionos_account_deletion_requests` with the 14-day grace).

## Decisions (the devil rules on these)
- **D1 — One step-up method in this package: a code emailed to the account's address**, through
  grobase's existing login-OTP service:
  - `POST {config.baasUrl}/v1/auth/otp/request` with `apikey: <service key>` and `{email}`
    (Kong route ACL baas-admin, `apps/grobase/infra/docker/services/kong/conf/kong.yml:536-555`);
    answers 200 `{sent:true}` or 502 `send_failed`
    (`apps/grobase/src/control-plane/internal/loginotp/handler.go:38-56`);
  - `POST {config.baasUrl}/v1/auth/otp/verify` (public) with `{email, code}`; answers 200
    `{verified:true, proof}`, 401 `invalid_code`, 410 `expired`, 429 `too_many_attempts`
    (`handler.go:60-97`).
  - It is the same service `apps/opposite-osiris/scripts/auth/otp-client.mjs` calls.
  - grobase mounts these routes only with `EMAIL_OTP_ENABLED` on
    (`cmd/tenant-control/mount_loginotp.go:23-30`); off answers 404.
  - It works for every user, password or OAuth. It adds no session and no sign-in alert.
  - grobase limits a code (TTL `EMAIL_OTP_TTL_SECS` = 300 s, 5 attempts) but **not** how often a
    code is requested, so the bridge's rate limit on contract 1 is the only one.
  - Password and passkey step-ups come with P3-1/P3-2.
- **D2 — The address comes from GoTrue, never from the request**:
  `GET {config.baasUrl}/auth/v1/admin/users/<session.userId>` with the service key, the same call
  shape as `scripts/bridge-workspace-invites.mjs:102`. The app-session token carries no email, and
  the bridge stores only `email_hash`. No email in a response or a log: the client sees a masked
  form (`d•••@g•••.com`).
- **D3 — The verify answer's proof is checked, not trusted.** Per `handler.go:60-67` the proof is
  an HS256 JWT signed with `GOTRUE_JWT_SECRET`, claims `{otp: <lowercased email>, aud: "otp-proof",
  iat, exp = iat + 5 min}`, no `iss`/`sub`. The bridge checks, with the secret it already uses for
  `mintAccountJwt` (cite where it reads it; if that is not GoTrue's secret, stop and report):
  - the header `alg` is exactly `HS256` and the signature verifies (constant-time compare);
  - `aud === 'otp-proof'` and `exp` is in the future;
  - `otp` equals the lowercased address from D2.

  The proof is "not single-use after minting"; the bridge consumes it in the same request and never
  returns it to the client. Any check failing → 502 `sudo_proof_invalid` (a grobase or secret
  fault, not the user's) and an audit row.
- **D4 — Sudo is per session (`jti`), 10 minutes, granted only after D3.** A revoked session's jti
  can't be used anyway (P0-4). `requireSudo` failures answer 403 `{code:'sudo_required'}`, which
  P1-5's client signal already catches.
- **D5 — Revoking a session needs no sudo.** It is protective: a user under attack must cut
  sessions fast. Deleting the account and changing the username need it.
- **D6 — Shared code store.** A step-up code and a pending login code for the same address share
  grobase's store. A step-up request may invalidate an in-flight login code for that address (one
  code per address). Caveat in the module; acceptable because both need the same inbox.

## Contracts (module `scripts/bridge-account-sudo.mjs`, mounted in `bridge-account-mounts.mjs`)
1. `POST /api/account/sudo/email`
   - Rate limit 5 per 10 min per user.
   - D2 address, then grobase request.
   - Outcomes:

     | outcome | answer |
     |---|---|
     | grobase 200 `{sent:true}` | 202 `{ method: 'email', sentTo: <masked> }` |
     | the bridge's own limit | 429 |
     | grobase 404 (flag off), 502 `send_failed`, any other status, timeout, network | 503 `sudo_unavailable` |
     | GoTrue has no address for the user | 409 `no_email` |
   - Audit `sudo.code_sent` before the call.
2. `POST /api/account/sudo/verify {code}`
   - `code` must be exactly 6 digits, else 422.
   - grobase verify, then D3, then `grantSudo(kv, session)`.
   - Outcomes:

     | grobase answer | bridge answer |
     |---|---|
     | 200 and D3 passes | 204, audit `sudo.granted` |
     | 401 `invalid_code` | 422 `code_invalid` (never 401: the client treats a 401 as a session problem) |
     | 410 `expired` | 410 `code_expired` |
     | 429 `too_many_attempts` | 429 `code_locked` |
     | 200 and D3 fails, or 200 with no proof | 502 `sudo_proof_invalid`, audit `sudo.proof_rejected` |
     | 404, other status, timeout, network | 503 `sudo_unavailable` |
3. `GET /api/account/sudo` returns `{ active: boolean, expiresAt? }` for the current session (UI
   state).
4. `POST /api/account/username {username}`
   - `requireSudo`; rate limit 3 per 24 h per user; audit `account.username_changed` first.
   - The write is `PATCH osionos_profiles?user_id=eq.<uid>` as the user (P1-1 grants the column).
     The hold and uniqueness triggers decide: 23505 → 409 `username_unavailable`, one code for
     "taken" and "held" (no oracle); 23514 → 422.
   - Then `osionos_bridge_identities.username` is set by the service role to the same value, so
     the legacy readers agree (the P1-1 sync trigger runs identities → profiles only). If that
     second write fails, say what state is left and test it.
5. `POST /api/account/deletion` `{successorUserId?}`
   - `requireSudo`; audit `account.deletion_requested` first.
   - INSERT as the user into `osionos_account_deletion_requests`. The DB defaults
     `scheduled_for`; the CHECK forbids a shorter grace.
   - Already requested → 409 with the existing row. A successor must be a member of a workspace
     the caller owns, else 422. Responds 201 `{ requestedAt, scheduledFor }`.
6. `GET /api/account/deletion` returns the caller's row or 404.
   `DELETE /api/account/deletion` cancels: no sudo, audit `account.deletion_cancelled`, 204.
   Nothing executes a deletion here (P5-6).

## Acceptance (`tests/bridge/`, fakes for grobase OTP, GoTrue admin and PostgREST that apply their rules)
1. Sudo flow, happy path: code sent, then verify, then `GET sudo` reports active. Expired after
   10 min of injected clock. A second session of the same user is NOT in sudo.
2. Proof checks, one test each, every one → 502 `sudo_proof_invalid` and no sudo granted:
   - a proof signed with another secret;
   - `alg: none` and `alg: HS512` headers;
   - `aud` other than `otp-proof`;
   - a proof whose `otp` is another address;
   - an expired proof;
   - a grobase 200 with no proof.
   Also: grobase 404 (flag off) on either route → 503 `sudo_unavailable`.
3. The address is never in a body, a header the bridge sends to the client, or a log line (capture
   console). The request body cannot choose the address (an `email` field is ignored and a test
   proves the grobase fake saw the GoTrue address).
4. Username: without sudo → 403 `sudo_required`; with sudo → 200; "taken" and "held" → identical
   409 bodies; identities are updated too; a failing identities write leaves the state the spec
   says.
5. Deletion: without sudo → 403; with sudo → 201 and `scheduledFor` ≥ 14 days out; a second
   request → 409; cancel → 204 and the row is gone; a successor outside the caller's workspaces →
   422.
6. Audit failure on any audited route → 503 and no write.
