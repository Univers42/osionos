## Why (verified anchors)

1. **Six client calls hit no route.** `src/store/settings/useAccountSettingsStore.ts:45,66,79` (GET/PATCH `/api/account/settings`) and `useAccountEmailsStore.ts:58,70,89,100` (GET/POST/DELETE/make-primary) match nothing in `scripts/bridge-account-mounts.mjs:54-80` (the `modules` array; imports at `:49-51`); the fallthrough is `{ ok:false, message:'Not found.' }` with no code, which `classifySettingsError` (`src/store/settings/settingsStoreUtils.ts:71-77`) reads as `unavailable`. **The same classifier reads a 503 whose code ends `_unavailable` or `_off` as `unavailable` (`:74`), and `trySettingsGet`/`withSettingsFallback` (`:115-129`) then return `null`: a real outage would look like a missing route. F-1 keeps that rule (`docs/account-platform/wp/F-1.md:35`), so these routes never answer an outage with such a code (Contract "Errors").**
2. **The settings PATCH sends keys the server will not take.** `ProfilePanel.tsx:99` sends `{ security: { ...security, hasPassword: true } }` and `:100` sends `{ security: { ...security, preferredMfaMethod } }`: the whole `security` object, including the read-only fields the server reports. `reset` (`useAccountSettingsStore.ts:74-85`) PATCHes a full default object but has no caller (`rg 'reset\(' src | rg -i account` finds none). Under "every other key is 422" all three would fail and roll back.
3. **`preferredMfaMethod` has no server home.** `rg -i 'preferredMfa|preferred_mfa' scripts ../../root-integration/models` finds nothing; only `tests/e2e/support/twoStepStub.mjs:33-34` fakes it. It only orders the options the modal offers (`types.ts:20`, `twoStepMethods.ts:21-25`); no bridge code reads it for a decision. The generic per-user store exists: `osionos_user_settings (user_id, section, value jsonb, version)` with `section ~ '^[a-z][a-z0-9_-]{0,31}$'` (`osionos-account-profiles-migration.sql:214-222`), the atomic `osionos_user_settings_merge(p_section, p_patch)` (`:311-334`, `SECURITY INVOKER`, keyed on `osionos_account_uid()`, callable by `osionos_account_user`), RLS owner-only (`:635-645`). The erasure registry already deletes the table by `user_id` (`osionos-account-erasure-migration.sql:322`). `bridge-preferences.mjs` is the proven pattern: `readSection :102-107`, `mergeSection :109-112` (both `asUser`). Only `bridge-preferences.mjs` and `bridge-self-views.mjs:151` call the merge, with fixed sections, so no existing route writes section `security`.
4. **`hasPassword` cannot be proven from the tree.** GoTrue's admin payload never carries `encrypted_password` (`bridge-account-identities.mjs:24-26`, `internal/models/user.go:31` `json:"-"`; the GoTrue source is not in these trees, see Not verified). `public.users.password_hash` is the constant `'managed-by-gotrue'` for gateway users (`auth-gateway-users-reconcile-migration.sql:29,74`). So neither `true` nor `false` is provable. `signInMethods.ts:32-33` shows the password row only when the value is a boolean and `ProfilePanel.tsx:81` renders it only when that row exists, so an omitted field is the honest answer. Side effect, accepted by Decision 2: with the row hidden, the password modal cannot be opened from Settings at all.

## Contract

**Mount:** two new modules appended to `modules` in `bridge-account-mounts.mjs` (array `:54-80`, last entry today the identities routes at `:79`), after `createAccountIdentitiesRoutes`: `createAccountSettingsRoutes({ config, pg, kv, verifySession, env: deps.mfaEnv ?? process.env })` and `createAccountEmailsRoutes({ config, kv, verifySession, fetchImpl: deps.mfaFetch ?? fetch })`. Mount order is safe: no earlier module claims `/api/account/settings` or `/emails` (verified by `rg`). Each answers `false` for a path that is not its own; a sub-path (`/api/account/settings/x`, `/api/account/emails/x`) is its own and answers 404 `not_found` (a different code from the missing-route 404, so F-1 reads it as an answer). Order inside a handler: `callerSession` (`bridge-account-sudo.mjs:73-80`) → verb check → `rateLimit` → work. Errors through `respondWithError` (sudo module `:64-71`). The session verifier is the default one: an aal1 `mfa_pending` token gets 403 `mfa_required` (`scripts/bridge-session-token.mjs:184-185`), like the passkey routes.

**Errors (condition 1, orchestrator ruling).** A store, GoTrue or kv failure on these two routes answers **503 `settings_read_failed`**, and never a code ending `_unavailable` or `_off`, so `classifySettingsError` (`settingsStoreUtils.ts:74`) returns `failed` and the client shows an error. This includes the rate-limit step: `rateLimit` (`bridge-guard.mjs:167`) rethrows whatever the kv store throws, and `bridge-kv.mjs:35` throws 503 `kv_unavailable`, which the classifier would read as `unavailable`; each handler therefore catches a non-429 failure of `rateLimit` and rethrows it as 503 `settings_read_failed` (still fail closed, ADR 0002). 429 `rate_limited` passes through. The same code covers a failed PATCH write. Caveat to carry in the header: one code for read and write failures; the message says which.

**GET `/api/account/settings`** → 200
```
{ userId, security: { passkeysEnabled, preferredMfaMethod? }, updatedAt? }
```
- `userId` = `session.userId`. No query, header or body can name another user.
- `security.passkeysEnabled` = `env.PASSKEYS_ENABLED === '1'`; always present (a plain flag read, no I/O).
- `security.preferredMfaMethod` = `value.preferredMfaMethod` of the caller's `security` section (`pg.asUser(session).get('osionos_user_settings?section=eq.security&select=value,updated_at&limit=1')`, the `readSection` shape of `bridge-preferences.mjs:102-107`), only if it is `'totp'` or `'recovery'`; else omitted. `updatedAt` = the row's `updated_at`, omitted without a row.
- **No `pendingDeletionAt`** (Why 6, condition 9).
- **Absent means unknown, never a default:** `hasPassword`, `passwordUpdatedAt` (Why 4), `supportAccessGrantedUntil`, `removedAt`, `createdAt`, `pendingDeletionAt` are never sent. `types.ts` makes `createdAt`/`updatedAt` optional in the same change (nothing in `src` reads them; see "Before editing"). The client keeps an absent key as `undefined` (Client below).
- One source only (the section read). The read throwing → 503 `settings_read_failed` (log `account_settings_source_failed`, no ids). The handler calls only `pg.asUser(session)`, never `asService`.
- Isolation, bridge side (verdict F5, holds): `asUser` mints an account JWT from the session (`scripts/bridge-pg.mjs:168-177`) and RLS is `user_id = osionos_account_uid()`. The defence is therefore the DB; B3 proves the handler does not weaken it.

**PATCH `/api/account/settings`** → 200 with the same body as GET after the write.
- Body: JSON object (`readBody`, 413/400 as the sudo module `:90`). Allowed shape exactly `{ security: { preferredMfaMethod: 'totp' | 'recovery' } }`.
- **Validation (condition 7).** Runs after `callerSession` and the rate limit, before any write, in this order: the body is a plain object; its own keys (`Object.keys`) are exactly `['security']`; `security` is a plain object whose own keys are exactly `['preferredMfaMethod']`; the value is one of the two methods. Any other top-level key, any other `security` key (including `hasPassword`, `passkeysEnabled`, `passwordUpdatedAt`, `pendingDeletionAt`, `userId`), an inherited or prototype key (`__proto__`, `constructor`, `prototype`: `JSON.parse` makes `__proto__` an own key, so it fails the exact-keys test), a mix of one valid and one invalid key, a non-object, or a value outside the two methods → 422 `invalid_body`; the message names the offending key, never the value. An empty body or empty `security` → 422 `empty_patch`. Zero writes on any 422. Caveat: a duplicate key in the raw JSON collapses in `JSON.parse` (last wins) and cannot be detected after parsing; the surviving value is still validated.
- **Write (condition 8):** `pg.asUser(session).rpc('osionos_user_settings_merge', { p_section: 'security', p_patch: { preferredMfaMethod } })` (the `mergeSection` shape, `bridge-preferences.mjs:109-112`). One statement, so two tabs both land. No `asService` call anywhere in the GET or PATCH handler. Failure → 503 `settings_read_failed`.
- **No sudo.** Evidence: the value orders two options in a modal and grants nothing (Why 3; `types.ts:20`: "the server never trusts it"); it is reversible and read by no decision. A sudo prompt on a cosmetic reorder trains users to dismiss sudo. A stolen session can reorder two buttons and nothing more. Still behind the session verifier and a rate limit. No audit row (nothing irreversible); see Q4.
- **Rate limit (condition 14):** `rateLimit(kv, ['account-settings', userId], { limit: 120, windowMs: 60_000 })` (same numbers as `bridge-preferences.mjs` `SETTINGS_LIMIT` `:46`), 429 `rate_limited` with `retry-after`. With kv down the step fails closed: 503 `settings_read_failed`, no pg or GoTrue call (ADR `docs/account-platform/adr/0002-bridge-kv-fails-closed.md`); it is never skipped.
- Every other verb → 405 `method_not_allowed`, before any call.

**GET `/api/account/emails`** → 200 `EmailRecord[]` (`types.ts:42-51`), exactly one element today:
`{ _id: 'primary-<userId>', userId, email, isPrimary: true, verifiedAt: email_confirmed_at ?? null, createdAt: created_at, updatedAt: updated_at ?? created_at, removedAt: null }` from the GoTrue admin user read. `_id` matches `defaultEmail` (`defaults.ts:41-53`) so a persisted local list collapses onto it. No `osionos_user_emails` read (Why 7). The address is the caller's own and is returned in clear (same exposure as the profile); never logged. GoTrue unreachable or non-2xx → 503 `settings_read_failed`; 404 or an address that is not a string → 200 `[]` (no address is a fact, not an outage). Rate limit `['account-emails', userId]`, 30 per 60 s (each call reaches GoTrue), same kv-down rule. Other verbs → 405.
- **Shared read (condition 11):** new `scripts/bridge-gotrue-user.mjs` exports `readGotrueUser({ config, fetchImpl }, userId)` (8 s timeout) and the shared header builder `gotrueAdminHeaders(config)` (`{ Accept: 'application/json', apikey, Authorization: Bearer }`, the shape at `bridge-account-identities.mjs:52-55`), returning the payload or throwing 503. Only the emails module uses it in F-3. Moving `readIdentities` (`bridge-account-identities.mjs:48-62`) and `accountAddress` (`bridge-account-sudo.mjs:140-151`) onto it is **F-3c**, recorded in `docs/account-platform/LEDGER.md` as an open follow-up row in the F-3 commit (the F-1 row already mentions "Open F-3c: one shared GoTrue admin read (three copies after F-3)"; the F-3 row names it and the helper's exports).
