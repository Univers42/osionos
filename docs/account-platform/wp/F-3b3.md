# F-3b3 — the data export carries the secondary addresses, opened from the seal

r2: devil D-F-3b3s PROCEED-WITH-CONDITIONS; conditions C1-C9 and decisions D1-D7 are folded in below.

## Why (verified anchors)

- `osionos_user_emails` (root F-3broot, live since 2026-10-24) holds each secondary address as
  `email_enc` (AES-GCM, `bridge-seal.mjs`) plus `email_hmac`. Its registry row has
  `export_columns = NULL` (root `models/osionos-account-erasure-migration.sql:314`), so today's
  export (`scripts/bridge-account-export-runner.mjs:78-84`) leaves the user's own addresses out.
  That is a gap in the right of access.
- The registry path cannot list them, and must not be loosened to. `planTables` refuses any
  export column matching `SECRET_NAME` (`scripts/bridge-account-export-archive.mjs:35,72`, which
  includes `_enc$` and `hmac`). The root check `p5_export_no_secrets` refuses the same names
  (`scripts/verify/models-grants/account-checks.sql:2961-2997`). Both guards stay exactly as they are.
- The opener already exists. `openAddress(row, env)` (`scripts/bridge-account-email-rows.mjs:79`)
  returns the address, or `null` when the row does not open or its HMAC does not match.
  `keysUsable(env)` (`:71`) says whether both keys are well formed.
- The runner already gets `env` (`createExportRunner({ pg, env, … })`, `:123`), but
  `buildJobArtifact` (`:78`) does not receive it yet.

## Contract

1. After the registry tables are read, the runner reads the owner's `osionos_user_emails` rows with
   the existing `readTable` (same keyset paging on `id`, same `budget`, same caps). The read uses a
   fixed plan: table `osionos_user_emails`, select `id,user_id,email_enc,email_hmac,created_at,verified_at`,
   scope `['user_id']`, no filter. `bridge-account-email-rows.mjs` exports the select list as
   `COLUMNS` and the runner builds the plan from it:
   `{ table: 'osionos_user_emails', columns: COLUMNS.split(','), scope: ['user_id'], filter: null }`.
   That plan is a constant, not a registry row. Only the MAPPED table (contract 2) is pushed into
   `tables`; the raw rows never are (C5).
2. Those rows become one exported table named `osionos_user_emails`. Its columns are exactly
   `id, email, readable, created_at, verified_at`, in that order:
   - `email` is `openAddress(row, env)`, or `null`;
   - `readable` is `email !== null`.
   `email_enc`, `email_hmac` and `user_id` never reach the artifact in any format.
3. The new table goes in name order among the registry tables, like every other table. It is
   present even when the user has no rows (an empty table, as every registry table is).
4. When rows exist and `keysUsable(env)` is false, the job fails with `export_sealed_unavailable`.
   Nothing is stored, and the failed row carries the code: never a done export with silently
   unreadable addresses. With no rows, unusable keys are not an error. The check runs inside
   `buildJobArtifact`, after the fixed-plan read and before `ensureBucket`, so a failure makes no
   bucket and no put (C3). `export_sealed_unavailable` already matches `KNOWN_CODES` (`runner:38`).
5. With usable keys, a row that does not open is exported with `email: null, readable: false`, and
   the job still finishes as done, but only when at least one row opens. When rows exist and NONE
   opens, the job fails with `export_sealed_unavailable` too (C4, D2). `keysUsable` checks only the
   form of the keys, so this is what catches a wrong key.
6. The CSV formula prefix applies as for any other string cell. `=x@example.com` is a legal local
   part under `normaliseAddress`, so it is exported as `'=x@example.com` in CSV.
7. The runner's header `Caveat:` gains these points (C8):
   - a sealed address that no longer opens (a key rotated away without `_PREVIOUS`, or a corrupted
     row) is exported as unreadable, not left out;
   - a wrong key and a corrupted row look alike;
   - the addresses sit in clear in the stored artifact until it expires (7 days), and the download
     needs a session, not sudo.
8. No duplicate table (C6). If `planTables` returns a plan named `osionos_user_emails`, the job fails
   with `export_forbidden_column` before any data read. The registry must never become a second door
   to that table.
9. A missing table is not a failed export (C9). A PostgREST "table not found" answer (404, or code
   `PGRST205`) on the fixed-plan read yields an empty `osionos_user_emails` table and a numbers-only
   `console.warn`, so a database without the F-3broot table still exports. Any other error fails the
   job as today.

Decisions (D1-D7 of the verdict):
- Fail rather than omit (D1, D2).
- A failed export still spends the daily limit, as today (D3, out of scope).
- The root reason text at `erasure-migration.sql:314` becomes stale. A separate root follow-up,
  F-3b3root, changes the text only, and `export_columns` stays NULL (D4, D7).
- Cleartext in the owner's artifact is accepted and documented (D5).
- Pending rows are exported, with `verified_at` null (D6).

Put the row-to-export mapping, a function of `(rows, env)` returning the table, in
`bridge-account-email-rows.mjs`, next to `openAddress`. The runner only wires it.

## Tests

Before editing, run the two export test files once with the one-file command and record their
counts. Seal rows with the real `createSeal` path (or the email helpers that already do), not a stub
of `openAddress`.

Seeded rows use the real `createSeal` path, never a literal such as `'v1.sealed'` (C7).

- E1: a user with one verified and one pending address. The JSON export has an `osionos_user_emails`
  table with both addresses in clear, `readable: true`, and exactly the columns of contract 2, in
  order. Assert the exact key set of every row and of the table's `columns` (C5).
- E2: assert the seeded `email_enc` and `email_hmac` strings are each longer than 20 characters.
  Then assert neither appears in the raw JSON, the CSV, or any ZIP entry. The zip is STORE
  (`scripts/bridge-zip.mjs:14`), so its raw bytes can be searched.
- E3: user B's row sits in the same table with a real `user_id`. B's address is absent from user A's
  export, and the request path the fake saw contains `user_id=eq.<A>`.
- E4: keys unset, rows present → the job is `failed` with `error_code === 'export_sealed_unavailable'`
  (not `export_failed`), and `store.puts === 0`, `store.buckets === 0`, `store.objects.size === 0` (C3).
- E5: keys unset, no rows → the job is `done`, and the table is present and empty.
- E6: two rows, one good and one with a mismatching `email_hmac` → the job is `done`, and only the bad
  row is `email: null, readable: false`.
- E6b: every row fails to open (keys of the right form, wrong lookup key) → the job is `failed` with
  `export_sealed_unavailable` (C4).
- E7: the CSV cell for `=x@example.com` is `'=x@example.com`.
- E8: no column of the exported table matches `SECRET_NAME`, imported from the archive module.
- E9: a registry row `{table_name:'osionos_user_emails', column_name:'user_id', export_columns:['id']}`
  → the job is `failed` with `export_forbidden_column`, and no read of the emails table is made (C6).
  The `SECRET_NAME` path is already tested at `bridge-account-export.test.mjs:250`.
- E10: the fake with the emails table removed (it answers 404 / `PGRST205`) → the job is `done`, and
  the table is present and empty (C9).
