# F-3b3 — the data export carries the secondary addresses, opened from the seal

## Why (verified anchors)

- `osionos_user_emails` (root F-3broot, live since 2026-10-24) holds each secondary address as
  `email_enc` (AES-GCM, `bridge-seal.mjs`) plus `email_hmac`. Its registry row has
  `export_columns = NULL` (root `models/osionos-account-erasure-migration.sql:314`), so today's
  export (`scripts/bridge-account-export-runner.mjs:78-84`) leaves the user's own addresses out.
  That is a gap in the right of access.
- The registry path cannot list them, and must not be loosened to. `planTables` refuses any
  export column matching `SECRET_NAME` (`scripts/bridge-account-export-archive.mjs:35,71`, which
  includes `_enc$` and `hmac`). The root check `p5_export_no_secrets` refuses the same names
  (`scripts/verify/models-grants/account-checks.sql:2961-2997`). Both guards stay exactly as they are.
- The opener already exists. `openAddress(row, env)` (`scripts/bridge-account-email-rows.mjs:79`)
  returns the address, or `null` when the row does not open or its HMAC does not match.
  `keysUsable(env)` (`:71`) says whether both keys are well formed.
- The runner already gets `env` (`createExportRunner({ pg, env, … })`, `:123`), but
  `buildJobArtifact` (`:78`) does not receive it yet.

## Contract

1. After the registry tables are read, the runner reads the owner's `osionos_user_emails` rows with
   the existing `readTable` (same keyset paging on `id`, same `budget`, same caps). The read uses a
   fixed plan: table `osionos_user_emails`, select `id,user_id,email_enc,email_hmac,created_at,verified_at`,
   scope `['user_id']`, no filter. That plan is a constant in the runner, not a registry row.
2. Those rows become one exported table named `osionos_user_emails`. Its columns are exactly
   `id, email, readable, created_at, verified_at`, in that order:
   - `email` is `openAddress(row, env)`, or `null`;
   - `readable` is `email !== null`.
   `email_enc`, `email_hmac` and `user_id` never reach the artifact in any format.
3. The new table goes in name order among the registry tables, like every other table. It is
   present even when the user has no rows (an empty table, as every registry table is).
4. When rows exist and `keysUsable(env)` is false, the job fails with `export_sealed_unavailable`.
   Nothing is stored, and the failed row carries the code: never a done export with silently
   unreadable addresses. With no rows, unusable keys are not an error.
5. With usable keys, a row that does not open is exported with `email: null, readable: false`.
   The job still finishes as done.
6. The CSV formula prefix applies as for any other string cell. `=x@example.com` is a legal local
   part under `normaliseAddress`, so it is exported as `'=x@example.com` in CSV.
7. The runner's header `Caveat:` gains one sentence: a sealed address that no longer opens (a key
   rotated away without `_PREVIOUS`, or a corrupted row) is exported as unreadable, not left out.

Put the row-to-export mapping, a function of `(rows, env)` returning the table, in
`bridge-account-email-rows.mjs`, next to `openAddress`. The runner only wires it.

## Tests

Before editing, run the two export test files once with the one-file command and record their
counts. Seal rows with the real `createSeal` path (or the email helpers that already do), not a stub
of `openAddress`.

- E1: a user with one verified and one pending address. The JSON export has an `osionos_user_emails`
  table with both addresses in clear, `readable: true`, and the columns of contract 2 in order.
- E2: neither the base64 `email_enc` nor the hex `email_hmac` of any row appears in the JSON, CSV or
  ZIP bytes (search the raw bytes; for ZIP, the uncompressed entries).
- E3: user B's row never appears in user A's export.
- E4: keys unset, rows present → the job is `failed` with `error_code = export_sealed_unavailable`,
  and no storage put is made.
- E5: keys unset, no rows → the job is `done`, and the table is present and empty.
- E6: a row whose `email_hmac` does not match → `email: null, readable: false`, and the job is `done`.
- E7: the CSV cell for `=x@example.com` is `'=x@example.com`.
- E8: no column of the exported table matches `SECRET_NAME`, checked by importing it from the archive module.
- E9: the registry path still refuses `email_enc`. A registry row listing it fails the job with
  `export_forbidden_column`. Add this only if no existing test already covers it.
