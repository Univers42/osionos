## Orchestrator amendment (2026-10-24), binding over everything below

**v1 serves only platform-wide cells. There is no `scope = 'workspace'` and no `workspace_id` filter.** Why: the route would serve two additive views of the same events, the `scope='all'` cells and the per-workspace cells. `all.events − Σ(shown workspace cells).events` then gives the event count of the suppressed small workspaces, which is the differencing route of cond 8, through scope instead of grain. Dropping the per-workspace view closes that route and also removes the small-workspace check.

The text below changes as follows:
- **Rollup:** keep `osionos_activity_daily`, but with no `scope` column and no `workspace_id` column. The key is `PRIMARY KEY (day, event, surface)`, all NOT NULL, with `CHECK (distinct_users >= 5)`. The rebuild inserts only the platform-wide cells. Root item 4, root check `p4_activity_rollup_key` and mutant M1 follow this shape.
- **Raw table:** `osionos_activity_events` still stores `workspace_id`, which the owner's own `sys:my-activity` reads. Erasure and retention are unchanged.
- **Route:** `GET /api/account/admin/insights` accepts `days`, `granularity=day`, `event` and `surface` only. A `workspace_id` key answers 400 `bad_query`, like any other unknown key. The small-workspace check, its audit flag and its tests are removed.
- **Admin UI:** no workspace picker.
- **Per-workspace insights for workspace admins** are a later package with its own privacy review. They are not in P4-5.
- **Remaining Caveat:** differencing across overlapping day windows, and dominance within a cell. Keep it as written.

**Order: P4-5-root -> P4-5-bridge-a -> P4-5-bridge-b -> P4-5-app.** Each part is at most about 800 changed lines (one implementer session). The raw table holds a per-user behaviour log, the rollup is the only thing admins ever see, and erasure must delete the raw rows, so the **devil verdict is mandatory** (`rules/risk.md`: data/schema, security-sensitive, wide blast). It was given (D-P4-5s); its conditions are folded below. Nothing here ships to production before it is in the ledger.

## Decisions (S = stated here; D = D-P4-5s decisions below)

- S1. **Own-activity read is an `owner`-scope `sys:` source** (service-role read plus `user_id=eq.<uid>`), like `my-pages`. The table is a plain service-role-only table (no `osionos:account-plane` comment, no RLS policy for `osionos_account_user`, no `account_plane_expected` row). Reason: a partitioned account-plane table needs per-child policies and column grants that the sweep does not cover; owner scope reuses the audited path and needs no new role reach.
- S2. **Admins read only the rollup.** There is no admin route, view or grant that touches `osionos_activity_events`. The rollup has no user column.
- S3. **The admin route re-reads the role** with `readPlatformRole` on every request. A claim is never trusted.
- S4. **Suppression is on `distinct_users`, not on event count**, and it is applied **when the rollup is written** (cells below 5 are never stored), not when the response is built.
- S5. **Consent is the new `activity_tracking` preference (D1).** Nothing is recorded for a user who has not switched it on; fail closed.

## Contract

### P4-5-root — SQL (root repo, about 600 lines)

File: `models/osionos-activity-analytics-migration.sql`, one `BEGIN ... COMMIT`, idempotent (`CREATE ... IF NOT EXISTS`, `CREATE OR REPLACE`), style of `models/osionos-workspace-invites-migration.sql`, ends with `NOTIFY pgrst, 'reload schema'`. Postgres feature floor: nothing newer than PG 15 is used (no `NULLS NOT DISTINCT` is needed once the rollup key is NOT NULL, item 4), because the desktop zonky version is UNVERIFIED; the gates pin the image tag (see Load).

1. **Table `osionos_activity_events`**, `PARTITION BY RANGE (ts)`:
   - `id bigint GENERATED ALWAYS AS IDENTITY`, `ts timestamptz NOT NULL DEFAULT now()`, `user_id uuid NOT NULL`, **no FK**: a FK from a partitioned table to `users` costs a lookup per insert and the erase path deletes explicitly via the registry. The name `user_id` matches the user-keyed pattern, so the registry row is mandatory (item 6).
   - `workspace_id uuid` (nullable in the raw table), `event text NOT NULL`, `surface text NOT NULL`.
   - `PRIMARY KEY (id, ts)`.
   - **No content, no IP, no user agent, no title, no free text, no jsonb.** Only ids, an event name and a surface name.
   - `CHECK (event IN ('page_open','page_create','page_edit','search','share','export','login','database_view'))` and `CHECK (surface IN ('editor','database','canvas','chat','search','settings','admin'))`. The closed list is the contract: adding an event is a migration plus a bridge vocabulary edit plus a test. **Seedability (cond 12):** the table has no other CHECK and no NOT NULL column without a default that the generic seeder cannot fill; the first literal of each list (`page_open`, `editor`) is valid together. Check `p4_activity_canary_seedable` seeds a row through `pg_temp.p5_insert` and asserts `ok`.
   - Index `osionos_activity_events_user_ts_idx ON (user_id, ts DESC)` on the parent (propagates to children). This serves the owner read with `order=ts.desc&limit=200`.
   - A DEFAULT partition `osionos_activity_events_default`, closed like any child. **A row there is a failure, not a sink** (item 3).
2. **Child naming and closing.** Children are `osionos_activity_events_yYYYYMM` (so the `osionos_` sweep covers them at boot). Each child, at creation, in the same maintain call: `ENABLE ROW LEVEL SECURITY`, `REVOKE ALL ON ... FROM PUBLIC, anon, authenticated`, `GRANT SELECT, INSERT, DELETE ON ... TO service_role` (cond 5). The sweep does not cover children made after boot, so closing at creation is the only guard; a check proves it on a child created by maintain, not only on boot-time children.
3. **`osionos_activity_maintain(raw_months int DEFAULT 13, rollup_months int DEFAULT 25)`**, `SECURITY DEFINER`, `SET search_path = public, pg_temp`, `REVOKE ALL FROM PUBLIC`, `GRANT EXECUTE TO service_role` only. Returns `(ok boolean, created int, dropped int, rollup_pruned bigint, default_rows bigint)`. Body, in this order:
   1. `PERFORM pg_try_advisory_xact_lock(<constant bigint, named in the file header>)` is the first statement; when it is not granted the function returns `ok = true` with zero counts and `RAISE NOTICE 'activity_maintain: skipped, another run holds the lock'` (two bridge replicas, cond 3).
   2. `SET LOCAL lock_timeout = '2s'` (CREATE/DROP take `ACCESS EXCLUSIVE` on the parent, which blocks and is blocked by the bridge's INSERTs; the erasure migration's own precedent is `lock_timeout = '5s'` at `models/osionos-account-erasure-migration.sql:64`).
   3. All month arithmetic is UTC-pinned: `date_trunc('month', now() AT TIME ZONE 'UTC')`; partition bounds are `timestamptz` built from that value with `AT TIME ZONE 'UTC'`.
   4. **Create the current month plus the next two** if missing. **Before creating a month** it moves any DEFAULT rows whose `ts` falls in that month into a temp table (`DELETE ... RETURNING` into it), creates the child, closes it (item 2), and re-inserts the rows (cond 2). No row is lost; the DEFAULT never blocks creation.
   5. **Drop** children whose upper bound is older than `now() - raw_months` using `DROP TABLE IF EXISTS`.
   6. **Prune** `osionos_activity_daily` rows with `day` older than `rollup_months` (25).
   7. `default_rows` is `count(*)` over the DEFAULT partition with a `LIMIT`-bounded subquery (cap 1000). The bridge treats `default_rows > 0` as an alarm, and the verify check treats it as a failure (`SKIP` is not allowed).
   8. `EXCEPTION WHEN OTHERS` does **not** swallow: it issues `RAISE NOTICE 'activity_maintain: failed: %', SQLERRM` and returns `ok = false` with the counts so far, so the bridge logs and counts it (cond 4). `lock_not_available` is reported the same way (a logged skip), within about 2 s.
   Caveat to put in the file header: raw retention is by whole partition, so data lives up to one month longer than the setting; a drop is irreversible; the advisory lock is per database, not per bridge.
4. **Rollup table `osionos_activity_daily`**: `day date NOT NULL`, `scope text NOT NULL CHECK (scope IN ('all','workspace'))`, `workspace_id uuid NOT NULL` (the all-zero uuid `00000000-0000-0000-0000-000000000000` for `scope = 'all'`), `event text NOT NULL`, `surface text NOT NULL`, `events bigint NOT NULL`, `distinct_users integer NOT NULL CHECK (distinct_users >= 5)`, `PRIMARY KEY (day, scope, workspace_id, event, surface)` (cond 1: every key column is NOT NULL, so the key is valid on any PG). `scope = 'all'` cells count every tracked user once across all workspaces and include events with no workspace; `scope = 'workspace'` cells are per `workspace_id`. Without the scope split the draft's rollup could not answer an unfiltered query: distinct users cannot be summed across workspaces (one person in two workspaces would count twice). **The CHECK `distinct_users >= 5` makes a sub-5 cell unstorable** (cond 11, D3). **No column whose name matches the user-keyed pattern** (no `user_id`, no `actor`, no `owner`); `distinct_users` is an `integer`, and `p5_erasure_complete` scans name patterns only on uuid/varchar/text/citext/json columns (`account-checks.sql` about `:2290-2365`), so the name is not flagged; the new no-user-column check applies the same type filter and still asserts no such name. Only counts are stored: no set, no HLL, no array. `GRANT SELECT, INSERT, UPDATE, DELETE TO service_role`; closed like a service-role-only table (FORCE RLS plus a `service_role_all` policy). The table carries no `osionos:account-plane` comment.
5. **`osionos_activity_rollup(for_day date)`**, same security as item 3 and the same advisory lock family (a different constant). Returns `(status text, cells int)`. Rules (cond 6, 11):
   - It reads **one closed day** (one partition), never the parent as a whole: `WHERE ts >= for_day AND ts < for_day + 1` (UTC) so partition pruning applies.
   - It refuses `for_day >= (now() AT TIME ZONE 'UTC')::date` with the error `day_not_closed`.
   - **Dropped-day guard:** when the raw partition covering `for_day` does not exist, it returns `status = 'partition_gone'` and **touches nothing** (an existing rollup day is never zeroed). It also refuses a day older than the raw retention minus one month (`status = 'too_old'`).
   - **Rebuild, not patch:** in one transaction it `DELETE`s the day's rollup rows and `INSERT`s `scope='all'` cells (grouped by event, surface) and `scope='workspace'` cells (grouped by workspace_id, event, surface, rows with a non-null workspace only), each with `count(*)` and `count(DISTINCT user_id)`, `HAVING count(DISTINCT user_id) >= 5`. Cells below 5 are therefore **deleted at rollup time** (never stored). Re-running a day with data still present yields the same rows (idempotent); a user erased since the last run drops out of the next rebuild.
   - **Lateness tolerance, stated:** the timer rolls up yesterday and the day before. An event that arrives (is inserted) more than two days after its `ts` day, or whose `ts` day was already rolled up twice, is **not** in the rollup (it stays in the raw table until retention). The rollup is a daily snapshot, not a live count.
6. **Registry.** One additive row in the seed of `models/osionos-account-erasure-migration.sql`, next to the `ai_events` row at `:207`: `('osionos_activity_events','user_id','owner','delete', NULL, NULL, NULL, NULL, '<reason>')` with the same nine-column shape as that row (the `export_columns` value `'{ts,event,surface,workspace_id}'` goes in the `x` slot if the seed's shape takes it there; check against `:195-198`). 1. `createActivityEmitter({ pg, env, now, isTracked = () => false })` returns `{ emit(session, event, surface, workspaceId), stats(), flush(), close({ deadlineMs }) }`. **`isTracked` is part of the signature** and its default is `() => false` (cond 14d): with `OSIONOS_ACTIVITY=1` and no `isTracked` supplied, nothing is queued and no INSERT is issued.
2. **Emit never blocks a request.** `emit` is synchronous, validates `event` and `surface` against the vocabulary module, calls `isTracked(session)` (synchronous, see item 8), pushes onto an in-memory array and returns. It never awaits the database and never throws into the caller (a thrown error is caught and counted as `dropped.invalid`).
3. **Bounded memory and flood control (cond 14a).** Queue cap `ACTIVITY_QUEUE_MAX` (default 5000 entries, each about 100 bytes, so about 0.5 MB). Per-user cap `ACTIVITY_USER_PER_MIN` (default 50 events per user per fixed one-minute window). Over either cap the new event is dropped and counted: `dropped.overflow` (queue full) or `dropped.user_rate` (one user over its cap). A flooding user cannot evict another user's queued events (drop-new, never drop-old). No unbounded retry buffer.
4. **Batching.** Flush when the queue reaches `ACTIVITY_BATCH_SIZE` (default 200) or every `ACTIVITY_FLUSH_MS` (default 2000), through `pg.asService().post('osionos_activity_events', rows, { prefer: 'return=minimal' })`, one request per batch, one batch in flight at a time. The flush timer is `unref()`ed. The flush interval and batch size are named constants. **Caveat (file header):** events in the queue are lost on a crash or SIGKILL (at most one flush interval plus one batch), and on a store failure the failed batch is dropped.
5. **DB down.** A failed flush drops that batch (no re-queue: a re-queue under a long outage fills the cap and then drops anyway, while competing with fresh events), increments `dropped.store`, and applies a backoff of `ACTIVITY_FLUSH_MS * 2^n` capped at 60 s before the next attempt. A success resets the backoff. Events arriving during backoff still queue up to the cap.

## Security and privacy edge

- The raw table holds ids, an event name and a surface name only: no content, no IP, no user agent, no title. That caps what a database dump or a bug can reveal to "who did which kind of thing when".
- Nothing is recorded for a user who has not switched `activity_tracking` on (default off, separate from `beacon_consent`); the gate is a cache with a 60 s TTL, stated as a caveat.
- A user reads only rows whose `user_id` is the verified session uid (service-role read with a server-side equality filter, uid never taken from the request); `user_id` is not in the column allowlist. Nobody but `service_role` has a grant on either table or any child, so PostgREST with an `authenticated` JWT returns nothing (proved by `models-grants`, on children created by maintain too).
- Admins reach only `osionos_activity_daily` through one route that re-reads the role every request (a revoked admin loses access at once), is rate limited, audited per read, and never returns a per-user field. There is no code path from an admin session to the raw table.
- Erasure deletes the raw rows (registry `delete`). The rollup stays: it holds no user id and, because cells below 5 are never stored, no cell about fewer than 5 people, so it is aggregate data. This is a stated position (D3), accepted by the orchestrator.
- Retention is bounded by the maintain function (raw 13 months, rollup 25 months, whole-partition drops for raw).
- The emitter is opt-in by env and by per-user preference and fails closed; a dropped event is a counter, never an error to the user.
- Caveat on k-anonymity: see bridge-b item 4. It is a floor on cell size, not a differential-privacy guarantee.
