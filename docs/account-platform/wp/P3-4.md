## Decisions (D-P3-4, 2026-10-22) — binding; they supersede the sections they name

**Reuse (the user's rule: extend what exists, never duplicate).**
- R1. **The settings audit stops being a second, local-only log.**
  `src/store/settings/useSettingsAuditStore.ts` already posts every settings action to
  `POST /api/settings/actions`, and no bridge module implements that route (`rg settings/actions
  scripts` → nothing), so every record dies in localStorage.
  - P3-4-g implements the route in its own module, over `writeAudit`
    (`scripts/bridge-guard.mjs:224-246`), into the same `osionos_bridge_audit_events` table the
    viewer reads.
  - The audited fields: actor = the session user, event type `settings.<action>`, the
    `action` text bounded at 64 characters, `metadata` capped at 2 KB of JSON (larger → 413).
  - Rate limit: 60/min per user.
  - The client store is not changed.
- R2. **The users list's `?q=` reuses the directory's matching**: the predicate behind
  `GET /api/directory/search` (`scripts/bridge-social.mjs:63`). It uses the trigram index
  P1-1 built (`models/osionos-account-profiles-migration.sql:278-280`).
  - If the predicate is inline, P3-4-c extracts it into a named function inside
    `bridge-social.mjs` and calls it from both routes. That one-function change is added to
    P3-4-c's OWNS.
  - The admin list does **not** apply the directory's opt-out and block filters. An admin sees
    every account.
- R3. The Admin space is the existing `src/widgets/admin-space`, extended (why 2). No second
  admin shell.

**Open questions, settled:**
1. **"CRUD" means read + update** (the profile's editable columns and the platform role). Create
   is P3-5's invite flow; delete is P5-6's deletion executor.
2. **Renaming another user is admin-only.**
3. **The users list gets search** (R2) in P3-4-c and P3-4-d. It is keyset-paginated with or
   without `q`.
4. **A timed suspension is enough.** At sign-in, a suspended account gets 403
   `account_suspended` with `suspendedUntil`, so the user is told. No sweeper; sessions revoked at
   the suspension stay revoked.
5. **The audit viewer is admin-only.** Admins see `user_agent` and `ip_hash` (the
   abuse-investigation fields; `ip_hash` is already a hash). A moderator does not see the audit
   viewer.
6. **Moderators reach the Admin space** from the rail. Inside, they see only the moderation
   section; users and audit are admin-only. This is the draft's P3-4-b design, confirmed.
7. **Staff can open a case without a report.** P3-4-e adds `POST /api/admin/moderation/cases`,
   which creates a report row whose reporter is the acting moderator and whose reason is
   `opened_by_staff`. The ordinary decision flow then applies. It is audited.
8. **The platform vocabulary is three roles: admin, moderator, user.** `guest` is ignored: grobase
   seeds it and nothing assigns it.

**P3-4-a — the role read.**
1. **The first admin is the env admin (C1).** The role read is
   `is_admin === true ? 'admin' : readPlatformRole(userId)`. The identity flag set from
   `OSIONOS_ADMIN_EMAILS` (`resolveAdminFlag` in `scripts/bridge-api.mjs`) stays the root of
   trust, so there is always a way in, and no seed step or new write is needed. An env admin
   cannot be demoted from the UI: removing one is an env change, and `PUT …/roles` on an env
   admin answers 409 `role_from_env`. *Test:* a session minted for an `OSIONOS_ADMIN_EMAILS`
   address carries `platform_role: 'admin'` and `is_admin: true`.
2. **The existing gate stays green (C2).** With ruling 1, `tests/bridge/bridge-admin-verified.test.mjs`
   is unchanged and must pass. It is **not** in a's OWNS; if it goes red, the implementation is
   wrong, not the test.
3. **An expired grant confers nothing (C3).** `readPlatformRole` filters
   `or=(expires_at.is.null,expires_at.gt.<now>)` on `public.user_roles`. A `Caveat:` line says
   the role is read at mint and at each admin request, so an expiry takes effect on the next
   admin request, not inside one. *Test:* a `user_roles` row with `expires_at` in the past
   answers `role: 'user'`.
4. **The role is re-read from the verified session, never from the request (C4).** The re-read
   keys on `session.userId` (the verified token's `sub`). No route reads a role, user id or
   `is_admin` from a query or a body for authorisation. *Test:* `?role=admin`,
   `{"role":"admin"}` and `?userId=<other>` change neither the actor's authorisation nor the
   target of the read.

**P3-4-c — the users API.**
5. **A role change revokes the target's sessions (C5, variant a).** `PUT …/roles` writes the role,
   then revokes every live session of the target through P0-4's revoke path
   (`osionos_sessions.revoked_at`, `revoked_reason = 'admin'`). That also kills the routes that
   still gate on the claim (`scripts/bridge-perms.mjs`, the agent route in `bridge-api.mjs`),
   within one revocation poll (≤ 10 s, ADR 0003). The spec's "loses its power on the next
   request" holds only for the admin routes, which re-read the role; the other routes follow
   within the poll. *Test:* after a role revoke, the target's existing token answers 401 on a
   perms route.
6. **Admin reads of one user are audited; list reads are not (C5).** `GET …/users/:userId` writes
   one `admin.user.read` audit row; `GET …/users` (the list) writes none.
7. **The detail route has an explicit select allowlist (C11).** It names its columns, with the
   same "the select is exactly the allowlist" assertion and mutant as the list. It never answers
   an email, a setting, a session token, a deletion state or `search_doc`. *Test:* a seeded
   extra `email` column does not appear in the answer.
8. **No `?q=` in P3-4 (C10).** R2 and settled open question 3 are void. The directory predicate
   references `profile->>headline`, which exists on the view `osionos_people_directory` and not
   on the table the admin list reads, and the keyset fake cannot apply `ilike`/`wfts`. ADR 0005
   records what would have to change. The list is keyset-paginated by `(created_at, id)`, with no

9. **c may own two files (C14):** `scripts/bridge-account-users.mjs` (the routes) and
   `scripts/bridge-admin-role.mjs` (new: `readPlatformRole`, the `requireRole(session, roles)`
   gate and the admin audit helper). e and g import the gate from there; nobody writes a second
   copy. Each file stays ≤ 300 lines.

**P3-4-e — moderation.**
10. **The state is the most severe live decision, not the newest (C6).** The sign-in and request
    checks read the subject's `subject_kind = 'user'` reports (C7) that carry a live decision:
    `ban`, or `suspend` with `until > now()`. A ban wins over a suspension. A `warn` or `dismiss`
    on one report never lifts a decision on another. A ban or suspension is lifted only by
    re-deciding **the same report** (to `dismiss`), which writes a `moderation_decision` audit row

11. **Only person reports move a person's state (C7).** A decision on a `message`-kind report

12. **The warn notification is a `system` notification (C8),** a value the CHECK already allows

## Why

### 1. There is no platform role: the session carries one boolean

- The app-session token's payload is built in `scripts/bridge-api.mjs:437-459`: `{ iss, aud, sub,
  provider, workspace_ids, roles, is_admin, jti, iat, iat_ms, exp }`. `roles` (`:448`) is the
  **workspace** role map; the only platform fact is `is_admin` (`:449`), a boolean.
- `verifyAppSessionToken` (`scripts/bridge-api.mjs:461-508`) hands the caller
  `{ userId, workspaceIds, roles, isAdmin, raw }` (`:501-507`) — `isAdmin` (`:505`) is the same
  boolean. There is no `moderator` anywhere in the session.
- The flag is one bit per identity row, not a role: `resolveAdminFlag`
  (`scripts/bridge-api.mjs:1552-1568`) reads `osionos_bridge_identities.is_admin` (`:1562`) and
  promotes it from `OSIONOS_ADMIN_EMAILS` (`scripts/bridge-api.mjs:217-222`).
- The client mirrors it exactly: `isAdminFromSessionToken`
  (`src/features/auth/model/userStore.helpers.ts:92-95`) reads `payload.is_admin === true`, and
  `useIsAdmin` (`src/features/auth/model/useIsAdmin.ts:21-23`) is the reactive wrapper.
- **The four platform roles the plan names already exist as rows** in grobase's catalogue:
  `apps/grobase/scripts/migrations/postgresql/007_permissions_system.sql:81-89` seeds `admin`,
  `user`, `guest`, `moderator` and `service_role` into `public.roles` (the table, `:41-49`);
  `public.user_roles` (`:51-59`) assigns them per user, with a default-role trigger on
  `auth.users` (`:135-140`). Nothing in the osionos app reads either table.

### 2. The Admin space exists and cannot be reached

- `src/widgets/admin-space/ui/AdminSpaceView.tsx:52-72` — the view renders the Templates
  directory and shows "Administrator access required." to anyone else.
- `src/widgets/workspace-grid/model/layoutPersist.ts:104-106` — `adminTab()` builds the tab. **It
  is never called**: `adminTab` appears exactly once in `src/**` and `tests/**`, at its own
  definition.
- Everything else is already in place: the tab kind (`"admin"`,
  `src/widgets/workspace-grid/model/layoutTree.ts:14`), the pane that renders it
  (`src/widgets/page-renderer/ui/PaneContent.tsx:138-145`), the stable tab id
  (`src/widgets/workspace-grid/model/layoutPersist.ts:22`).
- The rail has no admin entry: the four groups are `src/widgets/activity-rail/model/railItems.ts:71-112`
  (workspace / workbench / conversations / apps) and the rail's bottom block holds Account and
  Settings only (`src/widgets/activity-rail/ui/ActivityRail.tsx:141-151`).

### 3. No users administration exists

- No route lists the accounts and no route changes a role. What exists is org-scoped and fuzzy:
  `/api/people` and `/api/directory/embed` (`scripts/bridge-profile.mjs:256-257`), and the
  per-workspace roster `GET /api/workspaces/:id/members` (`scripts/bridge-collab.mjs:204-206`).
- The typed profile table is there and nobody administers it: root
  `models/osionos-account-profiles-migration.sql:176-213` — `osionos_profiles`, `user_id` primary
  key, `display_name`, `username`, `directory_opt_out`, `version` — with the listing index
  `(display_name, user_id)` at `:258-259`, which is exactly the keyset the plan asks for.
- The platform role rows exist (why 1) but nothing writes `public.user_roles`.

### 4. The moderation queue's reports exist; the decisions do not

- Root `models/osionos-social-migration.sql:122-137` — `osionos_user_reports` with
  `status IN ('open','reviewing','resolved','dismissed')` (`:131-132`) and the index
  `(status, created_at DESC)` (`:135-136`).
- The bridge reads and writes **the caller's own** reports: `GET`/`POST /api/social/reports`
  (`scripts/bridge-social.mjs:294-315`), the filter is `reporter_id=eq.<caller>`
  (`scripts/bridge-social.mjs:295`). **Nobody can read the queue**: a moderator cannot see another
  person's report. The client side exists too (`src/shared/social/reportApi.ts:13-30`,
  `src/store/social/useReportsStore.ts`, the shape in `src/store/social/types.ts:44-58`).
- There is no warn / suspend / ban anywhere: `suspend|banned|moderation` matches nothing in
  `src/**` or `scripts/**` except `src/features/baas-console/ui/TenantAccountSection.tsx:24` (a
  tenant status string), a Vite recorder and a tokenizer list.
- The pieces a suspension would use exist: `public.osionos_sessions.revoked_reason` already admits
  `'admin'` (root `models/osionos-account-foundation-migration.sql:181`).

### 5. No audit viewer

- The audit table is written and never read: `writeAudit` (`scripts/bridge-guard.mjs:224-246`)
  inserts into `osionos_bridge_audit_events`; the table is root
  `models/osionos-bridge-migration.sql:128-135` with the index `(provider, subject, created_at DESC)`
  (`:148`), and P0-1's four columns (`actor_id`, `session_id`, `ip_hash`, `user_agent`) plus the
  actor index at root `models/osionos-account-foundation-migration.sql:251-253` and `:269`.
- The table is service-role-only (root `models/rls-hardening-migration.sql:115-116` and the catalog
  pass at root `models/osionos-service-role-only-migration.sql:37-48`), so the bridge reads it with
  `asService` — never with a user token.

### 6. The plumbing this work needs is already there — no new dependency, no new table

- `scripts/bridge-pg.mjs:157-166` (`asService`) and `:168-181` (`asUser(session)`).
- `scripts/bridge-paging.mjs:63-87` (`encodeCursor`/`decodeCursor`), `:100-134` (`keyset`),
  `:140-155` (`pageOf`) — the keyset cursor, already unit-tested
  (`tests/bridge/bridge-paging.test.mjs`).
- `scripts/bridge-guard.mjs:167-178` (`rateLimit`), `:224-246` (`writeAudit`).
- `scripts/bridge-account-mounts.mjs:22-32` — the one seam into `bridge-api.mjs`;
  `scripts/bridge-api.mjs:4293` — `createAccountHandler({ config, pg, kv, verifySession })`.
- `deploy/bridge-fly/Dockerfile:24-33` — the explicit COPY list; a module in the static import
  closure that is missing from it fails `tests/bridge/bridge-dockerfile-closure.test.mjs:55-59`.

**Rejected, one line each.** A new `osionos_user_roles` table — grobase's `roles`/`user_roles`
already hold exactly the four roles the plan names (why 1). A `osio.admin` feature flag for the
Admin space — the role *is* the gate, and a flag would be a second source of truth. Reading the
roles through `asUser` — the account role's RLS is `user_id = osionos_account_uid()`
(`docs/account-platform/adr/0001-account-jwt.md`), so it can only ever see the caller's own row;
an admin reading *other* users needs the service role (ADR 0001:40). Trusting the session claim in
the admin routes — the claim is as old as the token, so a role revoked after the sign-in would keep
its power until the token expires; the routes re-read the roles instead. One shared registry file
for the admin sections — three later packages would edit it and conflict on merge; the sections are
discovered by Vite's `import.meta.glob` instead (no new dependency).

## Contract

Every bridge route below needs an app session (`deps.verifySession`, the token verifier
`scripts/bridge-api.mjs:461-508`) and answers the shared error shape
`{ ok: false, message, code? }` (`scripts/bridge-api.mjs:2331-2338`; the `code` must match
`/^[a-z][a-z0-9_]*$/`). Admin reads use `asService` (ADR 0001:40 — "Directory, admin and background-job
reads keep the service role"); no admin route ever uses a user's own rows.

### P3-4-a — the platform role: the claim and the client hook

**Security edge.** Who may call what: the sign-in path reads **the caller's own** role rows
(`user_roles?user_id=eq.<sub>`) through the service role and signs the answer into the caller's own
token; the token is HMAC-signed with `OSIONOS_APP_SESSION_SECRET`
(`scripts/bridge-api.mjs:456-458`), so nobody else can put a claim in it. What a non-owner sees:
nothing — the claim is about the caller, and it is **a hint, never the authority**: every admin
route re-reads the roles at call time (P3-4-c/e/g).

1. **The vocabulary, in two homes.** The four names and their rank:
   - `scripts/bridge-roles.mjs` (**new**): `PLATFORM_ROLES = ['admin','moderator','user','guest']`,
     `ROLE_RANK = { admin: 3, moderator: 2, user: 1, guest: 0 }`,
     `roleAtLeast(role, min)` (false for an unknown or null role),
     `roleFromNames(names)` (the highest-ranked name, `null` for an empty list),
     `readPlatformRole(client, userId)` → `{ role, names }`.
   - `readPlatformRole` makes **two** service reads: `user_roles?user_id=eq.<id>&select=role_id`,
     then `roles?id=in.(<ids>)&select=id,name` — the ids **unquoted**, like
     `scripts/bridge-api.mjs:1388`. A failed read answers `{ role: null, names: [] }` (fail closed:
     no role → `guest`), never a throw.
   - `src/features/auth/model/platformRole.ts` (**new**) holds the **same four names and the same
     rank** for the app. The app cannot import from `scripts/**` (nothing in `src/**` does today),
     so the two copies are pinned against each other by the agreement test in P3-4-b.
2. **The claim.**
   - `signAppSessionToken` (`scripts/bridge-api.mjs:437-459`) takes a `platformRole` and mints
     `platform_role: <name>` next to `is_admin` (`:449`). `is_admin` stays **`platformRole ===
     'admin'`** — one source, so the two can never disagree.
   - `verifyAppSessionToken` (`:461-508`) returns `platformRole` beside `isAdmin` (`:505`); a token
     without the claim answers `null`.
   - `createUserSession` (`:1444-1490`) takes `platformRole` and passes it to the signer (`:1468`).
   - `readClaimsInOrder` (`:1613-1619`) and `readClaimsConcurrently` (`:1633-1649`) read the role
     at sign-in and pass it on; `createBridgeHandoff` (`:1651-1671`) threads it (`:1655`).
   - The role read is **best-effort**: a failure degrades to `null` (no role) and never blocks the
     sign-in — the same shape as the admin-flag read (`:1641`).
3. **The client.**
   - `platformRoleFromSessionToken(token)` in `src/features/auth/model/userStore.helpers.ts`: the
     claim's `platform_role` when it is one of the four; **`'admin'` when the token carries
     `is_admin === true` and no `platform_role`** (a token minted by an older bridge during a
     rolling deploy — the fallback keeps the admin space reachable); `null` otherwise.
   - `usePlatformRole()` in `src/features/auth/model/usePlatformRole.ts` (**new**) is the reactive
     hook; `useUserStore` gains `platformRole: () => platformRoleFromSessionToken(get().activeSession()?.accessToken)`
     (`src/features/auth/model/useUserStore.ts:674` is the line to copy) and the store interface
     gains the selector next to `isAdmin` (`src/entities/user/model/types.ts:86`).
   - `src/features/auth/index.ts:14` exports the hook beside `useIsAdmin`.
   - **`useIsAdmin` and `isAdmin` are not touched.** They keep answering the legacy boolean and
     stay exported; after P3-4-b nothing in `src/**` calls `useIsAdmin` — say so in the commit
     report, and leave the deletion to a named follow-up (it is a public export of the auth barrel).
4. **Out of scope.** `scripts/bridge-perms.mjs` (the permission-engine proxy — a different product)
   and `src/features/settings/permissions/**` (the ABAC matrix) keep their own role vocabulary.

### P3-4-b — the Admin space shell, the rail entry, the role-gated views

**Security edge.** The rail item and the section nav are **client-side affordances**; the bridge is
the authority. A caller with no role sees **no** Admin item and, if the tab is restored from a
persisted layout, today's refusal card (`src/widgets/admin-space/ui/AdminSpaceView.tsx:65-72`) — never
a section body.

1. **The section model** — `src/widgets/admin-space/model/adminSections.ts` (**new**):
   ```ts
   export interface AdminSection {
     id: string;
     label: string;
     Icon: LucideIcon;
     /** The lowest platform role that may open the section. */
     requiredRole: PlatformRole;
     load: () => Promise<{ default: React.ComponentType }>;
   }
   export function visibleSections(sections: AdminSection[], role: PlatformRole | null): AdminSection[];
   ```
   `visibleSections` keeps a section when `roleAtLeast(role, section.requiredRole)`; an unknown role
   (`null`) keeps **nothing**. It is pure — the canvas test exercises it directly.
2. **The sections are discovered, not registered.** The shell reads
   `import.meta.glob('./sections/*/section.ts')` (a **Vite built-in, no new dependency**), so a later
   package (d, f, g) adds a section by creating `src/widgets/admin-space/sections/<id>/section.ts`
   and touching nothing else. The glob is lazy (`{ eager: false }`) so every section is its own
   chunk. The built-in **Templates** section stays inline in `AdminSpaceView.tsx` (today's code,
   `:32-35` and `:74-131`) and is described by the same `AdminSection` shape;
   `src/widgets/admin-space/model/templateSeed.ts` is **not** touched (P2-4-c owns it).
3. **The shell** — `src/widgets/admin-space/ui/AdminSpaceView.tsx`:
   - The gate becomes "the caller has at least one visible section", not a hard-coded role: a
     moderator (whose Moderation section exists) opens the space; a `user`/`guest`/no-role caller
     sees today's refusal card, unchanged.
   - A left nav of the visible sections plus the selected section's body. The selection is client
     state, defaulting to the first visible section. A deep link (`?admin=<id>`) is a follow-up.
   - The Templates section renders exactly as today (the two surfaces of `:32-35`).
   - The file stays ≤ 300 lines (COMMON.md): put the nav in its own file under
     `src/widgets/admin-space/ui/` if it does not fit.
4. **The rail** — `src/widgets/activity-rail/model/railItems.ts`:
   - `RailItem` gains `requiredRole?: PlatformRole` (the interface is `:51-60`);
     `visibleRailItems(group, role)` (`:116-118`) drops an item whose `requiredRole` the role does
     not meet, **before** the existing `isAvailable` check (`:117`) — an item can be unavailable for
     two different reasons.
   - A new item in the `workspace` group (`:72-84`):

### P3-4-c — the users administration API (bridge)

**Security edge.** Who may call what: a session whose platform role — **re-read from
`public.user_roles` + `public.roles` at call time, never taken from the claim** — is `admin`. What a
non-owner sees: nothing; every route answers 403 `admin_required` **before any row is read**. What
an admin sees about another user: the public profile fields and that user's platform roles —
**never** an email, a setting, a session token or a deletion state.

1. **The routes** — `scripts/bridge-account-users.mjs` (**new**, Node built-ins only, tabs, ≤ 300 lines):
   - `GET /api/account/admin/users?limit=&cursor=` — the keyset list.
     The read: `osionos_profiles?select=user_id,display_name,username,directory_opt_out,created_at,updated_at&order=display_name.asc,user_id.asc&limit=N+1`
     (plus the `or=(...)` page filter `keyset()` builds), through `asService`.
     The page: `keyset({ order: [['display_name','asc'],['user_id','asc']], cursor, limit })` and
     `pageOf(rows, order, take)` (`scripts/bridge-paging.mjs:100-155`). The order matches the index
     `osionos_profiles_display_name_user_idx` (root
     `models/osionos-account-profiles-migration.sql:258-259`), so the list is an index scan, not a sort.
     The answer: `{ ok: true, users: [...], nextCursor: string|null }`.

     resolution=merge-duplicates,return=minimal`; revoking = `DELETE
     user_roles?user_id=eq.<id>&role_id=eq.<roleId>`. The `role_id` comes from the `roles` row for
     that name — the bridge never invents a uuid.

     request): the four rows are seeded by root
     `apps/grobase/scripts/migrations/postgresql/007_permissions_system.sql:81-89`.
     **An admin may not revoke their own `admin` role** → 422 `self_role_change` (a lockout).
   - **Every write writes an audit row first** (`writeAudit`, `scripts/bridge-guard.mjs:224-246`):
     `event_type` `admin_user_update` / `admin_role_change`, `details` `{ targetUserId, fields }` /
     `{ targetUserId, role, action }`. No audit row, no action — that is the guard's own contract
     (`scripts/bridge-guard.mjs:219-222`).
   - **Rate limit:** 60/min per admin for the reads, 30/min for the writes, through
     `rateLimit(kv, ['admin-users', uid], …)` (`scripts/bridge-guard.mjs:167-178`).
   - **Sudo is not required**: `requireSudo` (`scripts/bridge-guard.mjs:194-200`) has **no caller**
     in `scripts/**` today (P1-2b owns the grant), so requiring it would make the action
     unreachable. The role gate plus the audit row are the gate; a `Caveat:` line says so, and
     adding sudo is a follow-up once P1-2b lands.
   - The module is **appended** to the `modules` list in `scripts/bridge-account-mounts.mjs:25` and
     **copied by name** in `deploy/bridge-fly/Dockerfile:24-33`. `scripts/bridge-api.mjs` is **not**
     touched.
2. **The keyset fake** — `tests/bridge/support/keyset-postgrest.mjs` (**new**): a table-driven

### P3-4-e — the moderation queue: the root SQL and the bridge API

**Security edge.** Who may call what: a session whose **re-read** role is `moderator` or `admin`.
What a non-moderator sees: 403 `moderator_required` before the queue is read. What a moderator sees
about a reported user: the report (reporter id, category, details, subject) and the target's display
name — never the reporter's email, never the target's settings, never the target's sessions.

1. **The root SQL** — `models/osionos-user-moderation-migration.sql` (**new**, root repo):
   - `ALTER TABLE public.osionos_user_reports ADD COLUMN IF NOT EXISTS decision TEXT CHECK (decision IS NULL OR decision IN ('warn','suspend','ban','dismiss'))`,
     plus `decision_until TIMESTAMPTZ`, `decision_by UUID`, `decision_at TIMESTAMPTZ`,
     `decision_note TEXT`.
   - **The decisions live on the report row — no new table**: the report is the queue item and the
     decision is its outcome. A user's current state = the newest decision among the reports that
     carry one (`decision_at DESC`, `decision IS NOT NULL`). `decision_until` is the end of a
     suspension; `null` means "until it is lifted".
   - `CREATE INDEX IF NOT EXISTS osionos_user_reports_subject_decision_idx ON public.osionos_user_reports (subject_user_id, decision_at DESC) WHERE decision IS NOT NULL;`
     — the state lookup of item 4 is filtered by `subject_user_id`; without this index it is a seq
     scan on every sign-in.
   - The file is idempotent (`ADD COLUMN IF NOT EXISTS` + a `DO` block that replaces a CHECK whose
     definition differs — the house drop-and-add pattern, root
     `models/osionos-social-migration.sql:81-84`.
   - It adds **no grant**: the table stays service-role-only — the catalog pass revokes every
     `osionos_%` relation from `PUBLIC`, `anon` and `authenticated` on every boot (root
     `models/osionos-service-role-only-migration.sql:37-48`).
   - **The file lands in the alphabetical pass**: it only ALTERs a table that
     `osionos-social-migration.sql` creates, and that file is in `ORDERED_FIRST` (root
     `scripts/apply-models-migrations.sh:132`). `ORDERED_LAST` is **not** touched. Say so in the
     report.
2. **The check** — root `scripts/verify/models-grants/checks.sql` gains one row
   `moderation_columns` in the pattern of `:72-84`: the five decision columns exist on
   `public.osionos_user_reports`, the decision CHECK admits exactly the four values, and the table
   is not reachable by `anon` or `authenticated`. Root `scripts/verify/models-grants.sh` gains the
   matching `check_count "$1" m1 moderation_columns` line next to `:465`.
3. **The routes** — `scripts/bridge-account-moderation.mjs` (**new**):
   - `GET /api/account/admin/reports?status=&cursor=` — the queue, service role:
     `osionos_user_reports?select=id,reporter_id,subject_user_id,subject_kind,subject_id,category,details,status,decision,decision_until,decision_by,decision_at,created_at&order=created_at.desc,id.desc&limit=N+1`
     (plus the `or=(...)` page filter), **always filtered by `status`** (default `open`) so the
     query walks the existing index `(status, created_at DESC)` (root
     `models/osionos-social-migration.sql:135-136`).
     The answer: `{ ok: true, reports: [...], nextCursor: string|null }`.
   - `POST /api/account/admin/reports/:id/decision` — the body `{ decision, note?, until? }`:
     - `decision` is `warn`, `suspend`, `ban` or `dismiss`; anything else is 422 `invalid_decision`.
     - `warn`: the decision columns are written and the target is notified (the notification table
       exists — `osionos_notifications`).
     - `suspend`: `until` is **required** (an ISO timestamp in the future, at most 30 days out) →
       otherwise 422 `invalid_until`. The target's sessions are revoked:
       `osionos_sessions?user_id=eq.<id>&revoked_at=is.null` → `revoked_at = now(),
       revoked_reason = 'admin'` — the column already admits `'admin'` (root
       `models/osionos-account-foundation-migration.sql:181`).
     - `ban`: `until` must be **absent** (a ban is indefinite) → 422 `invalid_until` when it is
       present. The sessions are revoked the same way.
     - `dismiss`: clears the decision (the report is closed, the user is not punished).
     - The report's `status` moves `open → reviewing → resolved` (a decision) or `→ dismissed`
       (a dismissal) — the four values the column's CHECK already allows (root
       `models/osionos-social-migration.sql:131-132`).
     - **A moderator may not decide on their own report** (`reporter_id` = the caller) → 403
       `self_report`. **A moderator may not decide on a report whose target is an admin** → 403
       `target_is_admin` (an admin is judged by another admin; the plan has no super-admin).
     - Every decision writes an audit row **first**: `event_type` `moderation_decision`, `details`
       `{ reportId, targetUserId, decision, until }`.
   - **The sign-in refuses a suspended or banned user** — `scripts/bridge-api.mjs`'s claim read
     (`readClaimsInOrder` `:1613-1619` / `readClaimsConcurrently` `:1633-1649`) gains one service
     read: `osionos_user_reports?subject_user_id=eq.<sub>&decision=not.is.null&select=decision,decision_until,decision_at&order=decision_at.desc&limit=1`.
     A `ban` refuses the handoff (403 `account_banned`); a `suspend` whose `decision_until` is null
     or in the future refuses it (403 `account_suspended`); a suspension whose `decision_until` has
     passed lets the sign-in through. The read is best-effort like the admin-flag read (`:1641`):
     a failed read **does not block the sign-in** — say so in a `Caveat:` line.
     **This is the one file P3-4-e shares with P3-4-a: P3-4-a must have merged.**
4. **The module** is appended to `scripts/bridge-account-mounts.mjs:25` and copied by name in
   `deploy/bridge-fly/Dockerfile:24-33`.

## Open questions (settled in Decisions D-P3-4 above; kept for the record)

1. **"users CRUD" — the bridge has no GoTrue admin API.** Creating an `auth.users` row and deleting
   one are GoTrue's business (a delete cascades every account table), and the bridge never writes
   `auth.users` today. P3-4-c implements **read + update** (the profile's editable columns + the
   platform role). Is that the intended "CRUD", or must P3-4 grow a create/invite flow (P3-5's
   territory) and an account-deletion flow (P5-6's)?
2. **Which role may change another user's display name?** P3-4-c gives it to `admin` only. A
   moderator who decides on a report may want to rename a troll — but a display name is user-facing
   content. Keep it admin-only, or give the moderator a rename right?
3. **The users list has no search and no filter.** The plan says "keyset paginated" and nothing
   else, so the admin scrolls through 10 000 rows. Is a `display_name`/`username` search wanted
   before this ships? (It would need a trigram index — root
   `models/osionos-account-profiles-migration.sql:278-280` already builds one on
   `display_name`/`username`.)
4. **A suspension ends at `decision_until`, but nothing restores the account when the time passes.**
   The sign-in check (P3-4-e item 3) is time-aware, so the user may sign in again — but the sessions
   revoked at the suspension stay revoked and the user is never told. Is a timed suspension enough,
   or does the platform need a sweeper that restores the access and notifies the user?
5. **The audit viewer's projection.** `ip_hash` and `user_agent` are on every audit row
   (`scripts/bridge-guard.mjs:229-238`). P3-4-g returns neither. Should an admin see them (they are
   the abuse-investigation fields), or is the projection the right call?
6. **Is the moderator supposed to see the Admin space at all?** The plan says "Admin space
   reachable from the rail for admins", but the queue is a moderator's job and the plan also lists
   "role-gated views". P3-4-b gives the rail item the `moderator` role (an admin outranks a
   moderator) and gates the sections inside. If the space must be admin-only, the rail item's
   `requiredRole` becomes `admin` and the moderator's queue has to live elsewhere — say which.
7. **A user with no report cannot be suspended from the console** (P3-4-e's decisions live on a
   report row). Should the console be able to open a case against a user with no report (a synthetic
   report row), or is a report a precondition?
8. **The `guest` role.** grobase's catalogue seeds it
   (`007_permissions_system.sql:84`) and nothing assigns it. Does it mean "a signed-out visitor",
   and does the account plane ever use it — or should the platform vocabulary be three roles?
