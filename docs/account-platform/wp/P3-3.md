## Decisions (D-P3-3, 2026-10-22) — binding; they supersede the sections they name

**D1 — Reuse (the user's rule: extend what exists, never a parallel copy).**
- The access token keeps its format `osionos_v1.<payload>.<hmac>` (`scripts/bridge-api.mjs:458`).
  `signAppSessionToken` (`:437-459`) and `createUserSession` (`:1504-1550`) are **not touched** —
  they are P3-4-a's OWNS. The refresh token is a new credential, not a second access token.
- No new revoke-all route: "revoke all" is the existing bridge logout
  (`/api/auth/bridge/logout`, `scripts/bridge-api.mjs:4291-4293`) driven by the existing client seam
  (`src/features/auth/model/bridgeLogout.ts:114-131`). The panel calls that; it does not invent one.
- No new session store: `src/store/settings/useAccountDevicesStore.ts` **is** the sessions store
  (its paths are wrong today) and is rewritten in place.
- No new settings section: the Profile panel's "Devices" block
  (`src/features/settings/profile/ProfilePanel.tsx:204-208`) becomes the Sessions block; the
  registry anchor changes in place (`src/features/settings/model/sections.ts:106`).
- The refresh route mounts through the one account seam (`scripts/bridge-account-mounts.mjs:27-39`),
  not through `bridge-api.mjs`'s dispatcher.

**D2 — The refresh token.** Format `osb_rt.<base64url(payload)>.<base64url(hmac)>`; the payload is
`{ iss:'osionos-bridge', aud:'osionos-refresh', sub, fam, jti, iat, exp, provider, email, name,
workspace_ids, roles, is_admin }`; the HMAC is the app-session secret (`config.appSessionSecret`,
`scripts/bridge-api.mjs:162`) — no new env var, no new dependency. The raw token is never stored,
never logged, never audited; the row keeps `sha256(token)` hex in `osionos_sessions.refresh_hash`
(the column and its CHECK exist: root `models/osionos-account-foundation-migration.sql:177`).

Why signed *and* hashed: the hash is the lookup key and the single-use proof; the signature carries
the family, the expiry and the claims the next access token must repeat, so a refresh needs no
claim re-read. Caveat: the refresh token repeats the workspace roles, so a role change (P3-4) lands
on the next sign-in — P3-4's "a role change revokes the sessions" closes that hole.

**D3 — One family per sign-in.** The sign-in's row is the family root: `family_id = id`,
`parent_id = NULL`. A rotation writes a **new** row (ADR 0003's rule: the row id is the access
token's jti, so a new token is a new row) with `family_id` = the root's id and `parent_id` = the row
it replaces. The columns exist (`...migration.sql:178-179`); nothing writes them today.

**D4 — Reuse detection.** The row keeps the hash of the token it issued, and the rotation writes a
child row. So "this token was already rotated" = "the row holding this token's hash has a child".
Presenting such a token revokes the **whole family** (`revoked_reason = 'refresh_reuse'`, allowed by
the CHECK at `...migration.sql:181`), writes the audit row **first**, and answers 401
`refresh_token_reused`. Order matters: the reuse check runs before the rotation, and the rotation's
INSERT runs after the audit — so a failed rotation leaves the old token usable and the client may
retry.

**D5 — The family is the unit of revocation.** `DELETE /api/account/sessions/:id` revokes every row
of that row's family (the bridge resolves the family with the service role, which the revoke write
already uses — ADR 0003). Without this, "sign this device out" revokes one access token and the
device is still signed in through the next refresh.

**D6 — The list is one row per family.** The newest live generation of each family (the caller's
own generation when the caller has one in that family). This needs `family_id` in the account
role's SELECT — the grant does not have it today (`...migration.sql:207`) — so **P3-3-a writes the
root migration that adds it**. The read stays `asUser` (ADR 0001/0003): the service role is never
used to read the owner's rows.

**D7 — The client kind comes from the user agent.** No row column and no request header carries a
client kind; the Electron shell appends `Electron/<version>` to its UA, and the client already
detects the desktop shell (`src/widgets/top-bar/model/desktop.ts:45`). The panel classifies each
row's `user_agent` into web / desktop / mobile. Caveat: the Tauri desktop shell sends a plain
browser UA and lands in "web"; a lying UA lands wherever it likes.

**D8 — The client must persist the access token's expiry, not the handoff's.** See Why 3; the fix
is split: P3-3-a answers the delivered token's expiry, P3-3-b persists it.

**D9 — No new dependency, no new env var, no generated file, no new table.**
`OSIONOS_SESSION_RECORDS` still switches the whole feature on and off
(`scripts/bridge-sessions.mjs:51-55`): with the records off there is no refresh token, no refresh
route and no session rows.

## Why

### 1. There is no refresh token: the access token is the only session credential
- The access token is minted by `signAppSessionToken` (`scripts/bridge-api.mjs:437-459`):
  `osionos_v1.<base64url(payload)>.<base64url(hmac)>`, `exp = iat + sessionTtlSeconds` (`:440`),
  the TTL default 1 h (`:105`, `:206`).
- The session it returns carries **no** refresh credential: `refreshToken: ''`
  (`scripts/bridge-api.mjs:1545`).
- The only refresh token in the app is the **auth gateway's**, passed through untouched by the login
  proxy (`scripts/bridge-api.mjs:4241`) and stored by the client
  (`src/features/auth/model/userStore.helpers.ts:159`, `:187`;
  `src/features/auth/model/useUserStore.ts:331`). Nothing consumes it: `grep -rn "refresh"
  scripts/*.mjs` finds no refresh route (only the gateway passthrough and unrelated words), and
  `grep -rn "api/auth/bridge/refresh" scripts/ src/` finds nothing outside the vendored
  `src/shared/notion-database-sys` (whose own auth routes belong to the playground API, not to the
  osionos bridge). The app holds a credential it can never use.
- Consequence: after one hour the access token stops verifying
  (`scripts/bridge-api.mjs:489-492` → 401) and the user is signed out. The plan's "1 h access token
  plus a rotating refresh token" is half-built: the first half exists, the second does not.

### 2. The rows have the columns a refresh family needs — and nothing writes them
- `public.osionos_sessions` already has `refresh_hash` (root
  `models/osionos-account-foundation-migration.sql:177`), `family_id` and `parent_id` (`:178-179`),
  and a `revoked_reason` that already allows `'refresh_reuse'` (`:181`).
- `scripts/bridge-sessions.mjs` writes none of them: `recordSession` (`:146-168`) inserts only the
  nine columns, and the revoke (`:211-243`) writes only `revoked_at`/`revoked_reason`. `AUTH_METHODS`
  lists `'refresh'` (`:41`) and no code path uses it.
- So no table and no column has to be created; only the **grant** has to change (D6), and the
  bridge has to write what is already there.

### 3. The client's session dies long before its token does
- The consume response answers the **handoff's** 90 s expiry, not the token's:
  `createBridgeHandoff` overwrites the sealed record's `expiresAt` with `now + handoffTtlMs`
  (`scripts/bridge-api.mjs:1717`, `:1721`; the TTL is 90 s at `:104`) and `consumeHandoffToken`
  returns it (`:1745`); the consume route answers it as-is (`:4164`).
- The client persists that value (`src/features/auth/model/useUserStore.ts:239`) and drops every
  record whose `expiresAt` has passed (`useUserStore.ts:149`). The access token it holds is still
  good for another ~1 h (`scripts/bridge-api.mjs:440`), so a reload drops a live session.
- P0-4 already hit this from the other side: the **row's** expiry is decoded from the token, never
  from the handoff (`scripts/bridge-sessions.mjs:120-139`, `:153`). The **response** was left alone.

### 4. The Sessions panel reads routes that were never served
- The store reads `GET /api/account/devices` (`src/store/settings/useAccountDevicesStore.ts:43`) and
  deletes `/api/account/devices`, `/api/account/devices/:id` (`:55`, `:66`, `:79`). No such route
  exists: the bridge serves `/api/account/sessions` and `/api/account/sessions/:id`
  (`scripts/bridge-sessions.mjs:255-268`). The store therefore always falls back to its local
  default (`useAccountDevicesStore.ts:44`, `:46`) and never shows a real session.
- The panel that renders it is the Profile panel's "Devices" block
  (`src/features/settings/profile/ProfilePanel.tsx:204-208`), with a table of fabricated rows
  (`:126-136`), a "Log out" button per row (`:135`) and a "Load more devices" button that only
  records an action (`:207`).
- The generic settings tests carry the same dead path (`tests/canvas/settings-api.test.ts:265-279`).

### 5. "Revoke one" would not end a device
- Today's revoke ends exactly one row (`scripts/bridge-sessions.mjs:214-224`: the PATCH filters on
  `id` and the caller's `user_id`). The panel's button is per row
  (`src/features/settings/profile/ProfilePanel.tsx:135`), so the user reads it as "sign this device
  out".
- With a refresh token, one device holds several access tokens (one per rotation, D3). Revoking one
  row would leave the device signed in through the next refresh — the button would lie. The unit of
  revocation has to be the family (D5).

### 6. The panel has no client kind to group by
- The rows carry `user_agent` and `ip_prefix` (`scripts/bridge-sessions.mjs:37`,
  `models/osionos-account-foundation-migration.sql:172-175`) and nothing else: there is no client
  column, and the request headers carry no client kind (`clientMeta` reads the IP header and the
  UA only, `scripts/bridge-guard.mjs:139-155`).
- The plan asks for web / desktop / mobile. Without a signal, the grouping is a UA heuristic (D7),
  and the honest statement of its limit is a `Caveat:` on the classifier.

## Contract

### P3-3-a — the rotating refresh token (bridge + root SQL)

**Root SQL — `models/osionos-session-refresh-migration.sql` (new, in the root repo).**
1. It grants the account role `family_id` on `public.osionos_sessions`, so the owner can read the
   family of a row through `asUser`:
   - `REVOKE ALL ON public.osionos_sessions FROM osionos_account_user;` then
     `GRANT SELECT (id, created_at, expires_at, last_seen_at, auth_method, ip_prefix, user_agent,
     revoked_at, revoked_reason, family_id) ON public.osionos_sessions TO osionos_account_user;`
     — the same revoke-then-grant shape as the foundation migration
     (`...migration.sql:206-208`), so a replay changes nothing.
   - `refresh_hash` stays out of the grant: the owner never needs it, and the role must not be
     able to select it (the foundation file says why, `...migration.sql:201-203`).
   - The RLS policy is untouched (`...migration.sql:214-215`) and no table or column is added:
     `family_id`, `parent_id`, `refresh_hash` and `'refresh_reuse'` already exist (`:177-181`).
     The migration does add at least one index for the hot path:
     `CREATE INDEX IF NOT EXISTS osionos_sessions_family_live_idx ON public.osionos_sessions
     (family_id) WHERE revoked_at IS NULL;` (and ideally a second one on `(refresh_hash)`), because
     the refresh lookup and the family collapse are otherwise seq scans on a table that grows ~720
     rows/family over the 30-day TTL (`foundation migration:29-31` has no family_id index).
   - It must be idempotent (a second run changes no ACL) and must pass the root gates.
   - ADR 0003 is amended by the orchestrator before dispatch (the rotation INSERT is a third
     writer; D5 changes the revoke PATCH filter from `id` to `family_id`; the rotation copies
     `ip`/`user_agent` metadata): P3-3-a does not edit the ADR itself.

**The refresh token (`scripts/bridge-sessions.mjs`).**
2. `mintRefreshToken({ config, now, claims })` returns `{ token, expiresAt, hash }`:
   - `token` = `osb_rt.<base64url(payload)>.<base64url(hmac)>`; the HMAC is over the encoded
     payload with `config.appSessionSecret` (the same secret that signs the access token,
     `scripts/bridge-api.mjs:457`) — no new env var (D9).
   - `payload` = `{ iss:'osionos-bridge', aud:'osionos-refresh', sub, fam, jti, iat, exp, provider,
     email, name, workspace_ids, roles, is_admin }` (D2). `exp` = the family root's expiry +
     `REFRESH_TTL_SECONDS` (default 7 days, `OSIONOS_BRIDGE_REFRESH_TTL_SECONDS` may override it;
     a non-positive or non-numeric value falls back to the default).
   - `hash` = `sha256(token)` hex (64 chars — the CHECK at `...migration.sql:177`).
   - The payload is read back by `readRefreshToken(token, config, now)`: the format, the signature
     and `exp` are checked; anything wrong → `null` (the caller answers 401, never 500).
3. The sign-in rows carry the family's first token. `recordSession`
   (`scripts/bridge-sessions.mjs:146-168`) gains `refresh_hash` and `family_id` in the INSERT body
   and returns `{ row, refreshToken }` instead of the row alone; `recordDeliveredSession`
   (`:171-174`) returns `null` when the records are off (unchanged) and the same shape otherwise.
   - The family root's `family_id` = its own `id` (the token's jti, `:150`), `parent_id` = NULL.
   - The refresh token's `fam` claim = that same id, so the client never has to be told the family.
   - The raw token is returned to the caller **once** and is never written anywhere but the hash.
4. The two delivery points put the refresh token in the response (the only `bridge-api.mjs` lines
   this package touches):
   - `handleBridgeConsume` (`scripts/bridge-api.mjs:4156-4165`): the answer keeps its shape
     (`{ ok, persona, session, expiresAt, message }`) and `session.refreshToken` carries the new
     token.
   - `handleAuthProxy` (`:4202-4245`): the top-level `refreshToken` field stops carrying the **auth
     gateway's** token (`:4241`) and carries the osionos one; the gateway's token is not needed
     (the bridge never refreshes with it) — say so in a comment on that line.
   - Both answers also carry `expiresAt` = the **delivered token's** expiry (decoded from the
     token), not the handoff's 90 s expiry (Why 3, D8). The handoff's expiry stays inside the
     handoff record.
   - The refresh token is only minted when the records are on. With the records off the response
     carries `refreshToken: ''` and the client behaves as it does today.

**The refresh route (`scripts/bridge-sessions.mjs`, mounted through the account seam).**
5. `POST /api/auth/bridge/refresh` — the refresh token is the credential; **no** session token is
   read, and an `Authorization` header is never accepted as an alternative (one credential, one
   way).
   - **Body:** `{ refreshToken: string }`. Missing/blank → 422 `refresh_token_required`. A body
     larger than 16 KB → 413 (the house limit, `scripts/bridge-api.mjs:106`, read with the reusable
     helper `bridge-social-core.mjs:59` `readJsonBody`). A request that carries an `Authorization`
     header but no body answers 422 `refresh_token_required`, not 401 — the header is never an
     alternative credential.
   - **Rate limit:** `rateLimit(kv, ['session-refresh', ipPrefix || 'unknown'], { limit: 60,
     windowMs: 60_000 })` (`scripts/bridge-guard.mjs:167`), applied **before** the token is read.
   - **Steps, in this order:**
     1. the records off → 503 `session_records_off` (the same off state as the session routes,
        `scripts/bridge-sessions.mjs:261-263`);
     2. the token's format/signature/expiry → 401 `refresh_token_invalid` or 401
        `refresh_token_expired`;
     3. the row that holds `sha256(token)` — read **directly with the service role** (`asService`),
        not through the polled revoked-ids set, so a revoked session's refresh token fails at once on
        every replica → none → 401 `refresh_token_invalid`;
     4. the row's `user_id` ≠ the token's `sub` → 401 `refresh_token_invalid` (never a hint about
        the other account);
     5. the row is revoked → 401 `session_revoked`;
     5a. the family root predates the user's cutoff (`bridge-session-cutoff.mjs` `cutoffMicros`) →
         401 `session_revoked` (the logout-all hole: the cutoff write does not touch session rows, so
         a refresh token minted before "log out of all devices" must not keep minting);
     6. **the reuse check** (D4): the row has a child → the family is revoked (below) → 401
        `refresh_token_reused`;
     7. the audit row (`writeAudit`, `scripts/bridge-guard.mjs:224-246`) with the event type
        `session_refresh` — **before** the INSERT; a failure → 503 `audit_unavailable` and no row
        is written;
     8. the new access token: `signAppSessionToken` with a **new** jti and the claims the refresh
        token carried. The refresh token's claims are rebuilt into the call's arguments as:
        `workspace = { _id: refreshPayload.workspace_ids[0] }`,
        `memberWorkspaces = refreshPayload.workspace_ids.slice(1).map((_id) => ({ _id, role:
        refreshPayload.roles[_id] || 'member' }))`, `isAdmin = refreshPayload.is_admin === true` —
        only the first workspace's `_id` is needed (name/slug are not in the token, and
        `signAppSessionToken` re-derives `roles` from these, `scripts/bridge-api.mjs:437-459`);
     9. the INSERT of the new row: `id` = the new jti, `user_id` = the row's, `created_at` = now,
        `expires_at` = the new token's `exp`, `auth_method` = `'refresh'` (the CHECK allows it,
        `...migration.sql:171`), `ip_prefix`/`ip_hash`/`user_agent` **copied from the parent row**
        (the same client), `family_id` = the parent's `family_id`, `parent_id` = the parent's `id`,
        `refresh_hash` = the new token's hash;
     10. the answer: 200 `{ accessToken, refreshToken, expiresAt }` — nothing else (no persona, no
        workspaces, no ip).
   - **The rotation's failure keeps the old token usable:** the INSERT failing → 503
     `session_record_unavailable` and no child row exists, so the same refresh token still
     refreshes (the client retries). The reuse check reads "the row has a child" *because* the
     child means "the rotation succeeded".
   - **The reuse answer** (step 6): the whole family is revoked in one PATCH
     (`family_id=eq.<root>` and `user_id=eq.<the row's user>`, `revoked_at` = now,
     `revoked_reason` = `'refresh_reuse'`), every returned id is applied locally to the revocation
     tracker (`config.sessionRevocations.applyLocal`, the pattern at
     `scripts/bridge-sessions.mjs:230-234`), the audit row (`session_refresh_reuse`) is written
     **before** the PATCH, and the answer is 401 `refresh_token_reused`. The client treats that code
     as "someone else used this sign-in" (P3-3-b).
6. **The revoke route becomes family-scoped** (D5). `DELETE /api/account/sessions/:id`:
   - the id must be a uuid (`scripts/bridge-sessions.mjs:246-252` → 422 `invalid_session_id`);
   - the rate limit and the audit row stay as they are (`:212`, `:213`);
   - the bridge reads the row with the **service** role (`id=eq.<id>` and `user_id=eq.<caller>`) to
     learn its `family_id` — a row that is not the caller's is a 404 `session_not_found`, exactly
     like today (`:225-227`); "not yours" and "already revoked" must look the same;
   - the PATCH then revokes **every** row of that family (`family_id=eq.<root>` and
     `user_id=eq.<caller>` and `revoked_at=is.null`), with `revoked_reason` = `'user'`; when the
     row's `family_id` is NULL (a legacy row minted before families existed) only that named row
     is revoked, so legacy sessions never collapse into one another;
   - every revoked id is applied locally from the rows the PATCH returned (never from the path id);
   - the answer is 204, as today. Revoking the **current** session is still allowed, and it
     triggers a local sign-out of that account (P3-3-b) rather than only dropping the row —
     otherwise the user stays signed in for up to 10 s.
7. **The list is one row per family** (D6). `GET /api/account/sessions`:
   - the read stays `asUser` with `select=id,created_at,expires_at,last_seen_at,auth_method,
     ip_prefix,user_agent,family_id`, `revoked_at=is.null`, `expires_at=gt.<now>`,
     `order=created_at.desc`, `limit=50` (`scripts/bridge-sessions.mjs:183-192`); the grant it needs
     is the root migration of this package;
   - the rows are collapsed per `family_id`, treating NULL as "each row is its own family"
     (`family_id ?? id`), so legacy rows do not collapse into a single row and revoking one does not
     revoke them all;
   - the collapse must survive the 50-row limit: read distinct families (or prune superseded
     generations — a new DELETE write path that needs an ADR 0003 amendment), because ~720
     generations/family over 30 days otherwise hides the user's other devices behind the newest
     family;
   - within a family: the caller's own generation when the caller has one in that family,
     otherwise the newest generation of the family;
   - the cutoff filter (`:196`) and the `current` marker (`:205`) stay as they are;
   - the answer's shape is unchanged: `{ sessions: [{ id, createdAt, expiresAt, lastSeenAt,
     authMethod, ipPrefix, userAgent, current }] }` — **no** `familyId` in the answer (the client
     never needs it) and never `refresh_hash`, never `ip_hash`, never a raw address.
8. **The route mounting.** The refresh route is added to the module the account seam already loads
   (`scripts/bridge-account-mounts.mjs:29-35`): `createSessionsRoutes` answers
   `POST /api/auth/bridge/refresh`. The module order in the list is unchanged (the sessions module
   is first, `bridge-account-mounts.mjs:30`). No new line is appended to the
   mounts list — the route is part of the sessions module.
9. **The off state stays one state.** With `OSIONOS_SESSION_RECORDS=off` or without a service key
   (`scripts/bridge-sessions.mjs:51-55`): no refresh token is minted, the refresh route answers
   503 `session_records_off`, and the session routes keep answering 503 (`:261-263`). The boot
   line names the reason (`:65-69`).

### P3-3-b — the client keeps the session alive

10. **A new pure module `src/features/auth/model/sessionRefresh.ts`** (no store, no `import.meta.env`
    — the house rule of `src/features/auth/model/bridgeLogout.ts:9`):
    - `REFRESH_SKEW_MS` (5 min) and `isBridgeAppTokenExpired` are reused
      (`src/features/auth/model/userStore.helpers.ts:72-77`), not copied;
    - `needsRefresh(token, now = Date.now())` → true when the bridge token's `exp` is within the
      skew or past;
    - `refreshBridgeSession({ apiBase, refreshToken, fetchImpl, signal })` → `POST
      ${apiBase}/api/auth/bridge/refresh` with `{ refreshToken }` → a discriminated result:
      `{ ok: true, accessToken, refreshToken, expiresAt }` or `{ ok: false, code, status }` with
      the bridge's stable `code` (`refresh_token_invalid`, `refresh_token_expired`,
      `session_revoked`, `refresh_token_reused`, `session_records_off`, `rate_limited`,
      `session_record_unavailable`) or `'unreachable'` when the network failed. It never throws.
    - `REFRESH_REUSE_CODE = 'refresh_token_reused'`.
11. **The store grows one action** (`src/features/auth/model/useUserStore.ts`): `refreshAccount(
    userId)`:
    - it reads the account's refresh token from the persisted record
      (`useUserStore.ts:133-156`), calls `refreshBridgeSession`, and on success replaces the
      access token, the refresh token and the expiry **in the in-memory session and in the
      persisted record** (`useUserStore.ts:158-161`) and re-saves the workspaces/context;
    - on `refresh_token_reused` (D4) it signs **that account** out locally
      (`clearPersistedBridgeSession`, `:169-180` + the in-memory delete at `:370-379`) and notifies
      the user with a notice that says the sign-in was reused — the existing `REVOKED_NOTICE`
      pattern (`src/features/auth/model/bridgeLogout.ts:98-102`) is the model, a new notice text is
      not a copy of it;
    - on `refresh_token_invalid` / `refresh_token_expired` / `session_revoked` it signs that account
      out as well (the session is gone);
    - on `rate_limited` / `session_record_unavailable` / `unreachable` it **keeps** the session and
      retries later (the timer below); the user is not told anything about a transient failure;
    - it never throws and never touches another account.
12. **The boot refresh** (`resolveInitialState`, `src/features/auth/model/useUserStore.ts:350-366`):
    before the persisted records are restored, every record whose access token is expired or inside
    the skew is refreshed (D8 makes the record survive long enough to be refreshed). A record whose
    refresh fails for good is dropped as today; a record that fails transiently is kept and the
    timer retries.
13. **The timer.** A module-level interval (60 s) started by the store when a bridge session is
    present, stopped when none is: it refreshes the **active** account when
    `needsRefresh(accessToken)` is true. Only one refresh per account is in flight at a time (one
    promise per user id).
14. **The 401 retry.** `src/shared/api/sessionRevocation.ts` today reports only `session_revoked`
    (`:31-45`). A **new** wrapper `src/shared/api/sessionRefreshAware.ts` sits next to it in the
    fetch stack (`src/shared/api/client.ts:79`): on a 401 whose body does **not** say
    `session_revoked` it asks the store to refresh the account that owns the token and replays the
    request **once** with the new token; a second 401 is handed back untouched. A revoked session is
    never retried (the revocation wrapper already owns that case).
    - This is the last item of the package: if the session runs out of time, P3-3-b ships without it
      and reports it under `deviations:` — the timer (13) then covers the normal case.
15. **The cross-tab lease.** Two tabs of the same account that refresh at the same moment would make
    the second one a **reuse** and kill the family (D4). The client therefore serializes the
    rotation per account:
    - the lease is taken **before** the route call, in this order: check the published result →
      take the lease → call the route → publish the result → release the lease. A tab that calls
      the route before checking the lease trips reuse detection;
    - a lease record in `localStorage` (`osionos:refresh-lease:<userId>`, 10 s) is taken before a
      rotation; a tab that finds a fresh lease waits for the published result instead of rotating;
    - the rotated tokens are published in `localStorage` (`osionos:refresh-result:<userId>`), and a
      tab that finds a published result **newer than its own token adopts it** instead of rotating;
    - the `storage` event updates the other tabs' stores without a reload.
    - Caveat: a tab that dies mid-rotation leaves the lease behind — it expires after 10 s; a
      rotation that succeeds but whose result is never published (the tab died) leaves the family
      rotated with nobody holding the new token: the account is signed out on the next refresh
      attempt (the old token is a reuse) — that is the intended outcome of a stolen-token policy.

## Security edges

1. **Who may call what.**
   - `GET /api/account/sessions` and `DELETE /api/account/sessions/:id`: a verified app session,
     and only the caller's own rows (the read is `asUser` under the owner-read policy,
     root `...migration.sql:214-215`; the write filters on the caller's `user_id`).
   - `POST /api/auth/bridge/refresh`: **no** session token; the refresh token in the body is the
     credential. It is accepted only in the body, never in a header or a query string (a URL ends
     up in logs).
   - The revoke-all path is the existing logout: a verified session, no body
     (`scripts/bridge-api.mjs:4247-4255`).
2. **What a non-owner sees: nothing.** Another user's session id in the revoke path is a 404 that
   looks exactly like "already revoked" (`:225-227`); another user's refresh token is a 401
   `refresh_token_invalid` that says nothing about the account; the list never contains another
   user's row (the RLS + the `asUser` read).
3. **What never leaves the bridge:** the raw refresh token (only its sha256 is stored), `ip_hash`,
   `family_id`, `parent_id` and `refresh_hash` are never in a response body; the list answers the
   eight keys of item 7 and nothing else; the audit `details` never carry a token (the house rule
   of `scripts/bridge-guard.mjs:219-222`).
4. **The reuse alarm kills the whole family** — including the legitimate user's live session. That
   is the point of the detection, and it is why the client serializes the rotation (item 15): a
   benign double refresh must not look like a theft.
5. **The refresh token lives where the access token lives** (the persisted session record in
   `localStorage`). Caveat: that storage is readable by any script the page runs, and the refresh
   token outlives the access token — the reuse detection is the mitigation, not the storage. An
   HttpOnly cookie would be the stronger answer and is **not** in this package (open question 3).
6. **The derived credentials still outlive a revoke** (ADR 0003): the IDE token (15 min), the
   account JWT (120 s), the LiveKit grants (up to 6 h). The panel's copy must not promise more than
   the platform does.
7. **A revoke of the family is enforced on the other replicas within one poll (10 s), or the
   stale threshold (60 s)** (`scripts/bridge-session-tracker.mjs:34-35`); locally it applies at
   once (`scripts/bridge-sessions.mjs:230-234`).

   persisted record's `expiresAt` is the handoff's 90 s expiry and `readPersistedBridgeSessions`
   drops expired records, so a handoff sign-in is dropped 90 s after.
2. **OQ2 (HttpOnly cookie).** Decision: keep the JSON field; defer the cookie. Reason: the client
   already stores the access token the same way and a cookie changes CORS/SameSite for every bridge
   call plus the desktop origin; reuse detection is the mitigation for the localStorage exposure.
3. **OQ3 (refresh TTL).** Decision: 7 days, matching `BRIDGE_SESSION_TTL_MS`
   (`useUserStore.ts:63`). Reason: bounds table growth (vs. 30 days) and forces re-login more
   often; row growth itself is addressed by condition 7, not the TTL.
4. **OQ4 (desktop client-kind header).** Decision: no. Reason: D7's UA heuristic is honest about
   its limits and a new column is a root SQL change outside this package; the Electron shell's
   `Electron/` UA token is already detectable.
5. **OQ5 (load more).** Decision: no. Reason: the route has no paging by design (50 live
   generations) and adding a cursor the route does not support is out of scope; revisit only if
   users hit the cap.
6. **OQ6 (write `last_seen_at`).** Decision: no. Reason: one write per request is the P0-5
   problem, and the panel can show the family's sign-in (creation) time; a single write per
   rotation is a cheaper future option.
7. **OQ7 (roles repeated in the refresh token).** Decision: keep repeating roles; P3-4's "role
   change revokes sessions" is the required companion. Reason: re-reading claims on every refresh
   would couple P3-3 to P3-4-a's OWNS and add a DB read to the hot path; the revoke-on-role-change
   closes the hole.
