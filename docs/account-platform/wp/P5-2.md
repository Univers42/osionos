## Why
- **The MCP server impersonates a user chosen by environment variable.** `mintApiSession`
  (`scripts/osionos-mcp-server.mjs:292-336`) signs an HMAC over `{provider, subject, email, name, jti}`
  with the bridge's shared secret and POSTs it to `/api/auth/bridge/session`. The identity comes from
  `OSIONOS_MCP_EMAIL` / `OSIONOS_MCP_NAME` / `OSIONOS_MCP_SUBJECT` (`:189-193`), default
  `claude.mcp@osionos.local` with a subject derived from the email (`uuidFromHash` `:181-187`, `:190-192`; `:176-181`
  is `stableStringify`). Whoever can set those variables becomes any Prismatica user, and an email listed in
  `OSIONOS_ADMIN_EMAILS` becomes an administrator (`scripts/bridge-api.mjs:251-255`, `:1635`).
- **The dev fallback.** `bridgeSecrets()` (`:204-211`) tries `OSIONOS_MCP_BRIDGE_SECRET`,
  `OSIONOS_BRIDGE_SHARED_SECRET`, `JWT_SECRET` and then the literal `'dev-secret-change-in-production'`
  (`:209`), and `mintApiSession` walks the list on 401 (`:301-324`). A bridge left with that secret is
  open to anyone who knows the string. The same list is shown by `osionos_status`
  (`:701-703`, `mode` at `:701`) and the `osionos://server` resource (`:678-680`: `identityEmail`, `hasBridgeSecret`).
- **The env-file loader makes it silent.** The server reads `.env.local`/`.env` files from five
  directories at import (`:24-46`, `ENV_FILES` `:24-31`) and sets any variable not already set, so a secret in a parent
  repo's env file arms the HMAC path without the operator choosing it.
- **The bridge side is correct for its real caller and must stay.** `/api/auth/bridge/session`
  (`scripts/bridge-api.mjs:4703`, `handleBridgeSession` `:4529-4540`) verifies the signature with
  `config.sharedSecret`, which defaults to `''` and then answers 503 (`:186`, `:424-425`). Its legitimate
  caller is the Prismatica gateway (the website hand-off), not MCP. Removing the route would break
  every login. The fix is in the client.
- **The PAT exists, half-wired.** The store, the vocabulary and the management routes are merged:
  `scripts/bridge-pat-store.mjs` (`PAT_PREFIX = 'osio_pat_'`, `:39`), `scripts/bridge-pat-permissions.mjs`
  (`PAT_RESOURCES` has the single resource `pages`, `:56-79`), `scripts/bridge-account-tokens.mjs`
  (`GET`/`POST`/`DELETE` `/api/account/tokens`, `:288-290`). The Bearer middleware (P5-1-d) is the
  missing half and is the only place a PAT becomes a session.
- **A PAT today cannot do what MCP does.** The MCP tools call (`scripts/osionos-mcp-server.mjs`):
  `GET /api/workspaces` (`:643`, `:764`, `:797`), `GET /api/pages/all?workspaceId=` (`:639`),
  `GET /api/pages/:id` (`:820`), `GET /api/blocks?pageId=` (`:821`, with `.catch(() => [])`),
  `POST /api/pages` (`:839`), `PATCH /api/pages/:id` (`:872`, `:911`) and
  `POST /api/pages/:id/blocks` (`:892`). Of those, P5-1-d's allowlist covers two rows. The rest answer
  `403 pat_route_not_allowed` by design (P5-1 spec, `target/specs/P5-1.md`, P5-1-d contract 2.3). There
  is no `/api/blocks` route in `scripts/bridge-api.mjs` (searched: no match), so that call is a 404 swallowed
  by the `catch`; it is dead.
- **The client already caches and retries.** `createMcpApiClient` (`scripts/osionos-mcp-api.mjs:96-158`)
  takes `OSIONOS_MCP_JWT` as a fixed bearer (`:105-106`) and retries once on `401 session_revoked`
  (`:30`, `isRevoked` `:82-85`). A PAT is that same bearer shape; the swap is one `session()` branch. There is no
  parallel client to write.
- **Second token system, same word.** `services/osionos-ai` has its own `osn_pat_` tokens
  (`services/osionos-ai/src/pat/token.ts:15`, `PAT_PREFIX = 'osn_pat_'`), its own table
  `ai_access_tokens` and the remote MCP endpoint `POST /api/ai/mcp`
  (`services/osionos-ai/src/routes/mcp.ts`), listed in `AccessTokensPanel`
  (`src/features/settings/ai/AccessTokensPanel.tsx`, anchor `ai-access-tokens`). That is a different
  credential for a different server; this package does not merge them (decision 1) and does not touch it.
- **The panel is half there.** The Developer section (`src/features/settings/model/sections.ts:182-187`)
  renders `DeveloperPanel` (`src/features/settings/developer/DeveloperPanel.tsx`): list, create, revoke one,
  revoke all, with the Name/Kind/Permissions/Created/Expires columns (`:23`). It has no "last used", no
  "which app is this", no MCP preset, and no word telling the user a token can act through MCP. The list
  select omits the column: `LIST_COLUMNS = 'id,name,kind,scopes,grants,created_at,expires_at,revoked_at,revoked_reason'`
  (`scripts/bridge-pat-store.mjs:43`) and the mapper has no `lastUsedAt` (`tokenEntry`, `scripts/bridge-account-tokens.mjs:181-192`).

## Decisions proposed

1. **Two token systems:** keep separate in this package; the pointer line (c-5) stays. Reason: `osn_pat_`
   (`services/osionos-ai/src/pat/token.ts:15`) is another resource server with another table; merging is a P5-x of
   its own, and neither panel may fetch the other's list.
2. **Legacy window:** no `OSIONOS_MCP_LEGACY_HMAC` flag. Reason: the flag would re-add the very path the package
   exists to remove, no in-tree caller exists (grep above plus F5 list); the refusal text names the replacement
   variable and the Settings path, and the migration note goes in the commit body.
3. **Hardening `/api/auth/bridge/session` against `claude.mcp@osionos.local` / admin emails:** out of scope, file as a
   separate devil-gated issue. Reason: bridge-side change on the login path (BR:4529-4540); anyone holding the shared
   secret can still mint sessions, so operators should rotate it after this ships (state in the report, no code).
4. **`/api/workspaces` masking:** no new `workspaces` resource; read-gated by `pages:read` with the fixed projection
   of condition 2 (`_id, id, name, slug, role`). Reason: pages need a workspace id to be used at all, the projection
   removes `settings`/`permissions`, and a new resource would grow `bridge-pat-permissions.mjs` (P5-1-c's file).
5. **Audit cadence:** accept one `pat_use` row per token per hour for this package; the panel and Caveat say "accurate
   to the hour". Reason: changing P5-1's audit decision touches the claim logic outside a's OWNS; page rows carry
   their own `updatedAt`. Open a follow-up for a per-write row on `POST/PATCH` if abuse forensics are wanted.
6. **`useMcpSettingsStore` connections:** not the authorized apps; leave `src/features/settings/mcp/**` alone. Reason:
   they are per-member app toggles in a local store, not credentials (the existing `mcp` section, `sections.ts`,
   id `mcp`); the plan row (`plans/for-all-users-in-reactive-panda.md:184`) says tokens.
7. **P5-1-d final shape:** hard gate, not a note: condition 15's `rg` check runs first and a stops on any mismatch.
   Reason: the line numbers come from an uncommitted tree; a mismatch silently changes the allowlist API.

## Residual risk after P5-2-b (D-P5-2b condition 5, recorded 2026-10-23)

P5-2-b removes the MCP server's shared-secret mint, but the bridge route it used stays: `POST /api/auth/bridge/session` (`scripts/bridge-api.mjs:4738`, `handleBridgeSession` `:4559`). Whoever holds `OSIONOS_BRIDGE_SHARED_SECRET` can still mint a handoff for **any** subject. Today it is bounded only by the timestamp skew and the single-use jti (`claimBridgeReplay`).

Holders are the website sign-in flow and the desktop supervisor (`apps/osionos-electron/native/supervisor.mjs` in the root tree). The secret is therefore a master key, not a per-caller credential.

Follow-up, not in P5-2:
- per-caller secrets, or a GoTrue-signed proof of the subject;
- an audit row per mint;
- rotating the secret once P5-2-b ships, because the MCP host config no longer needs it.
