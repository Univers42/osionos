# F-3b2 — make a verified secondary the primary address

## Why (verified anchors)

- F-3b added, verified and removed secondary addresses. The primary is GoTrue's `email`, and changing
  it is not routed yet: `scripts/bridge-account-emails.mjs:16` says make-primary answers 404, and
  `ID_ROUTE`/`ACTIONS` (`:42,45`) know only `code` and `verify`.
- GoTrue facts, **measured** on the live funnel on 2026-10-24 with two throwaway users the probe
  deleted (`groot-wt/deploy/probe/gotrue-email-change.mjs`, logs `groot-wt/logs/probe-gotrue-email-change-*.log`).
  They match `internal/api/admin.go` v2.188.1, `adminUserUpdate` lines 141-260.
  `PUT /auth/v1/admin/users/{id}` with `{ email, email_confirm: true }`:
  - answers 200, sets `email` and `email_confirmed_at`, leaves no `new_email` pending, and sends no
    mail (that path has no mailer call);
  - updates the email identity's `identity_data.email`/`email_verified`, but only a re-read shows
    it, because the PUT response's `identities` are stale;
  - **keeps the sessions**: the old access token's getUser is 200, and the old refresh token
    returns 200 with a token carrying the new `email` claim;
  - makes sign-in with the old address 400 and with the new one 200;
  - answers **500 with code 23505** for an address another user holds, because the update path has
    no duplicate check (create has one, admin.go:351);
  - lower-cases an upper-case address.
- The admin flag is read by address hash, not by identity:
  `resolveAdminFlag` (`scripts/bridge-api.mjs:1694-1711`) PATCHes and reads
  `osionos_bridge_identities?email_hash=eq.<hash>`, using `limit=1` for the read. The table's key is
  `(provider, subject)`, with `UNIQUE (user_id)` (root `models/osionos-bridge-migration.sql:13-26`).
  `email_hash` has no other reader (`rg email_hash scripts/`).
  - **The hole once primaries can change:** admin A moves off address X, and A's row keeps
    `email_hash(X)` until A signs in again. If user B then makes X primary, B's sign-in reads A's
    row and becomes admin.
  - Live today: 78 identity rows, 2 admins, 0 duplicate hashes (read-only query, 2026-10-24).
- The pieces to reuse are in place:
  - `ownRow`, `guardMutation`, `primaryAddress` and `recordOf` (`scripts/bridge-account-email-flow.mjs`);
  - `isAvailable`'s inputs and `findAccountByEmail` (`scripts/bridge-gotrue-user.mjs:66`);
  - `gotrueAdminHeaders` (`:26`) and `readGotrueUser` (`:34`);
  - the rows API (`scripts/bridge-account-email-rows.mjs:101-128`).

## Contract

### Route

`POST /api/account/emails/:id/primary`, with no body. It goes through the router's existing
dispatch, rate limit and `respondWithError`. `ID_ROUTE` gains `primary`, `ACTIONS` gains
`primary: ['POST', makePrimary]`, and the header comment's line about make-primary answering 404
is replaced.

### `makePrimary` (new module `scripts/bridge-account-email-primary.mjs`, ≤150 lines)

1. `guardMutation` (sudo first, then the keys check; nothing is read before both pass).
2. `ownRow(ctx, session, id)` gives `{ row, address: S }`. `primary-<uid>` keeps its 409, and an
   unknown or foreign id keeps its 404, through `ownRow`'s own rules.
   - `row.verified_at` null → 409 `email_unverified`, "Verify this address before making it primary."
3. `P = primaryAddress(ctx, userId)`, lower-cased as today. `S === P` → 409 `already_primary`.
4. **Recheck at promote time** (the add-time check is old by now):
   - `findAccountByEmail(S)` returns an account whose `id !== userId`, confirmed or not
     (GoTrue's unique index refuses both) → 409 `email_taken`;
   - no account and `complete === false` → 503 `email_unavailable`;
   - a lookup failure → 503 `email_unavailable`.
5. **Keep the old primary as a verified secondary**, when `P` is non-empty:
   - `rows.verifiedByOther(userId, hmacOf(P))` is true → do not keep it, and answer `previous: null`.
     Someone else proved they own `P`'s mailbox.
   - Otherwise insert `P` already verified, through a new rows method
     `insertVerified(userId, address, atIso)`. It seals and hashes exactly as `insert` does, sets
     `verified_at`, and on `unique_violation` reuses the caller's own row, marking it verified.
     Remember whether this call created the row, for compensation.
6. Audit `account.email_primary_requested` (no addresses in `details`) BEFORE the GoTrue call.
7. GoTrue: a new `updateGotrueEmail({ config, fetchImpl }, userId, address)` in
   `bridge-gotrue-user.mjs` sends `PUT /auth/v1/admin/users/<encoded id>` with
   `{ email: address, email_confirm: true }` and `gotrueAdminHeaders`. It has the same timeout as
   `readGotrueUser` and returns nothing on 2xx. It throws `{ code }`:
   - `gotrue_email_taken`: a 500 whose JSON `code` or `error_code` is `23505`, or a 422 `email_exists`;
   - `gotrue_write_failed`: any other non-2xx;
   - `gotrue_write_unknown`: a network error or timeout, where the outcome is unknown.
8. Outcome handling:
   - `gotrue_email_taken` → compensate, then 409 `email_taken`.
   - `gotrue_write_failed` → compensate, then 503 `email_unavailable`.
   - `gotrue_write_unknown` → re-read with `readGotrueUser`:
     - its email equals `S` → continue as a success;
     - it equals `P` → compensate, then 503;
     - the re-read fails → no compensation, and 503. A kept `P` row is harmless; see the GET dedupe.
   - **Compensate** means delete the `P` row only when step 5 created it.
9. Success:
   - `rows.remove(userId, row.id)` (the `S` row). A failure is logged by code only and does not
     change the answer.
   - Audit `account.email_primary_changed`.
   - Answer 200 `{ primary: <EmailRecord of S, isPrimary: true, verifiedAt: now>, previous: <id of the kept P row> | null }`.
10. Sessions are not revoked. The measurement shows GoTrue keeps them, and changing that is a
    product decision outside this package.

### GET dedupe

`GET /api/account/emails` drops a secondary whose opened address equals the primary. The case
arises after step 9's remove fails, or after an unknown outcome. Count it in `x-emails-skipped`,
like a row that does not open.

### Admin flag bound to the identity (in `bridge-api.mjs`, `resolveAdminFlag` only)

- Both the promotion PATCH and the read are scoped by the identity key:
  - read: `osionos_bridge_identities?provider=eq.<p>&subject=eq.<s>&select=is_admin&limit=1`;
  - PATCH: `…?provider=eq.<p>&subject=eq.<s>&email_hash=eq.<hash>&is_admin=is.false`, so it only
    promotes the caller's own row, and only while it carries the listed address.
- Encode `<p>` and `<s>` with `encodeURIComponent`.
- Behaviour that stays the same: env-listed and verified → admin; DB-recorded admin with the env
  list empty → admin; any error → the env-only answer.
- Behaviour that changes on purpose: a DB-recorded admin whose address changed stays admin.
  Admin is the person, not the address. Replace the Caveat at `:1789` to say so.
- The row of a different subject never decides anyone's flag.

### Client

- `src/shared/api/accountEmailsApi.ts`: `makePrimaryEmail(id)`, a POST through the existing `call`.
- `src/store/settings/useAccountEmailsStore.ts`: `makePrimary(id)`. Not optimistic: on success it
  re-reads the list. `sudo_required` goes through the same path the other actions use.
- `src/features/settings/profile/EmailAddressList.tsx`: a "Make primary" control on each verified
  secondary only. It opens an inline confirm in the shape of the existing `RemoveConfirm`, with
  copy from `emailCopy.ts`:
  "You'll sign in with {address} from now on. {current} stays on your account as a secondary address."
  When `previous` is null, the success notice says the old address was not kept.
  - The control is a real `<button>`, keyboard reachable, with an accessible name that includes the
    address. It meets the 44 px touch target at 375 px.
  - Use the existing `Button` tones and tokens only.
- The persona's cached email (the user store) updates at the next sign-in. The Emails list is the
  source of truth. Say so in a `Caveat:` above `makePrimary` in the store.
