# F-3b2 — make a verified secondary the primary address

r2: devil D-F-3b2s PROCEED-WITH-CONDITIONS; conditions C1-C12 and decisions 1-10 are folded in below (`target/review/D-F-3b2s/VERDICT.md` has the reasoning).

## Why (verified anchors)

- F-3b added, verified and removed secondary addresses. The primary is GoTrue's `email`, and changing
  it is not routed yet: `scripts/bridge-account-emails.mjs:16` says make-primary answers 404, and
  `ID_ROUTE`/`ACTIONS` (`:42,45`) know only `code` and `verify`.
- GoTrue facts, **measured** on the live funnel on 2026-10-24 with two throwaway users the probe
  deleted (`groot-wt/deploy/probe/gotrue-email-change.mjs`, logs `groot-wt/logs/probe-gotrue-email-change-*.log`).
  They match `internal/api/admin.go` v2.188.1, `adminUserUpdate` lines 141-260.
  `PUT /auth/v1/admin/users/{id}` with `{ email, email_confirm: true }`:
  - answers 200, sets `email` and `email_confirmed_at`, leaves no `new_email` pending, and sends no
    mail (that path has no mailer call);
  - updates the email identity's `identity_data.email`/`email_verified`, but only a re-read shows
    it, because the PUT response's `identities` are stale;
  - **keeps the sessions**: the old access token's getUser is 200, and the old refresh token
    returns 200 with a token carrying the new `email` claim;
  - makes sign-in with the old address 400 and with the new one 200;
  - answers **500 with code 23505** for an address another user holds, because the update path has
    no duplicate check (create has one, admin.go:351);
  - lower-cases an upper-case address.
- The admin flag is read by address hash, not by identity:
  `resolveAdminFlag` (`scripts/bridge-api.mjs:1694-1710`) PATCHes and reads
  `osionos_bridge_identities?email_hash=eq.<hash>`, using `limit=1` for the read. The table's key is
  `(provider, subject)`, with `UNIQUE (user_id)` (root `models/osionos-bridge-migration.sql:13-26`).
  `email_hash` has no other reader (`rg email_hash scripts/`).
  - **The hole once primaries can change:** admin A moves off address X, and A's row keeps
    `email_hash(X)` until A signs in again. If user B then makes X primary, B's sign-in reads A's
    row and becomes admin.
  - Live today: 78 identity rows, 2 admins, 0 duplicate hashes (read-only query, 2026-10-24).
- The pieces to reuse are in place:
  - `ownRow`, `guardMutation`, `primaryAddress` and `recordOf` (`scripts/bridge-account-email-flow.mjs`);
  - `isAvailable`'s inputs and `findAccountByEmail` (`scripts/bridge-gotrue-user.mjs:66`);
  - `gotrueAdminHeaders` (`:26`) and `readGotrueUser` (`:34`);
  - the rows API (`scripts/bridge-account-email-rows.mjs:101-128`).

## Contract

### Route

`POST /api/account/emails/:id/primary`, with no body. It goes through the router's existing
dispatch and `respondWithError`, and has its own budget (step 1). `ID_ROUTE` gains `primary`, `ACTIONS` gains
`primary: ['POST', makePrimary]`, and the header comment's line about make-primary answering 404
is replaced.

### `makePrimary` (new module `scripts/bridge-account-email-primary.mjs`, ≤150 lines)

`ownRow` and `primaryAddress` stay in `bridge-account-email-flow.mjs`. Export them there (additive),
and import them from the new module.

1. Before any read:
   - `guardMutation` (sudo first, then the keys check).
   - **Lock (C1):** `kv.setNx('email-primary:<uid>', <jti>, 60_000)`. A held lock → 409
     `primary_busy`, "Another change of your primary address is running." A kv failure → 503
     `email_unavailable` (fail closed). The lock is released with `kv.del` in `finally`. The TTL is
     above the worst path: lookup 5 s, read 8 s, PUT 8 s, re-read 8 s.
   - **Budget (C4):** `userBudget(ctx.kv, ['email-primary', uid], { limit: 5, windowMs: 600_000 })`
     from `bridge-account-email-send.mjs`. Over budget → 429.
2. `ownRow(ctx, session, id)` gives `{ row, address: S }`. `primary-<uid>` keeps its 409, and an
   unknown or foreign id keeps its 404.
   - `row.verified_at` null → 409 `email_unverified`, "Verify this address before making it primary."
3. Read the GoTrue user once with `readGotrueUser`. `P` is its `email`, trimmed and lower-cased, and
   `confirmedP` is whether `email_confirmed_at` is non-empty (C5). A read failure → 503.
   `S === P` → 409 `already_primary`.
4. **Refusals at promote time** (the add-time check is old by now). Each comes before any write:
   - `S` is in `ctx.config.adminEmails`, lower-cased → 409 `email_taken`, with the same code and copy
     as the other refusals (C6). The admin role must not be reachable through the account plane.
   - `findAccountByEmail(S)` returns an account whose `id !== userId`, confirmed or not (GoTrue's
     unique index refuses both) → 409 `email_taken`.
   - No account and `complete === false` → 503 `email_unavailable`. A lookup failure → 503.
   - **Sudo is spent (C3):** `kv.getDel('sudo:<jti>')`, then restored on any failure before the PUT,
     exactly as `bridge-account-password.mjs:131-134` does.
5. **Keep the old primary as a verified secondary**, only on evidence (C5): `P` is non-empty AND
   `confirmedP`. Otherwise `previous: null`.
   - `rows.verifiedByOther(userId, hmacOf(P))` is true → do not keep it, and answer `previous: null`.
   - Otherwise insert `P` already verified, through a new rows method
     `insertVerified(userId, address, atIso)`. It seals and hashes exactly as `insert` does and sets
     `verified_at`.
     - On `unique_violation`, reuse the caller's own row (marking it verified) when there is one.
       When there is none (another user verified `P` in between), answer `previous: null` and go on.
     - Remember whether this call CREATED the row, for compensation.
6. Audit `account.email_primary_requested`, with no addresses in `details`, BEFORE the GoTrue call.
   If it fails, the call fails, and nothing has changed in GoTrue.
7. GoTrue: a new `updateGotrueEmail({ config, fetchImpl }, userId, address)` in
   `bridge-gotrue-user.mjs` sends `PUT /auth/v1/admin/users/<encoded id>` with
   `{ email: address, email_confirm: true }` and `gotrueAdminHeaders`. It has `readGotrueUser`'s
   timeout and returns nothing on 2xx. It throws `{ code }` (C2):
   - `gotrue_email_taken`: a 500 whose JSON `code` or `error_code` is `23505`, or a 422 `email_exists`;
   - `gotrue_write_failed`: any other 4xx with a GoTrue JSON body, except 408 and 429;
   - `gotrue_write_unknown`: EVERYTHING else. That covers any 5xx including 502/503/504, a
     408/429, a non-JSON body, a network error and a timeout.
8. Outcome handling:
   - `gotrue_email_taken` → compensate, then 409 `email_taken`.
   - `gotrue_write_failed` → compensate, then 503 `email_unavailable`.
   - `gotrue_write_unknown` → re-read with `readGotrueUser` first:
     - its email equals `S` → continue as a success;
     - it equals `P` → compensate, then 503;
     - the re-read fails → no compensation, and 503. A kept `P` row is harmless; see the GET dedupe.
   - **Compensate** means delete the `P` row only when step 5 CREATED it.
9. Success:
   - `rows.remove(userId, row.id)` (the `S` row). A failure is logged by code only.
   - **End the other sign-ins (C3)** with the shared `endOtherSignIns` from
     `bridge-account-password.mjs`. Export it there (additive) and use reason `'logout_all'`, not a
     new enum value. When both revoke paths fail → 503 `email_changed_signout_failed`, with a message
     saying the address HAS changed. The answer carries `x-session-revoked: all` in the cut-off
     fallback, as the password change does.
   - Audit `account.email_primary_changed`, best effort (C7). A throw is logged by code and the
     answer stays 200.
   - Answer 200 `{ primary: <EmailRecord of S, isPrimary: true, verifiedAt: now>, previous: <id of the kept P row> | null }`.
10. An address added to `OSIONOS_ADMIN_EMAILS` AFTER it became someone's primary promotes that
    account at its next sign-in, as for any account. Say so in the module's `Caveat:`.

### GET dedupe

`GET /api/account/emails` drops a secondary whose opened address equals the primary. The case
arises after step 9's remove fails, or after an unknown outcome. Count it in `x-emails-skipped`,
like a row that does not open.

### Admin flag bound to the identity (in `bridge-api.mjs`, `resolveAdminFlag` only) (C8)

- The read and the promotion PATCH are both scoped by the identity key, with each value encoded by
  `encodeURIComponent`:
  - read: `osionos_bridge_identities?provider=eq.<p>&subject=eq.<s>&select=is_admin&limit=1`;
  - PATCH: `…?provider=eq.<p>&subject=eq.<s>&is_admin=is.false`, NOT scoped by `email_hash`.
- A missing or non-string provider or subject answers the env-only value without any request.
- Behaviour that stays the same: env-listed and verified → admin; DB-recorded admin with the env
  list empty → admin; any error → the env-only answer.
- Behaviour that changes on purpose: a DB-recorded admin whose address changed stays admin, and a
  refresh whose token carries a stale email still reads the admin row (`readRefreshClaims`). The row
  of a different subject never decides anyone's flag.
- Replace the Caveat text at `:1789-1791` (inside the comment block `:1782-1792`) with: the column
  `email_hash` is now written and never read; a DB admin stays admin across email changes.

  - The control is a real `<button>`, keyboard reachable, with an accessible name that includes the

  - Use the existing `Button` tones and tokens only.
