## Why

- **The app's button is half-finished: a user cannot create, label or make one do anything.** The
  slash menu can insert a `button` block (`src/features/slash-commands/model/slashMenuCatalog.tsx:282-291`,
  `blockType: "button"`), but the editable editor has **no `case "button"`**: the switch in
  `src/features/block-editor/ui/BlockEditor.tsx:456-1104` runs from `heading_1` to `home_views` and
  falls through to `default:` (`:1088-1103`), so in an editable page a button block renders as a plain
  editable paragraph. Only the read-only renderer draws a button
  (`src/entities/block/ui/ReadOnlyBlock.tsx:426-427` → `ButtonBlockReadOnly`, `:575-624`), and that one
  only navigates: `page://<id>` opens a page (`:583-605`), a `/…` href is an anchor (`:607-615`),
  anything else is a button that does nothing (`:617-623`).
- **Nothing in the app can write the button's own fields.** `buttonLabel` / `buttonHref` /
  `buttonVariant` are declared on `Block` (`src/entities/block/model/types.ts:160-162`) and are written
  in exactly two places: the seed helper (`src/data/seedBlockHelpers.ts:57-59`) and the Markdown
  serializer (`src/services/page-actions/pageMarkdownSerialize.ts:113-117`). There is no editor, no
  panel, no popover. The button is a rendering with no authoring surface.
- **The database already has a button, and it is a flat action list — not a program.** The submodule's
  `ButtonConfig` (`src/shared/notion-database-sys/packages/contract-types/src/index.ts:155-164`) carries
  `actions?: AutomationAction[]` (`:414-427`: `set_property`, `notify`, `webhook`, `open_url`,
  `add_page`) — a flat list with no branch, no loop and no variable. Its editor is
  `src/shared/notion-database-sys/src/components/ButtonEditorPanel.tsx:41-105` (label + at most 5
  actions, `:92`), its runner is `executeButtonActions`
  (`src/shared/notion-database-sys/src/lib/automations/actionExecutor.ts:33-67`) and its cell is
  `renderButton` (`src/shared/notion-database-sys/src/components/views/table/cellRenderers/SpecialCellRenderers.tsx:117-126`).
  **That tree is off-limits** (COMMON.md: never edit `src/shared/notion-database-sys/**`), so the program
  model is app-owned and *aligned* with that vocabulary — never a fork of it.
- **The formula VM is bridged and budgeted, and the app has no caller for it yet.**
  `initFormulaEngine` / `evalFormula` / `validateFormula` live in
  `src/shared/notion-database-sys/src/lib/engine/bridge.ts:72-94` / `:142-152` / `:199-207`; P4-2 landed
  the budget sentinel `FORMULA_BUDGET_EXCEEDED` (`:68`) and the pure mapping `surfaceEvalResult`
  (`:136-140`). `grep -rn "evalFormula\|validateFormula\|initFormulaEngine" src` outside the submodule
  returns **nothing**: the app never initialises the engine, so no app formula has ever been evaluated.
- **The app's own automations are keyboard macros, not programs.**
  `src/features/automations/model/types.ts:66-70` types a trigger as `{ type: "keyboard"; combo; when }`
  and an action as `{ type: "run_command"; commandId }` — a flat keyboard → command mapping with no
  condition over data and no steps. It is the wrong model to extend; do not touch it.
- **The page-action vocabulary exists and is the app's own.** `PAGE_ACTION_NAMES`
  (`src/services/page-actions/index.ts:33-51`) lists 17 actions (`copy_link`, `duplicate`,
  `move_to_trash`, `lock_page`, `notify_me`, `turn_into_dashboard`, …) and `PageActionName` is derived
  from that list so the runtime vocabulary and the type cannot drift (comment `:29-32`; derivation `:53`).
  `usePageActions` (`src/entities/page/model/usePageActions.ts:99`, body `:116-264`) is its runner: it
  snapshots a version before a write (`:174-177`), logs the action (`:166-172`) and pushes a toast (`:171`).
- **Permissions are the bridge's job, and the bridge already answers "refused" for a page write.**
  `PATCH /api/pages/:id` is handled by `handlePageUpdate` (`scripts/bridge-api.mjs:3612-3671`): the page
  must be readable (`requireReadablePage`, `:3620`), the caller must be the owner or a workspace member
  holding `update` (`ownerOrWorkspaceAccess`, `:3627` and `:1116-1123`), and ownership is re-checked
  (`:3628`). The client's own mapping of the answer is `publishResultFor`
  (`src/store/sync/publishResult.ts:23-28`): **403 → "refused"**, 404 → "gone", anything else →
  "failed". A program that writes must go through that route with the clicker's own token, so a
  reader's click can never escalate.

## Contract

### P4-3-a — a button that runs a program (do this one first)

**The model**

1. `Block` gains **one** optional field: `buttonProgram?: ButtonProgram`, declared next to the other
   button fields (`src/entities/block/model/types.ts:160-162`). The type lives in a new file
   `src/entities/block/model/buttonProgram.ts` — a block's own field type belongs to the block, and
   that file must import **nothing** (no `@/`, no `@notion-db/`) so a `tests/canvas` test can import it
   under plain node: the canvas loader mirrors the `@/` alias but not `@notion-db/contract-types`
   (`tests/canvas/ts-extension-loader.mjs:43-56`).
2. **The AST** (JSON, `version: 1`):
   - `ButtonProgram = { version: 1; steps: ProgramStep[] }`.
   - `ProgramStep` is one of:
     - `{ op: "set"; name: string; value: ProgramValue }`
     - `{ op: "if"; condition: ProgramValue; then: ProgramStep[]; else?: ProgramStep[] }`
     - `{ op: "repeat"; count: ProgramValue; steps: ProgramStep[] }`
     - `{ op: "forEach"; items: ProgramValue; as: string; steps: ProgramStep[] }`
     - `{ op: "action"; action: ProgramAction }`
   - `ProgramValue` is a JSON primitive (`string | number | boolean | null`) → a **literal**, or
     `{ formula: string }` → a **formula**. Anything else is invalid.
   - `ProgramAction` (P4-3-a) is `{ type: "notify"; message: ProgramValue }` or
     `{ type: "set_property"; property: string; value: ProgramValue }`. `notify` shows a toast;
     `set_property` sets a **property of the page that hosts the button** — the database's
     `set_property` acts on a *row* (`actionExecutor.ts:41-43`), do not confuse the two.
     **Unknown property:** `set_property` on a property that does not exist on the host page **creates**
     a new `PagePropertyEntry` with `key` = `property`, `label` = `property`, `value` = the resolved
     value (type inferred, defaulting to the value's own type) — the other properties are untouched.
     It never fails silently.
   - `parseButtonProgram(input: unknown): { ok: true; program: ButtonProgram } | { ok: false; error: { path: string; message: string } }`
     is **strict** and **total: it never throws** (a hand-edited `.omd` can carry a 10^6-deep object;
     recursive descent must return `{ok:false}` rather than blow the stack or let `JSON.parse` throw
     `RangeError`). An unknown `op`, a missing field, a wrong type or an unknown key is an error naming
     the path (`steps[1].then[0].op`). Limits: **depth ≤ 8** (checked **during** the descent, so a
     10^6-deep object is rejected without a crash), **nodes ≤ 500**, a formula ≤ 2 000 characters, a
     variable name ≤ 64 characters matching `/^[A-Za-z_][A-Za-z0-9_]*$/`, **every string value ≤ 2 000
     characters**, and **total serialized program ≤ 64 KB**. `version` must be
     `1`; another version is an error, never a silent default.
3. **Persistence.** The page-file codec's self-check fails on a field that is in none of its three lists
   (`src/features/page-file/model/pageFileCodec.ts:76-84`; enforcement is the canvas test
   `tests/canvas/page-file-codec.test.ts:189-198` over `blockFieldNames()`,
   `tests/canvas/page-file-codec-fixtures.ts:154-162` regex-reads `types.ts`), so `buttonProgram` must be
   classified: it rides the **overlay** (Markdown cannot carry a program) — add `buttonProgram: isPlainRecord`
   to `EXTRA_BLOCK_KEYS` (`src/features/page-file/model/blockOverlay.ts:58-91`, the `isPlainRecord` check at
   `:45-51`) and update the comment that lists the overlay keys (`pageFileCodec.ts:47-52`).
   `MARKDOWN_KEYS` (`:59-65`) does not change — `buttonLabel` / `buttonHref` / `buttonVariant` stay
   Markdown-carried.
   `Caveat:` the overlay's checks are shallow (a plain object, nothing more — `blockOverlay.ts:45-51`), so
   a hand-edited `.omd` can carry any object under `buttonProgram`. The parser is the only real gate, and
   it runs on every click.

**The interpreter** — `src/services/button-program/interpreter.ts` (new, pure)

4. `runButtonProgram(program, ctx): Promise<ProgramRunResult>` is the only exported entry point. `ctx`
   carries:
   - `props: PropertyMap` — the formula context (`key → value`, `bridgeTypes.ts:48`); the interpreter
     defines its own `PropertyMap = Record<string, unknown>` (or a type-only import) and **must not
     value-import `bridgeTypes.ts`**, so the canvas runner's import graph holds no
     `notion-database-sys` path;
   - `evaluateFormula(formula: string, props: PropertyMap): unknown` — **injected**; the interpreter
     never imports the engine, so it is unit-testable without the wasm (the wasm is `--target web` and
     cannot load under node — the reason P4-2 made the mapping a pure function, `bridge.ts:136-140`);
   - `runAction(action: ProgramAction, scope: ProgramScope): Promise<ActionOutcome>` — **injected**;
   - `runPageAction(name: string, …)` — **injected** (P4-3-c), bound to the **host** page's id, running
     one of `PAGE_ACTION_NAMES` through `usePageActions` (`usePageActions(pageId, workspaceId)` at
     `:99`, body `:116-264`); the name→callback map (17 names; `translate` needs a locale,
     `export`/`import`/`version_history` open UI) lives in `usePageActions.ts`, which P4-3-c owns;
   - `now(): number` — injected, so the wall-clock budget is testable;
   - `limits?: Partial<ProgramLimits>` — the defaults in item 5.
5. **Budgets** (`ProgramLimits`; the defaults are fixed by the plan, the overrides exist for the tests):
   - `maxSteps: 10_000` — every step **entered**; a step inside a loop body counts on every iteration;
     the loop step itself counts once when the loop is entered. Pinning: `repeat 1000 { notify }` costs
     1 (the repeat) + 1000 (the notify) = 1001 steps;
   - `maxIterations: 1_000` — **per loop site, shared across all instances** of that `repeat`/`forEach`
     (so `repeat(1000){ repeat(1000){} }` cannot run 10^6 iterations of an empty body);
   - `maxSideEffects: 50` — side-effecting actions only (`set_property`; a `notify` is **not**
     side-effecting — it changes no data);
   - `maxNotifies: 50` — per run (D3: notify is not a side effect but gets its own cap);
   - `maxWallMs: 2_000` — a **detection** budget: checked before every step **and** at every loop
     iteration (empty bodies included); it cannot abort an in-flight PATCH, so the real bound on writes
     is `maxSideEffects` (50).
   A budget stop **ends the run** (fail-closed): the remaining steps do not run, the log records the
   limit's name (`steps` / `iterations` / `side_effects` / `wall_time` / `notifies`) and the result is
   `{ ok: false, stoppedBy: "budget", limit, log }`. A budget stop is never a silent truncation.
   **`forEach` over more items than the cap is a budget stop, not a truncation**: a formula may return
   an array of any size, so a for-each over 1 500 items ends the run with `limit:"iterations"` and
   records how many items were not visited.
6. **Evaluation.**
   - The two engine sentinels are **not** values: `FORMULA_ENGINE_UNAVAILABLE` (`bridge.ts:59`) and
     `FORMULA_BUDGET_EXCEEDED` (`bridge.ts:68`).
   - A **condition** that evaluates to a sentinel is **false** (fail closed) and the log records
     `formula_unavailable` / `formula_budget_exceeded`.
   - A **value** that evaluates to a sentinel makes the step **fail**: the step is skipped, nothing is
     written, the log records the reason. `#BUDGET_EXCEEDED` must never land in a page property.
   - Truthiness of a condition: `false`, `0`, `""` and `null` are false, everything else is true (a
     non-empty string is true even when it reads `"false"`).
   - The formula context is the **host page's own properties**, as `key → value` from
     `PageEntry.properties` (`src/entities/page/model/types.ts:41-48`) — the same shape the header
     slots read (`src/pages/notion-page/model/headerBinding.ts:19-27`). A variable set by a `set` step
     shadows a property of the same name for the rest of the run. The context is **never** the property
     entry: passing the entry would make `toJsonValue` render `"[object Object]"` (`bridgeTypes.ts:50-57`).
     It exposes **properties only** — no title, no clicking user (D2).
   - Variable scope is **flat**, except a for-each binding: a `set` shadows a property for the rest of
     the run; a `forEach`'s `as` binding lives and dies with the loop body (D8).
7. **The run log.** `ProgramRunResult.log` is an ordered array of
   `{ index, op, label, status, detail? }`, `status` ∈ `ok | skipped | failed | blocked | cancelled`,
   `label` a short human phrase ("Set `x`", "If", "Repeat ×3", "Notify"). The log holds **at most 200
   entries**; past that the run keeps going but the log stops growing and its last entry says `truncated`
   — the log is a view, not a budget. `Caveat:` the log lives in memory for the run only; a reload loses
   it.
8. **The app wiring** — `src/services/button-program/runProgram.ts` (new), the only module that touches
   the engine and the network:
   - it calls `initFormulaEngine()` once (`bridge.ts:72-94`) before the first formula and passes
     `evalFormula` (`:142-152`) as `evaluateFormula`;
   - **one write path, not two**: it does **not** open its own `api.patch`; it reuses the house path
     `publishPage` (`src/store/sync/pageOutbox.ts:62-69`), which patches `/api/pages/:id` with the
     clicker's page JWT and maps the answer through `publishResultFor`
     (`src/store/sync/publishResult.ts:23-28`). A refused write leaves no pending outbox entry.
   - `set_property` **merges, never replaces**: it reads the host page's full `properties` array,
     substitutes the one key, and writes the full array back. The bridge assigns the column wholesale —
     `assignPayloadValue(row, payload, 'properties', 'properties', (value) => safeJsonArray(value))`
     (`scripts/bridge-api.mjs:865`) — and `safeJsonArray` maps a non-array to `[]`
     (`scripts/bridge-api.mjs:310-312`); locally `applyPagePatch` is a shallow spread
     (`src/store/usePageStore.ts:107-113`), so a partial body wipes the other properties too. Criterion:
     a page with three properties, a program setting one → the other two survive in the PATCH body and
     in the store.
   - before writing, it takes a **version snapshot first**, like every house page write
     (`src/entities/page/model/usePageActions.ts:174-177`); program writes are versioned, not unversioned.
   - the answer is mapped with the app's own mapping (`publishResultFor`,
     `src/store/sync/publishResult.ts:23-28`): `ok` → patch the local page (`patchPage`,
     `src/store/usePageStore.ts:370-375`) and log `ok`; **`refused` (403) → log `blocked` and write
     nothing, not even locally**; `gone` (404) → `failed`; anything else → `failed`.
   - `notify` pushes a toast through the app's toast store
     (`packages/osionos-ui/src/primitives/useToastStore.ts:37-50`, `push` `:39-43`).
   - **Result seam (D10):** the run result is held in a last-run holder inside `runProgram.ts` (owned)
     or a React context in the new `src/features/button-program/` folder, which P4-3-b's OWNS must name,
     so P4-3-b's popover (a separate tree; `src/store/**` is off-limits) can read it. Criterion: the
     e2e clicks the button, opens the popover, sees the log.
9. **The button runs the program.**
   - `ButtonBlockReadOnly` (`src/entities/block/ui/ReadOnlyBlock.tsx:575-624`) gains: when
     `block.buttonProgram` is present **and parses**, a click runs the program and `buttonHref` is
     ignored (the program is the button's behaviour). A block with no program keeps today's behaviour
     unchanged.
   - The editable editor gains `case "button":` in `src/features/block-editor/ui/BlockEditor.tsx` (the
     switch at `:456-1104`): the block renders as a button (the same classes as `BUTTON_BASE_CLASS`,
     `ReadOnlyBlock.tsx:556-563`), the label comes from `buttonLabel` (falling back to `content`, `:576`),
     and a click runs the program. The label is **not** editable in P4-3-a — that is P4-3-b's popover.
     Say so in the final report. **P4-3-a ships no authoring surface** (D9): a program can only be
     seeded, as the e2e already does.
   - A **locked** page renders its blocks read-only
     (`src/features/block-editor/ui/BlockEditorSurface.tsx:695-703`), so its buttons run too — with the
     reader's own permissions. **The lock is not a write barrier** (D17): `handlePageUpdate`
     (`scripts/bridge-api.mjs:3612-3671`) has no locked check, so a program on a locked page can still
     write.
   - A program that fails to parse never runs: the click shows one toast ("This button's program is
     invalid") and the block behaves as the plain button (no navigation).
   - **Re-entrancy:** a second click while a run is in flight, or a confirmation pending, is ignored —
     otherwise two runs double every budget (2 × 50 writes) and two logs interleave. Criterion: a
     double click calls the action handler once.
10. **Security edge — who may call what, and what a non-owner sees.**
    - The program runs **in the clicker's browser**, from the page's own content. It is never sent to
      the server as code and never evaluated there.
    - Every write goes out with the **clicker's own page JWT** (`getActivePageJwt`), and the bridge
      decides: `handlePageUpdate` requires the page to be readable and the caller to be the owner or a
      workspace member holding `update` (`scripts/bridge-api.mjs:3620-3628`). A reader without `update`
      gets 403 → the log says `blocked` and **nothing is written, not even locally** (tested: `patchPage`
      refuses when `!canEditPage(page, getCurrentPageAccessContext())`,
      `src/store/usePageStore.ts:370-371`; bridge answers 403 → `refused`,
      `src/store/sync/publishResult.ts:25-28`, `scripts/bridge-api.mjs:3620-3628`).
    - A non-owner sees the button, its label and the program source (it is page content, like any
      block). They see **no** other page's data: a program can only read the host page's own properties,
      which every reader of the page already sees (`PageEntry.properties` has no per-property ACL,
      `src/entities/page/model/types.ts:41-48`).
    - A viewer can **run** the program; they cannot widen their own rights, because the bridge — not the
      program — decides every write. `Caveat:` the program decides *what to attempt*; a program written
      by an owner can ask a reader to attempt a write the reader may not do. The answer is `blocked`,
      never a silent success.
    - `set_property` writes a property **of the host page**. A program that targets another page is not
      expressible in P4-3-a (the action has no target field) — say so; a target is P4-3-c.
    - No `webhook` and no `add_page` in P4-3-a: a webhook would let a page author make every reader fire
      an outbound request, and `add_page` needs the database store context. Both are P4-3-c.

### P4-3-c — destructive steps, the database action executor, the page actions

16. **Destructive steps ask for confirmation.** A step is destructive when its action is in a fixed
    list: the page actions that change the page's state (`move_to_trash`, `lock_page` —
    `PAGE_ACTION_NAMES`, `src/services/page-actions/index.ts:33-51`) and a row deletion. The check is
    by **resolved action name, not action type**: `type === "page_action" && DESTRUCTIVE.has(name)`
    (the carrier is `{type:"page_action", name:"move_to_trash"}`); a type-only check never fires.
    The destructive set must be **total over `PAGE_ACTION_NAMES`** (17 names): every name classified
    destructive-or-not, and a name added later fails the test until classified. Before running one, the
    program **pauses** and asks with a `ConfirmDialog`
    (`packages/osionos-ui/src/index.ts:28`), naming the action. "Cancel" **aborts the run**: the log
    records `cancelled` and the remaining steps do not run. The confirmation is **per run**, not per
    program: every destructive step asks again. The confirmation lives in the **app wiring**
    (`runProgram.ts`), never in the pure interpreter: the interpreter's `runAction` simply receives
    the answer. A destructive step nested in an `if.then` or inside a for-each body still asks, and
    the dialog names the action.
17. **The database action executor.** When the button runs inside a **database row**, the row's actions
    are executed by the submodule's `executeButtonActions`
    (`src/shared/notion-database-sys/src/lib/automations/actionExecutor.ts:33-67`) — the app **calls** it
    and never edits it. It needs `ButtonActionContext` = `{ storeApi, page, databaseId }` (`:25-29`).
    Find where the app holds the object-database store API and the row context; if a record page cannot
    carry that context, say so in the final report and ship the page-scoped actions only (D5). **Do not
    build a parallel executor.**
18. **The page actions.** A `{ type: "page_action"; name: string }` step runs one of
    `PAGE_ACTION_NAMES` through `usePageActions` (`src/entities/page/model/usePageActions.ts:99`, body
    `:116-264`) — **injected**, not called from the module (condition 15). The name is validated
    against the list at runtime (the AST keeps `name: string`, so the block model does not import the
    service and the two cannot drift silently); an unknown name is a `failed` step, never a silent
    no-op. A page action that writes takes the version snapshot first (`snapshot`, `:174-177`) and

    page-action log**.
19. **Security edge.** A page action runs **as the clicker**: `move_to_trash` archives the page through
    the bridge (`archivePage`, `:211-217`) and the bridge's own rule applies. `Caveat:` the page-action
    runner writes one version per action, so a program that loops over page actions writes one version
    per action — bounded by the 50-action budget.

## Decisions (D-P4-3s)

- **D1 — The `/button` route: popover only.** A workbench tab needs `TabKind`
  (`src/widgets/workspace-grid/model/layoutTree.ts:14`), a tab factory
  (`src/widgets/workspace-grid/model/layoutPersist.ts:63-137`), the pane dispatch
  (`src/widgets/page-renderer/ui/PaneContent.tsx:78`) and a lazy view
  (`src/widgets/page-renderer/ui/lazyViews.tsx`) — none in P4-3-b's OWNS, so a tab is impossible in this
  package; it is a later package owning those four files.
- **D2 — The formula context: the host page's properties only.** No title, no clicking user in P4-3-a:
  least privilege, and no P4-3-a action needs either; the map is one line (`bridgeTypes.ts:48`) if ever
  wanted.
- **D3 — `notify` is not a side effect, but it gets its own cap.** A toast changes no data, so it stays
  out of `maxSideEffects`; but a program must not bury a reader's screen → add `maxNotifies: 50` per run.
- **D4 — Two budgets, two scopes: confirmed.** The host budgets are per run, the VM's fuel per evaluation
  (`bridge.ts:68`'s caveat), the 2 s wall the real bound — provided it is checked at every step *and*
  every iteration (condition 9).
- **D5 — A record-page button and the database executor: P4-3-c ships the page-scoped actions only.**
  `executeButtonActions` needs `{storeApi, page, databaseId}`
  (`src/shared/notion-database-sys/src/lib/automations/actionExecutor.ts:25-29`) and the app holds no
  `DatabaseStoreApi` for a mounted record page; that context is not established, so it is out of scope
  and the report says so (`P4-3.md:431-434` already plans this).
- **D6 — `add_page` and `webhook` stay out of P4-3-a.** A webhook may only arrive with a server-side
  SSRF allowlist and per-run consent — a page author must never make every reader fire an outbound
  request; `add_page` waits for the database store context of D5.
- **D7 — The write path is the house path.** One function writes a page (`publishPage`,
  `src/store/sync/pageOutbox.ts:62`); the spec's own `api.patch` is dropped (condition 2), with the
  merged full `properties` array (condition 1) and a version snapshot (condition 3).
- **D8 — Variable scope is flat, except a for-each binding.** A `set` shadows a property for the rest of
  the run (`P4-3.md:145-146`); a `forEach`'s `as` binding lives and dies with the loop body. The spec
  does not say this today.
- **D9 — The step editor is the only authoring surface, so P4-3-a has none.** Item 12 removes "P4-3-a's
  JSON textarea" (`P4-3.md:222-223`), but no P4-3-a file in OWNS hosts one — so the slice billed as "a
  button that runs a program" (`P4-3.md:13-16`) ships no way to author one. P4-3-a must add that file
  to its OWNS or say in the report that a program can only be seeded (as the e2e already does,
  `P4-3.md:293-297`).
- **D10 — The run result needs a seam P4-3-b can read.** P4-3-a holds the result in the button
  component's state and P4-3-b's popover is another tree, while `src/store/**` is off-limits
  (`P4-3.md:394`): name the seam — a last-run holder inside `runProgram.ts` (owned) or a React context
  in the new `src/features/button-program/` folder, which P4-3-b's OWNS must then name. *Criterion:* the
  e2e clicks the button, opens the popover, sees the log.
