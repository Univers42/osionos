# P1-2s 👹 — one atomic username change, the only path that writes a username

Repo: **root groot**, branch `feat/acct-P1-2s` from root `feat/account-platform` **after P1-1
merges** (it builds on P1-1's profiles, history, hold triggers and legacy sync trigger). SQL and
its checks only. App P1-2b calls it. Origin: devil spec review D-P1-2b, finding F4 (2026-10-22).

## Why
- After P1-1 a username lives in two tables: `osionos_profiles.username` (typed, held 90 days by
  `osionos_username_history`) and the legacy `osionos_bridge_identities.username`. Chat mentions
  (`scripts/bridge-chat.mjs:294`) and the IDE sandbox user (`scripts/ide-username.mjs:64`) read the
  legacy one.
- The bridge cannot update both atomically. PostgREST gives one statement per request, and P1-1's
  legacy sync trigger copies identities → profiles on any `UPDATE OF profile, username,
  directory_opt_out` and never raises. A half-done change (profile written, identity not) is
  undone by the next legacy profile write.
- P1-1 grants the account role UPDATE on `osionos_profiles.username`, which lets a direct PATCH
  skip the sudo gate P1-2b adds.

## Contract — `models/osionos-account-username-migration.sql` (new; `ORDERED_LAST` right after P1-1's file)
The file follows P0-1's and P1-1's conventions: `BEGIN;`, the superuser guard, `SET LOCAL
lock_timeout = '5s'` with its Caveat, then `COMMIT;` and `NOTIFY pgrst, 'reload schema';`.

1. `public.osionos_account_change_username(p_username text) RETURNS text`
   - `LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public SET lock_timeout = '3s'`,
     owned by the migration's superuser. The migration's `SET LOCAL lock_timeout` covers only the
     migration transaction; a call through PostgREST inherits a session with none (D-P1-2s3), so a
     call blocked by a boot replay would hold a pool connection for the replay's whole run. With the
     attribute it fails `55P03` after 3 s instead; P1-2b maps that to 503 with `Retry-After`. The
     comment carries a `Caveat:` saying so.
   - **The caller, without `osionos_account_uid()`.** That function requires
     `current_user = 'osionos_account_user'` (root `models/osionos-account-foundation-migration.sql:145-154`),
     and inside a SECURITY DEFINER function `current_user` is the owner, so it would always return
     NULL (D-P1-2b2 #1).
     - Read `NULLIF(current_setting('request.jwt.claims', true), '')::jsonb` and apply the merged
       helper's claim expression verbatim (root `models/osionos-account-foundation-migration.sql:147-152`):
       `role = 'osionos_account_user'`, `aud = 'osionos-account'` as a string (an array `aud` is
       refused), and the lowercase-UUID regex on `sub` **before** the `::uuid` cast, so a malformed
       `sub` is 42501, never 22P02. D-P1-2s3 measured that `current_setting` does return the
       caller's claims inside SECURITY DEFINER under PostgREST's `SET LOCAL`.
     - The EXECUTE grant (item 2: the account role only) takes the place of the `current_user`
       test. Say so in a comment.
     - Any check failing → ERRCODE `42501`.
   - **Validation, before any lock:** `p_username` NULL, not matching
     `^[A-Za-z0-9_][A-Za-z0-9_.-]{2,31}$`, or `osionos_username_reserved(p_username)` → ERRCODE
     `22023`, a message naming the rule.
   - **Lock order: sign-in's order, identities then profile** (P1-1 §Locks). First
     `SELECT … FROM osionos_bridge_identities WHERE user_id = uid FOR UPDATE`, then
     `SELECT username FROM osionos_profiles WHERE user_id = uid FOR UPDATE`.
     - No profile row → ERRCODE `P0002`.
     - No identities row is allowed: nothing legacy to keep in step. Skip the identities update
       and say so in a comment.
   - **Same name:** `p_username` equal (exact case) to the current profile name → return it,
     writing nothing.
   - **Writes, identities first.** A table lock is taken by the first statement that writes, and a
     boot replay takes `SHARE ROW EXCLUSIVE` on `osionos_bridge_identities` (P1-1 file :80) before
     `osionos_profiles` (:246). D-P1-2s3 measured profile-first against the replay: `40P01`.
     Identities-first finished clean.
     - First `UPDATE osionos_bridge_identities SET username = p_username WHERE user_id = uid`
       (skipped when there is no identities row). Its unique index (`osionos_identities_username_uidx`,
       `models/osionos-social-migration.sql:30`) raises 23505 for a name another identity still
       holds from before P1-1; let it propagate.
     - The legacy sync trigger (`osionos_profile_from_identity`) fires on that UPDATE and tries to
       copy the name into the profile. It swallows its own errors (`EXCEPTION WHEN others` → WARNING,
       P1-1 file :568-570), so a held or taken name is not refused there.
     - Then `UPDATE osionos_profiles SET username = p_username WHERE user_id = uid AND username IS
       DISTINCT FROM p_username`. When the trigger already copied the name it changes nothing; when
       the trigger's copy was refused, P1-1's hold and unique-index rules raise 23505 here, and the
       whole call rolls back, identities included. That is the point.
     - As merged after R1-R3, the trigger copies only the identity columns that changed and skips an
       UPDATE that would change nothing, so the call writes one history row, bumps `version` once and
       copies no legacy `headline`/`bio`/`location` over typed values. D-P1-2s3 measured all three on
       the merged code. Checks 1, 2, 8 and 9 prove it on the new order; if any fails, stop and report
       rather than editing P1-1's trigger.
   - **A case-only rename** (`Bob` → `bob`) is a real change. It writes, and the history row P1-1's
     capture trigger records for `Bob` is harmless: the owner may reclaim it, and the
     `lower(username)` index already keeps others off it. Check 10.
   - Returns `p_username`.
2. **Grants:** `REVOKE EXECUTE … FROM PUBLIC`; `GRANT EXECUTE … TO osionos_account_user` only.
   `checks.sql`'s `secdef_exec` (anon and authenticated) stays 0. `account-checks.sql`'s
   `account_secdef_exec` (:10-18) counts every SECURITY DEFINER `osionos_%` function the account
   role may execute and turns 1 with this one (measured). Exempt exactly
   `osionos_account_change_username(text)` by signature, with a comment saying why it is the one
   SECURITY DEFINER function the role may call (it re-checks the claims itself and writes only the
   caller's rows). Any other function must still count.
3. `REVOKE UPDATE (username) ON public.osionos_profiles FROM osionos_account_user`. The function is
   now the only way the role can change a username. That revoke turns two P1-1 checks red (both
   measured by D-P1-2s3); update both in the same commit and say so:
   - `p1_role_column_acl`: drop `('osionos_profiles','username','UPDATE')` from the expected VALUES
     (:237).
   - `p1_hold` (:319-367): its B-refused and A-reclaims statements run as the role with a direct
     UPDATE, which now fails 42501 for both — B's refusal would pass for the wrong reason. Route both
     through `osionos_account_change_username`, and test the SQLSTATE, not `WHEN others`: B gets
     23505, A succeeds.

   Those three (`account_secdef_exec`, `p1_role_column_acl`, `p1_hold`) are the only existing rows
   this package may change.
4. `public.users.username` (the gateway's registration-time copy) is not touched. Say so in a
   comment: P1-1 reads it only at registration and backfill.
5. **"The only path" has a boundary; state it in the function's comment.** The legacy
   `PATCH /api/profile/me` still writes the identity row's `username` as the service role (app
   `scripts/bridge-profile.mjs:193,196`), and the sync trigger copies it into the profile without the
   sudo gate. The guarantee holds once P1-2b's contract 7 refuses `username` on that route.

## Checks (append to `scripts/verify/models-grants/account-checks.sql` before k5/k6)
Every check runs as the role with forged claims in a rolled-back transaction, never as postgres.
Every sample name is a valid one (3-32 characters, `^[A-Za-z0-9_][A-Za-z0-9_.-]{2,31}$`); a short
name is refused as a format error (22023) before any lock and would prove nothing.
1. `p2s_change` = 0: A changes `alice1` → `bobby1`. Both tables then say `bobby1`, exactly one history row
   holds `alice1` for A, and `version` moved by one.
2. `p2s_history_once` = 0: after check 1's change there is exactly one new history row (the legacy
   sync trigger added none).
3. `p2s_atomic` = 0: B's identity holds `taken1` with B's profile name NULL (the pre-P1-1 collision
   state). A's change to `taken1` raises 23505 (not 22023), and afterwards A's profile row, A's
   identity row and A's history rows are identical to before (compare `to_jsonb` of each).
4. `p2s_hold` = 0: B cannot take A's released-in-the-future `alice1` (23505); A can take `alice1` back.
5. `p2s_invalid` = 0: `'ab'`, `'admin'`, `'-x1'` and NULL each raise 22023.
6. `p2s_no_direct` = 0: the role's `UPDATE osionos_profiles SET username = 'zelda1'` fails 42501.
7. `p2s_no_uid` = 0: each of these → 42501, never 22P02: no claims; `aud` ≠ `osionos-account`;
   `aud` as an array `["osionos-account"]`; an upper-case `sub`; a malformed `sub` (`not-a-uuid`).
8. `p2s_version_once` = 0: after one change, `version` moved by exactly 1.
9. `p2s_keeps_typed_fields` = 0: A's typed `bio` differs from A's legacy `identities.profile->>'bio'`.
   After a username change, the typed `bio` (and `headline`, `location`) is unchanged.
10. `p2s_case` = 0: `Bob` → `bob` succeeds and `version` moves by 1. B cannot take `Bob`. A can
    take `Bob` back.
11. `p2s_no_identity` = 0: a user with a profile and no identities row can change their name.
