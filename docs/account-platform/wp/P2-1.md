## Why
- The public profile page (`/u/<username>`) does not exist. `ProfilePageView.tsx:31-51` renders an admin-authored template bound to a member row, but it is reachable only through the tab system (kind="profile" in `PaneContent.tsx:114-124`), not a public URL. The bridge has `GET /api/users/:username` (`scripts/bridge-account-profile.mjs:248-274`) which returns the allowlisted public card, but nothing renders it at a public path.
- The README page per user does not exist. P1-1's `osionos_profiles` has no `readme_page_id` column (P1-1.md:23 explicitly scopes it out to P2-1). The owner needs a "Customize" action that creates the page lazily on first edit and binds it to the profile via `readme_page_id` written through P1-2a's `PATCH /api/account/profile` with If-Match.
- `ProfileActions` in `profileChrome.tsx:28-32` returns `null` for the owner — no "Edit" or "Customize" entry exists. P1-6-c item 3 adds "Edit profile" (deep-link to Settings → public-profile), but "Customize README" is new here.
- The layout store has no router; deep-linking uses URL params like `?home=` (HomeTabView.tsx:28, `homeVariantStore.ts:28`). The profile page must open as a pane tab via a param (e.g., `?view=profile&user=<username>`).
- Reuse: `widgets/profile-page/**` (ProfilePageView, ProfileView, binding, useProfile), `pageToTab.ts` (tab descriptors), `PaneContent.tsx` (tab rendering), `PageBlocksRenderer.tsx` (read-only blocks), `scripts/bridge-account-profile.mjs` (profile routes), P1-6-c's profile page work (merged/in-flight on feat/account-platform), P2-4's profile-template binding (the profession surface).

## Open questions
1. **Which workspace holds the README page?** The owner's private workspace? A dedicated "profile" workspace? The page must be in a workspace the owner can write to and the public viewer can read (via the template's block reference). If the template renders the README blocks directly (not via a link), the page content is copied into the template at render time — no cross-workspace read needed. Clarify: does `ReadmeBlocks` read the page at render time (needs read access) or is the README content embedded in the template at authoring time? The spec says "a canvas or full-page layout with a header band above the README blocks" — this suggests the template *includes* the README blocks. If so, the README page is only for editing; the profile page reads its blocks directly at render time. The page can live in the owner's private workspace; the profile page (rendered by the viewer) fetches the blocks via the service role (template resolution is service-role). Confirm the template resolution path: `useTemplateForSurface` → `findSurfaceTemplate` → `fetchPageContent` (service role). So the template page is read by service role; the README page blocks are read by the same service role when the template renders them. The README page can be in any workspace the service role can read (all of them). Simplest: create it in the owner's first private workspace.
2. **Does the README page need a special surface type?** No — it's a normal `surface: "page"`. The "Customize" action opens it in the block editor like any page.
3. **What if the admin template doesn't include a README block?** The profile page falls back to `ProfileView` (built-in) when no template exists (`ProfilePageView.tsx:38-40`). If a template exists but has no README block, the README is simply not shown — that's a template authoring choice, not a code concern.
4. **The `?view=profile&user=<username>` param:** does it conflict with existing `?view=` (which deep-links a database view id in `PaneContent.tsx:96`)? The existing `?view=` is read inside `HomeTabView` and database views. A top-level param in `App.tsx` that opens a tab before the home view mounts avoids collision. Implement in `App.tsx` effect after layout restore.

## Orchestrator rulings (2026-10-23). These override the draft above wherever they differ.
1. **README content for other viewers is a server projection.** `GET /api/users/:username` returns `readme: { pageId, blocks }`. It is read through the service role for exactly `readme_page_id`, and only when that page's `owner_id` equals the profile's user and the page is neither archived nor trashed. Blocks are capped at 200 KB serialized; over the cap the response is `readme: { pageId, truncated: true }`. A reduced card (blocked or opted-out viewer) never carries `readme`. The client renders it with `PageBlocksRenderer` (`ReadmeBlocks.tsx`). The viewer never reads the page itself. This answers open question 1.
2. **Deep link is `?u=<username>`, not `?view=profile`.** `?view=` already carries database view ids. A `/u/<username>` path is a follow-up: it needs an SPA fallback on the proxy.
3. **The README page** is created in a workspace the owner owns: the active workspace when `owner_id` = the user, otherwise the first workspace they own. Title "README", surface `page`. Creation is lazy, on the first "Customize".
4. **Sub-packages:**
   - **P2-1-a (root):** `readme_page_id` column, grants, and the models-grants checks.
   - **P2-1-b (app, bridge):** owner columns, the PATCH, the public `readme` projection, and their bridge tests.
   - **P2-1-c (app, UI):** `?u=`, the data-source switch, `ReadmeBlocks`, the owner's "Customize" and "Edit profile", canvas and e2e.
   - Old P2-1-d is folded into c. I check the visuals in a browser.
   - Order: a → b → c, and c only after P1-6-c merges, because P1-6-c owns the "Edit profile" button and the saved-profile render.
5. **Route names** follow the code as it is now: use whichever of `PATCH /api/profile/me` and `PATCH /api/account/profile` P1-2a mounted. Don't add the other.
