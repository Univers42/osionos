## Why

*Every claim below was opened on the two trees named above.*

- **The blocked-users panel exists, but it is unreachable and it lies.**
  - The only blocked-users panel is `src/features/settings/social/BlockedUsersPanel.tsx:20-49`, stacked
    inside the Contacts section (`src/features/settings/social/SocialSettings.tsx:21-26`). The `contacts`
    registry entry has **`anchors: []`** (`src/features/settings/model/sections.ts:140-145`), so the panel
    has no anchor id: the settings search cannot find it and `?settings=contacts#blocked-users` has
    nothing to scroll to. The plan asks for a "Blocked users settings panel"; there is a list, in a
    section that cannot be searched.
  - It renders three states, not four (`BlockedUsersPanel.tsx:29-45`: loading, empty, loaded). The store
    keeps an `error` (`src/store/social/useBlocksStore.ts:23`) that the panel never reads, so a failed
    list renders "You haven't blocked anyone." — a false statement about a list the server refused to
    send. The only trace is a toast (`useBlocksStore.ts:44`).
  - After a block, the panel shows a raw user id. The client reads `reply.block`
    (`src/shared/social/blockApi.ts:27-30`) but the route answers `{ ok: true, userId, blocked: true }`
    (`scripts/bridge-social.mjs:287`) — there is no `block` key, so `blockUser` always resolves `null`,
    the store keeps its optimistic row (`useBlocksStore.ts:47-57`), and the panel prints
    `blocked.name ?? blocked.userId` (`BlockedUsersPanel.tsx:38`) — the UUID.
  - The unblock leaves a "blocked" connection behind. The block route sets the pair's connection to
    `status: 'blocked'` (`scripts/bridge-social.mjs:281-286`); the unblock route deletes only the block
    row (`scripts/bridge-social.mjs:289-294`). Afterwards `GET /api/connections` reports that pair with
    `status: 'blocked'` (`scripts/bridge-social.mjs:118-133` returns every edge) while the block list no
    longer has them. The app's store hides the contradiction (`src/store/social/useContactsStore.ts:43-48`
    keeps only `accepted`/`pending`), so it is visible only through the API.
- **Nothing enforces anything about who may reach you.** There is no moderation table, no policy row and
  no route:
  - the root SQL has no such table — the only per-user policy store is `osionos_user_settings`
    (`/home/dlesieur/Documents/groot-wt/root-integration/models/osionos-account-profiles-migration.sql:214-222`);
  - the bridge exposes exactly two settings sections (`scripts/bridge-preferences.mjs:36-39`);
  - a DM is opened for anybody (`scripts/bridge-chat.mjs:461-463` checks only the block list), a
    connection request is sent to anybody (`scripts/bridge-social.mjs:138-147` checks only the block
    list), and a comment lands on anybody's page (`scripts/bridge-comments.mjs:47-56` checks only page
    read access).
  - Nothing named "moderation" exists in `src/` or `scripts/` at all.
- **The storage for a limit already exists and is unused.** `osionos_user_settings` is keyed by
  `(user_id, section)` with a section-name CHECK `^[a-z][a-z0-9_-]{0,31}$`
  (`models/osionos-account-profiles-migration.sql:214-222`); the account role may read and write only its

  `osionos_user_settings_merge` (`:311-334`) merges a patch in one statement, so two writes to one

  entry in the bridge's section map.
- **The block-awareness that does exist is one helper, used in five places.** `blockedViewerBy`
  (`scripts/bridge-social-core.mjs:186-199`) hides a peer from the directory search
  (`scripts/bridge-social.mjs:75`, `scripts/bridge-profile.mjs:163`), the connection list

  `scripts/bridge-account-profile.mjs:228`); the block routes live in `scripts/bridge-social.mjs:255-293`.

## Decisions (D-P5-4, 2026-10-22) — binding; they supersede the sections they name

1. **One `moderation` section, no new table, no root SQL.** The limits live in the `moderation` section
   of `osionos_user_settings` (root SQL `:214-222`), read and written through the existing merge RPC
   (`scripts/bridge-preferences.mjs:90-93`). The root repo is untouched by all three packages.
2. **The section path is `/api/account/moderation-settings`**, next to the existing
   `/api/account/notification-settings` (`scripts/bridge-preferences.mjs:36-39`). The route is added to
   the **existing** settings module, not to a new module: a second module with its own section map and
   its own merge call would be a parallel copy of `bridge-preferences.mjs`.
3. **The limits are absolute, and the bridge computes them.** The client sends a duration from a fixed
   vocabulary; the bridge turns it into an absolute `until` with **its own clock**
   (`scripts/bridge-preferences.mjs` gains the per-section prepare step). A client with a wrong clock
   cannot extend a limit past six months.
4. **The vocabulary is the bridge's.** The modes and the durations are declared once in
   `scripts/bridge-moderation-core.mjs`; the app keeps a copy in `moderationModel.ts` and a canvas test
   compares the two (the P5-1-e precedent). The bridge file is new because `bridge-social-core.mjs` is
   already 407 lines — over the 300-line rule COMMON.md sets — and the moderation vocabulary is not a
   copy of anything in it.
5. **A failed policy read does not block the interaction.** The default policy is permissive, so a
   database hiccup that denies every DM, every connection request and every comment platform-wide is
   the worse failure. The read failure is a `console.warn` and the interaction goes through. The
   `Caveat:` line in the code must name exactly what this gets wrong: *one interaction that the user's
   limit would have refused reaches them during the outage.* (Open question 3 asks whether the ledger
   prefers the other trade-off.)
6. **The blocked-users panel moves; it is never copied.** The new `moderation` section owns it. A second
   copy of the list in the Contacts section would be the defect this package exists to remove.
7. **The modes.** `messages`: `everyone` | `connections` | `nobody`; `connections`: `everyone` |
   `nobody`; `comments`: `everyone` | `workspace` | `nobody`. "Followers only" is **not** offered: the root
   SQL has no follows table, so the mode could not be enforced (open question 1).
8. **The durations** are hours: `24`, `168`, `720`, `2160`, `4320` (24 h, 7 days, 30 days, 90 days,
   6 months) — the plan's "from 24 h to 6 months".
9. **A refusal says one thing.** The actor learns that the target is not accepting that interaction,
   and nothing else: not the mode (connections vs nobody), not the duration, not the expiry.

     returns the patch to store, or throws a 422 with a stable code. Its rules:
     - the body must be an object; an array or a string → 422 `invalid_body`;
     - a key that is not one of the three interactions → 422 `unknown_interaction`;
     - a mode outside the interaction's modes → 422 `invalid_mode`;
     - a mode other than `everyone` **requires** `durationHours`, and it must be one of
       `DURATION_HOURS` → 422 `invalid_duration`; with the mode `everyone` the duration is ignored and
       the stored entry is `{ mode: 'everyone' }`;
     - the computed entry is `{ mode, until: new Date(now + durationHours * 3_600_000).toISOString() }`.
       `until` is **absent** for `everyone` — the merge function strips nulls
       (`models/osionos-account-profiles-migration.sql:326`), so a stored `until: null` never survives;
   - `moderationPolicy(value, now = Date.now())` — the read half: the stored value → the effective
     policy. A missing row, a malformed row, an unknown mode or an `until` in the past → the default
     (`everyone`, no limit) for that interaction. A malformed `until` (not a date) is treated as
     expired, never as "no expiry".
     Distinct read-failed state (condition 2): `moderationPolicy` (and its caller) must distinguish a
     failed/unknown read from "no policy". On a read failure the interaction is still allowed (D5), but
     the failure is a `console.warn` that names the failure and carries **no** policy value, and is never
     reported as "no limit".
   - `moderationPolicyFor(config, fetchImpl, userId)` — the **service-role** read of one user's section:
     `rest(config, fetchImpl, 'osionos_user_settings?user_id=eq.<uid>&section=eq.moderation&select=value&limit=1')`.
     The service role is the same key the block check uses (`scripts/bridge-social-core.mjs:91-99`), and
     the section is a policy, not a private setting: only this one section and only the `value` column
     are read.
     Base-URL invariant (condition 1): `moderationPolicyFor` resolves against `config.baasUrl` while the
     merge write resolves against `pg.asUser`'s base (`OSIONOS_POSTGREST_URL || config.baasUrl`). The spec
     requires `OSIONOS_POSTGREST_URL` unset or equal to the service base; the bridge test asserts both
     resolve to the same base URL, and a mutant that points the read at a different base fails it. (Alternatively the read moves onto `pg.asService()`, which needs `scripts/bridge-api.mjs` in OWNS.)
   - `interactionRefusal(config, fetchImpl, { interaction, actorId, targetId, workspaceId })` — the
     decision. It returns `null` when the interaction is allowed, or
     `{ status: 403, code: 'interaction_not_allowed', message }` when it is not. The table:

     | interaction | mode | allowed when |
     |---|---|---|
     | messages | `everyone` | always |
     | messages | `connections` | an **accepted** connection edge exists between the actor and the target |
     | messages | `nobody` | never |
     | connections | `everyone` | always |
     | connections | `nobody` | never |
     | comments | `everyone` | always |
     | comments | `workspace` | the actor is a member of the **page's** workspace |
     | comments | `nobody` | never |

     - the accepted-connection read is
       `osionos_connections?or=(and(requester_id.eq.<actor>,addressee_id.eq.<target>),and(requester_id.eq.<target>,addressee_id.eq.<actor>))&select=requester_id,addressee_id,status&limit=1`
       — the shape the block check already uses (`scripts/bridge-social.mjs:146`), so the pair is read
       without touching `pair_key`;
       - the pair read's index plan must be proven, not asserted: the `or=(and(...))` shape is served by
         the two single-column indexes (`models/osionos-social-migration.sql:73-75`), two probes; a root
         gate row asserts the plan (EXPLAIN) for this read, or the read uses the `pair_key` unique index
         (`:63-71`) with a canonical lowercase pair (P5-4-b does not use `pair_key` here).       - `Caveat:` the database does **not** compare text: it compares **uuids**
         (`requester_id < addressee_id`, `models/osionos-social-migration.sql:63-67`), and a uuid ordering
         equals the canonical lowercase hex ordering, so the bridge's `localeCompare`
         (`scripts/bridge-social.mjs:149`) agrees for canonical ids. The real defect is a non-canonical
         (uppercase) id making the PATCH match zero rows — that is condition 3, not a pair-key bug.
         P5-4-b's pair read never uses `pair_key`.
       - the workspace-membership read reuses `workspaceMembership`
         (`scripts/bridge-social-core.mjs:153-160`) with the page's `workspace_id`;
       - the messages are one per interaction and disclose nothing else: "This person is not accepting
         messages from you.", "This person is not accepting connection requests from you.", "This person
         is not accepting comments on their pages.";
       - **a failed policy read never refuses**: the read is wrapped, a failure is a `console.warn`, and
         the interaction goes through (D5). The `Caveat:` line names what that gets wrong.
       - **a failed BLOCK read refuses (orchestrator override)**: when the read that decides whether two
         users have a block between them fails (store error, timeout, malformed answer), the interaction is
         refused with 503 and nothing is written — never allowed. Only the interaction-LIMIT policy read
         keeps the fail-open-but-loud ruling.

## Security edges (all three packages)

- **Who may call what.** `GET`/`PATCH /api/account/moderation-settings` need the caller's app session;
  the read goes through the caller's own account token (`aud: 'osionos-account'`) and the write through
  the merge RPC, so the caller can only ever touch their own row. The block routes keep the session
  they had (`scripts/bridge-social.mjs:335`).
- **What a non-owner sees.** Nothing of the moderation section. The enforcement reads the target's
  section with the **service role**, exactly as the block check reads the block table
  (`scripts/bridge-social-core.mjs:91-99`), and the value never leaves the bridge: it is not in a
  response body, not in a log line and not in a notification. The refusal says one thing
  ("This person is not accepting messages from you.") and discloses neither the mode nor the duration
  nor the expiry — the actor learns that they were refused, which they already know.
- **What the target sees.** Their own modes, their own expiry, their own blocked list — nothing of
  anybody else's.
- **The block still wins.** A blocked pair is refused by the block check before the moderation check
  runs (`scripts/bridge-social.mjs:143-148`, `scripts/bridge-chat.mjs:463-464`); the moderation policy can
  only be stricter, never looser. A block is permanent until it is lifted; a limit expires on its own.
- **A comment on somebody else's page** is judged by the **page owner's** policy, and the owner
  commenting on their own page is never refused.
- **Out of scope (condition 4):** a workspace channel is not a DM, so "who can direct message me" does
  not stop a channel message; a workspace invite creates no connection edge (it writes
  `osionos_workspace_members`), so the `connections` limit is not bypassed that way, but the invitee
  becomes a workspace member; a block is **not** enforced on comments at all (no `osionos_user_blocks`
  read in `scripts/bridge-comments.mjs`).
- **A block does not stop a comment (condition 5):** blocking hides both directions, the directory, the
  connection list, the profile card and the DM, and notifies nobody — but it does not stop a comment.
- **The moderation section is a policy, not a secret.** Its content is read through the service role by
  the bridge; it never contains a credential, and it is not exposed to a third party. The account role
  cannot read another user's row (`models/osionos-account-profiles-migration.sql:644-647`), so a
  compromised session cannot read somebody else's limits with the account token.
- **The refusal is a 403, not a 404.** The target is not hidden from the actor: a blocked peer is
  already refused with 403 by the block check, so the moderation refusal does not reveal the existence
  of the target any more than the block check does.
- **The unblock restores the pair to `declined`, never to `accepted`** — the pre-block status is not
  recoverable, and a limit that lapses is never silently re-granted.

## Decisions (D-P5-4s)

Adopted from D-P5-4s (2026-10-22). These supersede the open questions of the draft.

1. **Followers only — not now.** Do not add the mode; when P2-3's follow graph lands, add it to the
   same vocabulary in `bridge-moderation-core.mjs` + `moderationModel.ts` and keep the section in
   `osionos_user_settings`. A mode that cannot be enforced must not exist.
2. **Pre-block status — keep the root repo untouched.** The unblock restores `declined` and the copy
   says the pair must ask again. Preserving it needs a guarded root column + backfill (separate root
   package); a `declined` restore is honest rather than silent.
3. **Fail-open vs fail-closed (policy read) — keep fail-open (D5), but loud.** A hiccup that denies
   every DM platform-wide is the worse failure; a silent fail-open that reads as "no limit" is how this
   becomes the third panel that lies. The failure must be distinguishable (condition 2) and never
   reported as "no limit".
4. **The `contacts` anchors — a later package.** The moderation section carries its own anchor and the
   panel moved; the contacts search index is a different change with a different owner.
5. **The pair key — not fixed here.** P5-4-a must not depend on a silent zero-row PATCH (condition 3)
   and P5-4-b's pair read must not use `pair_key`. The database compares uuids, not text, so the
   disagreement the draft describes does not exist; the real defect is the unverified PATCH.
6. **Caching the policy — cache the raw stored value for 5 s per user id** and evaluate the expiry on
   every call, so an expired limit is never extended by the cache; a limit lowered by the user is
   enforced up to 5 s late. The absolute `until` makes a short cache safe.
7. **The audit — P5-4-b writes no audit row.** P5-4-c records the change through `recordSettingsAction`
   with the interaction and the mode only, and the trail is local-only until P3-4's route lands. The PAT
   audit is a root-table contract P5-1 already defined.
8. **The handle in the blocked list — no.** Keep the display name. `identitySummaries`' select is fixed
   and asserted by the social stub, and widening it touches every caller for a cosmetic gain.

**Orchestrator override (D-P5-4s): a BLOCK fails closed.** When the read that decides whether two users
have a block between them fails (store error, timeout, malformed answer), the interaction is refused
(503, no write) — never allowed. Only the interaction-LIMIT policy read keeps the reviewer's
fail-open-but-loud ruling (decision 3). Tests: the block-read-failure case refuses with 503 and writes
nothing; mutant: make the failed block read allow → that test fails.
