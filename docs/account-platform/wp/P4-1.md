## Why

### 1. There is no `sys:` source anywhere, and no route that could serve one

- The account-wide catalog knows four families and nothing else: the live mounts, the user's own
  in-app databases, the workspace tables (Folders/Files) and the demo seeds —
  `src/widgets/database-view/model/allDataSources.ts:58-72`. Nothing in it is scoped to the
  caller's own account rows.
- The provider interface is the app's injection point into the vendored registry
  (`src/shared/notion-database-sys/src/store/sources/dataSourceRegistry.ts:44-48`); the app
  registers exactly one provider (`src/widgets/database-view/model/dataSourceProvider.ts:60-63`),
  and it lists live mounts, user-created databases, workspace tables and seeds.
- The account plane has one mounted module and two routes:
  `scripts/bridge-account-mounts.mjs:24-31` mounts `createSessionsRoutes` and nothing else, and
  that module answers `GET /api/account/sessions` and `DELETE /api/account/sessions/:id`
  (`scripts/bridge-sessions.mjs:255-267`). There is no per-user data-source route.

### 2. `DatabaseBlock.tsx` has no `sys:` branch, and a `sys:` id today renders the demo seed

`src/widgets/database-view/ui/DatabaseBlock.tsx` dispatches on the database id in five branches:
the live mount (`:167-195`), the Home carousels (`:200-222`), the workspace tables (`:224-232`),
the known seed databases (`:234-257`) and the fallback for a user-created database (`:259-283`).
None of them is a `sys:` id, and the last branch renders the demo seed adapter under whatever id it
was given (`:268-282`). The plan's "`DatabaseBlock.tsx:91` gets a `sys:` branch" is therefore a
statement about intent, not a line number: the branch goes next to the other id dispatches, after
the live branch and before the known branch, so a `sys:` id never reaches
`getKnownDatabaseAdapter()` (`:137-140`).

### 3. A user's VIEW configuration is not saved anywhere

- The ObjectDatabase host persists an in-view edit through the adapter's `persistState` hook
  (`src/widgets/database-view/model/knownDatabaseState.ts:62-63`).
- Every read-only adapter uses that hook only to DISCARD the edit and re-emit a reload
  (`src/widgets/database-view/model/recentsDatabaseState.ts:141-143`,
  `src/widgets/database-view/model/templatesDatabaseState.ts:131`,
  `src/widgets/database-view/model/workspaceDatabaseState.ts:90`).
- The one adapter that writes back writes the PAGE, not the view
  (`applyWorkspacePersist`, `src/widgets/database-view/model/workspaceDatabaseWrites.ts:60`), and
  only for the workspace tables.
- The view diff helper that already exists is content-based, not identity-based, exactly because a
  reload rebuilds every object (`viewStateChanged`,
  `src/widgets/database-view/model/readOnlyPersist.ts:27-31`). It is the right primitive to reuse
  for the view-only diff P4-1-c needs.

### 4. Six of the eight planned sources have a backing table in the root models today; two do not

Verified in `/home/dlesieur/Documents/groot-wt/root-integration/models/`:

| source | backing table | root file:line |
|---|---|---|
| `my-pages` | `public.osionos_pages` | `osionos-bridge-migration.sql:49` |
| `my-tasks` | `public.osionos_tasks` | `osionos-tasks-migration.sql:17` |
| `my-published` | `public.osionos_published_pages` | `osionos-publish-migration.sql:7` |
| `my-connections` | `public.osionos_connections` (+ `public.osionos_user_blocks`) | `osionos-social-migration.sql:55`, `:111` |
| `my-workspaces` | `public.osionos_workspace_members` + `public.osionos_workspaces` | `osionos-bridge-migration.sql:39`, `:28` |
| `my-sessions` | `public.osionos_sessions` | `osionos-account-foundation-migration.sql:165` |
| `my-activity` | **none** | the only activity table is `user_activities` in the legacy `users` schema (`models/user.sql:44`) — the gateway's log, not the platform's event stream; the plan's `osionos_activity_events` arrives with P4-5 |
| `my-followers` | **none** | there is no `osionos_follows` in `models/` at all (grep over `models/*.sql`); P2-3 owns follows and followers |

Both missing tables are why the two sources are later sub-packages and not stubs: a source with no
table would answer an empty list forever, which reads as "you have no activity" instead of "this
feature is not built".

### 5. The security edges the six sources have, and where they differ

- **`my-sessions` is account-plane.** The account role may SELECT exactly nine columns
  (root `models/osionos-account-foundation-migration.sql:207`) under an owner-read RLS policy
  (`:214-215`). `ip_hash` and `refresh_hash` are NOT in the grant and must never be: `ip_hash` is a
  keyed HMAC of the caller's address and `refresh_hash` the refresh token's hash. `ip_prefix` IS in
  the grant, and the column's own CHECK refuses a /32 (`:176-178`), so it can only ever hold a
  network. The existing session route already reads the same nine columns through `asUser`
  (`scripts/bridge-sessions.mjs:37`, `:192`).
- **The other five are service-role tables.** The account role has no grant on
  `osionos_pages`, `osionos_tasks`, `osionos_published_pages`, `osionos_connections`,
  `osionos_workspaces` or `osionos_workspace_members` — they are service-role only with a
  `service_role` policy (root `models/osionos-bridge-migration.sql:187-207`,
  `models/osionos-tasks-migration.sql:75`, `models/osionos-publish-migration.sql:19`,
  `models/osionos-social-migration.sql:181`). So their scoping is the filter in the path, and the
  bridge must never fetch them unfiltered and filter in JS. The precedent is the existing task
  route (`scripts/bridge-tasks.mjs:37`: `owner_id=eq.<session.userId>`).
- **`my-published` would otherwise carry the page's body.** `public.osionos_published_pages.content
  JSONB NOT NULL` (root `models/osionos-publish-migration.sql:13`) is a copy of the page at publish
  time. A source that returned it would put a private page's whole body in a dashboard cell.
- **`my-connections` reads another person's row.** The edge table holds the peer's id, and the peer
  must be reduced to a public card. The reduced-card rule already exists in the profile route
  (`scripts/bridge-profile.mjs:88-97`: an opted-out subject or a viewer the subject blocked gets
  only `userId`, `name`, `avatar`) and the block set has a helper
  (`blockedViewerBy`, `scripts/bridge-social-core.mjs:182-195`) that must be reused, never copied.
- **`my-workspaces` exposes the caller's own membership** (`role`, `permissions`) — that is the
  caller's own data — and the workspace's `settings` JSONB, which can hold private workspace
  configuration, must stay out of the allowlist.
- **`my-pages` excludes pages the caller may edit but does not own.** The page write rule is
  separate from ownership (P3-6), and "my pages" is the owner's list, not "pages I can edit".
  A page whose `owner_id` is NULL belongs to nobody and is in nobody's list.

## Contract

### P4-1-a — the bridge: the six self sources

**A1 — a pure source registry.** New `scripts/bridge-self-sources.mjs` (Node built-ins only, no
I/O, ≤ 200 lines). It exports:

```js
export const SELF_SOURCES = [
  { id: 'my-pages', label: 'My pages', table: 'osionos_pages', scope: 'owner', order: 'updated_at.desc', columns: [...] },
  // …
];
export function selfSourceById(id) { /* the entry, or null */ }
```

- `id` ∈ `my-pages`, `my-tasks`, `my-published`, `my-connections`, `my-workspaces`, `my-sessions`.
- `columns` is the ORDERED allowlist. The PostgREST `select` is built from it; `select=*` is
  forbidden and a `Caveat:` says why (a new column on the table would leak into a dashboard).
- `order` is the PostgREST `order` value of the read (the table's own timestamp column, newest
  first). It is part of the registry so the cap of A6 cuts the OLDEST rows, not an arbitrary 200.
- The registry is the single place that knows a source's table, scope and columns. The route
  module must not name a table or a column itself.
- The registry is **pure and I/O-free** so it can be unit-tested without a server, and so the
  column allowlist can be asserted against a table's real columns in one test.

**A2 — the route.** New `scripts/bridge-self-data.mjs`, exporting
`createSelfDataRoutes({ config, pg, kv, verifySession })` and returning a handler with the
`createSessionsRoutes` shape (`scripts/bridge-sessions.mjs:255-267`).

- `GET /api/account/self-data/<source>` — `<source>` is exactly ONE path segment.
  - The path must match `/api/account/self-data/<segment>`; anything else (including
    `/api/account/self-data/views/<source>`) is **not** this route and the handler returns `false`
    so the next mounted module can try.
  - A segment that is not in `SELF_SOURCES` → `404 unknown_self_source`.
  - A session is required: `verifySession(bearerToken(request), config)`. No session → the bridge's
    own 401 (`scripts/bridge-social-core.mjs:80-85`).
  - The answer is `200 { ok: true, source, columns: string[], rows: object[], truncated: boolean }`.
    `columns` are the names in the allowlist order; each row has EXACTLY those keys.
  - The rows are built by an explicit per-source mapper that picks the allowlisted keys out of the
    raw row. A row is never spread (`{...row}`) into the answer.
  - The response is built by `sendJson(response, 200, body, config)`
    (`scripts/bridge-social-core.mjs:68`).
- **Rate limit:** 120 requests/minute per user, `rateLimit(kv, ['self-data', session.userId], …)`
  (`scripts/bridge-guard.mjs:167-178`); over the limit → `429 rate_limited` with
  `retryAfterSeconds`.

**A3 — the six reads.** Each source names its table, its scope filter and its allowlist. The
scope filter is part of the PATH string; there is no post-fetch filter anywhere in the module.

| source | read | scope filter | allowlist (the answer's columns) |
|---|---|---|---|
| `my-pages` | `osionos_pages` | `owner_id=eq.<uid>` | `id, title, icon, cover, surface, visibility, database_id, parent_page_id, created_at, updated_at, archived_at` |
| `my-tasks` | `osionos_tasks` | `owner_id=eq.<uid>` | `page_id, block_id, workspace_id, content, checked, due_at, updated_at` |
| `my-published` | `osionos_published_pages` | `owner_id=eq.<uid>` | `token, page_id, title, icon, published_at` |
| `my-connections` | `osionos_connections` | `or=(requester_id.eq.<uid>,addressee_id.eq.<uid>)` | `id, requester_id, addressee_id, status, source, created_at, responded_at` |
| `my-workspaces` | `osionos_workspace_members` + `osionos_workspaces` | `user_id=eq.<uid>` on the members | `workspace_id, role, permissions` + `id, name, slug, created_at, updated_at` |
| `my-sessions` | `osionos_sessions` | RLS owner read | `id, created_at, expires_at, last_seen_at, auth_method, ip_prefix, user_agent` |

Rules that hold for every row of the table:

- **`my-pages`** — `collaborators`, `properties`, `content`, `is_template`,
  `is_default_template`, `recurrence` and `template_surface` are NOT in the allowlist:
  `collaborators` holds other people's ids, `properties`/`content` are the page's body, and the
  rest are authoring metadata. A page with `owner_id IS NULL` is in nobody's list.
- **`my-tasks`** — the row is one `to_do` block, not one page: the key is `(page_id, block_id)`
  (root `models/osionos-tasks-migration.sql:26`). `owner_id` is not in the allowlist: it is the
  caller's own id, and the caller already knows it.
- **`my-published`** — `content` is NOT in the allowlist (Why, 5). `token` is the public slug of
  the caller's OWN published page; it is the caller's own secret and is in the list.
- **`my-connections`** — `intro_message` is NOT in the allowlist: it is another person's free text
  and the dashboard card does not need it. The row is the EDGE; the peer is a nested object built
  by A4.
- **`my-workspaces`** — the workspace's `settings` JSONB is NOT in the allowlist. The answer is
  the union of the caller's membership rows and the workspace rows they name, so a workspace the
  caller is a member of appears once, with the caller's own `role` and `permissions`.
- **`my-sessions`** — the read goes through `pg.asUser(session)`, NOT the service role. The
  allowlist is a SUBSET of the nine granted columns: the two revoked columns are dropped because
  the read filters them out (`revoked_at=is.null` and `expires_at=gt.<now>`, the same two filters
  as the existing session route, `scripts/bridge-sessions.mjs:187-188`). The row also carries one
  computed field, `current: boolean`, true when the row's id equals the caller's session jti
  (the same comparison the session route makes, `:205`).

**A4 — the peer card of `my-connections`.** A second read, after the edges:

- The peer ids are read from the directory view with an explicit column list
  (`user_id, display_name, username, profile, last_seen_at, directory_opt_out, headline` on
  `public.osionos_people_directory`, rebuilt over the profiles by root
  `models/osionos-account-profiles-migration.sql:683-700`), in chunks of 50 through the existing
  helpers `idChunks` and `inFilter` (`scripts/bridge-paging.mjs:34`, `:55`). The ids are chunked
  because an `in.(…)` list breaks at about 90 ids.
- The blocked set comes from `blockedViewerBy(config, fetchImpl, session.userId)`
  (`scripts/bridge-social-core.mjs:182-195`) — the helper, never a copy of it.
- The card is:
  - the **full public card** `{ userId, name, username, headline, avatar, lastSeenAt }` when the
    peer is in the directory and has not blocked the caller; else
  - the **reduced card** `{ userId, name, avatar }` — exactly the shape the profile route returns
    for an opted-out or blocked subject (`scripts/bridge-profile.mjs:90-97`).
- The direction is computed from the edge: `outgoing` when `requester_id` is the caller, else
  `incoming`.
- **Never in a card:** an email, an ip_hash, a settings row, a `directory_opt_out` flag, a
  `search_doc`, or any other column of the peer's rows.

**A5 — the workspace read.** `my-workspaces` is three reads, in this order:

1. `osionos_workspace_members?user_id=eq.<uid>&select=workspace_id,role,permissions&limit=200`
   (indexed: root `models/osionos-bridge-migration.sql:138`).
2. `osionos_workspaces?owner_id=eq.<uid>&select=id,name,slug,created_at,updated_at&limit=200`
   (indexed: root `models/osionos-bridge-migration.sql:137`).
3. only if read 1 named a workspace read 2 did not return:
   `osionos_workspaces?id=in.(…)` over the missing ids, chunked with `idChunks`/`inFilter`
   (`scripts/bridge-paging.mjs:34`, `:55`).
   `Caveat:` three round trips for one source, because the membership table is the only place that
   knows "this user belongs to this workspace" and the workspace table is the only place that
   knows the name.

**A6 — the limits and the failures.**

- Each source caps its answer at **200 rows**; the answer then carries `truncated: true`.
  `Caveat:` the cap is a row count, not a page: a user with 5,000 pages sees the 200 the query
  ordered first and the rest are unreachable from this source. The ordering is the table's
  `updated_at desc` for `my-pages` and `my-tasks`, `created_at desc` for the others. The bridge
  test does NOT assert the order: the harness honours only `id.asc` and `user_id.asc` and ignores
  every other order value (`tests/bridge/support/bridge-harness.mjs:84`), so the order is proved by
  the path, not by the mock.
- A store failure is a **`503 self_data_unavailable`**, never an empty list: an empty list is a
  true answer ("you have none") and a failure must not look like one. The same rule the share-rule
  review insisted on (P3-6's C-9).
- A missing table (PostgREST `PGRST205` / Postgres `42P01`) is also a 503, not an empty list. The
  desktop edition's migration list does not ship every file, so a table can be absent on a
  supported install.

**A7 — the mount.**

- The module is appended to the `modules` list in `scripts/bridge-account-mounts.mjs:25` and
  copied by name in `deploy/bridge-fly/Dockerfile:24-33`. `scripts/bridge-api.mjs` is **not**
  touched: the account seam dispatches to the mounted module
  (`scripts/bridge-api.mjs:4219-4220`, `:4293`).
- The module is ≤ 300 lines. If the six sources do not fit with the route, the per-source mappers
  move into `scripts/bridge-self-sources.mjs` — the registry file stays pure (A1).
- `bridge-dockerfile-closure.test.mjs` must pass: the new module is in the static import closure
  of `bridge-api.mjs`, so the Dockerfile must copy it
  (`tests/bridge/bridge-dockerfile-closure.test.mjs:53-58`).

**A8 — security edge (the bridge side).**

- **Who may call what:** an app-session holder, for their own rows only. There is no path
  parameter that names a user: the uid comes from the VERIFIED session
  (`session.userId`), never from the query string, never from the body.
- **What a non-owner sees:** nothing. Another user's rows are not in any answer; a forged
  `user_id` in a query parameter is impossible (the route takes no query parameter).
- **The service key never reaches an account-plane table.** `my-sessions` is read with `asUser`;
  the request carries the per-user JWT (`aud: 'osionos-account'`, `role: 'osionos_account_user'`,
  `scripts/bridge-pg.mjs:23-25`, `:168-181`), never the service key.
- **The legacy five are service-role reads whose scope is the path filter.** A missing filter
  would be a full-table read; the test asserts the filter (see Checks 1).
- **No write path.** The module answers `GET` only; a `POST`/`PATCH`/`DELETE` on the path is
  `405 method_not_allowed`.

### P4-1-b — the app: the provider, the adapter, the `sys:` branch

**B1 — the catalog.** New `src/widgets/database-view/model/sysDataSources.ts`:

```ts
export interface SysSource {
  id: string;              // "sys:my-pages"
  source: string;          // "my-pages" — the bridge's source id
  label: string;
  icon: string;
  description: string;
  titleColumn: string;     // the column that names the record
  defaultViewId: string;   // "<source>-default"
  columnTypes: Record<string, SysColumnType>;
}
export const SYS_SOURCES: SysSource[];
export function isSysDatabaseId(id?: string | null): boolean;
export function sysSourceById(id: string): SysSource | undefined;
```

- `isSysDatabaseId` accepts only `sys:` + a known source id. An unknown `sys:whatever` is not a
  sys id, so the block falls through to today's behaviour instead of rendering an empty database.
- `columnTypes` maps a bridge column name to a display type. The property id of a column IS its
  name, so a saved view's `visibleProperties` are the bridge's column names and stay valid when
  the bridge adds a column.
- The types used: `text`, `select`, `multi_select`, `number`, `checkbox`, `date`,

### P4-1-c — the saved views

**C1 — the bridge route.** New `scripts/bridge-self-views.mjs`, exporting
`createSelfViewsRoutes({ config, pg, kv, verifySession })`:

- `GET /api/account/self-data/views/<source>` → `200 { ok: true, source, views: { <viewId>:
  <view> } }`.
- `PUT /api/account/self-data/views/<source>/<viewId>` → body = the view object → `200 { ok: true,
  source, views }` with the merged map.
- `DELETE /api/account/self-data/views/<source>/<viewId>` → `200 { ok: true, source, views }` with
  the map minus that view.
- The path has TWO segments after `self-data/`, so it never collides with the row route (A2). The
  module is appended to the `modules` list in `scripts/bridge-account-mounts.mjs` (the same
  append-only file P4-1-a touches) and copied in `deploy/bridge-fly/Dockerfile`.
- An unknown `<source>` → `404 unknown_self_source`; a `<viewId>` that is not
  `^[A-Za-z0-9_-]{1,64}$` → `422 invalid_view_id`; a body that is not a plain object, or is larger
  than 8 KB, → `422 invalid_view`; a body whose `type` is not one of the known view types
  (`table`, `gallery`, `board`, `list`, `calendar`, `timeline`, `chart`) → `422 invalid_view`;
  a body whose `filters`, `sorts` or `visibleProperties` is not an array of at most 64 entries →
  `422 invalid_view`.
- Rate limit: 60 requests/minute per user, `rateLimit(kv, ['self-views', session.userId], …)`.

**C2 — the storage.** The section name is `sys-views-<source>`, derived from the source id — never
from the request. The name satisfies the table's CHECK
(`section ~ '^[a-z][a-z0-9_-]{0,31}$'`, root
`models/osionos-account-profiles-migration.sql:216`); the longest is `sys-views-my-connections`
(23 characters).

- The read: `pg.asUser(session).get('osionos_user_settings?section=eq.sys-views-<source>&select=value')`
  — the account role's SELECT grant (root `:636`) plus the owner-only RLS policy (root `:645`) are
  the enforcement, so the row is the caller's and only the caller's.
- The write: `pg.asUser(session).rpc('osionos_user_settings_merge', { p_section, p_patch })` — the
  merge function (root `:311-332`), granted to the role (root `:334`). It is the ONLY write path:
  a direct INSERT/UPDATE would lose a concurrent write, and the function's shallow merge with
  `jsonb_strip_nulls` is what makes "one view changed" not "the whole map replaced".
  - The patch for a save is `{ "<viewId>": <view> }`; the patch for a delete is
    `{ "<viewId>": null }` — `jsonb_strip_nulls` drops the key.
  - The returned merged value is the answer.
  - A `23514` (the value's 16 KB CHECK, root `:218-219`) → `413 view_too_large`.
- **The section is not a settings section.** `GET /api/preferences` still answers the
  `preferences` section and `GET /api/account/notification-settings` the `notifications` one; this
  package adds a third route family and does not widen those. Say so in a comment on the route.
  The section name is prefixed `sys-views-` so a settings panel that ever enumerates the table
  can tell these rows apart.

**C3 — the app.** New `src/widgets/database-view/model/sysDatabaseViews.ts`:

- `fetchSavedViews(sourceId): Promise<Record<string, ViewConfig>>` — `GET`, tolerating a `404`
  (the route is not deployed yet) by returning `{}`.
- `saveSavedView(sourceId, viewId, view): Promise<Record<string, ViewConfig>>` — `PUT`.
- `deleteSavedView(sourceId, viewId): Promise<Record<string, ViewConfig>>` — `DELETE`.
- All three go through the shared fetch chain with the app-session token (B2).
- The adapter's `persistState` (B2) diffs **the views only** — never the databases and the pages,
  which are the bridge's projection. A new or changed view is written with `saveSavedView`; a view
  that disappeared is deleted. The diff is a pure function in the same file, so it is unit-tested
  without a DOM:
  `diffViews(next: Record<string, ViewConfig>, previous?: Record<string, ViewConfig>): { saved:
  Array<[string, ViewConfig]>, removed: string[] }`.
- The write is asynchronous and `persistState` is synchronous (the host calls it detached). The
  adapter therefore fires the write and, when it settles, re-emits a reload: on success the
  reloaded state carries the saved view (the server is the truth) and the row edits are discarded;
  on failure the reloaded state drops the edit and a toast says the view was not saved. The
  reload must not loop: the reloaded state's views equal the saved ones, so the next diff is
  empty (the same argument as `viewStateChanged`,
  `src/widgets/database-view/model/readOnlyPersist.ts:21-26`).
- The default view is never written: it is rebuilt from the source on every load, so a saved map
  that loses it still renders.

**C4 — security edge (the saved views).**

- The view is written into the CALLER's own settings row, keyed by the session's uid
  (`osionos_user_settings_merge` takes the uid from `osionos_account_uid()`, root `:318-322`).
  A forged user id in the body is impossible: the body has no such key — an unknown key is a
  `422`.
- A view configuration is metadata (filters, sorts, visible columns, display settings). It never
  carries a row's values, so saving a view cannot leak one account's data into another's.
- What another user sees: nothing. The section is per user, the policy is owner-only, and the
  route answers only the caller's map.
- A view id is a bounded identifier (`^[A-Za-z0-9_-]{1,64}$`) and becomes a JSON key; a hostile
  id cannot escape the section.

## Open questions (ruled on in the Decisions block above; kept for the record)

1. **The saved views' storage — is `osionos_user_settings` acceptable, or do the views deserve
   their own table?** The contract reuses the account plane's per-user JSONB table (decision 4),
   which costs no migration, no grant and no check, and inherits the owner-only RLS. The cost: the
   views share a 16 KB value budget with any other `sys-views-*` section of the same source, and
   the section namespace is shared with the settings sections (P1-2a maps one section per route
   family; this package adds a route family, not a section to an existing one). A dedicated
   `public.osionos_user_views` table would give each view its own row and its own keyset paging,
   at the price of a migration, a grant, a policy and a new check in
   `scripts/verify/models-grants/account-checks.sql`. **The contract's choice is the reuse; say so
   in the report if the orchestrator disagrees.**
2. **The row cap of 200.** A user with 5,000 pages sees 200 of them and the rest are unreachable
   from the source. The keyset cursor exists (`scripts/bridge-paging.mjs:63-66`, `:123-134`) and
   could page the source, but a `sys:` block in a page has no pagination UI. Is a cap of 200 the
   right number, and should a truncated source say so in the UI?
3. **`my-pages` scope: owned only.** A page the caller can edit in a shared workspace (a
   collaborator) is NOT in `my-pages`. "My pages" could also mean "every page I can open", which
   would need the workspace membership rule (P3-6) and would widen what the source exposes.
4. **`my-workspaces` scope: the membership is the authority.** A workspace row the caller owns
   without a membership row would still appear (the owner read covers it), but a workspace the
   caller is a member of always appears. The sign-in writes both rows in one transaction
   (root `models/osionos-bridge-migration.sql:252`), so the two agree today. Is the membership the
   right definition of "my workspaces", or should the owner's workspaces only count?
5. **`my-connections`: one row per EDGE, with the peer nested.** The alternative is one row per
   PERSON (a peer the caller both sent to and received from would appear twice as two edges). The
   edge reading is what the existing `/api/connections` answers
   (`scripts/bridge-social.mjs:110-135`); the person reading is what a people list wants. Which
   one does the dashboard want?
6. **`my-connections` and the colleague edges.** `/api/connections` also SYNTHESISES colleague edges
   from shared workspaces (`insertColleagueEdges`, `scripts/bridge-social-core.mjs:290`) — a
   side effect of a GET. Does `sys:my-connections` reproduce that (it would make the source WRITE
   on a read, which P0-5 forbids for `GET /api/connections`), or does it list only the stored
   edges? **The contract lists only the stored edges** — no write on a read.
7. **The `sys:` block's insertion path.** The contract reaches a `sys:` source through the Source
   picker (view settings → Source), which rebinds a view of an EXISTING database block. Is a
   first-class insertion ("add my pages to this page") wanted, and if so is it a slash command
   (`src/features/slash-commands/model/useSlashSelect.ts:108-120` creates the inline database
   today)?
8. **The export path.** `src/features/page-export/model/databaseExportSource.ts:36-48` resolves a
   database block to tabular data from the object-database store. A `sys:` block's rows live in
   the adapter, not in the store, so a CSV export of a page holding a `sys:` block may produce
   nothing. Is the export in scope for P4-1, or is it a named follow-up?
9. **The app's own `DataSourcePicker.tsx`.** The vendored `SourcePickerScreen` lists every
   registered provider, so the `sys:` sources appear there. The app's own
   `src/widgets/database-view/ui/DataSourcePicker.tsx` lists the live mounts only
   (`:33-41`, `:68-97`). Should the `sys:` sources appear in that picker too, or is the view
   settings picker enough?
10. **`sys:my-activity` and `sys:my-followers` — who owns the read path.** P4-1-d depends on P4-5's
    grant decision (account-plane with a column grant, or service-role only) and P4-1-e on P2-3's
    API shape (a table read, or the existing route). Neither is decided here; each is re-specced
    against the merged state of its dependency, like P2-4's d and e.
11. **The `my-sessions` row's title.** The contract makes the session id the record's title (a
    uuid) and shows the method and the creation time in the other columns. A computed label
    ("password — 2026-10-22 14:03") would read better in a card; it would be a computed field
    beside `current`, which the bridge already computes. Not decided.
