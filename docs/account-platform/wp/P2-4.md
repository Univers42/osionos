## Why

### 1. The `template_surface` CHECK refuses every profession and every seeded template

- **Root SQL** — `models/osionos-admin-migration.sql:23-24`:
  `ADD COLUMN IF NOT EXISTS template_surface TEXT CHECK (template_surface IS NULL OR template_surface IN ('profile', 'marketplace-app'))`.
- **Root SQL** — `models/osionos-bridge-migration.sql:66`: the same CHECK, inline in
  `CREATE TABLE public.osionos_pages`. On an install where the table already exists, the
  `ADD COLUMN IF NOT EXISTS` at `models/osionos-bridge-migration.sql:77` is a no-op, so the
  constraint created at line 66 is the live one.
- **App type** — `src/entities/page/model/types.ts:84`:
  `templateSurface?: "profile" | "marketplace-app"`.
- **App validator** — `src/features/page-file/model/pageFileMeta.ts:46-48`:
  `TEMPLATE_SURFACES = ["profile", "marketplace-app"]`. `metaFromPage` writes the key through
  `oneOf` (`src/features/page-file/model/pageFileMeta.ts:160`) and `patchFromMeta` reads it
  through `oneOf` (`src/features/page-file/model/pageFileMeta.ts:183`), so any other value is
  dropped, never coerced.
- **Bridge** — three sites compare against the same two literals:
  `scripts/bridge-api.mjs:753` (read: an unknown surface becomes `undefined`),
  `scripts/bridge-api.mjs:831-833` (create: an unknown surface is not written),
  `scripts/bridge-api.mjs:871-873` (update: same). Compare
  `scripts/bridge-api.mjs:114`, where the sibling allowlist `PAGE_SURFACE_VALUES` is a `Set`.

### 2. The seed mismatch: six seeded template pages carry a tag the app and the server refuse

- The six admin-designed templates declare surfaces outside the allowlist:
  `src/data/templates/studentDashboard.ts:25` `'student-dashboard'`,
  `src/data/templates/clubHomepage.ts:25` `'club-homepage'`,
  `src/data/templates/gradeCalculator.ts:25` `'grade-calculator'`,
  `src/data/templates/classNotes.ts:25` `'class-notes'`,
  `src/data/templates/todoList.ts:25` `'todo-list'`,
  `src/data/templates/resume.ts:25` `'resume'`.
- They are pushed to the server with that tag: `src/store/pageStore.actions.ts:122` posts
  `templateSurface: sp.templateSurface`.
- The bridge drops it (`scripts/bridge-api.mjs:831-833`), so the server row keeps
  `template_surface = NULL` and `useTemplateForSurface`
  (`src/widgets/page-renderer/model/useTemplateForSurface.ts:26-32`) can never find those
  templates. The six templates are inert.
- The app's own types lie about it: `src/store/pageStore.helpers.ts:523-525` casts the open
  string through `as PageEntry["templateSurface"]`, with a comment admitting the unions are
  narrower.

### 3. No profession template exists, and nothing lets a user pick one

- The admin space lists exactly two surfaces: `src/widgets/admin-space/ui/AdminSpaceView.tsx:32-35`.
- The onboarding asks for a workspace intent only: `src/features/workspace-onboarding/ui/WorkspaceIntentModal.tsx:20-24`
  (`work`, `personal`, `school`); the kits live in
  `src/features/workspace-onboarding/model/starterKits.ts:33`.
- No profession catalogue exists: `src/data/templates/index.ts:16-21` exports the six seed
  templates and nothing else; `src/data/seedPages.ts:146-151` seeds exactly those six.

### 4. Home regeneration overwrites user edits

- `src/widgets/page-renderer/ui/MainContent.tsx:48-51` — `homeDashboardNeedsRefresh` returns
  `true` when `homeDashboardVersion !== HOME_DASHBOARD_VERSION` (`MainContent.tsx:28`, value
  `10`) **or** when `hasHomeDashboardSections(page)` is false.
- `src/widgets/page-renderer/ui/MainContent.tsx:36-46` — `hasHomeDashboardSections` counts only
  `database_inline` and `home_views` blocks and needs at least four. A user who deletes one
  dashboard section drops below the threshold, so their own edit makes the page "stale".
- `src/widgets/page-renderer/ui/MainContent.tsx:116-134` — the effect then rebuilds the page
  with `createHomeDashboardPage` (`MainContent.tsx:56-87`) and keeps only `title`, `icon` and
  `cover` from the existing page (`MainContent.tsx:121-126`). Every user block — a paragraph, a
  callout, a deleted section, a reordering — is dropped.
- The Home page is client-local: its id is `home-dashboard:<workspaceId>`
  (`src/widgets/database-view/model/databaseViewCatalog.meta.ts:176-178`), and
  `isPersistedPageId` (`src/store/pageStore.helpers.ts:52-54`) accepts only a 24-hex Mongo id or
  a UUID. So the Home page is never written to the server; the edits live in the localStorage
  cache (`savePagesCache`, `MainContent.tsx:128` and `:132`) and the loss is permanent.
- The greeting is baked at seed time: `MainContent.tsx:114` reads the persona name once, and
  `src/widgets/database-view/model/databaseViewCatalog.ts:137-144` says so in the source.

### 5. The security edge of the profession itself

The profession is a public attribute of a profile, in the same class as the headline:

- A viewer of another member's profile sees the subject's profession.
- A viewer the subject blocked, or a subject who opted out of the directory, sees the reduced
  card only: `scripts/bridge-profile.mjs:90-97` returns `userId`, `name` and `avatar` and
  nothing else. The profession must not appear there.
- The profession is written by its owner and by nobody else.

### P2-4-b — Home regeneration must not overwrite user edits

**B1 — The re-seed trigger.** `src/widgets/page-renderer/ui/MainContent.tsx:48-51` —
`homeDashboardNeedsRefresh` returns `true` **only** when:

- the Home page does not exist yet, or
- `page.homeDashboardVersion !== HOME_DASHBOARD_VERSION` (a deliberate bump by a later
  package), or
- `page.homeProfession !== currentProfession` (added by P2-4-e; compare `?? null` on both
  sides, or an absent field and a `null` field would look like a change).

`hasHomeDashboardSections` (`src/widgets/page-renderer/ui/MainContent.tsx:36-46`) is **removed**
as a trigger and deleted. A stale seed is caught by the version check: every change to the
seed's structure bumps `HOME_DASHBOARD_VERSION`, so no separate "is this layout still current"
probe is needed.

**B2 — Every re-seed is a three-way merge (decision 7).**

- **Fingerprints.** The page records what it seeded in a new client-local field,
  `homeSeedFingerprints?: Record<string, string>`, on `PageEntry`, next to
  `homeDashboardVersion` (`src/entities/page/model/types.ts:76-77`). It maps each seed block id
  to a fingerprint of that block as it was seeded: FNV-1a over `JSON.stringify(block)`, in hex.
- **The merge is a pure function** in a new `src/widgets/page-renderer/model/homeContentMerge.ts`:
  `mergeHomeContent(current: Block[], nextSeed: Block[], fingerprints?: Record<string, string>): { content: Block[]; fingerprints: Record<string, string> }`.
  It decides each block by this table:

| Block | Rule |
|---|---|
| in `current`, id not in `fingerprints` | the user's: kept, in place |
| seeded, in `current`, fingerprint unchanged | replaced in place by `nextSeed`'s block of the same id; removed when `nextSeed` no longer has that id |
| seeded, in `current`, fingerprint changed | the user edited it: kept as written, and its old fingerprint kept so it stays "edited" |
| seeded, absent from `current` | the user deleted it: stays deleted, and its fingerprint entry kept |
| in `nextSeed`, id never seeded | new: inserted after the nearest preceding `nextSeed` block that is in the result, else first |

- **No Home page yet:** `content = nextSeed`, with every block fingerprinted.
- **Legacy pages** (no `fingerprints`; every Home cached before this change): a `current`
  block whose id is also in `nextSeed` counts as seeded and unchanged, and every other block
  counts as the user's. Write a `Caveat:` in the source. A seed block someone edited *before*
  this change loses that edit once, on the first merge. Today it loses it on every reload.
- **Fingerprint caveat**, also in the source: the fingerprint covers the whole block JSON. If
  the editor normalises a block on load (adds a default key), an untouched seed block reads as
  edited. That failure is the safe direction: the block keeps its old seed content and nothing
  is lost. The fix would be to fingerprint a normalised projection.
- **Idempotent:** a second merge with the same `nextSeed` returns the same content and the same
  fingerprints.

**B3 — The re-seed must not loop.** After the write the page carries
`homeDashboardVersion: HOME_DASHBOARD_VERSION` (`src/widgets/page-renderer/ui/MainContent.tsx:85`),
so B1's first condition is false on the next run. The effect's dependency list already contains
the page object (`MainContent.tsx:137`); assert the no-loop in the test.

**B4 — What is preserved.** The Home page is client-local, so nothing new is persisted: the
merged content and its `homeSeedFingerprints` go through `savePagesCache`
(`src/widgets/page-renderer/ui/MainContent.tsx:128`). Neither field joins the page-file
front-matter (`src/features/page-file/model/pageFileMeta.ts:40-58`).
