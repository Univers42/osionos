## Why (verified anchors)

- **Four routes answer a bare access token.** TOTP `verify` ends in `upgraded()` (`scripts/bridge-account-mfa.mjs:72-75`, called `:119`); `disable` calls it too (`:150-162`); recovery `verify` answers `{ ok, accessToken, expiresAt, aal: 2, remaining }` (`scripts/bridge-account-mfa-recovery.mjs:186-187`). No refresh token in any of them.
- **The token is the same session, same jti.** `issueAal2` (`scripts/bridge-account-mfa-state.mjs:96-111`) signs with `jti: raw.jti` and `exp: raw.exp`. Sudo is keyed on that jti (`scripts/bridge-guard.mjs:185-199`).
- **Confirm and disable cut every session.** `confirm` (`bridge-account-mfa.mjs:104-118`) and `disable` (`:150-160`) call `cutAllSessions` (`:54-57`), which writes `sessions_valid_after = atMs`. A verify of an already-verified factor and the recovery verify write **no** cut-off (`:117` takes `ctx.clock()`; recovery has none).
- **The cut-off refuses the old family.** `refreshSession` calls `assertSessionNotCutOff(config.sessionCutoffs, payload.sub, payload.fam_iat_ms)` (`scripts/bridge-sessions.mjs:513`); it refuses when `issuedAtMs*1000 < cutoff` (`scripts/bridge-session-cutoff.mjs:144-155`). A family born at `iat == atMs` passes (strict `<`).
- **So the symptom is real after confirm and disable:** the only refresh token the device holds belongs to the cut family; when the aal2 access token dies (`config.sessionTtlSeconds`, about 1 h) the refresh answers 401 `session_revoked` and the user signs in again. After a plain/recovery verify the old family still refreshes, but to aal1: a refresh never raises assurance (`bridge-sessions.mjs:462-463`).
- **How sign-in mints a family.** `recordSession` (`bridge-sessions.mjs:186-204`) decodes the access token, calls `mintRefreshToken` (`scripts/bridge-refresh-token.mjs:49-72`) with `refreshClaimsFor` (`:161-178`), inserts the root row (`id = family_id = jti`, `:189-202`) via `insertRow` (409 on a duplicate jti, `:206-213`) and returns `{ row, refreshToken }`. `recordDeliveredSession` (`:221-224`) is the config-gated wrapper (null when `sessionRecords` is off). Rotation (P3-3-a): `refreshSession` `:496-528`, reuse detection `hasChild` + `answerReuse` `:410-440`, unique `parent_id` index in `/home/dlesieur/Documents/groot-wt/root-integration/models/osionos-session-refresh-migration.sql:47`. `revokeFamily` (`:343-348`) is module-private.
- **A family born aal2 refreshes ungated.** `refreshClaimsFor` drops `mfa_req` when `aal === 2` (`:176`), and `nextTokens` only keeps aal1 gating if the refresh payload carries `mfa_req` (`:463`).
- **Client.** The two-step client calls `adoptSessionToken` → `adoptStepUpToken` with the access token only (`src/features/settings/profile/twoStepClient.ts:60-63`; `src/features/auth/model/useUserStore.ts:441-448`), which spreads `{ ...live, accessToken }` and keeps the old `refreshToken`. The refresh path stores both via `applyRefreshed` + `persistRefreshed` (`useUserStore.ts:424-437`) and sends `session.refreshToken` (`sessionRefresh.ts:102-114`). The `verify`/`disable` calls are typed `{ accessToken?: string }` (`twoStepClient.ts:69,71`).
- **`recordSession` cannot be reused as is for the same jti:** the row id is the jti and `insertRow` answers 409 on a repeat. The new family therefore needs a **new jti**, hence a new access token (see Contract).

## Contract

**Response (all four routes):** the existing fields stay; add `refreshToken: string` (`osb_rt.…`, as sign-in and `/refresh` return it) and `refreshExpiresAt` is **not** added (the client never reads it). `expiresAt` is the new access token's expiry in ms. When session records are off (`recordDeliveredSession` returns null) the field is absent and nothing changes from today.

**Mint (one function, no copy):** a new exported `startStepUpFamily({ config, pg, request, session, nowMs, gated })` in `scripts/bridge-sessions.mjs` (kept small; if the file passes the 300-line limit more than it already does, put it in `scripts/bridge-session-stepup.mjs`, which imports `recordSession`). It signs an aal2 access token with a **fresh jti** (`signAppSessionToken`, same workspaces/roles/admin/provider as `issueAal2`, `exp = raw.exp`, never later than the old family) and calls `recordSession(..., { authMethod: 'refresh' })` unchanged. `issueAal2` is not duplicated: it gains an optional `jti` and the routes pass the new one. `gated` decides whether the refresh payload keeps `mfa_req` (see open question 1; default: `true` after confirm/verify, `false` after disable, so a refresh never raises assurance and the sign-in-with-2FA behaviour is unchanged).

**Old family:** revoked in the same step with the existing `revokeFamily` (export it; reason `step_up`), for all four routes. After confirm/disable the cut-off already refuses it; for a verify of an enrolled factor and the recovery verify there is no cut-off, so the explicit revoke is what makes "the old family stays refused" true. The revoke runs **after** the new root row is inserted (never leaves the device with no family). The old access token (≤1 h) expires by itself; it is not revoked individually.

**Attacker with only the OLD refresh token:** nothing. `holderOf` finds its row, `revoked_at` is set → 401 `session_revoked` (`bridge-sessions.mjs:511`); after confirm/disable the cut-off refuses it first. It also cannot reach the new family: the new token is a different family and its hash is not derivable.

**Mint fails after the factor is verified: fail closed on the token, never undo the factor.** The factor flip/code spend/cut-off already happened and are not reversible (a spent code stays spent). The route answers 503 `session_record_unavailable` with no access token; the client keeps its old tokens and the UI says "try again" (the next verify needs a fresh code; the old access token still works until expiry unless the cut-off refused it, in which case the user signs in again as today). Fail-open (answer an aal2 token with no refresh) would re-create this bug silently, so it is rejected. When records are *off* the route answers as today (not a failure).

**Unchanged:** the verify code is single-use (`claimStep` `:79-87`, `spend` recovery `:157-160`) and runs before the mint; one mint per accepted code. The rate limits, lock-out and `countAttempt` stay as they are (`VERIFY_LIMIT`, `bridge-account-mfa.mjs:133`; recovery `:175`). The mint does not retry.

**Client:** `adoptStepUpToken(userId, accessToken, refreshToken?)` writes both to the live store and the saved record, the same shape `applyRefreshed` writes; an absent `refreshToken` keeps today's behaviour. `twoStepClient.ts` passes `body.refreshToken` through; the types gain `refreshToken?: string`. Cross-tab: the refresh single-flight publishes `prev` → new tokens (`sessionRefresh.ts:188-216`); the step-up does not publish, other tabs holding the old refresh token get a 401 and sign out once (see open question 3).

## Open questions

1. **Assurance of the new family.** Default above keeps `mfa_req` so a refresh drops to aal1 (like sign-in). If the user wants the device to stay aal2 for the family's 7 days, `gated=false` is one flag, but a stolen new refresh token would then mint aal2 tokens for 7 days: decide before building.
2. **Sudo carry-over.** The new jti loses `sudo:<old jti>` (`bridge-guard.mjs:191`), so right after a verify `regenerate`/`disable` ask for sudo again. Not verified whether the UI copes; copying the grant to the new jti is a 3-line option.
3. **Other tabs / `persistRefreshed` publish.** Not verified whether another tab of the same user races the old refresh token; the step-up does not publish through the `Published` channel.
4. **`sessionRecords` off** in a deployment: assumed "no refresh anywhere", so the field is absent; not verified for the fly config.
5. **Session list.** `redateSession` (`bridge-account-mfa.mjs:63-69`) patches by `family_id = old jti`; the new family needs no redate (its `created_at = atMs`), the old one is revoked; the list collapse not re-tested.

## Orchestrator decisions (2026-10-24), binding over the open questions above

1. **The new family carries the assurance it was minted with, so `gated=false` and no `mfa_req`.** A refresh within the family keeps aal2 until the family's absolute lifetime ends or the family is revoked. This is how a GoTrue session keeps its AMR across refreshes. Dropping to aal1 on every refresh would ask for the code every hour, which is the bug this package exists to remove. The risk that a stolen refresh token keeps minting aal2 is the same risk as any stolen refresh token. The P3-3-a reuse detection and the per-session revoke already bound it. The devil review must rule on whether that bound is enough.
2. **The sudo grant moves with the session.** The step-up copies `sudo:<old jti>` to `sudo:<new jti>` with the SAME expiry, never a new one, so `regenerate` right after a verify does not ask for sudo again. This adds no new grant: the user has just proved a factor.
3. **Other tabs (open question 3).** A tab holding the old refresh token gets 401 `session_revoked` on its next refresh and signs in again. The spec accepts this, and the e2e asserts the old token is refused. Cross-tab adoption of the new token is out of scope (a later P3-3 item).
4. **Session records off (open question 4).** When session records are off, there are no families: the routes answer exactly as today, with no `refreshToken` field, and a bridge test pins that.
5. **Sessions list (open question 5).** One bridge test lists sessions after a verify and expects one live row for this device (the new family) and the old one gone or marked revoked, whichever the list already does for a revoked family.
