## Why (verified anchors)

- **Four routes answer a bare access token.** TOTP `verify` ends in `upgraded()` (`scripts/bridge-account-mfa.mjs:72-75`, called `:147`); `disable` calls it too (`:162`, route `:150-163`); recovery `verify` answers `{ ok, accessToken, expiresAt, aal: 2, remaining }` (`scripts/bridge-account-mfa-recovery.mjs:186-187`). No refresh token in any of them.
- **The token is the same session, same jti.** `issueAal2` (`scripts/bridge-account-mfa-state.mjs:96-111`) signs with `jti: raw.jti` and `exp: raw.exp`, and returns `expiresAt` as an **ISO string**. Sudo is keyed on that jti (`scripts/bridge-guard.mjs:185-199`).
- **Confirm and disable cut every session.** `confirm` (`bridge-account-mfa.mjs:102-116`, doc comment `:101`) and `disable` (`:150-163`) call `cutAllSessions` (`:54-57`), which writes `sessions_valid_after = atMs`. A verify of an already-verified factor takes `ctx.clock()` (`:145`) and writes **no** cut-off; the recovery verify has none either.
- **The cut-off refuses the old family.** `refreshSession` calls `assertSessionNotCutOff(config.sessionCutoffs, payload.sub, payload.fam_iat_ms)` (`scripts/bridge-sessions.mjs:513`); it refuses when `issuedAtMs*1000 < cutoff` (`scripts/bridge-session-cutoff.mjs:144-155`). A family born at `iat_ms == atMs` passes (strict `<`).
- **So the symptom is real after confirm and disable:** the only refresh token the device holds belongs to the cut family; when the aal2 access token dies (`config.sessionTtlSeconds`, about 1 h) the refresh answers 401 `session_revoked` and the user signs in again. After a plain/recovery verify the old family still refreshes, but to aal1 when it was born gated: a refresh never raises assurance (`bridge-sessions.mjs:462-463`).
- **How sign-in mints a family.** `recordSession` (`bridge-sessions.mjs:186-204`) decodes the access token, calls `mintRefreshToken` (`scripts/bridge-refresh-token.mjs:49-72`) with `refreshClaimsFor` (`:161-178`), inserts the root row (`id = family_id = jti`, `:189-202`) via `insertRow` (409 on a duplicate jti, `:206-213`) and returns `{ row, refreshToken }`. `recordDeliveredSession` (`:221-224`) is the config-gated wrapper (null when `sessionRecords` is off, `:222`; `sessionRecordsFromConfig` `:70-73`). Rotation (P3-3-a): `refreshSession` `:496-529`, reuse detection `holderOf` `:408-412` + `hasChild` + `answerReuse` `:414-440`, unique `parent_id` index in `/home/dlesieur/Documents/groot-wt/root-integration/models/osionos-session-refresh-migration.sql:47`. A rotated child row has `family_id = holder.family_id` and `id = tokens.jti` (`:466-485`), so **after one refresh the latest row id is not the family root**. `revokeFamily` (`:343-348`) is module-private and filters `family_id = familyId` (or `id = rowId` when there is none); it returns the count of rows it revoked. `stampRevoked` applies every revoked row id locally (`:335-337`), so the caller's current access token dies at once on this replica and within one poll (10 s) on others (ADR 0003 "What a revoke does not end").
- **A family born aal2 refreshes ungated.** `refreshClaimsFor` drops `mfa_req` when `aal === 2` (`:176`), and `nextTokens` only keeps aal1 gating if the refresh payload carries `mfa_req` (`:463`). So `recordSession` of an aal2 access token yields an **ungated** family; `gated` cannot be expressed and is not a parameter.
- **Client.** The two-step client calls `adoptSessionToken` (`src/features/settings/profile/twoStepClient.ts:61-63`) → `adoptStepUpToken` (`src/features/auth/model/useUserStore.ts:441-448`) with the access token only; it spreads `{ ...live, accessToken }` and keeps the old `refreshToken`. The modal calls it at `src/features/settings/profile/TwoFactorModal.tsx:65` (confirm) and `:82` (disable). The refresh path stores both via `applyRefreshed` + `persistRefreshed` (`useUserStore.ts:424-437`) and sends `session.refreshToken` (`sessionRefresh.ts:102-114`) through `refreshOne` (`useUserStore.ts:458-464`), reading `currentTokens` (persisted record first, `:417-422`). Only two client callers exist: `confirmEnrolment` (`twoStepClient.ts:66`) and `disableTwoStep` (`:68`). Plain-verify of an enrolled factor and recovery verify have **no client caller** (`rg '2fa/verify|recovery/verify' src`).
- **`recordSession` cannot be reused as is for the same jti:** the row id is the jti and `insertRow` answers 409 on a repeat. The new family therefore needs a **new jti**, hence a new access token (see Contract).
- **Sudo has no TTL read.** The kv interface offers `get/set/setNx/getDel/incrWithTtl/del` only (`scripts/bridge-kv.mjs:97-134`), no remaining-TTL call. The grant is `sudo:<jti>` (`bridge-guard.mjs:185-199`); its expiry exists only in the best-effort ISO string `sudo-expires:<jti>` (`scripts/bridge-account-sudo.mjs:222-227`, errors swallowed), read by the status route (`:274-276`). `password.mjs:135` spends `sudo:<jti>` by raw jti.
- **The lookup exists twice.** `liveRowOf` (`bridge-sessions.mjs:367-377`, live rows only, used at `:383`) and `ownFamily` (`scripts/bridge-account-password.mjs:102-105`, any row, used at `:121`) are the same read.
- **ADR 0003 rule 3 today:** "Nothing but `bridge-sessions.mjs` writes `osionos_sessions`" (`docs/account-platform/adr/0003-session-rows-are-written-by-the-bridge.md:35`); `redateSession` (`bridge-account-mfa.mjs:64-70`, `PATCH ... family_id = raw.jti`) already bends it and is wrong for a rotated session.

## Contract

**Response (all four routes):** the existing fields stay; add `refreshToken: string` (`osb_rt.…`, as sign-in and `/refresh` return it). `refreshExpiresAt` is **not** added (the client never reads it). `expiresAt` stays the **ISO string** `issueAal2` returns (`bridge-account-mfa-state.mjs:96-111`); the new access token's expiry is that value. When session records are off (`recordDeliveredSession` returns null) the field is absent and nothing changes from today (see "Records off").

**Shared row lookup (C3, one copy):** `bridge-sessions.mjs` exports `sessionRowOf(pg, { sessionId, userId })`, the one read of `id,family_id,revoked_at` for a row the user owns (any state, `limit 1`). `liveRowOf` and `ownFamily` are **deleted**: `revokeSession` (`:383`) uses `sessionRowOf` and treats a row with `revoked_at` as absent (same 404 as today); `bridge-account-password.mjs:121` uses `(await sessionRowOf(deps.pg, { sessionId: own, userId: session.userId }))?.family_id ?? own`, lower-cased as today. ADR 0003 stays true: the module that reads is not a writer.

**Mint (one function, no copy, C2/C4/C9/C12):** a new exported `startStepUpFamily({ config, pg, kv, request, session, nowMs })` in a new `scripts/bridge-session-stepup.mjs` (`bridge-sessions.mjs` is 567 lines; it only gains the `sessionRowOf` and `revokeFamily` exports). The new module does **no `pg` write of its own**: it imports `recordDeliveredSession` and `revokeFamily` and calls them. Its header carries the one-line ADR 0003 amendment: "the step-up insert calls `recordSession`; it writes nothing else". Steps, in this order:
1. Records off (`!config.sessionRecords?.enabled`): return `null`; the route answers as today (see "Records off").
2. **Live row only (C2):** `row = await sessionRowOf(pg, { sessionId: session.raw.jti, userId: session.userId })`. Row exists and `revoked_at` set → 401 `session_revoked`, **no new family, nothing minted**. No row (legacy token minted before records) → mint anyway, with no old family to revoke.
3. Sign the access token with `issueAal2(session, config, { nowMs, jti: randomUUID() })` (`issueAal2` gains an optional `jti`, otherwise unchanged; same workspaces/roles/admin/provider; `exp = raw.exp`, so the access token never outlives the old session).
4. `recordDeliveredSession(config, pg, { request, accessToken, authMethod: 'refresh' })` — unchanged `recordSession`; the refresh payload has no `mfa_req` and no `aal` (the family is not gated). Persona is omitted: the refresh payload's `email`/`name` are not read on rotation (`nextTokens` `:445-486`).
5. Revoke the old family (next section). Order is insert then revoke, so the device is never left without a family.
6. **Single mint (C12):** a call whose revoke of the old family returned `0` rows (row existed in step 2) lost a race with another accepted verify that revoked it first; it revokes its own new family (best effort) and answers 401 `session_revoked`. Hence two parallel accepted verifies leave at most one live new family.
7. Sudo copy (best effort, below). Return `{ token, expiresAt, refreshToken }`.

The three TOTP/recovery routes call it from their final step (`upgraded()` becomes async and takes the request; recovery `:186-187` likewise); one accepted code is exactly one `startStepUpFamily` call, after `claimStep`/`spend`. The new family's refresh expiry is `familyRefreshExp(config, raw.exp)` (`bridge-refresh-token.mjs:79-81`), i.e. a fresh refresh TTL (about 7 days) from every step-up, not capped by the old family; accepted (a factor, or sudo for disable, was just proven).

**Assurance (C1, orchestrator decision 1, binding):** the new family is **not gated**. A refresh inside it stays aal2 until the family's absolute expiry or a revoke. In this tree "aal2" means only "not mfa-pending" (`scripts/bridge-session-token.mjs:182-185,204`); a gated family refreshes to aal1 (`bridge-sessions.mjs:463`), an ungated family refreshes without an `aal` claim, which counts as aal2. So a **stolen refresh token from a post-step-up family needs no code for up to `familyRefreshExp` (about 7 days)**; today it can never be used alone. Accepted bound, recorded in the new `docs/account-platform/adr/0009-step-up-family-keeps-aal2.md` (short): reuse detection (`bridge-sessions.mjs:414-440,514`, fires only when thief and owner both refresh), per-session revoke, sudo on destructive routes (`bridge-guard.mjs:194-199`), and the 7-day absolute lifetime. The ADR states that the alternative (hourly code prompt) is the bug this package removes.

**Old family (C3/C13):** revoked with the existing `revokeFamily` (export it; reason `step_up`), called with `familyId: row.family_id` and `rowId: row.id` from the step-2 row (never `session.raw.jti` as the family id: that matches zero rows after the first refresh). All four routes do it. After confirm/disable the cut-off already refuses it; for a verify of an enrolled factor and the recovery verify there is no cut-off, so the explicit revoke is what makes "the old family stays refused" true. The revoke runs **after** the new root row is inserted. The old access token **is** revoked too: `stampRevoked` applies the revoked row ids locally at once and other replicas within one poll (10 s). `redateSession` (`bridge-account-mfa.mjs:64-70`) is removed from the step-up path (the new root row has `created_at = atMs`); it stays only on the records-off path, unchanged.

**Sudo (C5, orchestrator ruling):** after the revoke, copy the grant only when `kv.get('sudo:<old>') === userId` **and** `kv.get('sudo-expires:<old>')` parses to a future instant. Then `remaining = max(1, expiry - now)`; write `sudo:<new>` (value = userId) and `sudo-expires:<new>` (the **same ISO string**) with TTL `remaining`. No `sudo-expires` or past: copy nothing. Never extend, never create. A copy failure is swallowed (the user is asked for sudo again); a mint failure is not.

**Attacker with only the OLD refresh token:** nothing. `holderOf` finds its row, `revoked_at` is set → 401 `session_revoked` (`bridge-sessions.mjs:510`); after confirm/disable the cut-off refuses it first. It also cannot reach the new family: the new token is a different family and its hash is not derivable.

**Failure (C6, fail closed on the token, never undo the factor).** The factor flip, code spend and cut-off already happened and are not reversible (a spent code stays spent, `bridge-account-mfa.mjs:118-126`, recovery `spend` `bridge-account-mfa-recovery.mjs:156-159`).
- (a) The root-row insert fails: 503 `session_record_unavailable`; the body has no `accessToken` and no `refreshToken`. On **plain verify and recovery verify** the old session is still live (no cut-off): the client keeps its tokens and says "try again" (needs a fresh code). On **confirm and disable the cut-off has already refused the old family, so this device is signed out everywhere with the factor already flipped (confirm) or already deleted with its codes (disable, `:156-160`)**: say so plainly in the 503 message ("two-step verification changed; you are signed out, sign in again"), and the client shows the sign-in (see Client).
- (b) The old-family revoke throws after the insert: 503, same body; the unused new row is revoked best effort. The old family stays live (fail-safe: if it was gated it still reaches only aal1).
- (c) The sudo copy throws: ignored.
- Fail-open (answer a bare aal2 token with no refresh) would re-create this bug silently and is rejected. When records are *off* the route answers as today (not a failure). The mint does not retry.

**Records off (C7):** when `startStepUpFamily` returns `null`, routes call `issueAal2` with the **old jti** exactly as today, answer today's body (no `refreshToken`), call `redateSession` as today, and write no sudo key (sudo on the old jti stays valid because the jti is unchanged).

**Unchanged:** the verify code is single-use (`claimStep` `bridge-account-mfa.mjs:118-126`, recovery `spend` `bridge-account-mfa-recovery.mjs:156-159`) and runs before the mint. The rate limits, lock-out and `countAttempt` stay (`VERIFY_LIMIT` defined `bridge-account-mfa-state.mjs:32`, used `bridge-account-mfa.mjs:133`; recovery `:175`).

**Client (C9/C10):**
- `adoptStepUpToken(userId, accessToken, refreshToken?)` writes both to the live store and the saved record, the same shape `applyRefreshed` writes; an absent `refreshToken` keeps today's behaviour. `adoptSessionToken(userId, accessToken, refreshToken?)` (`twoStepClient.ts:61-63`) forwards it; `confirmEnrolment` (`:66`) and `disableTwoStep` (`:68`) types gain `refreshToken?: string`. `TwoFactorModal.tsx:65,82` pass `done.refreshToken`. **No client change for plain/recovery verify** (no caller): they are tested bridge-side only.
- **In-flight refresh must not win over the step-up (C10):** in `refreshOne` (`useUserStore.ts:458-464`) remember the refresh token each rotation started from; when its result arrives, `adopt` and `signOut` do nothing unless `currentTokens(userId)?.refreshToken` still equals that token. This covers both a late `applyRefreshed` overwriting the step-up tokens and a late 401 `session_revoked` (the step-up revoked the family the rotation used) signing the user out. `sessionRefresh.ts` is not touched.
- **Mint failure on confirm/disable:** the modal recognises the 503 `session_record_unavailable` of those two calls, shows the sign-in message and drops the local session through the store (an exported thin wrapper over `clearLocalSession`, `useUserStore.ts:397`, if no export exists). It must not call `logoutUser`, which would try to revoke an already-refused session.
- Cross-tab: the step-up does not publish; other tabs holding the old refresh token get 401 and sign in once (Decision 3).
