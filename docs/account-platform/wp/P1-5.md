# P1-5 — settings stores reach the bridge with the right token, and never report a success that did not happen

Repo: osionos app, branch `feat/acct-P1-5` from `feat/account-platform` (after P1-3b, `0346daf5`).
Frontend only; the routes themselves land in P1-2, so every account route still answers 404 on
this branch. Facts below are from research run R-P1-25 (2026-10-22); re-check each anchor before
editing.

## Why
1. **Wrong token.** Every settings store calls the bridge through `trySettings*`
   (`src/store/settings/settingsStoreUtils.ts:76-111`), whose default is `settingsJwt()` →
   `getActiveJwt()` (`src/shared/api/client.ts:54`), the gotrue-only token. It is blank for a bridge
   session, and the bridge only accepts the `osionos_v1.` app-session token
   (`scripts/bridge-api.mjs:447-479`). So under a bridge session every store silently stays local.
   `getActivePageJwt()` (`client.ts:62-67`) works for both session kinds. `postAccountAction`
   (`src/features/settings/model/settingsCalls.ts:29-32`) has the same defect.
2. **False successes.** These are the ones that matter most:
   - **Account deletion.** `ProfilePanel.tsx:107-113` toasts "Account scheduled for deletion in
     30 days" and signs the user out, although no deletion route exists. `postAccountAction` returns
     `null` and nothing checks it.
   - **Two-step verification.** `ProfileSecurityModals.tsx:96` shows hard-coded recovery codes
     (`'A12B-C34D', …`) and says two-step verification is on.
   - **Password and 2FA disable.** `:72` and `:95` toast success on the same `null`.
   - **Devices.** The table always shows a hard-coded `'Ubuntu · This Device'` row
     (`ProfilePanel.tsx:92,161`).
   - **User ID.** The User ID row falls back to a fixed UUID (`ProfilePanel.tsx:165`).

   A user who believes their account is deleted or protected by 2FA when it is not has been told a
   security lie.
3. **Path collision.** `useNotificationSettingsStore.ts:43,57` uses `/api/notifications`, which
   `scripts/bridge-notify.mjs:62` owns as the chat inbox. The store reads the inbox shape and its
   PATCH answers 404.
4. **No sudo signal.** The bridge's `requireSudo` answers 403 `{ code: 'sudo_required' }`
   (`scripts/bridge-guard.mjs`). The client has no way to say "re-authenticate", and P1-6's
   `SudoPrompt` needs one.

## Contracts
1. **One token.** `settingsJwt()` returns `getActivePageJwt()`; every `trySettings*` default and
   `trySettingsUpload` use it. Delete the comment block at `settingsStoreUtils.ts:69-74` (it
   explains the old default) and the per-call `getActivePageJwt()` overrides that are now
   redundant. `postAccountAction` uses the same token.
2. **"Not offered yet" reads like offline, for settings sync.** In the `trySettings*` wrappers, an
   `ApiError` with status 404 or 501, or 503 with a code ending `_unavailable` or `_off`, returns
   `null`, exactly as when `API_BASE` is empty. The store keeps working locally with no error toast.
   Log one `console.info` per path per page load, naming the path. Every other error behaves as
   today.
   Caveat to state in the code: a genuine 404 on a route that exists (a mistyped path) is also
   silenced; acceptance 2 proves the classification, and P1-2's e2e proves the routes.
3. **Actions return an outcome, never a bare `null`.** `postAccountAction` becomes
   `runAccountAction<T>(path, body)`, returning one of:
   - `{ ok: true, data: T }`
   - `{ ok: false, reason: 'unavailable' | 'sudo_required' | 'failed', message: string }`

   `'unavailable'` covers offline (no `API_BASE` or no token) and the statuses in contract 2.
   - A success toast, sign-out or state change happens **only** on `ok: true`.
   - On `'unavailable'`, show an honest notice ("<Action> isn't available on this server yet").
   - On `'sudo_required'`, show nothing extra (contract 4 handles it).
   - On `'failed'`, show the message.

   Update every caller: deletion, password, 2FA enrol/verify/disable, and any other
   `postAccountAction` use.
4. **Sudo signal in the shared fetch path.** Add `src/shared/api/sudoRequired.ts` next to
   `sessionRevocation.ts`, in the same style:
   - `onSudoRequired(listener) → unsubscribe`;
   - the wrapper in `client.ts` reports every 403 whose body `code === 'sudo_required'`, with the
     request's method and path, and returns the response untouched.

   Compose it with `revocationAwareFetch` in the one place `client.ts` builds `api`; there must
   not be a second wrapper chain. No UI listens yet; P1-6 adds it.
5. **No invented data.**
   - Recovery codes are shown only from the server response; no fallback list.
   - The User ID row shows the persona's id or nothing; no literal UUID.
   - The devices table lists only rows the server returned. With none (offline or unavailable),
     it shows exactly one row for the current browser, labelled from `navigator.userAgent` the way
     `defaults.ts:40-53` already does; the hard-coded `'Ubuntu · This Device'` row goes.
   - "Log out of all devices" calls the existing, real `logoutUser(userId)` (sign-out-everywhere,
     `src/features/auth/model/bridgeLogout.ts:114`). Its copy says it signs this device out too.
     `useAccountDevicesStore.revokeAllExceptCurrent`'s `DELETE /api/account/devices` stays for
     P3-3 but is no longer what that button calls.
   - Deletion copy says 14 days (the grace period P1-1 enforces), not 30.
6. **Notification settings path** → `/api/account/notification-settings` (GET/PATCH, the same
   body shapes). P1-2 serves it.

## Tests (write first, see them fail)
1. `tests/canvas/sudo-required.test.ts`, following `tests/canvas/bridge-logout.test.ts`'s
   injection style: a 403 `{code:'sudo_required'}` reaches the listener with method and path and
   the response is returned untouched; a 403 with another code, or a 401, does not.
   Unsubscribing stops delivery. Composed with the revocation wrapper, a `session_revoked` 401
   still reaches its own handler.
2. `tests/canvas/settings-api.test.ts`:
   - `runAccountAction` returns the right outcome for 200, 204, 404, 501, 503 `x_unavailable`,
     503 `other`, 403 `sudo_required`, 500, a network `TypeError`, and offline;
   - the token is `getActivePageJwt()`'s for a bridge-shaped session;
   - the settings-sync classification returns `null` for 404 but throws for 500.

   If importing the real modules fails under `node --test` (`import.meta.env`), extract the
   classification into a pure function in `settingsStoreUtils.ts` and test that. Say which you did.
3. `tests/e2e/functional/settingsHonesty.spec.mjs` (the offline Playwright build):
   - Profile → Delete account → type the confirmation → the honest "not available" notice shows,
     the user is still signed in (the workspace is still there after the click), and no
     "scheduled for deletion" text appears;
   - two-step verification: no recovery code is ever rendered;
   - the devices table has exactly one row and no "Ubuntu" text unless the browser's UA says so.
