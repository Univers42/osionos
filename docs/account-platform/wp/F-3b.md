## Contract

### Secrets
Names only; values never printed. `OSIONOS_EMAIL_SEAL_KEY` (+ `_PREVIOUS`): 32 bytes base64, AES-256-GCM. `OSIONOS_EMAIL_LOOKUP_KEY`: HMAC-SHA256 key, >= 32 bytes. Read from `env` exactly like `OSIONOS_MFA_SECRET_KEY` (O5). They are separate from `OSIONOS_MFA_SECRET_KEY` so one leak or rotation does not move the other.
- **Absent or malformed** => every MUTATING route answers 503 `email_unavailable`, sends nothing, and the GET lists the primary with header `x-emails-secondaries: unavailable` (see Missing table). Preflight names the variables set/unset.
- **Equal keys (O4, amended by the orchestrator after the fold).** At module setup (`createAccountEmailsRoutes`), once, the RAW env strings are compared: seal vs `OSIONOS_MFA_SECRET_KEY`, lookup vs seal, lookup vs `OSIONOS_MFA_SECRET_KEY` (only when both sides are set and non-empty). Equal keys are treated EXACTLY like unset keys: every mutating route 503 `email_unavailable`, the GET lists the primary with `x-emails-secondaries: unavailable` (the primary comes from GoTrue and needs no key; blanking the modal helps nobody). The difference is the noise: exactly one startup log line names the equal variables (names only, never a value), never repeated per request.
- **Seal primitive.** `scripts/bridge-seal.mjs` exports `createSeal({ keyEnv, aadLabel, fail })` returning `{ seal(plain, userId, env), open(sealed, userId, env) }`; it takes the env NAME and loops current then `<name>_PREVIOUS` exactly as `openSecret` does (a malformed previous key is ignored). `bridge-account-mfa-totp.mjs` keeps `sealSecret(secret, userId, env)` / `openSecret(sealed, userId, env)` with the same signatures, the same `mfa_unavailable` code and the byte format `v1.`+base64(iv||tag||ct); its test (`tests/bridge/bridge-account-mfa-totp.test.mjs:102-103`) stays UNCHANGED. The email instance uses `keyEnv: 'OSIONOS_EMAIL_SEAL_KEY'`, `aadLabel: 'osionos-user-email:v1:'` and fails with 503 `email_unavailable`.
- **After opening a row** the HMAC of the opened address is recomputed with the lookup key and compared to `email_hmac`; a mismatch OMITS the row from the GET (counted in `x-emails-skipped`) and refuses it on every `:id` route as 404 `not_found`.
- **Rotation.** The seal key rotates through `_PREVIOUS`, but there is NO re-seal path: `_PREVIOUS` must stay set until a re-seal job exists. The lookup key has NO rotation: changing it orphans every `email_hmac`, the verified-unique index silently stops matching and every address looks free. Rotating it is unsupported without a backfill that re-HMACs every row from the opened address (a future package). Both rules go in the module `Caveat:`.

### Add (validation)
Trim, lowercase, `<= 254` chars. Charset: exactly one `@`; local part ASCII RFC 5322 `atext` (`A-Za-z0-9` and ``!#$%&'*+/=?^_`{|}~-``) in dot-separated non-empty atoms (no leading, trailing or doubled dot); domain: at least two dot-separated LDH labels (`[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?`), last label alphabetic of length >= 2. No `,;<>"()` and no control character (0x00-0x1f, 0x7f), no whitespace. Reason: grobase builds `To: %s` from the raw string (`loginotp/smtp.go` `buildMessage` `:31-33`), so a comma or a CRLF would be header injection. 422 `invalid_email` otherwise. (The sudo `ADDRESS_SHAPE` is looser and is NOT reused for validation; `maskAddress` is reused.)
Then: equal to the caller's primary => 409 `already_primary`. At most 3 unverified rows per user (409 `too_many_pending`); unverified rows older than 1 hour are deleted at add, BEFORE the cap check.

### Add (answer and effects)
The answer is written BEFORE the grobase request resolves, in ALL FOUR cases (a free address, another user's verified address, another user's confirmed GoTrue primary, the caller's own pending address). Order of effects, identical in every case:
1. limits and counters (next section) — a kv failure here => 503 `email_unavailable`, before anything else;
2. audit `account.email_add_requested` (details `{}`; never the address). The audit row comes BEFORE the row insert and the mail (`writeAudit`, `bridge-guard.mjs:218-224`); a failed audit is a 503 and nothing else happens;
3. row: insert a new unverified row, or, for the caller's own existing row (pending or verified), reuse it (no second row);
4. answer 202 `{id, sentTo: maskAddress(email)}`;
5. then a **detached promise** (`void Promise.resolve().then(task)`), scheduled in all four cases: the availability decision (GoTrue primary lookup + verified-by-another-user row + own-verified, see GoTrue primary lookup) and, only if the address is available AND the row is not verified AND the send budgets allow, the grobase request. For every "unavailable" case the task is a no-op with the same scheduling.
The task's failure (grobase down, 502 `send_failed` for an undeliverable address, GoTrue down, a thrown error) is caught inside the task and logged by CODE only, never with the address, a code or a proof; it never reaches the caller and never becomes an unhandled rejection. A row whose send failed STAYS and the 1-hour pending sweep removes it (insert-then-send with sweep — asserted exactly, B17). A free-but-undeliverable address therefore answers 202 like the others (otherwise 503 would be a deliverability oracle).
`createAccountEmailsRoutes` takes an optional `track(promise)` seam (default no-op) so tests can await the detached tasks deterministically.

### Counters
Per-user and per-target counters advance on EVERY request of the route that owns them, whatever the availability, so a counter's state never encodes whether an address is taken:
- add: `['email-add', userId]`, `['email-send', userId]`, `['email-target', hmac]`, `['email-send', 'global']`;
- resend: `['email-send', userId]`, `['email-target', hmac]`, `['email-send', 'global']` (`email-add` is the add-route counter and is not touched by resend);
- verify: `['email-verify', userId, rowId]`, `['email-verify-target', hmac]`, `['email-verify', 'global']`.
Mail is sent only when the address is available AND the row is unverified AND the per-target and global send counters are under their limits. Over the per-user limits => 429 `rate_limited` with `retryAfterSeconds` (own-account state, no oracle). Over the PER-TARGET or GLOBAL send budget => still 202, no mail (uniform; the `rateLimit` 429 is caught and turned into "suppress the mail"). The `email-target` counter advances even for an address that was found unavailable.

### Resend
`POST /:id/code` re-checks availability in the detached task exactly like add (verified-by-another-user, confirmed GoTrue primary of another user, unprovable) and never mails for an unavailable row. A row created while the address was free and later verified by someone else therefore stops mailing. A resend on the caller's own VERIFIED row sends nothing and answers the same 202. Unknown or other-user row id => 404 `not_found`.

### Verify
The address is OPENED from the row (`email_enc`, row `user_id` = session user), never taken from the body. Order:
1. sudo, UUID, row lookup (other user's / missing / HMAC-mismatch row => 404 `not_found`);
2. an already-verified own row => 200 idempotent with the record, grobase NOT called, no budget spent;
3. `{code}` must be six digits (422 `code_invalid`); budgets: `['email-verify', userId, rowId]` 10 per hour (429 `rate_limited`), `['email-verify-target', hmac]` 10 per 24 h across users (429 `rate_limited`, NOTHING forwarded to grobase), `['email-verify', 'global']` 300 per hour (503 `email_busy`, O2; acceptable because a code from the mailbox is still required);
4. `verifyCode` -> `checkProof(proof, {address})` -> spend `otp-proof:<sha256>` with `kv.setNx` (all extracted, see Extractions); a rejected proof audits `account.email_proof_rejected` and answers 502 `email_proof_invalid`;
5. availability (after the proof, so `email_taken` and the unprovable 503 are only visible to a holder of the mailbox): a confirmed GoTrue primary of another user (`findAccountByEmail`) => 409 `email_taken`; `complete === false` with no match => 503 `email_unavailable`;
6. `update ... set verified_at = now() where id = :id and user_id = :uid and verified_at is null`; a `23505` on the partial unique index (race loser) => 409 `email_taken` and the audit `account.email_verify_refused` (no address). Success audits `account.email_verified`.
Wrong code 422 `code_invalid`; expired 410 `code_expired`; locked 429 `code_locked` (the sudo mapping). Codes: **`email_taken` (409) is the only "address is already someone's" answer; `email_unavailable` (503) means an outage or an unset/misset key and nothing else.** kv/GoTrue/grobase/pg down => 503 `email_unavailable`.

### Remove
Audit `account.email_removed` first, then `delete ... where id = :id and user_id = :uid`; another user's id and a missing id are both 404 `not_found` (no ownership oracle).

### Abuse and privacy
- *Per-user:* `rateLimit` `['email-add', userId]` 5 per 10 min and 20 per day; `['email-send', userId]` 5 per 600 s (the sudo send budget shape); verify `['email-verify', userId, rowId]` 10 per hour. Per-user, so a second account cannot refill it. All through `rateLimit` / `limitOrFail` (`bridge-guard.mjs:167`, `bridge-account-settings.mjs:49`); no limiter is re-rolled.
- *Per-target send:* `['email-target', hmac]` 3 sends per hour ACROSS users (kv keys and logs never hold an address). Over => still 202, no mail.
- *Per-target verify (brute-force bound):* `['email-verify-target', hmac]` 10 per 24 h across users, spent on each verify attempt forwarded to grobase. Without it a caller adds a victim's address from a fresh account and gets 5 fresh guesses per code, 15 per hour, about 13 % per year per target, 72 mails a day to the victim, and 5 wrong guesses lock the victim's own pending sign-in code.
- *Global send:* `['email-send', 'global']` 60 per hour (under Kong's 200/h per IP, which the whole bridge shares). Over => uniform 202, no mail (O2) — a visible 503 would tell a caller that others are adding addresses. *Global verify:* `['email-verify', 'global']` 300 per hour; over => 503 `email_busy`.
- *Enumeration:* the add answer — status, body, headers — is byte-identical in the four cases, the audit row is the same, the counters are the same, and the response does not wait for the mail (it is written before the grobase request resolves). The three "unavailable" cases send NO mail. `email_taken` and the unprovable 503 appear only at verify, after a code that went to the mailbox. Residual: the detached task's CPU/network after the response is not observable by the caller except through mailbox delivery.
- *Code on another address:* the code is bound three times: grobase hashes `email:code`, the proof's `otp` must equal the row's opened address, the row is the caller's. A code for X cannot verify Y.
- *Codes in logs/audit:* no code, proof or address in audit `details`, in `console` output or in an error `message`. A test greps the captured output (non-empty first).
- *Cross-use:* a sudo proof or a sign-in proof for the same address is not accepted: the bridge only holds a proof it just obtained from `verifyCode` for this row, and the spend marker makes it single-use.
