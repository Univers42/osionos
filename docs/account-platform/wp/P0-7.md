## Why, and what is out of scope
The 10K-user ceilings are in the database: an unindexed people-directory view, reads with no limit,
`in.()` lists, scans on `email_hash`. Measure them where they live — the hot queries, on a seeded
10K database, in a throwaway container — so P0-5 and P1-1 can show a before/after number.
**Out of scope:** an HTTP load driver. The routes it would load (heartbeat, preferences) do not exist
yet; it comes with P0-5. Do not build it.

## Harness — `scripts/verify/account-load.sh`
- Same shape as `models-grants.sh`: grobase postgres image (`GROBASE_PG_IMAGE`, missing image = FAIL),
  `--network none`, a unique container name, removed on every exit path (trap), the grobase init +
  `scripts/apply-models-migrations.sh` exactly as that harness applies them. Never touches a running
  `mini-baas-*` container or a remote DB.
- Then `seed-10k.sql`, timed; then `ANALYZE`; then each query of `queries.sql` run `RUNS` times (default 30)
  with `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`; record each run's execution time and whether the plan holds a
  `Seq Scan` on a relation named in that query's budget.
- Output: one line per query `PASS|FAIL <id> p50=<ms> p95=<ms> seq_scan=<yes|no> budget=<ms>`, then
  `RESULT: <n> passed, <m> failed`, and the same data as JSON in `target/account-load/<UTC timestamp>.json`
  (with the image digest, `RUNS`, the git SHA). Exit 0 all within budget · 1 a breach or a failure ·
  2 docker missing. `--baseline` reports and always exits 0 unless the harness itself failed.
- Caveat lines required: plan timing in an idle container under-reports production latency
  (no concurrency, warm cache, no network); p95 over 30 runs is a coarse estimate.

## Seed — `seed-10k.sql`
Deterministic (`generate_series`, values from `md5(i::text)`, no `random()`), one transaction, finishes in
≤120 s on this host (report the time). Rows: 10,000 `auth.users` + their `public.users` rows (the people
directory reads these) + `osionos_bridge_identities` (with `email_hash`); 1,000 workspaces with 1–50 members
(skewed: a few large ones, 200+ members, since a colleague fan-out is a known ceiling); 100,000 pages;
20,000 connections; 50,000 feed shares. Read each table's real columns from `models/` and
`apps/grobase/scripts/migrations/postgresql/` — do not invent columns; a CHECK that rejects the seed is a
seed bug. The ids of a few known users go in a temp table the queries use.

## Queries — `queries.sql` + `budgets.json`
One query per id, written exactly as the bridge issues it today (cite the bridge file:line in a comment
above each, from `apps/osionos/app/scripts/bridge-*.mjs`; PostgREST filters translated to their SQL).
At least: `directory_search` (`bridge-social.mjs:70`), `directory_by_ids` with 50 ids
(`bridge-social-core.mjs:390`), `identity_by_email_hash` (`bridge-api.mjs` email_hash lookup),
`feed_shares_for_user`, `connections_for_user`, `workspace_members_of_large_workspace`,
`pages_of_workspace`. `budgets.json`: `{ "<id>": { "p95_ms": n, "no_seq_scan": ["table", …] } }` with
the plan's p95 targets (profile 60 ms, search 150 ms) split per query and justified in a `"why"` field.
