2. **GDPR functions: add nothing, edit nothing.** No uuid wrappers; they would be a second erase path. The `bridge-no-second-erase` test guards it; the desktop exposure is logged as a separate follow-up, not fixed here.

4. **Ownership with no (accepted) successor:** oldest admin, else oldest member; never delete a workspace that has another member; notify the new owner. Refusing the deletion would let one absent member block a legal erasure.
5. **`zlib.crc32`:** use it (Node 22.2+; `package.json` engines `22.x`, image `node:22-alpine` floats, `deploy/bridge-fly/Dockerfile:16`), with a module-load guard `typeof zlib.crc32 === 'function'` that fails the export module closed, and a test asserting it; no own table.

7. **Audit rows of a deleted user:** keep rows, null `ip_hash` and `user_agent` at erase. A retention-delete job needs the owner's policy and is out of P5-6.
8. **Tombstone:** one fixed uuid, because `author_id` is NOT NULL on the shared-content tables; NULL only where the column is nullable and the row is not shared content.
9. **Caps:** 50 MB / 250,000 rows / 7 days, labelled unmeasured defaults in the module `Caveat:`; the 15 s storage timeout makes 200 MB unsafe today. Raise only with a measurement artifact from a seeded heavy account.
10. **Executor host:** in-bridge timer, safe because every claim is `SKIP LOCKED` and the erase re-checks under `FOR UPDATE`; a dedicated worker is not needed for correctness. Require the double env switch (c-1) and that the owner enables it on **one** replica first.

## Design decisions (the devil ruled on these)

- **D1 — One registry drives both the export and the erasure.** A table `osionos_account_data_map` (root SQL) lists, per (table, column): the role the column plays (`owner`, `author`, `member`, `peer`), the erase action (`delete`, `anonymise` = set the column to the tombstone, or NULL only where the column is nullable and the row is not shared content, `transfer`, `scrub_jsonb`, `keep`) and whether and with which columns it is exported. The export reads it; the erase function loops over it. A catalog check (D2) fails when a user-keyed table is missing from it.
- **D2 — Completeness is a gate, not a promise, and it is name-independent.** `account-checks.sql` gains `p5_erasure_complete`: every `public` table with a column whose name is in the pattern list, **whatever its type** (uuid, text, `uuid[]`, jsonb: the text-typed `subject_id` columns are selected too), `user_id|owner_id|author_id|created_by|follower_id|followee_id|requester_id|addressee_id|actor_id|blocker_id|blocked_id|sender_id|reporter_id|subject_user_id|decided_by|creator_id|updated_by|new_owner|subject|subject_id` appears in the registry, or in an explicit `keep` row with a reason. The pattern is name-based and blind to a uuid stored inside a jsonb or an array and to differently named columns, so the **canary** is the real gate: `p5_erase_canary` seeds user A with a row in every registry table plus A's uuid inside a jsonb (`osionos_pages.collaborators`, `osionos-bridge-migration.sql:60`), an array and a text column (`ai_jobs.subject_id`, `ai_sentiment.subject_id`, `ai_moderation_events.subject_id` are text-typed), runs the erase, and asserts `row_to_json(t)::text LIKE '%'||A||'%'` finds **zero** rows in every `public` table except registry `keep` rows (each with a `reason`). **Keep rows the canary needs (R5),** each with a reason: `osionos_account_deletion_requests` (the executor's own state; cascades at the GoTrue delete), `osionos_account_erasure_objects` (the retry list; the bridge deletes it after the objects), `osionos_bridge_audit_events` (`subject_id`/`actor_id`: pseudonymous accountability, `ip_hash` and `user_agent` scrubbed), `auth_session_cutoffs` (must outlive the erase; cascades at the GoTrue delete). **Floor (R1):** a loop over the registry passes on an empty registry, so the canary asserts that the number of tables it seeded equals `count(DISTINCT table_name)` of the registry, that the registry holds at least a literal `N` rows (the count of the D2 query pasted in the commit body, written as a constant in the check so shrinking the registry is a visible diff), and that every table the next sentence names is present; `p5_erasure_complete`, `p5_export_reachable` and `p5_export_no_secrets` carry the same floors. The registry must also name, with the action in the commit message body: `public.users` (anonymise email/username, null `password_hash`), `user_profiles`, `osionos_bridge_identities` (display_name, email_hash, subject: erase), `osionos_mfa_totp`, `osionos_mfa_recovery_codes`, `osionos_ide_access`, `ai_access_tokens`, `ai_memories`, `ai_chunks`, `osionos_object_database_rows`, `osionos_follows` (both columns: delete), `osionos_presence`, the profile status columns (P2-3-a), and `osionos_user_settings` (deleted whole, so its `sys-views-*` sections, P4-1-c, `scripts/bridge-self-views.mjs:186`, go with it). Whether `public.users` and `user_profiles` are reachable and which columns exist is UNKNOWN until the registry query runs on the throwaway DB; a missing table is reported under `deviations:`, never skipped silently.
- **D3 — Erase is one idempotent SQL function, run as the service role, in one transaction.** `osionos_account_erase(p_user uuid)`. A second call re-runs the registry (it catches rows a late write recreated) and changes nothing else. The request row is **not** deleted by it: the bridge deletes the GoTrue user last, which cascades the row away.
- **D4 — Order inside the executor:** (0) re-read the request (cancelled or absent: stop, no side effect), (1) audit `account.deletion_executing` (fail-closed), (2) session cutoff + GoTrue ban + PAT revoke (any failure aborts that user before the erase), (3) `osionos_account_erase` (if it says `no_deletion_request` the user cancelled after step 0: unban), (4) one 70 s wait per batch, then the erase a second time, (5) delete the stored objects the erase recorded, then their rows, (6) delete the GoTrue user, (7) best-effort `account.deleted`. Steps 3-7 are retryable; a crash after any step is finished by the next run (the request row, with `erased_at`, survives until step 6 cascades it).
- **D5 — Workspaces (replaces the former rule).** For each workspace the user owns: (i) an accepted successor (`successor_accepted_at IS NOT NULL`) who is still a member → ownership transfers (`owner_id`, and the member row becomes `owner`); (ii) otherwise, if other members exist → the oldest `admin`, else the oldest member, both ordered `created_at, user_id` (the tie-break for equal `created_at`); a workspace that has another member is never deleted, and an `osionos_notifications` row (type `'system'`, the only generic value in the CHECK at `models/osionos-engagement-migration.sql:72`) goes to the new owner; its text names no user id and no user name (R5); (iii) no other member **and** no row in any workspace-keyed table (the registry rows with `workspace_column`: channels, messages, comments, `collaborators`) is authored or owned by a non-member (R8) → the workspace and its pages are deleted. If such a row exists the workspace is **kept**: `owner_id` becomes the tombstone, the user's member row is deleted, the user's own content follows D6, and the disposition `kept_orphaned` is returned and audited (Caveat: an orphaned workspace has no administrator until a human assigns one). Pages the user owns in a workspace they leave: `visibility = 'private'` → deleted; `shared|public` → passed to the workspace's (new) owner (`osionos_pages.visibility` default `private`, `owner_id` nullable: `osionos-bridge-migration.sql:53-60`). A successor who has not accepted, or who is no longer a member at execution time, is treated as no successor, and the erase result and the audit row say which. The check at request time (`bridge-account-identity.mjs:110-121`) is not trusted at execution time.
- **D6 — Authored shared content is anonymised, not deleted** (messages, comments, feed comments): the author column is set to the tombstone uuid (a-8). Personal rows (settings, favourites, tokens, push subscriptions, drafts, memories) are deleted; rows whose `UNIQUE` key includes the user are `delete`, never `anonymise`. The username history keeps the name held for its 90 days with `user_id` NULL (`osionos-account-profiles-migration.sql:224-231`, already ON DELETE SET NULL).
- **D7 — Export is an async job with a private, short-lived artifact.** The archive is stored in a private bucket under the owner prefix and served only by an owner-checked bridge route; there is no public or presigned URL. It expires in 7 days.
- **D8 — Both flows are single-flight and rate-limited,** and the executor is off until the flag flip (`OSIONOS_ACCOUNT_DELETION_EXECUTOR=1`, default unset, plus the second guard in c-1), so merging a, b and c deletes nothing.

Identifiers are validated `/^[a-z_][a-z0-9_]*$/` by a CHECK. `export_columns` never matches `hash|secret|token|password|recovery|totp|key|salt|ip_prefix` (check `p5_export_no_secrets` lists the offending names in its failing message). No grant to `anon`, `authenticated` or `osionos_account_user`.
2. **`osionos_account_deletion_requests` gains** `claimed_at timestamptz`, `attempts integer NOT NULL DEFAULT 0`, `last_error text`, `erased_at timestamptz`, `successor_accepted_at timestamptz` via `ADD COLUMN IF NOT EXISTS`. The account role's column grants (`:660-661`) are not widened: a check asserts it cannot read the five, and it holds no grant to set `successor_accepted_at` (a service-role route sets it, c-7). A `BEFORE DELETE` row trigger on the table, `WHEN (current_user = 'osionos_account_user' AND OLD.erased_at IS NOT NULL)` (a plain, non-`SECURITY DEFINER` function), raises `P0001` message `deletion_in_progress`; the GoTrue `ON DELETE CASCADE` runs as another role and is unaffected.
3. **`osionos_account_deletion_due(p_limit integer)`** (read-only twin) returns the `user_id`s with `scheduled_for <= now()`, uncancelled by construction (the row exists), `attempts < 5`, **without stamping anything**. **`osionos_account_deletion_claim(p_limit integer)`** returns at most `least(p_limit, 5)` of the same set (the cap is inside the function, so no caller can claim a batch that outlives its lease) with no live lease using `FOR UPDATE SKIP LOCKED` and stamps `claimed_at`; a lease older than 30 minutes is claimable again; a request with `erased_at` set stays claimable until its row cascades away. EXECUTE for the service role only. The lease only distributes work: it never blocks Cancel. Caveat: a lease is a clock, so a run longer than 30 minutes can be taken twice (the runner bounds a batch to 5 users with one 70 s wait and takes no user after 20 minutes, c-1); the erase re-checks under `FOR UPDATE` and is idempotent, which is the safety.
4. **`osionos_account_erase(p_user uuid)`** and **`osionos_account_erase_plan(p_user uuid)`**: both thin wrappers over one internal run body with an apply flag (library-first: the plan cannot drift from the erase). `SECURITY DEFINER`, `SET search_path = public, pg_temp`, `lock_timeout` pinned, EXECUTE for the service role only. Erase, in this order: (1) `SELECT … FROM osionos_account_deletion_requests WHERE user_id = p_user FOR UPDATE`; no row → `P0001 no_deletion_request`; `scheduled_for > now()` and `erased_at IS NULL` → `P0001 grace_not_over` (zero rows changed); a null `p_user` is refused; (2) set `erased_at = now()` if null (a re-run keeps the first value); (3) record every storage key into `osionos_account_erasure_objects` (item 5); (4) D5 (workspaces, pages), then D6 and the registry loop with `format('%I')` identifiers only, including `scrub_jsonb` for `collaborators` and the tombstone for `anonymise`; (5) null `ip_hash` and `user_agent` on the user's `osionos_bridge_audit_events` rows (subject and actor uuids stay as pseudonymous accountability once the identity row is gone). Returns `jsonb`: per-table counts and the workspace dispositions (`transferred`, `promoted`, `deleted`, `successor: accepted|not_accepted|left|none`). The plan returns the same shape with no writes. It never deletes the request row.
5. **`osionos_account_erasure_objects (user_id uuid, bucket text, key text, PRIMARY KEY (user_id, bucket, key))`**, service role only, no FK to `auth.users` (so it survives the cascade). Filled inside the erase transaction from: every `osionos_account_exports` row of the user (`bucket = 'account-exports'`, `key = id || '.' || format`), and each registry row with `object_bucket` set (avatar, banner, chat attachments; the implementer reads `scripts/bridge-avatar.mjs` and the attachments table first to name the key columns, and reports any class they cannot derive under `deviations:`). The bridge deletes the objects, then the rows; a retry reads this table; `ON CONFLICT DO NOTHING` makes the fill idempotent.
6. **`osionos_account_exports`** (job table): `id uuid PK`, `user_id uuid NOT NULL`, `format text CHECK (json|csv|zip)`, `status text CHECK (queued|running|done|failed|expired)`, `requested_at`, `started_at`, `finished_at`, `expires_at`, `bytes bigint`, `error_code text`. **No `object_key` column**: the key is derived `{id}.{format}` under the owner prefix. A partial unique index on `(user_id) WHERE status IN ('queued','running')` is the single-flight guard. The account role: SELECT on all columns and INSERT on `(user_id, format)` only; RLS owner policy on `user_id`; the service role ALL. Plus `osionos_account_export_claim()` (same lease pattern as item 3).
7. **GDPR uuid functions: none** (Decision 2). `gdpr-migration.sql` is not edited.
8. **Tombstone constant** `00000000-0000-4000-8000-000000000000`, defined once in this migration (a function `osionos_account_tombstone()` returning it, used by the loop). `author_id` is NOT NULL on `osionos_messages`, `osionos_feed_comments`, `osionos_page_comments`, `osionos_communities.creator_id`, `osionos_message_attachments.owner_id`, so NULL is wrong for those. No FK targets the tombstone.
9. **Checks** in `account-checks.sql` (names `p5_*`, each with the failing input in its message), all seeding **every** registry table (a 10-table seed passes while the other ~48 are wrong) and a second user with a row in each, so the mutant "remove the `p_user` filter" is killed:
   - `p5_erasure_complete` (D2 pattern vs registry), `p5_erase_canary` (D2, name-independent, with the floor and the keep rows), `p5_erase_idempotent` (run twice: second-run counts for erased data are zero and nothing else changed), `p5_erase_isolated` (the second user's rows byte-identical, **and** a non-member author's rows in the user's sole workspace byte-identical: the workspace is kept, R8), `p5_plan_matches_erase` (plan counts equal the real erase's on the same seed);
   - `p5_erase_refuses_live` (no request row → `P0001 no_deletion_request`), `p5_erase_refuses_early` (request scheduled tomorrow → `grace_not_over`, zero rows changed), `p5_cancel_erase_race` (two sessions driven by `run_races`, item 10: 50 randomly offset repetitions plus two deterministic lock-hold orderings; exactly one wins every time, never "cancelled and erased"; a cancel after `erased_at` is `deletion_in_progress`), `p5_dry_run_no_stamp` (after `_due` and `_plan`, `claimed_at IS NULL` on every row);
   - `p5_erase_transfer` (accepted successor → ownership moves; not accepted, successor left, no other member, other members present: the four branches of D5, plus private page deleted and shared page passed, a workspace with a non-member author kept as `kept_orphaned`, tie-break on equal `created_at`, and a notification row that contains neither A's uuid nor A's name; the accepted-successor branch is seeded through the accept route's column `successor_accepted_at`), `p5_no_fk_to_tombstone` (no FK targets it; no `anonymise` row has a `UNIQUE` including the user), `p5_erase_objects_recorded` (kill after the erase: the keys are in the table; a second run adds none), `p5_audit_scrubbed` (`ip_hash`, `user_agent` NULL, subject kept);
   - `p5_claim_skip_locked` (`run_races`: 6 seeded due users, a session that holds a claim of 3 open while a second claims 3: disjoint sets, union all 6; and `claim(50)` returns at most 5), `p5_erase_sequence` (one real-Postgres run of claim → erase → erase → delete the erasure-object rows → delete `auth.users` cascading the request row; the fake in b/c cannot prove the RPC shapes);
   - `p5_export_acl` (account role cannot read the five request columns, cannot insert `status`, and `osionos_account_exports.object_key` does not exist), `p5_export_single_flight` (second queued job → 23505), `p5_export_no_secrets`, `p5_export_reachable` (for every registry row with `export_columns`, `SELECT <cols> FROM <table> LIMIT 0` as `service_role` succeeds; both assert at least a literal `N` rows with `export_columns` so an empty registry fails, R1), `p5_no_exec_grants` (`anon`, `authenticated`, `osionos_account_user` cannot execute any new function).

10. **Two-session mechanism (R4): a background second `psql`, not `dblink`.** `account-checks.sql` is piped into ONE `psql` stream (`models-grants.sh:564-565`) and `rg 'dblink|SKIP LOCKED' scripts/verify models` finds nothing; the image is postgres:16-alpine + pg_net + pgvector (`apps/grobase/infra/docker/services/postgres/Dockerfile`) and `dblink` is not proved there, so it is not used (UNKNOWN = FAIL). Instead `models-grants.sh` gains a function `run_races` that uses the same `docker exec -i "${CTN}" psql` path as `psql_stdin` (`:171-179`): it seeds through `psql_stdin`, starts the first session in the background (`( ... | docker exec -i ... psql ) &`, output to a temp file), runs the second in the foreground, `wait`s, and prints its results as labelled rows through the same helper the other checks use, so `check_count` (`:233`) fails when a row is missing. Cases: (i) cancel/erase, 50 iterations, the second session starting after a random 0-30 ms offset, final state per iteration is exactly one of {request row gone and `erased_at` NULL and no data erased} or {`erased_at` set and the cancel refused with `deletion_in_progress`}, never both and never neither; (ii) two deterministic cases: session A holds `BEGIN; SELECT ... FOR UPDATE; SELECT pg_sleep(2)` on the request row while B cancels (B waits, then the erase that follows sees `no_deletion_request`), and A completes an erase while B cancels afterwards (`deletion_in_progress`); (iii) skip-locked: A claims 3 of 6 inside an open transaction with `pg_sleep(2)`, B claims 3. Caveat: the 50 randomly offset samples are timing samples, not an exhaustive interleaving; the two lock-hold cases are the deterministic proof. If the second session cannot be made to run in the throwaway container, the fallback is a single-session `SELECT ... FOR UPDATE NOWAIT` proof, and the race is reported under `deviations:` as unproven.

### P5-6-b — export (bridge; after a)

New `scripts/bridge-account-export.mjs` (routes + runner) and `scripts/bridge-zip.mjs` (a STORE-only zip writer using `zlib.crc32`, Decision 5, with the load-time guard; its header names the sibling `src/features/page-export/model/zipWriter.ts` and the test round-trips a file against the same CRC constants; no third writer). Mounted by appending to the `modules` array in `bridge-account-mounts.mjs` (`:42-58`) and to `deploy/bridge-fly/Dockerfile`'s COPY list (`:25` onward; `tests/bridge/bridge-dockerfile-closure.test.mjs` fails when the fly list misses a module); `bridge-api.mjs` is untouched.

1. **`POST /api/account/export`** body `{format}` (`json|csv|zip`, default `zip`). App session required, **sudo required** (`requireSudo`), rate limit 3 per day per user, audit `account.export_requested` before the insert (`writeAudit`, fail-closed 503). Inserts through `pg.asUser(session)`; a 23505 → 409 `export_in_progress` with the running job's id. Answers 202 `{id, status:'queued'}`.
2. **`GET /api/account/export`** lists the caller's jobs (newest first, max 10) through the account role: RLS is the scope. **`GET /api/account/export/:id`** answers that one job; a job that is not the caller's answers 404 `export_not_found`, identical to an unknown id.
3. **`GET /api/account/export/:id/download`** buffers (never "streams": `storageGet` reads the whole object, `bridge-storage-core.mjs:146-152`) the artifact: owner check through the account role first, then `storageGet(session.userId, '{id}.{format}', …, 'account-exports')` (the key is derived, no service-role read of a key column). The job's `bytes` over the cap → refused before the get. Status other than `done` → 409 `export_not_ready`; `expires_at` past → 410 `export_expired`. Headers `Content-Disposition: attachment`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`. The download is audited (`account.export_downloaded`). Caveat in the header: every download costs the object's size in memory (at most the cap).
4. **The runner** (an `unref`ed interval like `bridge-tasks.mjs:85-86`, 30 s): claims one job, reads the registry, validates every registry identifier against `/^[a-z_][a-z0-9_]*$/` before it enters a PostgREST path, and for each exported table pages by keyset (`id`/primary key, 500 rows) with the service key and the owner column in the **path** (the scope is never applied after the fetch, as `bridge-self-data.mjs:20-27` requires). It builds `json` (one file per table + `manifest.json` with the schema version, the time and per-table row counts), `csv` (one file per table, RFC 4180 quoting; a string starting `=`, `+`, `-`, `@`, tab or CR is prefixed with `'`, numbers are not), or `zip` (both). Zip entry names are generated from the registry as a fixed `table.json|csv` form, never from row data; the writer rejects empty, absolute, `..`, backslash, NUL and over-255-byte names. **Caps** `EXPORT_MAX_BYTES = 50 MB`, `EXPORT_MAX_ROWS = 250_000` (exported constants, unmeasured defaults named so in the module `Caveat:`, Decision 9): over either, the job fails with `error_code = 'export_too_large'`, **decided before the first `storagePut`** and never by truncating. It calls `ensureBucket(ownerId, 'account-exports', …)` first, then a single `storagePut`; marks `done` only after `storagePut` returns.
5. **What an export never holds:** other people's private data and secrets. Edge tables (`connections`, `follows`, `blocks`) carry the peer's id and public card only, through the same `peerCard` rule as `bridge-self-data.mjs:154`. A unit test recursively scans every jsonb key and every column name of the built archive against `hash|secret|token|password|recovery|totp|key|salt|ip_prefix`.
6. **Expiry sweep:** the same timer sets `expired` and deletes the object (derived key) when `expires_at` passes.
7. Caveat in the module header: a job is claimed by a lease, so a runner killed mid-archive leaves the job `running` until the lease ends; the archive is built in memory up to the cap, so concurrent exports cost memory (limit: one job per process at a time); the 15 s storage timeout is the practical size ceiling.

### P5-6-c — deletion executor (bridge; after a, parallel with b)

New `scripts/bridge-account-erasure.mjs`; started from `createAccountHandler`'s deps as `createAccountErasureRunner(deps)` (appended in `bridge-account-mounts.mjs`; `fetchImpl` is the runner's own dep defaulting to `fetch`). `bridge-account-identity.mjs` is **extended** (items 4, 6, 7), not duplicated. The module calls the existing helpers and re-implements none: `writeSessionCutoff` (`bridge-session-cutoff.mjs:197`), `revokeAllPats` (`bridge-pat-store.mjs:163`), `writeAudit` (`bridge-guard.mjs:224`).

1. **Gate (double switch):** the runner starts only when `OSIONOS_ACCOUNT_DELETION_EXECUTOR=1` **and** the account plane is configured. A second, independent guard refuses to start live (logs one warn naming the missing variable *names*, never values) when `OSIONOS_ACCOUNT_DELETION_DRY_RUN` is unset **and** `NODE_ENV=production` **and** `OSIONOS_ACCOUNT_DELETION_VERDICT` (the flag-flip verdict constant; set by the owner after the second verdict) is unset. Interval 15 min, `unref`ed, one run at a time per process; the owner enables it on one replica first. **Batch (R6):** `CLAIM_BATCH = 5` (the SQL caps it too, a-3); a run does steps 0-3 for every claimed user, sleeps **once** for 70 s, then does steps 4-7 for every user, and takes no further user once 20 minutes have passed since the claim (the rest wait for the next run), so a batch stays inside the 30-minute lease and no user is claimed twice. **`DRY_RUN=1`** calls only `osionos_account_deletion_due` and `osionos_account_erase_plan`: no claim, no erase, no ban, no cutoff, no PAT revoke, no audit write, no GoTrue call; the log prints the plan counts and a hashed id prefix (never the full id).
2. **Per claimed batch (D4):** steps 0-3 per user, then one wait for the batch, then steps 4-7 per user. (0) re-read the request through the service role: cancelled or absent → stop this user with `account_deletion_cancelled` and **no side effect** (no audit row, no cutoff, no ban, no PAT revoke; R2); (1) `writeAudit` `account.deletion_executing`, fail-closed 503 (ADR 0002 rule 6): audit store down → no later step runs; (2) `writeSessionCutoff` for the user, then ban the GoTrue user (`PUT {baasUrl}/auth/v1/admin/users/<id>` with `ban_duration`; call shape unverified, see override 4) so a re-sign-in is refused, then `revokeAllPats` (its `revoked_reason` becomes `'user'`, the only value besides `'admin'` the CHECK allows, `osionos-personal-access-tokens-migration.sql:90`; the audit row carries the real reason). **The ban is indefinite** (a `ban_duration` far beyond any grace, for example `876000h`) and ends only when step 6 deletes the user. A non-2xx on the ban, a failed cutoff or a failed PAT revoke aborts **that user**: `last_error` = `ban_failed`, `cutoff_failed` or `pat_revoke_failed`, `attempts` + 1, **no erase runs** (a user who can still sign in is never half-erased) (R3); (3) `rpc/osionos_account_erase`; if it answers `no_deletion_request` the user cancelled after step 0, so the runner **unbans** the GoTrue user (same endpoint, `ban_duration: 'none'`, shape unverified like the ban), logs `account_deletion_cancelled_after_ban` and stops; the cutoff and the revoked PATs are not undone (the user signs in again and re-creates tokens; the ledger states it); (4) one 70 s wait per batch (an injectable `sleep`; above `STALE_AFTER_MS = 60_000` plus margin, ADR 0003), then the erase **a second time** per user so a write by a still-valid token or the bridge's service key between steps 3 and 6 is erased; (5) delete the objects listed in `osionos_account_erasure_objects` with `storageDelete` (404 is success), then delete those rows; (6) `DELETE {baasUrl}/auth/v1/admin/users/<id>` with the service key (no existing DELETE example in the bridge; shape unverified, same override); (7) `writeAudit` `account.deleted`, session `{userId}` (no jti), details = the erase counts, the workspace dispositions and the successor outcome (`accepted|not_accepted|left|none`); **best-effort**: its loss is logged, never retried into a loop. Nothing here writes `osionos_sessions`.
3. **Failure:** any step failing records `last_error` (a stable code, never a message with SQL or a token), increments `attempts`, and moves on to the next user. After 5 attempts the request stays (the claim excludes it) and the run logs one `console.warn` per run naming the count. A permanent failure is a human's to fix; it is never auto-skipped past a step. A crash after any step is finished by the next run: every step is idempotent and the request row survives until step 6.
4. **Cancel vs erase is decided in SQL** (a-2, a-4): `cancelDeletion` (`bridge-account-identity.mjs:179-192`) keeps its audit-first behaviour (the `account.deletion_cancelled` row records an attempt, as ADR 0002 rule 6 defines) and its single `DELETE`; it no longer reads `claimed_at`. A `P0001 deletion_in_progress` from the trigger is mapped to 409 `deletion_in_progress`. A cancel before the erase deletes the row and the next run's step 3 stops.
5. **Never** reachable by an HTTP route, an admin route or a user session: the executor has no route. An admin who wants to force it edits the row through SQL, as the audit trail shows.
6. **Extend the status read** (`readDeletion`, `bridge-account-identity.mjs:164-177`) to add `inProgress: boolean` = `erased_at IS NOT NULL` (read through the service role because the account role cannot see it). A claim lease or a failed attempt does **not** set it, so the banner never says "running" for a dry run or a retry. Nothing else in that read changes.
7. **Successor acceptance:** new `POST /api/account/deletion/successor/accept` in `bridge-account-identity.mjs` (the session user must equal the request's `successor_user_id`; no sudo; audited before the write with `writeAudit`; refused when `erased_at` is set; sets `successor_accepted_at` through the service role). Without `successor_accepted_at` the successor is treated as none and the `account.deleted` audit row says so.
8. **Notify the successor at request time (R7):** when `POST /api/account/deletion` names a successor, after the request insert it writes an `osionos_notifications` row (type `'system'`, service role) to `successor_user_id` saying that a workspace owner named them successor and that they may accept; the text carries no user id and no user name. Best-effort: a failure is logged and never fails the request (the request already exists and is audited). There is no accept control in the UI in P5-6 (override 1), so acceptance stays an API action and the d ledger entry records that it is unreachable from the UI.

## Security edges (what each caller sees)

| Caller | Request export | Read/download another user's job | Run erase | Cancel deletion |
|---|---|---|---|---|
| Owner, with sudo | yes | their own only | no route; the timer only | yes until `erased_at` is set, then 409 `deletion_in_progress` |
| Owner, no sudo | 403 `sudo_required` | their own list is readable | — | yes |
| Another user | — | 404 `export_not_found`, same body as an unknown id | — | — |
| Named successor | — | — | — | may accept (c-7), nothing else |
| Admin (platform role) | no special path | 404 | no route; SQL by hand, audited | — |
| Anonymous / expired session | 401 | 401 | — | 401 |
| `anon` / `authenticated` / `osionos_account_user` DB roles | — | — | cannot execute the functions (`p5_no_exec_grants`) | the account role can DELETE its row, but not after `erased_at` (trigger) |

The erase function is `SECURITY DEFINER` and callable by the service role only, so the data-path risk is the registry: a wrong row deletes the wrong column, a missed row looks like success. That is why D1, D2 (with the canary) and the isolation check exist. Residual: tokens already issued stay valid for up to 10-60 s (derived ones longer, ADR 0003), which is why c-2 bans, runs a cutoff and erases twice.

## Findings that change the design

F1. **Cancel can race the erase and lose data silently.** Spec c item 4 (cancel reads `claimed_at`, then deletes) is read-then-delete: between the two the erase can commit. Also `osionos_account_erase` refuses only "no request row" (spec a item 4), it never re-checks `scheduled_for <= now()` or locks the row. The account role may DELETE the row (`osionos-account-profiles-migration.sql:663`), so a cancel after the erase commits succeeds and leaves an erased account with a "cancelled" request, still signed in.
F2. **Step 1 writes `osionos_sessions` from a new module.** ADR 0003 rule 3 (`adr/0003-...md:35`): "Nothing but `bridge-sessions.mjs` writes `osionos_sessions`". The primitive that already exists for "end every osionos_v1 token of a user" is the per-user cutoff: `writeSessionCutoff(config, fetchImpl, userId, writtenAtMs)` (`scripts/bridge-session-cutoff.mjs:197`, table `public.auth_session_cutoffs`, `models/auth-session-cutoffs.sql:22-24`). `revoked_reason='deletion'` is reserved (`osionos-account-foundation-migration.sql:181`) but the foundation header (`:25-29`) says it exists because CASCADE deletes rows; the cutoff covers refresh families (P3-3-a) too.
F3. **"A live token cannot write after the erase" is false.** ADR 0003 (`:18-30`): other replicas lag up to 10 s (60 s on a poll outage); the account JWT lives 120 s, IDE token 15 min, LiveKit up to 6 h. Between the erase commit (step 2) and the GoTrue delete (step 4) the user can also simply sign in again through GoTrue, and the registration trigger does not recreate rows, so they land in an erased-but-alive account. A late write by the bridge (service key, `owner_id` in the body) recreates orphan rows after the erase.
F4. **Audit after the irreversible step violates ADR 0002 rule 6** (`adr/0002-...md:20`: audit written before the irreversible action, failure blocks it). Spec c item 2 writes `account.deleted` at step 5, after step 4. Worse, step 4 cascades the request row away (`osionos-account-profiles-migration.sql:234`, ON DELETE CASCADE), so a crash after 4 leaves no row, no retry, and no audit.
F5. **Export objects are orphaned by the erase.** Erase (step 2) deletes `osionos_account_exports` rows (it holds `object_key`); step 3 then must delete "objects the registry knows", but the keys are gone and `bridge-storage-core.mjs` has no list-by-prefix (`:119`, `:140`, `:163` are put/get/delete only). Same for avatar/banner keys held in profile rows. The export archive is the user's whole life in one file; it must not survive them.
F6. **Dry run is not a dry run.** Spec c item 1 says dry-run "claims nothing destructive", but `osionos_account_deletion_claim` stamps `claimed_at` (a item 3). With c item 4/6 that makes real users' Cancel answer 409 `deletion_in_progress` and the banner say "Deletion is running" for 30 minutes after a dry run. It also logs ids only, not "exactly what it would erase" (the prompt's bar).
F7. **No successor ever accepts.** The route only checks membership of an owned workspace (`scripts/bridge-account-identity.mjs:110-121`). The P1-6-b client calls `requestDeletion()` with body `{}` (`src/shared/api/accountSecurityApi.ts:116`), so no UI names a successor at all. D5's "oldest admin, else oldest member" then hands workspaces to people who never agreed. The task's rule ("only to a successor who accepted") has no implementation anywhere.
F8. **D5 leaks private pages.** "Pages the user owns in a workspace they leave pass to that workspace's owner" includes `visibility='private'` pages (`osionos-bridge-migration.sql:53-60` shows `owner_id` nullable, visibility default `private`): the workspace owner gains pages they could not read.
F9. **D2 is name-based and its pattern list misses real columns.** My catalog scan of `models/*.sql` finds user-keyed columns the pattern lacks: `followee_id` (`osionos-social-follow-presence-migration.sql:58`), `reporter_id` and `subject_user_id` and `decided_by` (`osionos-social-migration.sql`, `osionos_user_reports`, `osionos_join_requests`), `creator_id` (`osionos_communities`, NOT NULL, ownership), `updated_by` (`ai_skills`, `ai_sentiment_settings`), `new_owner` (`osionos_page_owner_backfill`), `subject` (`osionos_bridge_audit_events`, `osionos_bridge_identities.subject`). Text-typed ids (`ai_jobs.subject_id`, `ai_sentiment.subject_id`, `ai_moderation_events.subject_id`) are invisible to a uuid pattern. `osionos_pages.collaborators JSONB` (`osionos-bridge-migration.sql:60`) holds user ids inside other people's pages. And **`public.users`** (email, password_hash; grobase table keyed by `id`, see `models/auth-gateway-users-reconcile-migration.sql:42-45`, `scripts/verify/models-grants/snapshot.sql:28-31`) plus `user_profiles` are keyed by `id`/outside `models/`: the highest-PII rows are not reachable by any `*_id` pattern. UNKNOWN until checked on the throwaway DB.
F10. **Storage limits contradict the caps.** `STORAGE_TIMEOUT_MS = 15_000` (`bridge-storage-core.mjs:29`, not overridable, file is MUST NOT TOUCH): a 200 MB `storagePut` in 15 s needs ~13 MB/s sustained. `storageGet` buffers the whole object (`:146-152`), so "streams the artifact" is false and every download costs the object's size in memory. Also `ensureBucket(ownerId, 'account-exports', ...)` (`:95`) is never called in the spec; the bucket must exist and be `public:false` (`:98-101` already does that).
F11. **Spec is stale on merged work.** P1-6-b merged (8acd0145f). `isAccountDeleteEnabled()` exists at `src/shared/config/featureFlags.ts:209`; the danger zone is `src/features/settings/ui/danger/AccountDangerZone.tsx` (typed username + sudo + the grace block with Cancel at `:88-93`), mounted at `src/features/settings/profile/ProfilePanel.tsx:138`; `handleDeleteAccount` and `/api/account/request-deletion` are gone from the app (only the vendored `notion-database-sys/.../account.routes.ts:318` still has that path). The "Why" bullet and open question 3 are void.
F12. **Desktop still ships the integer GDPR path.** `models/rls-hardening-migration.sql:55-58` grants `gdpr_export_my_data()` / `gdpr_request_deletion()` to `authenticated`; `apps/osionos-electron/native/firstrun.mjs:23-37` applies `gdpr-migration.sql` on the desktop. Nothing in `scripts/ src tests` calls them (`rg gdpr_` in the app: no hits), but they are PostgREST-callable there. They are the auth-gateway's system, not a second osionos erase path; leave them, forbid wrappers (Q2).
