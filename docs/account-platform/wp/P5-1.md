Simpler options that were rejected, one line each:

- **A signed JWT instead of an opaque secret**: a JWT cannot be revoked without a denylist, and the
  plan asks for a sha256 hash at rest and a revoke — that only works with a lookup.
- **A new `osionos_pat_sessions` table**: the PAT needs no session row; the internal session is
  minted per request and never persisted (ADR 0003's "derived credentials" list).
- **HMAC-SHA256 of the secret instead of sha256**: the secret is 256 bits of randomness, so there is
  nothing to brute-force; the keyed hash exists for low-entropy inputs (the email hash,
  `scripts/bridge-api.mjs:284-286`).
- **A token-prefix column so the list can show which token is which**: eight characters of a
  256-bit secret buy nothing; the name identifies the token.
- **A per-route `verifyPat` instead of one exchange**: every route verifies the bearer *inside*
  `bridge-api.mjs` (`readablePageAccess`, `scripts/bridge-api.mjs:1102-1103`), so a per-route check
  would mean an edit in every place; the header exchange needs exactly one.
- **The route applying the mask itself**: the mask would have to be applied in every route; the
  middleware applies it once.
- **A new `osio.pat` feature flag**: the registry entry is the switch; a flag would also touch
  `src/shared/config/featureFlags.ts`, which P5-3 will want.
- **An anchor inside the existing `mcp` section**: it would have to live inside another panel and
  would not be its own lazy chunk; the registry is the one list of sections.

**Open questions, settled:**
1. **One vocabulary.** `GET /api/account/tokens` returns `{ tokens, catalog }`. `catalog` is
   P5-1-c's vocabulary, and the panel renders its picker from it. There is no second copy in
   `patModel.ts`, no catalog route, and no comparison test.
2. **Last used is shown**, GitHub-style. The table gets `last_used_at timestamptz` (P5-1-a). P5-1-d
   writes it best-effort at most once per token per hour
   (`UPDATE … WHERE id = $1 AND (last_used_at IS NULL OR last_used_at < now() - interval '1 hour')`).
   A failed write never fails the request. A `Caveat:` line says the value is accurate to the
   hour.
3. **PATs survive a password change and "log out everywhere"**, like GitHub. The panel offers
   **Revoke all tokens** (one route in P5-1-b, sudo-gated, audited).
4. **Expiry is required, capped at 365 days.** The panel offers 7 / 30 / 90 days and a custom date
   up to the cap; the bridge refuses anything past the cap with 422.
5. **Audit budget.** Create, revoke and revoke-all are always audited. *Use* is audited on the same
   hourly cadence as `last_used_at` (one `pat.used` row per token per hour, written with it).
   Every request is still authenticated; only the audit row is throttled.
6. **The PAT surface stays at the two page routes** until P5-2 extends the allowlist.
7. **Classic `pages:read` includes `content`.** The panel's copy says so in one line and points to
   fine-grained tokens for metadata-only access.
8. **Desktop:** the existing ledger follow-up; not touched here.
9. **The vocabulary is pinned.** The attribute list in P5-1-c is a fixed constant, not derived from
   `pageRowToEntry`. A classic scope's mask is that full pinned list, **never `null`**, so a page
   field added later is readable by no existing token until someone adds it to the list. The
   canvas/bridge test fails when `pageRowToEntry` gains a key the vocabulary does not list, which
   forces that decision.

**Sudo.** Creating a token and revoking all tokens both require a sudo window: `requireSudo`,
`scripts/bridge-guard.mjs:194`, answering 403 `sudo_required`. The panel reacts through P1-5's
`sudo:required` event; P1-6 mounts the prompt. Until P1-2b's sudo route is merged, the window cannot
be opened live, so P5-1-e's e2e mocks the 403 and the retry.

## Why

### 1. There is no credential an app can hold

- The only long-lived credential the bridge issues is the **IDE token**
  (`scripts/bridge-ide-token.mjs:40-77`, minted at `:62`), and it is not a credential: it is a JWT
  signed with `OSIONOS_IDE_TOKEN_SECRET`, scoped to one workspace, and it dies with the IDE sandbox.
- The app session is `osionos_v1.<payload>.<hmac>` (`scripts/bridge-api.mjs:437-459`), minted by the
  gateway handoff (`scripts/bridge-api.mjs:4180`) and consumed by the app
  (`scripts/bridge-api.mjs:4184-4186`). It is a **session**, not a credential: it carries
  `workspace_ids` frozen at sign-in (`:447`), it expires with `config.sessionTtlSeconds`
  (`:440`, default 3600 s at `:105`), and it is refused by the per-user cut-off (`:493`) and by the
  per-session revocation set (`:494`). Handing one of those to a script, a CI job or an MCP client is
  exactly what the account platform must stop doing — P5-2 still does it, through a shared HMAC.
- Nothing in the tree mints, stores, lists or revokes a per-user API secret. The only "token"
  tables are `user_tokens` (root `models/user.sql:25`, a file the runner skips — it targets the
  auth gateway's own database, `scripts/apply-models-migrations.sh:28-35`) and the OAuth state
  (`scripts/bridge-oauth.mjs:130-134`), which is a 90-second handshake, not a credential.

### 2. The app-session token cannot be the answer, and a PAT cannot be one either

- The app-session token is verified by HMAC over its payload
  (`scripts/bridge-api.mjs:461-471`): the bridge can check it without a database read. A PAT must be
  revocable, and a revocable credential has to be **looked up**, so a PAT cannot be a self-verifying
  token: it is an opaque secret the bridge resolves to a row on every request.
- The verification is spread over ~20 call sites, not one middleware: `readablePageAccess`
  (`scripts/bridge-api.mjs:1102-1103`), `requireWorkspaceAccess` (`:973-975`),
  `requirePageScopeAccess` (`:1182-1184`), `handlePageUpdate` (`:3480`), the account modules
  (`scripts/bridge-sessions.mjs:260`), and the workstream handlers. A second credential therefore
  cannot be introduced "in the routes" without touching every one of them.
- The account plane already knows how to mint a **short-lived internal credential** for a user: the
  per-user account JWT, 120 s, `aud: 'osionos-account'`, role `osionos_account_user`
  (`scripts/bridge-pg.mjs:23-25`, `:56-65`). The PAT needs exactly the same trick, one layer up.

### 3. Nothing can list, revoke or audit a credential

- The account plane's session routes are the only owner-scoped resource today:
  `GET /api/account/sessions` and `DELETE /api/account/sessions/:id`
  (`scripts/bridge-sessions.mjs:255-268`). They list through `pg.asUser(session)` (`:192`) and write
  through `pg.asService()` (`:220-224`), which is ADR 0003's rule: the account role never writes its
  own rows.
- Every create, revoke and use must leave an audit row in `public.osionos_bridge_audit_events`
  (root `models/osionos-bridge-migration.sql:128-135`), written with `writeAudit`
  (`scripts/bridge-guard.mjs:224-246`) **before** the action it describes. The audit's `event_type`
  is free text, so `pat_create`, `pat_use` and `pat_revoke` need no schema change.
- The audit's `details` must never carry the secret (`scripts/bridge-guard.mjs:220-222`): the row
  records the token **id**, never the token.

### 4. The account plane has no table for a token

- `public.osionos_sessions` (root `models/osionos-account-foundation-migration.sql:165-184`) is the
  house model for an owner-scoped credential: `id UUID PRIMARY KEY`, `user_id … REFERENCES
  auth.users(id) ON DELETE CASCADE`, a `CHECK`-ed shape, `ENABLE ROW LEVEL SECURITY`, a service-role
  policy plus an owner-read policy filtered on `public.osionos_account_uid()`
  (`:209-215`), a **column** grant to the account role that excludes the secrets (`:206-208`), and
  the marker `COMMENT ON TABLE … IS 'osionos:account-plane'` (`:217`).
- The account role's column grants are the whole boundary: `GRANT SELECT (id, created_at, expires_at,
  last_seen_at, auth_method, ip_prefix, user_agent, revoked_at, revoked_reason)` — note what is
  **not** there: `refresh_hash`, `sudo_until` (`:207-208`). A PAT table must be built the same way,
  with `token_hash` on the far side of the line.

### 5. The Settings surface has no home for a credential

- The registry is the one list of sections: `SETTINGS_SECTIONS`
  (`src/features/settings/model/sections.ts:98-239`) drives the nav, the search, the palette
  (`src/features/settings/model/settingsCommands.ts:32-52`), the deep link and the panel map
  (`src/features/settings/ui/sectionPanels.tsx:32-78`). Its 19 ids are asserted verbatim by
  `tests/canvas/settings-sections.test.ts:44-55`, and the panel folders are bounded by
  `tests/canvas/settings-kit-adoption.test.ts:46-49` and `:79-82`.
- The `features` group holds `ai`, `mcp`, `public_pages` and `library`
  (`src/features/settings/model/sections.ts:195-214`); the `access` group holds `teamspaces`,
  `permissions`, `billing` and `plans` (`:217-238`). A credential belongs with the developer-facing
  sections, and P5-2 (authorized apps) and P5-3 (SSH/GPG keys) will want the same home.

## P5-1-a — the token table (root SQL)

Repo: root groot repo, `/home/dlesieur/Documents/groot-wt/root-integration`, branch `feat/acct-P5-1-a`
from `feat/account-platform`. SQL only; no app file changes.

### Contract

1. **A new migration file** `models/osionos-personal-access-tokens-migration.sql`, idempotent, one
   transaction, doing exactly this and nothing else:

   ```sql
   CREATE TABLE IF NOT EXISTS public.osionos_personal_access_tokens (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
     name TEXT NOT NULL CHECK (char_length(name) BETWEEN 1 AND 64),
     kind TEXT NOT NULL CHECK (kind IN ('classic','fine_grained')),
     -- classic: 'pages:read' / 'pages:write'; fine-grained: empty.
     scopes TEXT[] NOT NULL DEFAULT '{}',
     -- fine-grained: [{resource, attributes[], permissions[]}]; classic: empty.
     grants JSONB NOT NULL DEFAULT '[]'::jsonb,
     -- sha256 of the whole secret, hex. Never the secret.
     token_hash TEXT NOT NULL CHECK (token_hash ~ '^[0-9a-f]{64}$'),
     expires_at TIMESTAMPTZ NOT NULL,
     created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
     revoked_at TIMESTAMPTZ,
     revoked_reason TEXT CHECK (revoked_reason IN ('user','admin')),
     CHECK (expires_at > created_at),
     CHECK (kind = 'classic' OR scopes = '{}'),
     CHECK (kind = 'fine_grained' OR jsonb_array_length(grants) = 0),
     CHECK (jsonb_typeof(grants) = 'array')
   );
   ```

   - `grants` is `jsonb` and not a table of its own: a token's grant set is read with its token, in
     one row, and it is small (a handful of resources). **Rejected:** a
     `osionos_personal_access_token_grants` table — a second table, a second join, a second
     idempotency surface, for no query this package makes.
   - `CHECK (kind = 'fine_grained' OR jsonb_array_length(grants) = 0)` and its mirror are the
     "classic **or** fine-grained, never both, never neither" rule, enforced by the database as well
     as by the bridge.
   - The `expires_at > created_at` CHECK is the "expiry required" rule at the storage layer: a row
     without a future expiry cannot exist.
2. **The indexes, named and `IF NOT EXISTS`** (the house rule, root
   `models/osionos-account-foundation-migration.sql:186-190`):
   - `CREATE UNIQUE INDEX IF NOT EXISTS osionos_personal_access_tokens_hash_uidx ON
     public.osionos_personal_access_tokens (token_hash);` — the lookup, and the uniqueness that
     makes a hash collision a 409 instead of an ambiguity.
   - `CREATE INDEX IF NOT EXISTS osionos_personal_access_tokens_user_idx ON
     public.osionos_personal_access_tokens (user_id, created_at DESC);` — the owner's list.
3. **The grants, in the house order** (root
   `models/osionos-account-foundation-migration.sql:196-217`):
   - `DROP TRIGGER IF EXISTS osionos_personal_access_tokens_realtime_trigger ON
     public.osionos_personal_access_tokens;` — grobase's CREATE TABLE hook broadcasts every new
     public table's rows (`realtime_notify()`), and a row broadcast would carry `token_hash` to
     every realtime subscriber. The check `realtime_triggers` (root
     `scripts/verify/models-grants/checks.sql:85-88`) counts them.
   - `ALTER TABLE public.osionos_personal_access_tokens ENABLE ROW LEVEL SECURITY;`
   - `REVOKE ALL ON public.osionos_personal_access_tokens FROM PUBLIC, anon, authenticated;` — the
     `privileged` check (root `scripts/verify/models-grants/checks.sql:10-16`) counts any relation
     anon or authenticated can touch.
   - `GRANT ALL ON public.osionos_personal_access_tokens TO service_role;` — the `service_role_gaps`
     check (root `scripts/verify/models-grants/checks.sql:25-29`) requires full CRUD.
   - `REVOKE ALL ON public.osionos_personal_access_tokens FROM osionos_account_user;` **first** —
     a table-level grant left over from an earlier run survives a replay, and only this line takes it
     back (root `models/osionos-account-foundation-migration.sql:205-206`).
   - `GRANT SELECT (id, user_id, name, kind, scopes, grants, created_at, expires_at, revoked_at,
     revoked_reason) ON public.osionos_personal_access_tokens TO osionos_account_user;` — **column
     grants, never a table grant**. `token_hash` is deliberately absent: the account role cannot
     select it, so the owner's list route cannot leak it even by accident.
   - `DROP POLICY IF EXISTS osionos_personal_access_tokens_service_role_all …` then
     `CREATE POLICY osionos_personal_access_tokens_service_role_all ON
     public.osionos_personal_access_tokens FOR ALL TO service_role USING (true) WITH CHECK (true);`
   - `DROP POLICY IF EXISTS osionos_personal_access_tokens_owner_read …` then
     `CREATE POLICY osionos_personal_access_tokens_owner_read ON
     public.osionos_personal_access_tokens FOR SELECT TO osionos_account_user
     USING (user_id = (SELECT public.osionos_account_uid()));` — the wrapped helper is deliberate:
     it is evaluated once per query, not once per row (root
     `models/osionos-account-foundation-migration.sql:212-215`).
   - `COMMENT ON TABLE public.osionos_personal_access_tokens IS 'osionos:account-plane';` — without
     the marker the account role reaches a relation anon does not and the check `k1` fails (root
     `scripts/verify/models-grants/account-checks.sql:20-43`).
   - `NOTIFY pgrst, 'reload schema';` at the end.
4. **The account role never writes this table.** The bridge writes it through the service role
   (ADR 0003: "the one account-plane table whose writes do not go through `asUser`"), because the
   account role must not be able to write `token_hash`. The owner **reads** it through `asUser`.

## P5-1-b — the store and the three management routes (the bridge)

Repo: osionos app, `/home/dlesieur/Documents/groot-wt/integration/app`, branch `feat/acct-P5-1-b`
from `feat/account-platform`, **after P5-1-a is merged into the root branch**.

### Contract

1. **The store**, a new `scripts/bridge-pat-store.mjs` (Node built-ins only, ≤ 300 lines):

   - `export const PAT_PREFIX = 'osio_pat_';`
   - `export function mintPatSecret()` → `{ secret, hash }`: `secret = PAT_PREFIX +
     randomBytes(32).toString('base64url')` (43 characters after the prefix, 51 in all — the same
     generator shape as `scripts/bridge-api.mjs:248-250`), `hash = createHash('sha256').update(secret)
     .digest('hex')` (64 hex characters).
   - `export function hashPatSecret(secret)` → the same hex sha256. The hash covers the **whole**
     secret, prefix included, so a hash in the table cannot be replayed as a secret.
   - `export function isPatSecret(value)` → `typeof value === 'string' &&
     /^osio_pat_[A-Za-z0-9_-]{43}$/.test(value)`.
   - `export async function createPat({ pg, userId, name, kind, scopes, grants, expiresAt })` →
     inserts through `pg.asService()` and returns the row (`Prefer: return=representation`). The
     service role is the only writer: the account role has no INSERT on the table (P5-1-a step 3).
   - `export async function listPats({ pg, session })` → reads through `pg.asUser(session)` with
     `select=id,name,kind,scopes,grants,created_at,expires_at,revoked_at,revoked_reason`,
     `order=created_at.desc`, `limit=50` (the sessions list's shape,
     `scripts/bridge-sessions.mjs:37-38`, `:186-191`). The RLS policy does the owner filtering; the
     route adds **no** `user_id` filter and must not read the table with `asService`.
   - `export async function revokePat({ pg, userId, id, now })` → a service-role
     `PATCH … ?id=eq.<id>&user_id=eq.<uid>&revoked_at=is.null` with
     `{ revoked_at: now, revoked_reason: 'user' }`; returns true when a row changed. The `user_id`
     comes from the **verified session**, never from the request.
   - `export async function findPatByHash({ pg, hash })` → a service-role read of
     `osionos_personal_access_tokens?token_hash=eq.<hash>&select=id,user_id,kind,scopes,grants,
     expires_at,revoked_at` — the one read that must see `token_hash`, and it is a lookup by an
     indexed equality on a 256-bit secret, so there is no timing oracle and no enumeration.

2. **The routes**, a new `scripts/bridge-account-tokens.mjs`, mounted through the account seam

   config)`, `scripts/bridge-sessions.mjs:260`). **A PAT may never reach them** — a PAT that could

## P5-1-c — the vocabulary, the evaluator and the field mask (pure)

Repo: osionos app, branch `feat/acct-P5-1-c` from `feat/account-platform`. One new module and one
new test file; **no I/O, no bridge edit**. Merge it before P5-1-b (b imports the vocabulary) and
before P5-1-d (d imports the evaluator).

### Contract

1. **A new module `scripts/bridge-pat-permissions.mjs`** (Node built-ins only, no I/O, ≤ 300 lines)
   exporting:

   - `export const PAT_RESOURCES = { pages: { attributes: [...] } };` — the resource vocabulary.
     In P5-1 the only resource is `pages`, and its attributes are **exactly** the union of the keys
     `pageRowToEntry` returns (`scripts/bridge-api.mjs:726-756`) and the keys
     `pageUpdateRowFromPayload` reads (`scripts/bridge-api.mjs:853-875`):
     `_id, title, icon, cover, coverPosition, updatedAt, workspaceId, ownerId, visibility,
     collaborators, parentPageId, sortOrder, databaseId, archivedAt, content, properties, surface,
     isTemplate, isDefaultTemplate, templateSurface, recurrence`.
     The vocabulary grows with the route allowlist (P5-1-d), never on its own.
   - `export const PAT_PERMISSIONS = ['read', 'write'];`
   - `export function isPatScope(value)` → `value` is `resource:permission` and both halves are in
     the vocabulary. **There is no wildcard**: `pages:*` is not a scope.
   - `export function isPatGrant(value)` → `value` is an object with a known `resource`, an array of
     known `attributes` and an array of known `permissions`, all three non-empty.
   - `export function evaluatePat({ scopes, grants }, { resource, permission })` →
     `{ allowed: boolean, mask: string[] | null }`.
     - A **classic** scope `resource:permission` grants the pair with **no attribute restriction**:
       `mask === null`.
     - A **fine-grained** grant `{resource, attributes, permissions}` grants the pair restricted to
       its `attributes`: `mask` is the union of the attributes of every matching grant.
     - Two grants for the same resource → the mask is the **union** of their attributes.
     - **Deny by default.** A grant naming an unknown resource or an unknown permission is ignored
       entirely. An attribute that is not in the vocabulary is **dropped** from the mask — it never
       widens it. A malformed row (`scopes` not an array, `grants` not an array, a grant that is not
       an object) grants nothing and throws nothing.
   - `export function maskAttributes(entry, mask)` → a **new** object with only the mask's keys (plus
     `_id`, which is always kept: it is the resource's identity). The input is not mutated. A `mask`
     of `null` returns the entry unchanged. A key that is not in the mask is dropped even if it holds
     something the caller never asked for (`email`, `owner_id`, …).
   - `export function maskRequestPayload(payload, mask)` → a new object with only the mask's keys.
     Nothing is added. A payload that is not a plain object is returned unchanged (the route answers
     422 on its own).

2. **The vocabulary is the contract between the bridge and the app.** The app needs it to render the
   picker; P5-1-e copies it into `src/features/settings/developer/patModel.ts` **as a typed
   constant**, and the two copies are compared by the canvas test (open question 1 asks whether the
   bridge should serve it instead).

## P5-1-d — the Bearer middleware: a PAT is exchanged for an internal session

Repo: osionos app, branch `feat/acct-P5-1-d` from `feat/account-platform`, **after P5-1-c is merged**
(it imports c's module) and after P5-1-b (it reads the table through b's store).

### Contract

1. **How a PAT request is authenticated, relative to the app-session token.** The app session is a
   signed token the bridge verifies offline (`scripts/bridge-api.mjs:461-471`). A PAT is an opaque
   secret the bridge must **look up**. The bridge therefore does not add a second authentication
   system: it **exchanges** the PAT for an internal app-session token, in one place, before any route
   runs.

   - The exchange is one insertion in `scripts/bridge-api.mjs`: in `handleBridgeRequest`
     (`:4189-4245`), right after the URL is built (`:4194`) and **before** the first workstream
     module (`:4198`), the gate runs; the context gains a `patGate` key at `:4299`.
   - The gate **rewrites `request.headers.authorization`** to `Bearer <internal token>`. The PAT
     itself never reaches a route, a log line, an error message or the audit row. The internal token
     is `osionos_v1.<payload>.<hmac>` like any other (`scripts/bridge-api.mjs:437-459`), so every
     existing route authenticates it with the code it already has
     (`verifyAppSessionToken`, `:461-508`) and **no route changes**.
   - The internal token's claims: `sub` = the PAT's owner, `workspace_ids` = the owner's workspaces
     at request time, `roles` = the workspace roles, `is_admin` = **false** (a PAT never carries
     admin), `jti` = a fresh uuid, `exp` = **120 s** (`PAT_SESSION_TTL_SECONDS`, the same budget as
     the account JWT, `scripts/bridge-pg.mjs:25`).
     The TTL is forced by passing a config copy to `signAppSessionToken`
     (`sessionTtlSeconds`, `scripts/bridge-api.mjs:440`), never by changing the app session's own
     TTL.
   - **Caveat, in the source:** the internal session is a derived credential (ADR 0003's list) — it
     lives 120 s. It never leaves the server (the client only ever sees the PAT), and the PAT is
     re-read on every request, so a revoke takes effect on the **next** request.
   - **The workspace ids** come from the owner at request time: the private workspace from
     `osionos_bridge_identities.private_workspace_id` (root
     `models/osionos-bridge-migration.sql:19`) and the memberships from
     `osionos_workspace_members` (the same source `memberWorkspaceIds` reads,
     `scripts/bridge-api.mjs:3373-3383`). **No workspace → 403 `pat_no_workspace`** (the app-session
     token cannot be minted without one: `scripts/bridge-api.mjs:498-500`).

2. **The gate's steps**, in this order, in a new `scripts/bridge-pat-middleware.mjs`:

   1. Read the header raw. A bearer that does not match
      `/^Bearer\s+(osio_pat_[A-Za-z0-9_-]{43})$/` is **not** a PAT request: the gate returns and the
      normal flow continues (an app-session request must not pay for the gate, and a request with
      no header must not be 401'd here — the route answers that).
   2. `findPatByHash({ pg, hash: hashPatSecret(secret) })` (b's store, service role).
      - No row → **401 `pat_invalid`**. The answer is the same for "no such token" and "wrong
        secret": there is nothing to distinguish.
      - `revoked_at` set → **401 `pat_revoked`**.
      - `expires_at` ≤ now → **401 `pat_expired`**.
      - A store failure → **503** (the account plane's mapping,
        `scripts/bridge-pg.mjs:46`, `:101-113`), never a 401: a down database is not a bad token.
   3. **The route allowlist** — a table in the module, not a branch in the code:

      ```js
      export const PAT_ROUTES = [
        { method: 'GET',   pattern: /^\/api\/pages\/[0-9a-f-]{36}$/i, resource: 'pages', permission: 'read',
          maskRequest: false, maskResponse: true },
        { method: 'PATCH', pattern: /^\/api\/pages\/[0-9a-f-]{36}$/i, resource: 'pages', permission: 'write',
          maskRequest: true, maskResponse: false },
      ];
      ```

      - **The list is the whole surface.** A PAT on any other path — including
        `/api/account/tokens*`, `/api/workspaces`, `/api/pages` (the list), the MCP route, the SSE
        route — is **403 `pat_route_not_allowed`**. There is no "PAT-accepting route" flag anywhere
        else in the bridge.
      - The path is matched on `url.pathname` **and** `request.method`; a `GET` on a PATCH route is
        not allowed.
      - The pattern is deliberately narrow: `GET /api/pages/:id` is the single-page read
        (`handlePageRead`, `scripts/bridge-api.mjs:2506-2512`), not `GET /api/pages` (the list,
        `:3365`) and not `GET /api/pages/all` (`:2366`).
   4. `evaluatePat(row, route)` (c's module):
      - not allowed → **403 `pat_scope_denied`**.
      - allowed with `mask === null` (a classic scope) → no mask is installed at all.
   5. The internal session is minted and the header is rewritten (step 1).
   6. **The request mask** (only for a route with `maskRequest: true` and a fine-grained token): the
      gate attaches the mask to the request (`request.patMask = { attributes: [...] }`) and the one
      body reader applies it. `readJson` (`scripts/bridge-api.mjs:2123-2130`) gains one line: after
      the JSON is parsed, the payload is passed through `maskRequestPayload` when
      `request.patMask` is set. A route that reads its body elsewhere must apply the mask itself —
      P5-1's only write route reads its body with `readJson`
      (`scripts/bridge-api.mjs:3495`), so the one line covers it; a later package that adds a
      PAT-accepting route with another reader says so in its contract.
   7. **The audit.** `writeAudit(pg, { session, meta, eventType: 'pat_use', details: { tokenId,
      method, path, outcome } })` — **before the route runs**, so the row records the attempt
      (`scripts/bridge-guard.mjs:219-223`). `outcome` is `allowed`, `scope_denied` or
      `route_not_allowed`.
      - The `session` is the internal session object (`{ userId, workspaceIds, roles, isAdmin,
        raw: { jti } }`); the `jti` is the one the gate minted, so the audit row's `session_id` is
        filled.
      - The `meta` is `clientMeta(request, { ipHeader: config.clientIpHeader, hashSecret:
        config.ipHashSecret })` (`scripts/bridge-guard.mjs:139-154`), with the IP columns blanked
      when no header is configured — the peer is the proxy then
      (`scripts/bridge-sessions.mjs:112-115`).
      - **A PAT that does not resolve is not audited**: there is no subject to audit. It is a server
        log line only. This is stated in the module header.
      - **Cost, in a `Caveat:` line:** one audit INSERT per PAT request. The plan asks for every use
        to be audited; that is what this is. Open question 5 asks whether that is the budget.
   8. **The response mask** (only for a route with `maskResponse: true`): the gate patches the
      response before the route writes:
      - `response.writeHead(status, headers)` is **deferred** (stored, not sent) so the gate can
        still change the status;
      - `response.end(body)` computes the masked body and then sends the stored head and the body;
      - `response.write(chunk)` **throws** (`status: 500`, `code: 'pat_route_streams'`): a masked
        route may not stream, because a stream cannot be masked. The SSE route is not in the
        allowlist, so this is a safety net, not a path;
      - the mask applies to a **2xx JSON body only** — an error body (`{ok:false,message,code}`)
        passes through unchanged, and it carries no page attribute anyway;
      - any `content-length` header is dropped when the body is rewritten;
      - a body that is not JSON, or that cannot be masked, is **not** sent: the gate answers 500
        `pat_mask_failed`. Failing closed is the only safe answer: the unmasked body must never
        reach the client.
      The mask is `maskAttributes` (c's module): only the mask's keys survive, plus `_id`.
   9. **The request that is not a PAT** is untouched: no lookup, no audit row, no rewrite.

3. **What a PAT never gets**, in the module header:
   - it is never admin (`is_admin: false` in the internal token, so `session.isAdmin` is false);

## Security edges (all five packages)

- **Who may call what.** The three token routes need an **app session**; a PAT is refused on them
  (403 `pat_route_not_allowed`) before the route runs. The only PAT-accepting surface in P5-1 is
  `GET /api/pages/:id` and `PATCH /api/pages/:id`; every other path refuses a PAT.
- **What a non-owner sees.** Nothing of the token table: the account role's RLS policy scopes the
  read to `user_id = osionos_account_uid()` (P5-1-a), and the route adds no filter of its own. A
  token id belonging to another user answers **404**, not 403, on revoke — the id is not a probe.
- **What the secret looks like.** `osio_pat_` + 43 base64url characters (256 bits). Only its sha256
  is stored; the account role cannot even select `token_hash`. The secret is returned by exactly one
  route, exactly once, and appears in no list, no audit row and no log line.
- **What a PAT can do.** Exactly what its owner can do, minus what its grants withhold. A PAT is
  the user: the page ACL, the ownership rule, the sharing rule and the workspace gate all still
  apply. The field mask is an **extra** restriction on top, never a way around them.
- **What a PAT is never.** Never admin (`is_admin: false`), never a session (it cannot be cut off or
  revoked by a session cut-off — only an explicit revoke kills it), never a way to mint another PAT.
- **The audit.** One `pat_use` row per PAT request (the attempt, whatever the outcome), one
  `pat_create` and one `pat_revoke` per management action. The audit write happens **before** the
  action, so an audit outage means the action does not happen (503) — never the other way round.
- **The mask fails closed.** A body that cannot be masked is a 500, not an unmasked 200. An error
  body is not masked (it carries no attribute); a 2xx body is masked.
- **The client's copy of the vocabulary** is a copy: a drift between the bridge's list and the app's
  list shows a scope in the picker the bridge will refuse. The canvas test compares them (open
  question 1 asks for the better answer).

## Open questions (settled in Decisions D-P5-1 above; kept for the record)

1. **The vocabulary is written twice** — once in `scripts/bridge-pat-permissions.mjs`, once in
   `src/features/settings/developer/patModel.ts`. Should the bridge serve it
   (`GET /api/account/tokens/catalog`) so there is one list? The cost is one more route and one
   more round trip before the panel can render its picker; the benefit is that a scope the app
   offers is always a scope the bridge accepts.
2. **"Last used".** P5-1's table has no `last_used_at` and the panel shows no last-use column: the
   audit row is the record. The alternative is a column plus a conditional write per request (one
   more round trip per PAT call) or a read of the audit table per list (expensive for 50 tokens).
   Which does the ledger want?
3. **Does a password change or "log out everywhere" kill the PATs?** P5-1: no — only an explicit
   revoke does (the internal session is minted fresh, so the cut-off never reaches it,
   `scripts/bridge-api.mjs:493`). GitHub keeps PATs across a password change. Should osionos?
4. **The expiry cap.** P5-1 caps a token at one year and requires an expiry. Is one year the cap,
   and may a user pick a shorter one freely (7 days, 30 days) or only a date?
5. **The audit cost.** One INSERT per PAT request is what "every use is audited" costs. A client
   polling at 1 rps writes one row per second, forever, in a table that is not partitioned. Is that
   the budget, or should a use be audited once per token per minute (which would need the plan to
   change, not the code)?
6. **The first PAT-accepting surface.** P5-1 lists `GET /api/pages/:id` and `PATCH /api/pages/:id`
   because they are cheap and already ACL'd. P5-2 (MCP) needs `/api/workspaces`, `/api/pages/all`
   and the page writes. Should P5-1 list the MCP surface now, or is it right to keep the list at two
   routes until P5-2?
7. **A classic `pages:read` sees the whole page, `content` included.** Should a classic scope be
   limited to metadata (no `content`) and leave the body to fine-grained tokens only?
8. **The desktop edition** (`apps/osionos-electron/native/firstrun.mjs`) applies an explicit
   migration list, so the new table does not exist there and the desktop has no PATs. The ledger
   already tracks the desktop account plane as a follow-up; this package does not touch it.
9. **The `pages` attribute vocabulary is the page entry's keys** (`pageRowToEntry`,
   `scripts/bridge-api.mjs:726-756`). It is a public shape, not a stable API: a new page field is a
   new maskable attribute. Should the vocabulary be pinned instead (a fixed list the bridge
   enforces) so a new page field cannot be read by an old token without a decision?
