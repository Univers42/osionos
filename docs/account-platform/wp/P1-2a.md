# P1-2a 👹 — typed profile, public profile by username, preferences: the first account routes

Repo: osionos app, branch `feat/acct-P1-2a` from `feat/account-platform` **after P0-4 merges** (it
mounts through `scripts/bridge-account-mounts.mjs`) and **after root P1-1 merges** (the tables). The
routes that need sudo (username change, deletion request, revoking sessions from the UI) are P1-2b.
Facts are from research runs R-P1-25 and R-P1-2 (2026-10-22); re-check each anchor before editing.

## Why
- The profile is a jsonb blob behind `PATCH /api/profile/me` (`scripts/bridge-profile.mjs:182-206`).
  That route has no read for the caller's own profile (there is no `GET /api/profile/me`), no
  If-Match, and no validation beyond length. P1-1 adds typed `osionos_profiles` with a `version`
  column, CHECKs and owner-only RLS for the account role.
- No route reads or writes settings. `useUserPreferencesStore` calls `/api/preferences`, and after
  P1-5 `useNotificationSettingsStore` calls `/api/account/notification-settings`; both 404 today
  (R-P1-25 §1, §3).
- There is no way to look a person up by handle, which P2-1's `/u/<username>` needs.

## Contracts
Every route needs an app session (`deps.verifySession`). An owner's rows are read and written
through `pg.asUser(session)` (ADR 0001; `scripts/bridge-pg.mjs:168`), never through the service role.
An unavailable account plane answers 503 `account_plane_unavailable` (bridge-pg's mapping), never a
silent fallback.

1. **`GET /api/account/profile`** returns the caller's row:
   - every column the account role may SELECT, in camelCase;
   - `version`, also sent as `ETag: "<version>"`.

   No row (registration races the P1-1 trigger) answers 404 `profile_missing`; the client retries,
   and the next boot's backfill heals it.
2. **`PATCH /api/account/profile`** changes the caller's own profile.
   - **Body:** a subset of the editable columns (P1-1's role UPDATE list minus `username`). Any
     other key → 422 `field_not_editable` naming it. `username` is P1-2b and also 422 here.
   - **If-Match:** required; missing → 428 `precondition_required`. The write is
     `PATCH osionos_profiles?user_id=eq.<uid>&version=eq.<N>` with
     `Prefer: return=representation`.
   - **Results:**
     - zero rows → 412 `version_mismatch`, carrying the current row and `version` so the client
       can show what changed;
     - `23514` → 422 `invalid_field` naming the column, parsed from the constraint name, never the
       raw database message;
     - `23505` → 409;
     - success → 200 with the new row and ETag.
   - **Rate limit:** 60/min per user via `rateLimit(kv, ['profile', uid], …)`.
3. **`GET /api/users/:username`** looks a person up by handle, case-insensitive (P1-1's
   `lower(username)` index).
   - **Read:** through the service role (another person's row is not the caller's), with an
     **explicit column allowlist**: `userId, username, displayName, pronouns, headline, bio,
     location, company, website, links, timezone, orcid, patreon, avatarUrl, bannerUrl`.
   - **Reduced card:** when the subject opted out of the directory or blocked the viewer (reuse the
     block check the current `getProfile` uses, `bridge-profile.mjs:84-118`) and the viewer is not
     the subject, return only `userId, username, displayName, avatarUrl`.
   - **Not found:** an unknown name → 404 `user_not_found`; a name held in
     `osionos_username_history` → the same 404 (no "this name was taken" oracle).
   - **Never in a response:** email, settings, deletion state, `directory_opt_out`, `version`.
4. **Settings sections.** Two route families map to one section each, and nothing else is exposed:
   - `GET`/`PATCH` `/api/preferences` → section `preferences`;
   - `GET`/`PATCH` `/api/account/notification-settings` → section `notifications`.

   How they behave:
   - **GET:** returns the section's object, or `{}`.
   - **PATCH:** calls `rpc/osionos_user_settings_merge` as the user. A JSON object only; > 16 KB →
     413; `null` deletes a key. Returns the merged object.
   - **PUT:** if a store sends a full object with PUT today (read `useUserPreferencesStore` and
     `useNotificationSettingsStore` and say which methods and shapes they use), accept PUT as
     "replace the section" by merging the object plus a `null` for each key the client dropped.
     Do not change the stores (P1-5 owns them).
   - **Rate limit:** 120/min per user.
5. **Legacy `PATCH /api/profile/me` keeps working unchanged.** P1-1's sync trigger copies it into
   `osionos_profiles`. `GET /api/profile/:uuid` is unchanged. Say in a comment on each that P2-1 or
   P1-6 retires it.
6. **Module layout:**
   - `scripts/bridge-account-profile.mjs` holds routes 1–3;
   - `scripts/bridge-preferences.mjs` holds route 4;
   - each is appended to the `modules` list in `bridge-account-mounts.mjs` and to
     `deploy/bridge-fly/Dockerfile`'s COPY list. `bridge-api.mjs` is not touched; if the mount
     cannot reach `/api/users/` or `/api/preferences`, say why and stop.
   - Each file ≤ 300 lines, Node built-ins only.

## Acceptance (`tests/bridge/`, a fake PostgREST that APPLIES filters — extend P0-4's `support/session-postgrest.mjs` pattern)
1. Profile: GET returns the caller's row and its ETag. PATCH with the right If-Match → 200 and the
   version moves by one. Two PATCHes with the same If-Match → exactly one 200 and one 412 carrying
   the current row. No If-Match → 428. `username` in the body → 422. An unknown key → 422. A CHECK
   violation → 422 naming the column, with no SQL text in the body. Every request the fake received
   for routes 1–2 carried the per-user JWT (aud `osionos-account`), never the service key.
2. Isolation: A's session PATCHing with B's version, or with a forged `user_id` in the body, changes
   none of B's rows (assert on the fake's state).
3. `/api/users/:username`:
   - case-insensitive hit;
   - opted-out subject → the reduced card for another viewer, the full card for the subject;
   - a blocked viewer → the reduced card;
   - unknown name and held name → identical 404 bodies.
   - **Key-set assertion:** the full card's keys equal the allowlist exactly; adding a column to the
     fake's row (e.g. `email`) does not leak it.
4. Settings: PATCH merges, a `null` deletes, two concurrent PATCHes on one section both land
   (through the merge RPC, not read-modify-write), > 16 KB → 413, an array body → 422, an unknown
   section path → 404. The notification-settings path does not collide with
   `/api/notifications` (the inbox still answers its own shape).
5. `bridge-dockerfile-closure.test.mjs` passes with the two new modules.
