## Why

- The portal has no OAuth entry point (`rg -n "oauth|authorize" src` finds nothing in
  the website tree); the only sign-in paths are password, email-code and approval.
- GoTrue already declares Google, GitHub and 42 providers in the root compose, default off
  (`auth-api.yml:61-76`, `docker-compose.monolith.yml:780-795`); enabling is a credential +
  config act, not code.
- The measured live GoTrue (`ghcr.io/univers42/grobase-gotrue:latest`, v2.188.1) has **no
  42 provider** in its compiled provider list, so `GOTRUE_EXTERNAL_FORTYTWO_*` is ignored;
  42 must be a custom `oauth2` provider created through the GoTrue admin API.
- The account-takeover risk is the silent link: an unverified provider email that collides
  with an existing account must never merge. The guard runs inside the gateway's osionos-session
  mint, not in a browser route that can be skipped (R4).

- F1–F4: auto-link behaviour. With `GOTRUE_MAILER_AUTOCONFIRM=false` GoTrue refuses an
  unverified provider email (refused at callback, no link); with `true` (live today) it
  silently LINKS an unverified provider email to a confirmed password account and issues a
  session (account takeover inside GoTrue). Verified provider emails link in both modes.
- F5–F7: fresh emails and no-email. Verified fresh email → new user; unverified fresh email
  needs GoTrue SMTP; provider returning no email → `server_error`.
- F8: the `email` identity's `identity_data.email_verified` is false even on a confirmed
  password account; use `user.email_confirmed_at`, never that flag.
- F9: an OAuth access token's `amr` is `[{method:'oauth', timestamp}]`; a password token's is
  `[{method:'password'}]`. `app_metadata.provider` keeps the FIRST provider, so it cannot
  detect an OAuth sign-in.
- F10: 42 is reachable only as a custom `oauth2` provider (`custom:fortytwo`); built-in
  `fortytwo` → 400. Admin route refuses URLs resolving to private addresses. Returned keys
  include `attribute_mapping` ({} by default), `pkce_enabled`, `email_optional` (false).
- F11: PKCE. `/authorize` accepts `code_challenge` + `code_challenge_method=s256`; callback
  returns `redirect_to?code=<uuid>` in the QUERY (no fragment); `POST /token?grant_type=pkce`
  with JSON `{auth_code, code_verifier}` → 200 session; replayed code → 404
  `flow_state_not_found`. Without a challenge, implicit flow puts tokens in a FRAGMENT.
  Errors arrive as `?error=&error_code=&error_description=` (query, mirrored in fragment).
- F12: `redirect_to` outside `GOTRUE_URI_ALLOW_LIST` → GoTrue lands on `GOTRUE_SITE_URL`
  (no open redirect).
- F13: `POST /logout?scope=local` with the access token → 204; then `GET /user` → 403 and
  its refresh token → 400.
- F14: `GET /user` returns `identities[]` with `provider`, `identity_data.email_verified`,
  `created_at`.

   enabling steps are in "Owner runbook"; the merge changes nothing users see until that list

2. The new gateway route `POST /api/auth/oauth-session` answers `404` when the gateway's own
   copy of `PUBLIC_OAUTH_PROVIDERS` (same variable name, read from `process.env`) is empty, so
   the server half is dark too.
3. The guard in `handleOsionosSession` is live on merge for every existing caller, including the
   app's `/api/auth/exchange`; a password-only user still mints there (test pins it).
4. **Owner runbook step 0 (R8, binding):** the stack's `GOTRUE_MAILER_AUTOCONFIRM` must be
   `false` before any provider is ENABLED (F1: `true` = GoTrue links an unverified provider
   email to a confirmed account and issues a session, which no website or bridge guard can take
   back). Live is `true` today. Turning it off changes password sign-up confirmation; whether

5. **Register mode (C20):** when `AUTH_LOGIN_EMAIL_OTP=true`, `POST /api/auth/oauth-session`
   refuses with `409 oauth_requires_password_login` before any GoTrue call (fail closed, tested).
   The portal hides OAuth buttons in register mode. OAuth buttons render in login mode only.
6. **No auto-redirect without redirectUrl:** on callback success with no `redirectUrl` from the
   gateway, show a signed-in state and a link to `/`, no auto-redirect.

### Provider detection and collision guard (d2-a, R4, R5, R7)

2. `handleOsionosSession` runs the guard on **every** mint, for every token, with no OAuth
   detection and no skip: F9 makes `app_metadata.provider` unusable, and any skip is the bypass.
   The rule below lets a one-identity user (every password-only account today) through untouched,
   so the guard needs no detector. Tests (i)-(iii) of acceptance 3 pin that `amr` and
   `app_metadata.provider` change nothing.
3. For every token the gateway reads the user's identities from the `getUser()` answer it already
   makes (`user.identities`, F14); when that field is absent or not an array it answers
   `503 oauth_identity_unavailable` (never allow, never a second lookup path). It refuses with
   `409 { error: 'oauth_email_collision', message: 'This email is already linked to another sign-in method.' }`
   unless **one** of:
   - (a) the user has exactly one identity, or
   - (b) every non-`email` identity has `identity_data.email_verified === true` and is not
     `custom:fortytwo`, AND `user.email_confirmed_at` is set and not later than the earliest
     non-email identity's `created_at` (F8: the email identity's own `email_verified` flag is
     never read).
   The email identity's own flag is never read. A password-only user (one identity) is untouched,
   so today's sign-ins cannot regress; a test pins it.
   "Email-verified" for an identity is its `identity_data.email_verified === true`, **except**
   a `fortytwo` identity (provider `'fortytwo'` or `'custom:fortytwo'`) and **every** `custom:`
   identity is always treated as `email_verified: false` (fail closed). For 42 the account email
   is also treated as unconfirmed for this check, so (b) can never pass when 42 is involved.
   42 forces (b) false; subject = `id` (string), email = `email`, `email_optional` stays
   `false` (F6: GoTrue then refuses a provider sign-in with no email itself, which is the
   behaviour wanted). The existing incomplete-identity answer (`422`, `auth-gateway.mjs:972-975`)
   stays as the gateway's no-email answer; it names no provider.
4. On refusal the gateway calls `gotrue.logout(accessToken, 'local')` (ending that GoTrue
   session, F13) fire-and-forget, and mints nothing: no bridge call, no `redirectUrl`. The 409
   body is identical for every colliding address and names no provider. The response is not
   delayed by a slow logout. One audit event `osionos_bridge_refused` (with `reason:
   'oauth_email_collision'`, through the existing `audit()` helper) is recorded before answering; a
   failed logout is audited as `osionos_bridge_refused_logout_failed` and the answer is still 409,
   no bridge call. Unreadable identities → `503 oauth_identity_unavailable`, never allow.
5. A verified-on-both-sides email may link (GoTrue's own decision, R5); the gateway does not
   second-guess GoTrue's linking. The guard protects the osionos entry only (R4). The guard
   cannot undo a GoTrue link (no admin identity delete, `docs/account-platform/LEDGER.md:164`).
6. Limiter: add `osionosSession: 30` to `RATE_LIMITS` (`auth-gateway.mjs:97`, per minute) and call
   `rateLimit(clientIp(request), 'osionosSession')` (the existing helper, `:167`) before `getUser`
   in the shared mint; the 31st call from one IP in a window → 429 + `retry-after`, no GoTrue call.
   30, not 12: the app's `/api/auth/exchange` reaches this mint through the bridge; read how
   `clientIp` treats the bridge's forwarded address and say in the report whether app sign-ins share
   one bucket. The new `oauth-session` route uses the same key. There is no limiter on the mint
   today (the comment that says otherwise in the app is a C5-style follow-up, not d2).
7. The guard runs on every mint, including a refreshed OAuth token: a refresh keeps the identities,
   so the rule gives the same answer.

### PKCE and callback (d2-b, R3, R10)

6. PKCE only: the website always sends a `code_challenge` (R10; without one, tokens land in a
   fragment). `code_challenge` + `code_challenge_method=S256` via `queryParams` on
   `signInWithOAuth` (or a hand-built URL in `oauth-providers.ts`), and stores the pending flow
   in `sessionStorage` under the single key `prismatica.oauth.pending` =
   `{verifier, provider, createdAt}`. One pending flow per tab: read once and deleted on first
   read; ignored when older than 10 minutes; a new click replaces it. The PKCE verifier is the
   binding (F11: a consumed code is refused). There is no client `state`. The verifier (43-128
   chars, from `crypto.getRandomValues`) is generated per click. The authorize URL is
   `/auth/v1/authorize?provider=<google|github|custom:fortytwo>&redirect_to=<origin>/auth/callback&code_challenge=<S256>&code_challenge_method=s256`
   plus per-provider scopes (GitHub `read:user user:email`; 42 `public`). The code is never stored
   anywhere (C14); deleting the pending flow on first read is the client replay guard.
7. The callback page `src/pages/auth/callback.astro` + `src/scripts/auth-callback.ts`:
   - checks `PUBLIC_OAUTH_PROVIDERS` before any storage read or fetch; empty → fixed refusal,
     0 fetches;
   - reads `code` (and `error_code`) from `location.search`;
   - calls `history.replaceState` to strip the query (and any hash) **before** any app fetch or
     storage read (ordered log `['readQuery','replaceState','readVerifier','fetch',…]`);
   - reads the pending flow once and deletes it; with no pending flow (a replay, another tab,
     a hand-typed URL) it refuses without any fetch;
   - verifies the flow is not older than 10 minutes; refuses if stale;
   - sends `{code, verifier}` to the gateway route `POST /api/auth/oauth-session` (C3) with
     `credentials: 'include'`, through the existing `authClient`/`fetchWithBackoff` style of
     `useAuth.ts`; the page itself never calls GoTrue's `/token` and never sees a GoTrue token.
     The page carries a `no-referrer` meta (C11);
   - the gateway route exchanges `{auth_code, code_verifier}` with GoTrue, sets the refresh cookie,
     schedules the login alert, runs the shared guard + mint and answers with the same body as
     `POST /api/auth/osionos-session`, so the page then behaves like `completePortalLogin` after
     its `osionosSession` call;
   - follows `redirectUrl` only after `isTrustedOsionosRedirect` (`portal.ts:104`); otherwise
     blocks with the existing "Workspace redirect blocked" message. `redirect_to` is the constant
     `${origin}/auth/callback`, exact; `isTrustedOsionosRedirect` is used only for the gateway's
     `redirectUrl`; never read `next`/`return`/`redirect`; do not rely on the gateway's
     `startsWith` (`auth-gateway.mjs:1006`).
   - maps `error_code` (`provider_email_needs_verification` and others) to a plain message
     naming no account.
8. On a `409 oauth_email_collision` the callback shows "This email is already linked to another
   sign-in method. Sign in with your existing method, then link providers in Settings." (no
   provider named) and does not redirect.

## Security edge

- **Takeover (silent link):** the guard above, plus the test with a fake GoTrue returning an
  identity with `email_verified: false` over a password account (mutant: skip the check → test
  fails). 42 is always unverified. amr-based detection test: fake user `provider:'email'`,
  identities `[email verified, google unverified]`, `amr:[oauth]` → 409 + logout (kills
  provider-only); password user `provider:'email'`, identities `[email]`, `amr:[password]` →
  200 mint; a refreshed OAuth token still guarded.
- **Token in the URL:** the code (and any fragment) is stripped with `history.replaceState` before
  any app fetch or storage read; `redirect_to` is the constant `${origin}/auth/callback`, and GoTrue
  falls back to its site URL for anything off the allow list (F12); `isTrustedOsionosRedirect`
  (`portal.ts:104`) checks only the gateway's `redirectUrl`. A replayed code is refused client-side and
  by GoTrue. The code is already in Vercel/Kong logs and same-origin Referers; it is single-use
  and PKCE-bound; `no-referrer` meta on the page.
- **Enumeration:** the 409 text is identical for any colliding address and names no provider;
  per-IP limited via the gateway limiter (C6).
- **Open redirect:** `isTrustedOsionosRedirect` allowlist (`portal.ts:104-125`); untrusted
  `redirectUrl` is blocked with no navigation. `?next=https://evil` and `?return=//evil` never
  navigate.
- **PKCE verifier:** stored in `sessionStorage` only (allowed by R2), keyed by the single
  pending flow, read once and deleted; never the access/refresh token.
- **State:** none client-side; the verifier binding is the security (C9).
- **GoTrue linking (R5):** a verified-on-both-sides email may link inside GoTrue; the gateway
  does not prevent GoTrue's own linking decision, only the osionos mint.
- **Timing:** on refusal logout is fire-and-forget so the 409 is not measurably slower; audit
  recorded before answering.

## Acceptance checks

1. `PUBLIC_OAUTH_PROVIDERS` unset/empty → no OAuth button in the built portal (DOM assertion,
   not build grep) and the OAuth click handler refuses; import-time `console.warn` for unknown
   values (not build-time). `"google"` → Google button only. `"google,github,fortytwo"` → three
   buttons. An unknown value (`"apple"`) → ignored, no button. OAuth buttons render in login
   mode only; hidden in register mode.
2. Callback with `?code=...`: the URL is cleaned before any fetch; the pending flow is read once
   and deleted; a second load with the same code is refused without a network call; stale flow
   (>10 min) pruned.
3. Collision with an unverified identity: `409 oauth_email_collision`, `gotrue.logout` called,
   no bridge call and no `redirectUrl`; the body is byte-identical for two different addresses.
   amr-based detection: (i) fake user `provider:'email'`, identities `[email verified, google
   unverified]`, `amr:[oauth]` → 409 + logout; (ii) password user `provider:'email'`,
