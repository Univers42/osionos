## Why

### 1. Share rules are stored but never enforced on a page read or write
- The rules table exists: `public.osionos_share_rules` (root `models/osionos-share-rules-migration.sql:16-33`),
  with `resource_type` (`:19`), `resource_id` — `''` means the whole workspace (`:23`) — and a
  `permission` level in `('no_access','can_view','can_comment','can_edit','full_access')` (`:27-28`).
- The bridge writes and lists them through `/api/perms/rules`
  (`scripts/bridge-perms.mjs:32-34`, routes at `:256-283`; storage `scripts/bridge-perms-rules.mjs:96-158`).
- No page path ever reads them: `ruleStore` is referenced only inside `scripts/bridge-perms.mjs`
  (`:139`, `:154`, `:256`), never by the page read or write code.
- The page read rule is `canReadPageRow` (`scripts/bridge-page-read.mjs:52-59`): `visibility`
  + `owner_id` + `collaborators`, nothing else. The page write rule is `mayModifyPage`
  (`scripts/bridge-api.mjs:887-897`) and `canWritePageRow` (`:1087-1092`): owner, workspace
  role/permission, `collaborators` — nothing else.
- So a user the Share dialog granted `can_edit` on is refused 403 by the PATCH route, and a user
  granted `no_access` is still allowed. The 5 levels are the app's own vocabulary
  (`src/features/share/types.ts:16-20`, `levelAtLeast` at `src/features/share/sharePermissionBridge.ts:92-94`).

### 2. The unowned-legacy-page hole
- `scripts/bridge-api.mjs:890`: `if (!isPublished && existing.owner_id == null) return true; // legacy / unowned page — the workspace gate suffices (NOT for published apps)`.
- That branch is inside `mayModifyPage` (`:887-897`), the only place that asks "is this caller the
  owner, or a collaborator of this page". For a row with `owner_id IS NULL` it answers "yes", so
  the page-level rule is skipped for those rows entirely.
- The only gate left in front of it is the workspace gate (`ownerOrWorkspaceAccess`,
  `scripts/bridge-api.mjs:1056-1063`, permission `update` at `:3492` / `delete` at `:3916`).
  That gate asks `memberHasPermission` (`:878-884`): role `owner`/`admin` pass, else the
  membership's `permissions` array must carry `admin` or the exact permission. A membership that
  carries `admin` but not `update` therefore **writes an ownerless page** (the branch) while being
  refused on every owned page (`:891-896` has no `admin` fallback).
- The row has no owner, so nobody can re-share it, restore it, or take it back; and the server's
  READ rule has deliberately no legacy branch (`scripts/bridge-page-read.mjs:19-21`), so an
  ownerless **private** page is readable by nobody — a black hole nobody may even open.
- The client mirrors both halves and is more permissive than the server:
  `src/shared/lib/auth/pageAccess.ts:180` (write) and `isLegacyPage` → `canReadPage`
  (`:240-241`, used at `:251`).
- `tests/canvas/bridge-page-write-agreement.test.ts:137-150` asserts the bridge's
  `canWritePageRow` and the client's `canWritePage` agree on 1008 rows — so the server change and
  the client change must land together, and the spot test at `:200-203` ("an admin permission
  alone carries both writes on an unpublished page") changes answer.

### 3. No role gating on mounted databases — a viewer can run DDL
- `resolveAccessibleMount` (`scripts/bridge-api.mjs:2894-2902`) only proves the caller has *some*
  members row in a workspace linked to the mount; the member's `role` and `permissions` are never
  read. `accessibleMountIds` (`:2910-2916`) is the listing twin.
- `handleDatabaseRows` (`:3174-3191`) accepts every op of `DB_OPS` (`:3121`: list, get, aggregate,
  insert, update, delete, upsert, batch) for any member; `handleDatabaseTxn` (`:3211-3220`) and
  `handleDatabaseSqlRo` (`:3199-3209`) likewise.
- `handleDatabaseDdl` (`:3223-3231`) forwards the body to the query-router with no role check at
  all, so any member can run `create_table`, `drop_table`, `drop_column`, `add_column`,
  `alter_column_type` (the op list: root
  `apps/grobase/src/apps/query-router/src/query/dto/schema-ddl.dto.ts:27-33`).
- The query-router cannot be the gate: it authenticates the bridge's *tenant* api-key, so
  `@CurrentUser()` there is the tenant, not the end user (root
  `apps/grobase/src/apps/query-router/src/query/schema.controller.ts:52-76`). The bridge's own
  comment says so: "every route below ALSO enforces the per-user mount ACL" (`:3115-3120`) — it
  enforces *membership*, never *role*.
- The vocabulary is there: `osionos_workspace_members.role` ∈
  `('owner','admin','editor','viewer')` and `.permissions` (root
  `models/osionos-bridge-migration.sql:39-48`), and the app writes exactly
  admin → `['create','read','update','delete','admin']`, editor → `['create','read','update','delete']`,
  viewer → `['read']` (`scripts/bridge-workspace-invites.mjs:46-50`).

## Contract

### P3-6-a — the unowned-legacy-page hole
**Security edge.** Who may call what: any app-session holder. What changes: a page with no owner
is no longer writable by a membership that carries `admin` but not `update`/`delete`; it follows
the ordinary page rule (owner, workspace owner/admin, a membership carrying the route's
permission, or an explicit `editor`/`owner` collaborator). A non-owner of an ownerless page sees
exactly what a non-owner of an owned page sees — a 403 on write, and the same 404 on read.

1. **The branch is removed.** `scripts/bridge-api.mjs:890` — the `owner_id == null` early return
   disappears; `mayModifyPage` (`:887-897`) keeps its remaining four branches unchanged.
2. **The client mirror changes with it.** `src/shared/lib/auth/pageAccess.ts:180` — the same
   branch disappears. `isLegacyPage` (`:240-241`) and its use in `canReadPage` (`:251`) are removed
   too: the server has no such branch (`scripts/bridge-page-read.mjs:19-21`), so the client must
   not show an ownerless page the server will not serve.
3. **The data is repaired (root repo).** A new `models/osionos-unowned-pages-backfill-migration.sql`
   sets `owner_id` on every `osionos_pages` row with `owner_id IS NULL` to the `owner_id` of its
   workspace (`osionos_workspaces.owner_id`, root `models/osionos-bridge-migration.sql:49-53`).
   - A row whose workspace has no row, or whose workspace has a NULL `owner_id`, is **left
     alone** (never set to a random id) and counted.
   - The migration prints the number of rows it updated and the number it skipped.
   - Idempotent: a second run updates 0 rows.
4. **`src/features/page-file/model/pageSections.ts:71-74`** (`isMine`: an ownerless root is filed
   under "private" for everyone) is a display grouping, not a gate — **not touched**. After the
   backfill there is no ownerless row left to file. Say so in the commit report.
5. **No route changes its status code.** The PATCH/DELETE answer for an ownerless page moves from
   200 to 403 for the membership that carried `admin` only; every other status stays.

### P3-6-b — role gating on mounted databases
**Security edge.** Who may call what: a member of a workspace the mount is linked to. What a
viewer sees: the schema and the rows (read), never a write, never a DDL. What an editor sees:
read + row writes, never DDL. DDL changes the *shape* of a database other members' rows live in,
so it stays with the workspace owner/admin.

1. **`resolveAccessibleMount` returns the membership.** `scripts/bridge-api.mjs:2894-2902` — the
   returned object gains `member: { role, permissions }`, read with the existing
   `callerWorkspaceMember` (`:967-971`) for the mount's `workspace_id`. The call is made once per
   request and the result is carried on the returned context.
2. **Three predicates** (new, in `scripts/bridge-api.mjs` next to `memberHasPermission`):
   - `canReadDatabase(member)` — role `owner`/`admin`/`editor` → true; else the permissions array
     carries `read` or `admin` → true; else false.
   - `canWriteDatabase(member)` — role `owner`/`admin` → true; else the permissions array carries
     `update` or `admin` → true; else false.
   - `canRunDdl(member)` — role `owner`/`admin` → true; else the permissions array carries
     `admin` → true; else false.
   They mirror `memberHasPermission` (`:878-884`) and are exported for the tests.
3. **The gate sits on the route, on the op that is actually forwarded.**
   - `handleDatabaseRows` (`:3174-3191`) resolves the op **first** (the same `safe.op` the route
     forwards at `:3188`, whose unknown-op fallback is `list` at `:3183`), then:
     `list`/`get`/`aggregate` → `canReadDatabase`; `insert`/`update`/`delete`/`upsert`/`batch` →
     `canWriteDatabase`. An unknown op falls back to `list`, so it is gated as a read and
     forwarded as a read — the gate and the forwarded op can never disagree.
   - `handleDatabaseSqlRo` (`:3199-3209`) → `canReadDatabase`.
   - `handleDatabaseTxn` (`:3211-3220`) → `canWriteDatabase` (a transaction may carry writes).
   - `handleDatabaseDdl` (`:3223-3231`) → `canRunDdl`. The bridge does **not** parse the DDL op:
     the query-router validates it (root `schema-ddl.dto.ts:27-33`).
   - `handleDatabaseSchema` (`:3149-3170`) and `handleDatabaseList` (`:3124-3146`) → `canReadDatabase`.
4. **The refusal.** 403 with the bridge's own error shape (`errorJson`,
   `scripts/bridge-api.mjs:2333-2338`): `{ ok: false, message: 'You do not have permission to
   modify this database.', code: 'database_permission_denied' }` for a write/DDL refusal, and
   `code: 'database_read_denied'` for a read refusal. The message never names the caller's role.
5. **The mount ACL is unchanged.** A caller who is not a member of a workspace linked to the mount
   still gets 403 "Database is not linked to an accessible workspace." (`:2900`) — the new role
   gate is checked **after** the mount resolves, never before.

### P3-6-c — share rules on the single-page read and write
**Security edge.** Who may call what: any app-session holder. What a rule grants: read on one
page, or write on one page — nothing else. What a non-owner sees: with a `can_view` rule, the
page's title and content; with `can_edit`, the same plus the right to write the page's content —
but never the right to change who may read it (`withoutForeignSharingChanges`,
`scripts/bridge-page-read.mjs:99-109`, still applies to a rule-holder: the sharing keys
`visibility`, `collaborators`, `workspaceId` are dropped and listed in `ignored`).
A `no_access` rule answers 404, not 403 — a page the caller may not read must not be confirmed
by a different status.

1. **A pure evaluator** — new `scripts/bridge-share-rules.mjs` (Node built-ins only, no I/O):
   - `SHARE_LEVELS = ['no_access','can_view','can_comment','can_edit','full_access']` — the same
     order as `src/features/share/types.ts:18-20`.
   - `ruleMatchesCaller(rule, ctx)` — `ctx` is `{ userId, role, workspaceId }`. A `user` target
     matches on `userId` (case-insensitively, like `sameId`,
     `scripts/bridge-page-read.mjs:33-35`); a `role` target matches on `role`; a `workspace`
     target matches when the rule's workspace is the caller's; a `public` target matches every
     caller. `resource_type` must be `page`.
   - `bestShareLevel(rules, ctx, pageId)` — over the rules that match the caller **and** whose
     `resource_id` is `''` (workspace-wide) or the page's id: if any is `no_access`, the answer is
     `no_access` (**a deny beats every grant**, rule or base); otherwise the highest level, or
     `null` when none matches. Decision 2 below says why.
   - `shareDenies(level)` — `level === 'no_access'`.
   - `shareGrantsRead(level)` — `level` is at least `can_view`.
   - `shareGrantsWrite(level)` — `level` is at least `can_edit`. `can_comment` does **not** grant
     a write.
2. **The rules for one page** — `scripts/bridge-perms-rules.mjs` gains
   `listForPage(config, workspaceId, pageId)`: one read of
   `osionos_share_rules?workspace_id=eq.<ws>&resource_type=eq.page&select=…` (the same `SELECT`
   list as `:34`, the same `LIST_LIMIT` of `:33`), filtered in JS to `resource_id === '' ||
   resource_id === pageId`. It answers `[]` when the table is missing (the store's 503 mapping at
   `:115-128` applies) — **never** a crash, and never a silent "no rules" that would deny a grant
   the caller holds: a store failure is a 503 `share_rules_unavailable`, not a deny.
3. **Write.** `mayModifyPage` (`scripts/bridge-api.mjs:887-897`) and `canWritePageRow`
   (`:1087-1092`) take the rules for the page:
   - the page owner and the workspace owner/admin keep their access whatever the rules say (they
     must always be able to manage the page and its rules);
   - for everyone else a `no_access` rule that matches them refuses the write, even when the base
     rule (a membership carrying the permission, an `editor`/`owner` collaborator) would grant it;
   - otherwise `shareGrantsWrite(bestShareLevel(...))` adds a write the base rule did not grant.
4. **Read.** `readablePageAccess` (`:1102-1109`) and `requirePageOwnership`'s sibling
   `requireReadablePage` (`:1171-1174`) consult the same rule set, with the same precedence as
   item 3: owner and workspace owner/admin always read; a matching `no_access` answers 404 for
   everyone else, even on a `public`/`shared` page; otherwise a `can_view` rule makes a page the
   base rule refuses readable. `canReadAsNonMember` (`:1052-1054`) is unchanged.
5. **Where the rules are read.** Only on the single-page routes — `GET /api/pages/:id`
   (`handlePageRead`, `:2506-2512`), `PATCH /api/pages/:id` (`handlePageUpdate`, `:3477-3536`)
   and `DELETE /api/pages/:id` (`handlePageDelete`, `:3911-3933`). One `listForPage` call per
   request, its result threaded down the same call chain. The list (`:2363-2383`), the search
   (`:2464-2496`), the graph (`:2836-2860`), the feed (`scripts/bridge-feed.mjs:89`) and the
   profile gallery (`scripts/bridge-profile.mjs:246`) keep today's rule — **a named follow-up**
   (they expose metadata only; the content is fetched per page through the single-page route).
6. **A rule never widens the workspace scope.** A `can_view` rule on a page in a workspace the
   caller is not a member of does **not** grant the read: the workspace gate
   (`ownerOrWorkspaceAccess`, `:1056-1063`) runs first and its 403/404 stands. A rule can only
   add a grant *inside* a workspace the caller already reaches.

### P3-6-d — the client mirrors the share-rule grant
**Security edge.** The client is the affordance, the bridge is the authority. Until the client
knows the rules it **under-grants** (deny by default): a rule-holder sees no edit affordance and
the page is not editable, which is safe but not usable. This package makes the client agree; it
never makes the client the decider.

1. **`/api/perms/rules` also answers the workspace-wide rules.** `scripts/bridge-perms-rules.mjs:133-136`
   filters `resource_id=eq.<id>` when a `resourceId` is given, so the workspace-wide rules
   (`resource_id = ''`) never reach the Share dialog or the client. The route answers **both**
   (the page's rules and the workspace's), so the client can evaluate the grant. The Share dialog's
   own view may keep showing the page's rules only — say which you changed.
2. **The client evaluates the same levels.** `src/shared/lib/auth/pageAccess.ts` — the write
   predicate takes the rules for the page and grants the write when the level is at least
   `can_edit` (`SHARE_LEVELS` from `src/features/share/types.ts:18-20`, `levelAtLeast` from
   `src/features/share/sharePermissionBridge.ts:92-94`). The rules come from the existing
   `fetchRules` (`src/features/share/shareApi.ts:36-40`).
3. **The agreement test grows a share-rule axis.** `tests/canvas/bridge-page-write-agreement.test.ts`
   — the 1008-row table stays (no rules in it) and a second table crosses the same rows with a
   share rule (`can_view`, `can_edit`, `no_access`, a rule for another user) so the bridge and the
   client must agree on every cell.
4. **The client still may not change the sharing keys.** A rule-holder is a non-owner for
   `withoutForeignSharingChanges` (`scripts/bridge-page-read.mjs:99-109`) on both sides.

## Decisions (orchestrator, 2026-10-22, from the drafter's open questions)
1. **A rule never reaches a non-member** of the page's workspace: the workspace gate runs first
   (least privilege). Sharing outside the workspace is publishing (`osio.publish`), not a rule.
2. **`no_access` is an explicit deny** that beats every grant, for everyone but the page owner and
   the workspace owner/admin. The draft's "absence of a grant" reading made the Share dialog's "No
   access" do nothing, and its own test (`no_access` on a public page → 404) already needed a deny.
3. **`can_comment` reads, never writes**, here and on pages. The live-DB mapping is out of scope.
4. **`/api/perms/rules` answers the page's rules and the workspace-wide ones**; the Share dialog
   keeps showing the page's own (the client filters). Say so in the P3-6-d report.
5. **The list, search, graph, feed and profile gallery keep today's rule** — a named follow-up in
   the ledger. A page a `no_access` rule hides can still show its title there; that is today's
   behaviour, not a regression, and the P3-6-c report must say it.
6. **The backfill leaves a row alone** when its workspace has no row or no owner, and the report
   lists those page ids (ids only).
7. **Private ownerless pages go to the workspace owner** and stay private: readable by that owner
   only, instead of by nobody. Not archived.
