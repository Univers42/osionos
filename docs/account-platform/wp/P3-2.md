## Decisions (binding, from the orchestrator)

1. **AAL2 gate = a signed claim, enforced inside `verifyAppSessionToken`.** The session is *born* `aal:1` with `mfa_req:true` when the user has a verified factor; no marker, no side store. Fail-closed: if the factor lookup at mint fails, **no session is minted** (503).
2. **Recovery codes**: dedicated root table `osionos_mfa_recovery_codes`, HMAC-SHA256 with a server key, single use by one atomic `PATCH ... used_at=is.null` returning the row.
3. **TOTP**: GoTrue's `auth.mfa_factors` is **not** used; a bridge-owned AES-256-GCM-encrypted secret in root table `osionos_mfa_totp` is. Evidence and the replay rule are in Contract 3.
4. **Passkeys**: management-only here; **never** a second factor in this package (no `@simplewebauthn/server`, no new dependency).
5. **Lockout**: per `(user, IP)` exponential backoff; no hard account lock, ever.
6. **The fake 2FA UI is replaced in place** in `ProfilePanel.tsx` / `ProfileSecurityModals.tsx` / `useAccountPasskeysStore.ts`, never beside them.

## Why

`/api/account/2fa/{enroll,verify,disable}` and `/api/account/passkeys/*` have **no bridge handler**: `rg -n "account/2fa|account/passkeys" scripts` returns nothing; the only matches are the client (`ProfileSecurityModals.tsx:93,110,118`, `useAccountPasskeysStore.ts`) and the vendored `notion-database-sys/.../account.routes.ts`. So today the "Two-step verification" row (`ProfilePanel.tsx:197`) toggles a client-writable flag (`security.twoStepEnabled`, `ProfilePanel.tsx:219`) and nothing verifies a code. The passkey store stores whatever the browser sends, with `'browser-passkey'` as a fallback public key (`useAccountPasskeysStore.ts:78`) and a local record when the POST fails (`:85`). This package makes the claim true or removes it.

## Contract

### 1. AAL2 gate (sub-package a)

Claims added by `signAppSessionToken` (`bridge-session-token.mjs:98`), all optional parameters with defaults that keep today's output byte-identical for callers that pass nothing:

- `aal`: `1` or `2`. `mfa_req`: `true` only when the subject has a verified factor at mint time.
- `expiresAt`/`exp` override and `jti` already exist (`jti` param is at `:98`); a re-mint passes the old `jti`, `iat_ms = now`, and the old `exp`.

Verifier (`verifyAppSessionToken`, still sync, still no I/O): after the signature/exp/cutoff/revocation checks, `if (payload.mfa_req === true && payload.aal !== 2 && !opts.allowPendingMfa) throw 403 { code: 'mfa_required' }`. The fourth parameter `opts` defaults to `{}`. `VerifiedAppSessionToken` gains `aal` and `mfaPending`.

Because every handler, the webhook (`:4682`), PAT/IDE/rtc derivation, and the `osionos-ai` service call this one function, **every route family is covered by construction**; there is no route allowlist to maintain. The only callers that pass `allowPendingMfa:true` are: the step-up routes (`status`, `verify`, `recovery/verify`) through `verifyStepUp` exported by `bridge-account-mfa-state.mjs`, and `handleBridgeLogout` (`bridge-api.mjs:4653`).

Mint (`createUserSession`, `bridge-api.mjs:1530-1578`): before `:1557`, `mfaStateFor(userId)` (mfa-state module) reads `osionos_mfa_totp` for `status='verified'` through `pg.asService()`. Result true -> sign `{aal:1, mfa_req:true}`; false -> sign `{aal:2}` (a user with no factor is aal2 by definition: nothing to step up to). **A lookup error throws 503 `mfa_unavailable` and no token is signed** (fail-closed). No cache at mint (the lookup is one indexed row; a stale "no factor" answer at mint would be a bypass). The caller of `createUserSession` already treats a throw as a failed sign-in.

Step-up: `issueAal2(session, config)` re-signs the same subject/workspaces with the **same jti**, `aal:2`, no `mfa_req`, the old `exp`. Sessions rows and sudo keyed on jti survive. The aal1 token is still refused everywhere except the three step-up routes because its signed claim says so (no lookup involved).

Rollout: tokens minted before this change carry no `aal`/`mfa_req` and keep working for their remaining life (at most `sessionTtlSeconds`). The moment a factor becomes `verified` the route calls `writeSessionCutoff(userId)` (the existing function, `bridge-api.mjs:4635` area) and then returns a fresh aal2 token for the enrolling session, so every legacy token of that user dies and any re-mint is born aal1. Stated residual: a legacy token for a user who *already* had a factor cannot exist, because no factor existed before this package.

### 3. TOTP (sub-package a)

**Why not GoTrue.** GoTrue's `/auth/v1/factors/:id/challenge|verify` require the *user's* GoTrue JWT. The bridge holds one only on the password path (`lData.access_token`, `bridge-api.mjs:4598-4608`); the handoff, MCP and P3-1 exchange paths hold none, and P3-1 passwordless users may never have a GoTrue session. I could not run the pinned image in this read-only task, so the admin `GET /auth/v1/admin/users/:id` payload (factors with `status`) is **UNKNOWN = FAIL** for the reuse branch. Decision 3 names the fallback for exactly this case, so the bridge-owned store is used. Config evidence that GoTrue MFA exists is `auth-api.yml:46-49`; that is why this is a decision and not an omission. The GoTrue factor table is left unused (no parallel TOTP in two places).

**Secret storage.** Root table `osionos_mfa_totp(user_id uuid pk, secret_enc text not null, status text check in ('pending','verified'), last_step bigint not null default 0, created_at, verified_at)`. `secret_enc` = AES-256-GCM (`node:crypto`), 12-byte random IV, key `OSIONOS_MFA_SECRET_KEY` (32 bytes, base64). Env unset -> every `/api/account/2fa/*` route answers 503 `mfa_unavailable` and `createUserSession` treats the user as lookup-failed only if the user *has* a row (a deployment without the key and without factors keeps signing in). Preflight names the var as set/unset only. Key rotation is out of scope: a rotation requires re-enrolment (stated).

**Algorithm.** RFC 6238 over `node:crypto` HMAC-SHA1, 6 digits, 30 s step, window of +-1 step, base32 secret of 20 random bytes (`crypto.randomBytes`). `Caveat:` comment in the file header: tolerates +-30 s of clock skew only; a device further off is refused (escape hatch: recovery codes). Verified against the RFC 6238 Appendix B vectors in a test, so the 25-line implementation is checked against the standard, not against itself.

**Replay.** The accepted time step is stored: the accept is one atomic `PATCH osionos_mfa_totp?user_id=eq.U&status=eq.verified&last_step=lt.N` with `Prefer: return=representation`; zero rows = the step (or an earlier one) was already used -> 422 `code_invalid`. This survives a restart and works across replicas (no KV needed). A second code from the same step is refused too (strictly increasing steps).

**Routes** (all in `scripts/bridge-account-mfa.mjs`, mounted by a):

- `POST /api/account/2fa/enroll`: explicit button only. Requires a normal aal2 session (not pending) and sudo. If a `pending` row exists it is replaced (`upsert`), so factors never accumulate. Returns `{otpauthUrl}` only (the URL contains the secret; no separate `secret` field; the UI renders the QR from it and shows the base32 text only from the same URL parse) with `cache-control: no-store`. Audit `account.2fa.enrol` is written **before** the DB call (bridge-guard header rule), `details:{method:'totp'}`.
- `POST /api/account/2fa/verify` `{code}`: the only route that moves `pending -> verified` (first valid code confirms enrolment) and the step-up for an aal1 token. Uses `verifyStepUp`. On success of a *confirmation* it writes the cutoff (Contract 1 rollout), then returns `{ok:true}` plus the aal2 token. Never returns recovery codes (b serves them).
- `GET /api/account/2fa/status`: `{enabled, methods:['totp'], recoveryRemaining?, aal}` from the server; the UI never reads `security.twoStepEnabled` again.
- `POST /api/account/2fa/disable`: requires sudo **and** aal2. No account policy forces 2FA today (stated: none exists), so no policy refusal. Deletes the TOTP row, then (b adds) the recovery codes, writes a session cutoff and revokes the account's other sessions through `bridge-session-revocations` (tested).

### 4. Lockout (decision 5)

Key `(userId, ipHash)` where `ipHash` = sha256 of the `clientMeta` IP (`bridge-guard.mjs`). `recordFailure` uses `kv.incrWithTtl('mfa-fail:'+key, 3_600_000)`. After 5 failures it sets `kv.setNx('mfa-block:'+key, '1', min(30_000 * 2^(n-5), 900_000))` and answers 429 + `Retry-After`; success clears the counter. Additionally `rateLimit(kv, ['mfa-verify','ip',ipHash])` 30 per minute. No path ever sets a per-account lock, so an attacker with the password who fails from his own IP only blocks that IP. Recovery verify and (later) passkey step-up call the same two functions. Caveat (in file header): an attacker sharing the owner's NAT IP shares the owner's backoff; the owner's cost is a delay of at most 15 minutes, never a lock.

### 5. Recovery codes (sub-package b)

- Root table `osionos_mfa_recovery_codes(id uuid pk default gen_random_uuid(), user_id uuid not null, code_hmac text not null, created_at, used_at, unique(user_id, code_hmac))` (sub-package 0).
- Codes: 10 per set, `xxxx-xxxx` from the alphabet `23456789abcdefghjkmnpqrstuvwxyz` (31 symbols) using `crypto.randomInt`. Input is lower-cased and dash-stripped before hashing.
- Hash: `HMAC-SHA256(OSIONOS_RECOVERY_PEPPER, userId + ':' + normalised)`. Unset pepper -> routes 503; preflight names it set/unset only. Row lookup is by the hash value through PostgREST equality; the only in-process comparison is none, so `timingSafeEqual` is used where the bridge compares two hashes it holds (the dry check on the batch). Offline cracking needs the pepper, which the DB does not hold.
- `POST /api/account/2fa/recovery/generate`: requires a verified factor, an aal2 session and **zero existing rows** (no sudo: the session just completed verify). `POST .../regenerate`: sudo + aal2; delete-old and insert-new happen in one PostgREST RPC-free call sequence made atomic by inserting the new set with a `generation` stamp first and deleting rows with an older stamp second, so a crash leaves old+new, never zero (tested by failing the second call).
- `POST /api/account/2fa/recovery/verify` `{code}`: step-up via `verifyStepUp`; single use by `PATCH osionos_mfa_recovery_codes?user_id=eq.U&code_hmac=eq.H&used_at=is.null` with `Prefer: return=representation`; zero rows -> uniform 422 `code_invalid` (same body for unknown, used, malformed). Success -> `issueAal2`. Audit details `{method:'recovery', remaining}` only. Same lockout as Contract 4.
- Codes are shown **once**, in the response of generate/regenerate, `cache-control: no-store`; never logged, never stored in `settings`.
