# P0-5b 👹 — presence in the kv store, reads that do not write, bounded id lists

Repo: osionos app, branch `feat/acct-P0-5b` from `feat/account-platform` **after P0-4 merges** (the
kv in `createBridgeServer`). Its SQL half is P0-5a (root); the contract below is fixed, so the two
can be built in parallel. File:line below is the app repo.

## Why
- Every open client POSTs `/api/profile/heartbeat` every 45 s (`src/shared/people/usePresenceHeartbeat.ts:24,36-39`)
  and each one PATCHes `osionos_bridge_identities.last_seen_at` (`scripts/bridge-profile.mjs:139-143`)
  with no server throttle: 10K users online ≈ 222 writes/s on the identities row.
- "Online" is `now - last_seen_at < 90 s`, defined three times (`bridge-profile.mjs:51-58`,
  `bridge-social.mjs:44-49`, inline `90_000` at `bridge-social.mjs:121,175`). No test covers it.
- `GET /api/connections` writes colleague edges and reads up to 100 000 co-member rows
  (`bridge-social.mjs:89-104`, `bridge-social-core.mjs:226-310`) — P0-5a moves that into a trigger.
- `in.(…)` lists built from unbounded id sets are sent whole: `identitySummaries`
  (`bridge-social-core.mjs:384-390`, all peers of the caller's edges), `memberWorkspacesAmong` (`:170`),
  `emitNotifications` (`:368`), chat channels (`bridge-chat.mjs:168,182-183`), communities
  (`bridge-communities.mjs:87,102`), backlinks / workspace databases (`bridge-api.mjs:2797,3308,3312`),
  profile shares (60 ids, `bridge-profile.mjs:231-236`). Kong's header buffer is 4 KB
  (`bridge-paging.mjs` Caveat). The shared `idChunks`/`inFilter` (`bridge-paging.mjs:34-61`) exist
  but only tests use them; `bridge-api.mjs:1371-1381` keeps a private copy.
- Counts are rows fetched and `.length`ed: notifications unread (`bridge-notify.mjs:41-42`), likes,
  comments, shares (`bridge-feed.mjs:145-180,307-309`).

## Contracts
1. **`scripts/bridge-presence.mjs`** — the one definition of presence.
   - Heartbeat: `kv.set('presence:' + userId, String(nowMs), 90_000)`; then
     `kv.setNx('presence-pg:' + userId, '1', 600_000)` — only when that returns true, PATCH
     `last_seen_at` (so **at most one database write per user per 10 minutes**). Rate limit
     `rateLimit(kv, ['heartbeat', userId], { limit: 10, windowMs: 60_000 })` (several tabs beat
     independently). Response 204.
   - `onlineAmong(kv, userIds)` → `Set` of online ids, from ONE `getMany` per ≤ 100 keys. Add
     `getMany(keys)` to `bridge-kv.mjs` (Redis `MGET`, memory map) with tests; same key rules and
     fail-closed semantics as the other methods.
   - **Presence never fails a request.** A kv error inside `onlineAmong` → empty set, logged once per
     state change; a kv error on heartbeat → 204 without the PG write (the next beat retries).
   - Every projection that shows `online` uses `onlineAmong`; the three `isOnline` copies and the
     inline `90_000`s are deleted. `lastSeenAt` stays the database value (now up to 10 min coarse —
     say so in a Caveat where it is projected).
2. **`GET /api/connections` writes nothing and reads no co-member embed**: remove the
   `coMemberPath` read and `insertColleagueEdges` from the GET path (P0-5a's trigger creates edges at
   join time). Delete the code that becomes dead; keep what other routes still call.
3. **Every unbounded `in.(…)` list above goes through `idChunks(ids, 50)` + `inFilter`**, requests
   issued with bounded concurrency (≤ 4 in flight), results merged in the original order where the
   caller relies on order. `bridge-api.mjs`'s private copy is replaced by the shared one. A list that
   is already bounded at ≤ 50 by construction may stay, with a one-line comment naming the bound.
4. **Counts**: notifications unread → one request with `Prefer: count=exact` and no rows (read the
   total from `Content-Range`); likes + likedByMe + comments + shares for a post → ONE
   `POST rpc/osionos_feed_page_counts` `{ p_page_id, p_viewer }` returning
   `[{ likes, liked_by_viewer, comments, shares }]` (P0-5a). The existing response shapes of
   `getLikes`, `getReactions` (its comment count) and `getShares` do not change.

## Ship gate (local merge only)
P0-5a's trigger must be live before this bridge ships, or new colleague edges stop appearing (a
feature regression, not a leak). The RPC must exist too, or the feed counts 404 → the routes must
map that to a 503 with a stable code, never a crash.

## Acceptance (tests in `tests/bridge/`)
1. 20 heartbeats from one user over a simulated 10 minutes (injected clock) → exactly 1 PATCH of
   `last_seen_at`; the 11th beat inside one minute → 429; a kv error → 204 and no PATCH.
2. `onlineAmong`: online for 89 s after a beat, offline at 91 s; 250 ids → 3 `MGET`s; kv down →
   empty set, the list route still answers 200.
3. Every projection listed in Why shows `online` from presence (one test per module, existing
   fixtures), and no file under `scripts/` contains `90_000` or a second `isOnline`.
4. `GET /api/connections` issues no POST and no co-member embed (assert on the fake's request log);
   the existing connections suites (`bridge-social-connections*.test.mjs`) are updated only where
   they asserted the removed insert — list each changed assertion in your report.
5. 500 peer ids → 10 requests of ≤ 50 ids, never more than 4 in flight, merged result complete and
   ordered; the profile-shares path with 60 ids → 2 requests.
6. Counts: unread is one request with `count=exact`; a post's counts are one RPC call; an RPC 404
   → 503 `feed_counts_unavailable`.
