# F-1 — a settings 404 that carries a code is an answer; team members show names

Follow-up from P3-5-d's review (LEDGER row P3-5d). App repo only. Not 👹.

## Why (verified anchors)

1. `src/store/settings/settingsStoreUtils.ts:70` (`classifySettingsError`) reads **every** 404 as `unavailable` ("this bridge does not serve the route"). The store then keeps working locally with no error. So a real answer such as the teams route's 404 `team_not_found` or `workspace_not_found` (`scripts/bridge-workspace-teams.mjs`) makes `createTeam` keep a local team that the server refused.
2. The bridge's unmatched-route 404 is `{ ok:false, message:'Not found.' }` with no `code` (`scripts/bridge-api.mjs:4847`). `ApiError` defaults `code` to `'API_ERROR'` when the body has none (`packages/http-gate/src/errors.ts:27`). Thrown 404s of the form `Object.assign(new Error(...), { status: 404 })` also reach the client without a code.
3. The member picker in `src/features/settings/teamspaces/TeamsSection.tsx` shows raw user ids.

## Contract

- `classifySettingsError(404, code)` returns `unavailable` only when `code` is missing or `'API_ERROR'`. A 404 with any other code returns `failed`, so the caller shows the server's message. 501 and the 503 rule are unchanged. `isSettingsEndpointUnavailable` follows automatically.
- Update the doc comment above it to say this. Its Caveat line also changes: a 404 the bridge throws without a code is still read as "route missing".
- Grep every caller of `isSettingsEndpointUnavailable`, `classifySettingsError` and `withSettingsFallback`. Confirm that none depends on a coded 404 being `unavailable`; list them in the report. If one does, stop and report it rather than patching around it.
- `TeamsSection.tsx`: the member picker and the member rows show the person's display name, falling back to the username, then the id. Resolve names from the store the People panel already uses for workspace members. Do not add a fetch per row, and do not add a new store.
