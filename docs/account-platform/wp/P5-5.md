## Why

*Why the three packages exist at all, and why the panel cannot be built first.*

- **Nothing can list what a user has published.** The publish bridge mounts exactly two route
  shapes — `POST|DELETE /api/pages/:id/publish` and `GET /api/public/pages/:token`
  (`scripts/bridge-public.mjs:24-25`). There is no route that enumerates the caller's published
  pages, so the app has no way to show them.
- **The public token exists only in one component's local state.** `src/features/share/PublishSection.tsx:19`
  holds it in `useState`; `:23` sets it from the publish call and `:24` clears it on unpublish.
  Nothing anywhere reads the published state, so after a reload the Share dialog renders
  "Publish" for a page that *is* published (`src/features/share/PublishSection.tsx:33-37` chooses
  the button from that state alone) and the `/p/:token` URL is unrecoverable.
- **No status exists.** `published_at` is written by the bridge (`scripts/bridge-public.mjs:40`),
  declared in the root SQL (`models/osionos-publish-migration.sql:14`) and read by exactly one
  thing — the public GET (`scripts/bridge-public.mjs:57,62`). No surface compares it to the page,
  so nothing can say "the public copy is older than the page".
- **The account role cannot read the table at all.** `models/osionos-publish-migration.sql:17-21`
  enables RLS and grants the table to `service_role` only. `scripts/bridge-pg.mjs:168-183` mints the
  per-user account token for `asUser`; that role has no grant on this table, so a per-user read of
  the published rows is impossible today.
- **The Settings surface has a *different* thing called "publish".**
  `src/features/settings/public-pages/PublicPagesPanel.tsx:56` lists the workspace's pages as
  "Live"/"Private" from the local store and `:35-41` flips `page.visibility` locally only; `:45`
  fabricates `*.osionos.site` domains. `page.visibility` in the database is the marketplace and
  workspace-discoverability flag (`scripts/bridge-api.mjs:2561`, `scripts/bridge-collab.mjs:143`),
  **not** a web publication. The words "published" and "live" in this package therefore mean the
  publish snapshot, never `visibility`.
- **There is no section for it.** The registry is the one place a section is declared
  (`src/features/settings/model/sections.ts:13-16`); its only public-pages entry is
  `src/features/settings/model/sections.ts:206-209`, and the panel map is
  `src/features/settings/ui/sectionPanels.tsx:32-78`.

## P5-5-a — the account role may read its own published pages (root SQL)

Repo: root groot repo, `/home/dlesieur/Documents/groot-wt/root-integration`, branch
`feat/acct-P5-5-a` from `feat/account-platform`. SQL only; no app file changes.

### Contract

1. **A new migration file** `models/osionos-publish-account-migration.sql`, idempotent, doing
   exactly this and nothing else:
   - `REVOKE ALL ON public.osionos_published_pages FROM osionos_account_user;` **first** — a
     table-level grant left over from an earlier run survives a replay and only this line takes
     it back (the house pattern, `models/osionos-account-foundation-migration.sql:206-208`).
   - `GRANT SELECT (token, page_id, title, icon, published_at) ON public.osionos_published_pages
     TO osionos_account_user;` — **column grants, not a table grant** (a table grant would hand
     the role `content`, the whole snapshot body, `owner_id` and everything else;
     `models/osionos-account-foundation-migration.sql:203-208`).
   - `DROP POLICY IF EXISTS osionos_published_pages_owner_read ON public.osionos_published_pages;`
     then `CREATE POLICY osionos_published_pages_owner_read ON public.osionos_published_pages
     FOR SELECT TO osionos_account_user USING (owner_id = (SELECT public.osionos_account_uid()));`
     — the wrapped helper is deliberate: it is evaluated once per query, not once per row
     (`models/osionos-account-foundation-migration.sql:212-215`).
   - `COMMENT ON TABLE public.osionos_published_pages IS 'osionos:account-plane';` — without the
     marker the account role reaches a relation anon does not and check `k1` fails
     (`scripts/verify/models-grants/account-checks.sql:20-41`).
   - `NOTIFY pgrst, 'reload schema';` at the end, after the COMMIT if the file has one.
2. **The file joins `ORDERED_LAST`** in `scripts/apply-models-migrations.sh:132`, right after
   `osionos-account-profiles-migration.sql`. It needs the role and `public.osionos_account_uid()`
   (`models/osionos-account-foundation-migration.sql:145-156`), and the alphabetical pass would
   otherwise reach it before the role exists. The runner must still converge: the file is applied
   on every boot, so a second pass must change no ACL, policy or RLS flag (check `g`,
   `scripts/verify/models-grants.sh:267`).
3. **The gate learns the new table.** In `scripts/verify/models-grants/account-checks.sql`:
   - append `osionos_published_pages` to the `account_plane_expected` array (`:84-93`) — the file
     says "Later packages append theirs";
   - add a check `p5_published_read` that, with A's claims and the role set to
     `osionos_account_user`, proves: A sees exactly its own published row; B's published row is
     invisible; `SELECT content` is refused with 42501; and the service role still reads the
     table (the public GET depends on it, `scripts/bridge-public.mjs:57`).
   - register it in `scripts/verify/models-grants.sh` next to the other `check_count` lines
     (`:470-486`) so a failure fails the gate.
4. **What this package does NOT do:** it does not change the table's columns, does not add a
   `status` column, does not add a trigger, and does not touch `models/osionos-publish-migration.sql`.

## P5-5-b — `GET /api/account/published-pages` (the bridge)

Repo: osionos app, `/home/dlesieur/Documents/groot-wt/integration/app`, branch `feat/acct-P5-5-b`
from `feat/account-platform`, **after P5-5-a is merged into the root branch**.

### Contract

1. **One new route, `GET /api/account/published-pages`**, in a new module
   `scripts/bridge-account-published-pages.mjs`, mounted through the account seam
   (`scripts/bridge-account-mounts.mjs:22-31`). The module answers `true` when it handled the
   request and `false` otherwise, like every other module on that seam
   (`scripts/bridge-sessions.mjs:257-259`).
2. **The gate first.** `OSIONOS_PUBLISH_ENABLED !== '1'` → **404** `publish_disabled`, exactly like
   the whole publish feature today (`scripts/bridge-public.mjs:75`). The flag is read at call
   time from `process.env` (the account seam passes no `env`: `scripts/bridge-api.mjs:4293`), and
   the module's factory takes an optional `env` so a test can inject it.
3. **The session.** `verifySession(bearerToken(request), config)` — the app-session token
   (`scripts/bridge-api.mjs:4293` passes `verifyAppSessionToken`, which requires
   `aud === 'osionos-app'`, `scripts/bridge-api.mjs:461-508`). No session → 401.
4. **The rate limit.** `rateLimit(kv, ['published-pages', session.userId], { limit: 60, windowMs: 60_000 })`
   → 429 with `retryAfterSeconds` (the helper's shape, `scripts/bridge-guard.mjs:167-178`).
5. **The read is the caller's own, through the account role, never through the service role:**
   `pg.asUser(session).get('osionos_published_pages?select=token,page_id,title,icon,published_at&order=published_at.desc&limit=50')`.
   - The RLS policy from P5-5-a does the owner filtering; the route adds **no** `owner_id` filter
     and must not read the table with `asService`.
   - `limit=50` matches the sessions list (`scripts/bridge-sessions.mjs:38`) and keeps the page-id
     list below the `in.()` ceiling noted in step 6.
   - A 22023/42501 from PostgREST is the account plane being unavailable → **503**
     `account_plane_unavailable` (`scripts/bridge-pg.mjs:46`, `:101-113`). Never a silent empty
     list.
6. **The status.** One extra read, through the service role, over the ids the account role just
   returned: `pg.asService().get('osionos_pages?id=in.(<ids>)&select=id,title,icon,updated_at')`.
   The ids come from the caller's own rows and are UUIDs from the database.
   - `status = 'live'` when the page's `updated_at` ≤ the snapshot's `published_at`;
   - `status = 'outdated'` when the page's `updated_at` > `published_at` — the public link still
     serves the older copy, and that is what "Republish" is for;
   - a page row that is not there (deleted between the two reads) → `status = 'outdated'`; the
     published row is deleted with it by the FK cascade (`models/osionos-publish-migration.sql:9`).
   - **Caveat (name it in a comment):** `updated_at` is client-supplied up to five minutes in the
     future (`scripts/bridge-api.mjs:845-851`), so a page can be made to look current; the status
     is an advisory signal, not a guarantee. **Caveat:** `in.()` breaks around 90 ids, which is why
     step 5 caps the list at 50.
7. **The response.** `200` with `{ ok: true, pages: [...] }`, one entry per published page:
   `{ pageId, token, title, icon, publishedAt, status }`.
   - `title`/`icon` are the page's current ones when the page row was found, else the snapshot's
     (`title`, `icon` are in the P5-5-a grant).
   - **The key set is exactly those six.** Never `content`, never `owner_id`, never another user's
     row. `content` is not even readable by the account role (P5-5-a).
8. **The other two actions already exist and are NOT touched:** republish is
   `POST /api/pages/:id/publish` (the upsert keeps the token —
   `scripts/bridge-public.mjs:35-45`, `on_conflict=page_id` + `resolution=merge-duplicates`, and
   `token` is not in the body), unpublish is `DELETE /api/pages/:id/publish`
   (`scripts/bridge-public.mjs:48-53`). P5-5-b does not change either route, does not add an
   audit event to them, and does not change `scripts/bridge-public.mjs`.
9. **The mount and the image.** Append the module to the `modules` list in
   `scripts/bridge-account-mounts.mjs:25`, and add `scripts/bridge-account-published-pages.mjs`
   to the COPY list of `deploy/bridge-fly/Dockerfile` (the list is at `:24-33`;
   `tests/bridge/bridge-dockerfile-closure.test.mjs:56-60` fails on a missing transitive import).
   `scripts/bridge-api.mjs` is **not** touched — the seam exists exactly so later packages do not.

## Security edges (all three packages)

- **Who may call what.** `GET /api/account/published-pages` needs the caller's app session; the
  rows it returns are the caller's own, filtered by the database, not by the route. The service
  role reads only the *pages* of the ids the account role just returned.
- **What a non-owner sees.** Nothing. The published rows are RLS-scoped to
  `owner_id = osionos_account_uid()` and the route is session-scoped. The public link itself is a
  bearer secret: `GET /api/public/pages/:token` is unauthenticated and rate-limited per IP
  (`scripts/bridge-public.mjs:25`, `:56`). The panel shows the token to its owner only, in a
  read-only field (never in a toast, never in the URL bar, where it would land in a log).
- **The token must never travel in a query string** the panel builds; it is a path segment of the
  public URL and nothing else.
- **Unpublish is gated on page access today.** `scripts/bridge-public.mjs:49` requires
  `verifyPageAccess(request, pageId, 'update')` before it deletes the snapshot, so a user who has
  lost access to the source page cannot take their public copy down through that route. P5-5-b
  does not change it; it is recorded here and in the ledger as a known gap.
- **The snapshot body never reaches the account plane.** `content` is not in the P5-5-a grant, so
  the account role cannot select it at all.
- **`published_at` is server-written** (`scripts/bridge-public.mjs:40`), but the page's
  `updated_at` is client-supplied up to five minutes into the future
  (`scripts/bridge-api.mjs:845-851`): the status is advisory.
