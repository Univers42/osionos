## Contract

1. **Code custody in the gateway (cond 1).** The gateway, not GoTrue, generates the 6-digit code (`crypto.randomInt`), stores only
   `HMAC-SHA256(pepper, "<keyHash(email)>:<code>")`, compares with `timingSafeEqual`, and never logs, audits or returns the code.
   Limits: TTL at most `CODE_TTL_SEC = 600`; the attempt counter is incremented BEFORE the comparison (so parallel guesses cannot exceed the
   cap), at most `MAX_WRONG_CODES = 5` attempts per code and 5 per address per 600 s window across all that address's codes; past either the
   code record is deleted and every later try fails the same way as a wrong code; single use (the first success claims the code with the
   `incrWithTtl === 1` pattern of `login-otp.mjs` `release`, then deletes it). A new request replaces the live code and resets that code's
   counter, not the address counter.
   **One copy of the primitives (library-first):** new `scripts/auth/code-custody.mjs` exports `CODE_TTL_SEC` (600, = today's
   `TICKET_TTL_SEC`), `MAX_WRONG_CODES` (5), `isLoginCode` (`^\d{6}$`), `bumpCounter(store, key, ttlSec)` (the `incrWithTtl` wrong-guess count),
   `claimOnce(store, key, ttlSec)` (the `release` single-use claim) and the new `hashCode`/`sameCode` (HKDF pepper, HMAC, timing-safe compare).
   `login-otp.mjs` imports the constants, `isLoginCode`, `bumpCounter` and `claimOnce` and re-exports `TICKET_TTL_SEC`/`MAX_WRONG_CODES` under
   their current names; its answers, store keys (`otp:wrong:<id>`, `otp:release:<id>`) and audit events do not change.
   Caveat to put in the file header: counters are per store; with the memory store a gateway restart resets them and a code (kept in the
   same store) dies with them, so a restart can only shorten a code's life, never lengthen it; the per-address cap lets an attacker who knows an
   address lock its code sign-in for 10 minutes (same trade-off as recovery, stated).
2. **Verify through a gateway route, never browser-to-Kong (cond 2).** `POST /api/auth/otp/verify` `{email, code, turnstileToken}` via
   `protectedAction` with `RATE_LIMITS.signinCodeVerify`. On success the gateway looks the user up (condition 5), calls admin
   `generate_link {type:'magiclink', email}` for that existing confirmed user, takes `tokenHashFrom(result.body)`, calls
   `gotrue.verify('magiclink', hash)` (`gotrue-api.mjs:44`) and requires `body.user.email` to equal the requested address; then it answers like
   password login (`auth-gateway.mjs:772-775`): 200, the session body without `refresh_token` (`sanitizeAuthPayload`), the HttpOnly cookie from
   `refreshCookie`, `scheduleLoginAlert(request, email, 'success')`. No GoTrue `/auth/v1/verify` call is ever made by the browser. Every failure
   (wrong, expired, locked, used, unknown address, unconfirmed address, malformed code, lookup or GoTrue error) is ONE answer: 401
   `{error:'signin_code_invalid', message:'That code is not right or has expired. Request a new one.'}`; a code that is not `^\d{6}$` gets
   it before any lookup. Never "no such account", "banned" or "locked".
3. **Request route answers before the job (cond 3).** `POST /api/auth/otp/request` `{email, turnstileToken}` via `protectedAction`
   (`auth-gateway.mjs:557`) with `RATE_LIMITS.signinCodeRequest`. Always 202 `ACCOUNT_MAIL_ACCEPTED`. `requestSignInCode` normalises (lowercase, trim,
   cap 254 characters before hashing the bucket key), validates with `EMAIL_REGEX`, calls `accept` and returns; **the deliverable-domain check,
   the GoTrue lookup, the code issue and the mail all run inside the queued job after the 202** (the `resendJob` order, `account-mail.mjs:70-74`),
   nothing awaited before the answer. The banned check of the draft is removed from this path: a banned account gets the same silent job, and the ban
   is enforced at the handoff (condition 8). The mail carries only the numeric code (template pair `signInCode`, never a link).
4. **Per-kind address bucket and explicit limits (cond 4).** `addressBucketKey(email, kind)`: the three existing kinds keep today's key

## Security edge

- **Enumeration:** status, body and (as far as the queue allows) latency do not depend on existence; nothing is awaited before the 202, mail
  work runs after the response (`accept` → `queue.push`). Recovery conforms; the test pins it. Verify answers one generic 401. Timing cannot be
  asserted with a fake clock; the test asserts the response is produced before the job runs (job awaited separately), which is deterministic.
  `/availability` already tells a stranger whether an email is taken; out of scope, noted.
- **Takeover:** the code is gateway-held, hashed with a pepper, bound to one email, capped at 5 tries per code and per address, 600 s, single use
  (Contract 1). The request route accepts no `redirect_to`. A password reset already logs out every GoTrue session
  (`link-flows.mjs` `finish`), so older sessions do not outlive it. A browser-direct GoTrue verify no longer exists on this path, so the refresh
  token never reaches JS.
- **Rate limits:** per IP (`rateLimit`, `auth-gateway.mjs:167`), 3 per address per hour per kind, the daily mail cap
  `scripts/auth/mail-daily-cap.mjs`. Caveat for the code: the address bucket counts requests, so an attacker can exhaust the owner's 3 codes
  (same trade-off as recovery).
- **Untrusted input:** the address is normalised, lowercased and length-capped before it is hashed into a key; the code must match `^\d{6}$`
  before any lookup.
- **Bypass:** the gateway already refuses to boot with it in production (`guards.mjs:90`); the client build guard stops a missing site key
  shipping silently; the condition 10 refusal closes the optional-secret hole (held on C-1).
- **Direct Kong `/auth/v1/otp` and `/magiclink`:** closed at the rewrite (Contract 6). The rest of `/auth/` (including `/signup` and `/token`)
  stays reachable and unchanged; Kong's own filtering of the two paths is UNKNOWN, so the rewrite is the only control this spec adds.

## Decisions (D-P3-1ds)

Replaces "Open questions (d1)".

1. **Q1, exchange or gateway handoff: gateway handoff, accepted** with conditions 2 and 8. The gateway route is the one path that already carries
   the ban, MFA and cut-off checks (APP `bridge-api.mjs:1802-1830`) and needs no bridge CORS change (`:188`). The bridge exchange stays unused; whether
   GoTrue stamps `amr: otp` for a magiclink verify therefore matters only if someone later switches to it. Supersedes the draft's gateway `amr` check.
2. **Q2, TOTP: adopted from the verdict, no refusal.** The gateway neither refuses OTP sign-in for a TOTP-enrolled account nor reads the GoTrue factor
   list (`gotrue-api.mjs:49` is the wrong store: the osionos gate is `osionos_mfa_totp` via `mfaRequiredFor`). The handoff applies
   `mfaRequiredFor` as for a password login (`aal: 1, mfaReq: true`). A hard refusal later would have to read `osionos_mfa_totp` and fail closed on a
   read error, unlike `assertAccountNotRefused`. `link-flows.mjs:129-142` is right for reset and is not a model for sign-in.
3. **Q3, who mails and who holds the code: the gateway does both** (conditions 1 and 5). GoTrue is used only to look the user up, to mint the session
   after a verified code and to supply `hashed_token` once; it never mails and its `email_otp` is never used.
4. **Q4, Kong's public `/auth/v1/otp`: closed at the website rewrite** for `/otp` and `/magiclink` (condition 6), after a caller search that stops the
   work on a hit. `/token` and signup stay as they are; password signup staying open is existing behaviour and out of scope here. Whether Kong
   already filters the two paths is UNKNOWN.
5. **Condition 10: owner prerequisite plus the guard**, with the C-1 conflict above.
6. **d2 (OAuth) stays BLOCKED on owner credentials** and is not dispatched (see its section; the verdict's notes are added there).
