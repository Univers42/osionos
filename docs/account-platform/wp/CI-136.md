## 2. `tests/e2e/functional/professionTemplates.spec.mjs:39` — Home's `updatedAt` moves after a reload (CI only)

CI (both tries): `expect(await cachedHomeUpdatedAt(page)).toBe(updatedAtBefore)` at :76,
expected `21:10:02.474Z`, received `21:10:04.843Z`. The note survives, so Home was not re-seeded, but
something re-saved it. **It passes locally** (8.3 s), so it is timing-dependent: CI is slower (the reload
took 2.4 s to domcontentloaded in the trace; React booted ~2 s after navigation).

What the CI trace shows (`0-trace.trace` of shard 4): typing ends at t=11.15 s; two reads of the
settled `updatedAt` at 11.22 and 12.66 both return 02.474; reload at 12.80; the old page logs
`[perf] persistKnownDatabaseState` at 12.90 (the pagehide seam ran); the new page logs
"API unreachable — running in offline mode with seed data" at 14.95; Home opens at 15.9; the read at
19.30 returns 04.843. Wall clock and trace clock cannot be aligned exactly, so the writer is either the
old page's unload seam (`src/store/sync/usePageSync.ts:224-233` flushOnUnload → `flushAllBlockDrafts`,
`flushScheduledPagesCachePersist`) or the new page's boot/open path (offline seed merge, Home open,
`MainContent.tsx` Home regeneration guard from P2-4).

Do this, in order:
1. Reproduce: add a TEMPORARY `page.addInitScript` that wraps `Storage.prototype.setItem` and, when a key
   starting `osio:pages:` changes the `updatedAt` of the entry whose `_id` starts `home-dashboard:`,
   pushes `{old, new, stack: new Error().stack}` to `window.__homeWrites` (persist it across the reload
   via `sessionStorage`). Slow the browser with CDP: `const cdp = await page.context().newCDPSession(page);
   await cdp.send('Emulation.setCPUThrottlingRate', { rate: 6 })` (re-apply after the reload). Run the spec
   until it fails; print `__homeWrites`.
2. Find the writer from the stack. Fix the ROOT CAUSE: a code path that stamps a new `updatedAt` on a
   page whose content did not change (a no-op write) must not stamp. Do not change the test's assertion and
   do not add waits to make it pass. If the writer is legitimate (the content really changed), report what
   changed and stop for a ruling before changing the test.
3. Remove the temporary instrumentation. Add a unit test (tests/canvas, `node --test`) that pins the fix
   at the function you changed (red before the fix, green after), and keep the e2e as it is.
4. Prove it: the spec passes 3 times in a row WITH `rate: 6` throttling still applied locally (keep the
   throttle only in a scratch copy of the spec, not committed), and passes unthrottled.
