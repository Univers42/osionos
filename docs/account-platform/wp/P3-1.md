# P3-1 👹 — Sign-in and identities

Repo/branch: app = `/home/dlesieur/Documents/groot-wt/integration/app` on `feat/account-platform`;
root SQL = `/home/dlesieur/Documents/groot-wt/root-integration` on `feat/account-platform`.
Security-sensitive (devil gate).

## Why

- The auth proxy hard-codes the Turnstile token: `scripts/bridge-api.mjs:4585` sets
  `const turnstileToken = 'localhost-turnstile-token'` and forwards it for both register and login
  (`:4592`, `:4599`). In any deployment where `TURNSTILE_BYPASS_LOCAL` is false that token is
  rejected by the gateway, so sign-in and registration silently fail; in dev it bypasses the
  check entirely. There is no path for a browser-supplied token to reach the gateway.
- `PasswordModal` (`src/features/settings/profile/ProfileSecurityModals.tsx`, the `PasswordModal`
  component) already POSTs `{ currentPassword, nextPassword }` to `/api/account/password`, but no
  bridge module answers that path: `grep /api/account/password scripts/bridge*.mjs` returns nothing,
  so the button today always reports "isn't available on this server yet".
- There is no bridge route that turns an OAuth or email-OTP GoTrue session into an osionos session.
  `handleAuthProxy` (`scripts/bridge-api.mjs:4578-4615`) only knows the password flow (it calls the
  gateway's `/api/auth/login`). The handoff primitive it reuses (`consumeHandoffToken`,
  `bridge-api.mjs:1769`; `bridgeTokenFromRedirect`, `:4544`) is server-side only.
- There is no "linked sign-in methods" surface anywhere: `rg -n "linked identit|unlink" src scripts`
  finds only generic file unlink. `auth.identities` (GoTrue) is the source of truth and is never read
  by the bridge or the app.
- `P1-6.md` already owns the truth-telling shell: `ProfilePanel.tsx:194-198` has the "Account
  security" block with Email / Password / Two-step / Passkeys rows, and `PasswordModal` is wired at
  `:218`. P1-6-b (sudo prompt, danger zone) is specified in `docs/account-platform/wp/P1-6.md` but
  its `SudoPrompt` / `DangerZone` components are not present in this tree (no `src/features/settings/ui/sudo`
  or `ui/danger`), and `onSudoRequired` (`src/shared/api/sudoRequired.ts`) has no listener. P3-1
  extends that panel in place; it does not create a second security panel.
- The site key / secret contract is documented in `tests/canvas/fixtures/auth-environment.md:14-50`
  (bypass local, gateway verifies).

## Contract

Split into sub-packages. **Order: a → (b ∥ c after a) → d after a.** b and c both edit

### P3-1-a — Turnstile + auth exchange endpoint (bridge)

1. `handleAuthProxy` (`scripts/bridge-api.mjs:4578`) stops using the constant. It reads the token from
   the request body, accepting `turnstileToken` or `cf-turnstile-response` (first non-empty wins),
   trimmed, max 2048 chars. If none is present:
   - when `config.turnstileBypassLocal === true` (dev), keep `'localhost-turnstile-token'`;
   - otherwise answer 422 `{ code: 'turnstile_required' }` and do not call the gateway.
   The token that is forwarded is the one the browser sent, never a server constant.
   `config.turnstileBypassLocal` is added to `configFromEnv` (`scripts/bridge-api.mjs:~206`) from
   `env.TURNSTILE_BYPASS_LOCAL === 'true'`. Default false (fail closed). `TURNSTILE_SECRET_KEY` is
   not read by the bridge; verification stays in the gateway, and the bridge never mints a bypass.
2. Add `POST /api/auth/exchange` (browser-facing) to `handleAuthProxy`'s sibling in
   `scripts/bridge-api.mjs`: body `{ accessToken }` (a GoTrue access token from an OAuth or OTP
   callback). The bridge:
   - reads the GoTrue user via `GET {baasUrl}/auth/v1/user` with `Authorization: Bearer <token>`
     and the public api key;
   - if that fails → 401 `{ code: 'invalid_provider_token' }`;
   - otherwise calls the gateway's `/api/auth/osionos-session` with that token exactly as the
     password flow does (`:4604-4608`) and consumes the handoff (`consumeHandoffToken`);
   - records the session with `authMethod: 'oauth'` when the GoTrue user has a non-password
     provider, else `'email_otp'` (inferred from the GoTrue user's `app_metadata.provider`, never
     from the request);
   - returns the same `{ user, accessToken, refreshToken, workspaceIds, session }` shape.
   Rate limit 20/min per IP via `rateLimit` (no user session yet).
3. The password flow's `authMethod` stays `'password'` (`:4612-4614`); nothing else changes there.

### P3-1-b — Change password (app + bridge)

1. New module `scripts/bridge-account-password.mjs` (≤300 lines, Node built-ins only) exposing
   `POST /api/account/password` (and only that path). Mounted in `bridge-account-mounts.mjs`
   (append to `modules`, after sudo and identity routes). Added to the fly Dockerfile COPY list.
   Contract:
   - requires an app session (`callerSession` from `bridge-account-sudo.mjs`);
   - requires sudo (`requireSudo(kv, session)` → 403 `sudo_required` otherwise);
   - body `{ newPassword }` (and optional `currentPassword`, ignored by the server; the sudo proof
     is the authentication). `newPassword` must be a string, 8–128 chars; otherwise 422
     `invalid_password`. No password policy beyond length here (the gateway enforces the strength
     policy at registration; changing a password that sudo-gates is the user's own act);
   - reads the caller's address from GoTrue admin (reuse `accountAddress` shape from
     `bridge-account-sudo.mjs` — extract or duplicate? Extend: export `accountAddress`? It is
     currently private; the spec's implementer exports it from the sudo module rather than copying.
     If exporting is refused, report as deviation);
   - sets the password via `PUT {baasUrl}/auth/v1/admin/users/{userId}` with the service key,
     body `{ password: newPassword }`. A non-2xx → 503 `account_plane_unavailable`;
   - on success: revoke every other session row for this user except the current jti
     (iterate `osionos_sessions` where `user_id=eq.<uid>&revoked_at=is.null`, PATCH each
     `id=neq.<currentJti>` with `revoked_at` + `revoked_reason='password_change'`, and call
     `config.sessionRevocations?.applyLocal` for each). If session records are off, fall back to
     `writeSessionCutoff` (`bridge-api.mjs`'s helper — export it or reimplement through the same
     PostgREST call) which revokes all sessions including the current one; the client then
     re-authenticates. Audit row `account.password_changed` before the action (D8 of P1-2b);
   - answers 204 on success;
   - rate limit 5 per hour per user.
   Security edge: only the holder of a valid session with a live sudo grant may change the
   password; a non-owner or a session without sudo gets 401/403 and no audit row's action runs
   (the audit is written first, per P1-2b D8, but the password is never written).
2. `PasswordModal` already sends `currentPassword`; leave the field (P1-6 owns the modal) but the
   bridge ignores it. The modal's `onSaved` updates `security.hasPassword = true` (already wired
   at `ProfilePanel.tsx:218`). No new UI file. If P1-6-b's `SudoPrompt` is present, the 403
   `sudo_required` opens it automatically through `sudoRequiredAwareFetch`; if it is absent, the
   change password action is unreachable in production and the implementer must stop and report.

### P3-1-c — Linked identities (app + bridge)

1. New module `scripts/bridge-account-identities.mjs` exposing:
   - `GET /api/account/identities` → `{ identities: [ { provider, identityId, email, linkedAt } ] }`,
     read from GoTrue admin `GET /auth/v1/admin/users/{userId}` (service key), projected to an
     allowlist of `{ provider, id, identity_id, email, created_at, last_sign_in_at }` → camelCase.
     Never returns tokens or raw metadata.
   - `DELETE /api/account/identities/:provider` (provider path segment, lowercased) → unlinks that
     provider. Requires sudo. Refuses with 409 `{ code: 'last_sign_in_method' }` if removing it would
     leave zero methods. Otherwise calls GoTrue admin to delete the identity and answers 204.
     Rate limit 10 per hour per user. Audit row `account.identity_unlinked` with `{ provider }`.
   - "Methods" are counted as: one for a password (GoTrue user has a non-null `encrypted_password`
     or `app_metadata.providers` includes `'email'` with password), plus one per OAuth identity in
     the GoTrue `identities` array. Email-OTP is not a separate method: it is the email channel
     itself. If the count is ≤ 1, refuse.
   Mounted in `bridge-account-mounts.mjs` (append). Added to fly COPY list.
2. App UI: extend `ProfilePanel.tsx`'s "Account security" section (`:194-198`) with one
   `SettingRow` "Linked sign-in methods" listing providers (Google, GitHub, 42) with Link/Unlink
   actions, and a small modal `LinkedIdentitiesModal` in `ProfileSecurityModals.tsx` (new export,
   same file, keep ≤300 lines; if it would exceed, split into `LinkedIdentitiesModal.tsx`).
   The row reuses the existing `runAccountAction` seam; a 403 opens the sudo prompt. No new section
   in `sections.ts`.
   Security edge: a user sees and unlinks only their own identities; the bridge never accepts a
   `userId` in the body; an unlinked provider can be re-linked by signing in with it again.

## Risk scores (1-5)
| axis | score | why |
|---|---|---|
| blast radius | 4 | new session-minting endpoint, password write, identity delete, sign-in for every user |
| reversibility | 3 | a minted session is revocable (P0-4); an unlinked identity or overwritten password is not restorable |
| cost on failure | 5 | account takeover |

## Findings that drive the conditions
- F1 `/api/auth/exchange` is a bypass of gateway hardening. Any GoTrue access token mints an osionos session, including one from the plain GoTrue password grant (Kong is public on :8000), which skips Turnstile and the gateway lockout. Inferring `email_otp` from `app_metadata.provider` is wrong: `email` is also the password provider.
- F2 The spec's Turnstile "fail closed" rests on the gateway. `docker-compose.public.yml:71` sets `AUTH_TURNSTILE_OPTIONAL: "true"` on the gateway, so the public funnel is not closed. The bridge never verifies (OQ7).
- F3 The bridge compose block (`docker-compose.yml:94`) passes `AUTH_GATEWAY_URL` but not `TURNSTILE_BYPASS_LOCAL`. With the new default false, every local app sign-in 422s, and the app Portal has no widget.
- F4 Contract mismatch: `PasswordModal` posts `{ currentPassword, nextPassword }` (`ProfileSecurityModals.tsx:73`); the spec's bridge reads `newPassword`. The button would 422 forever.
- F5 Password written straight to GoTrue admin with only length 8-128: weaker than the registration policy; GoTrue's own refresh tokens stay valid after the change.
- F6 OAuth/OTP/reset are specified without state, PKCE, a redirect allowlist, enumeration answers or session revocation on reset.
- F7 Last-method count: admin `GET /admin/users/{id}` is not proven to expose `encrypted_password`; passkeys are ignored; check-then-delete races.
- F8 `GOTRUE_MAILER_AUTOCONFIRM=true` (`apps/grobase/config.env:49`) means "verified email" is not a real signal locally; no test could show the collision guard.
- F9 Sub-packages are not disjoint (see C13-C16).

## CONDITIONS (paste into the spec)

### P3-1-a (bridge)
1. **Exchange accepts only passwordless proofs.** Decode the GoTrue JWT after `GET /auth/v1/user` succeeds and require `amr` to contain `oauth` or `otp` as the most recent method, with `iat` no older than 300 s; reject `password` and `token_refresh`-only tokens with 401 `invalid_provider_token`. If the pinned GoTrue emits no `amr`, STOP and report (UNKNOWN = FAIL). The gateway password path stays the only password route.
2. **`authMethod` is derived from the verified `amr`, not `app_metadata.provider`**: `oauth` when the amr method is `oauth`, `email_otp` when `otp`. Both values are in `AUTH_METHODS` (`models/osionos-account-foundation-migration.sql:171`). Add a mutant: client-supplied `authMethod` ignored.
3. **Exchange hardening.** Body `{ accessToken }` only (reject any other key), 4096-char cap, rate limit 20/min per IP AND 10/min per GoTrue user id (`rateLimit` from `bridge-guard.mjs:167`), every refusal audited without the token, response `cache-control: no-store`. Return `refreshToken: ''` explicitly and state it (the spec's "same shape" promised a GoTrue refresh token the endpoint does not receive).
4. **Turnstile verified by the bridge, independent of the gateway** (resolves OQ7): when `turnstileBypassLocal` is false, `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` with `TURNSTILE_SECRET_KEY` (name only, never logged) before calling the gateway; secret unset and bypass false → 503 `turnstile_unconfigured`; siteverify failure → 422 `turnstile_failed`; Cloudflare unreachable → 503. Siteverify call goes through the existing URL guard/fetch timeout. Caveat comment: Cloudflare outage blocks password sign-in (exchange is unaffected).
5. **Bypass is explicit and loud.** `turnstileBypassLocal` is true only for `env.TURNSTILE_BYPASS_LOCAL === 'true'`; when true and `NODE_ENV=production` or `GROBASE_PUBLIC_ADDRESSES` is set, boot fails with a clear error (reuse `bridgeBootLine`). Without one of the two, production app sign-in is dead.

The 4 KB exchange handler must live in a new module `scripts/bridge-auth-exchange.mjs` (bridge-api.mjs is 4863 lines; the rules cap files at 300); bridge-api.mjs gets one import and one dispatch line. Add it to the fly Dockerfile COPY list (or rely on the glob in the root bridge Dockerfile; `tests/bridge/bridge-dockerfile-closure.test.mjs` must pass).

## D-P3-1b condition 10: the gateway mint path (read 2026-10-23)

The gateway's `POST /api/auth/osionos-session` (`apps/opposite-osiris/scripts/auth-gateway.mjs:950-972` at the
pinned 47ca59e7) accepts ANY live GoTrue access token: it calls `auth.getUser()` and signs a bridge payload
(`provider, subject, email, name, emailVerified, jti`). It reads no `amr`, no `iat` and no session age, so a
GoTrue access token obtained by refresh mints a new osionos session like a fresh sign-in.

Consequence for P3-1-b: a password change revokes every other osionos family, but a holder of the user's
website GoTrue refresh token can refresh and mint a new osionos session afterwards, unless GoTrue ends its own
sessions on the admin password PUT (condition 9 decides). Until the follow-up below ships, the release note
says: "Changing your password signs out your other osionos sessions; a sign-in to the website made before the
change stays valid until it expires."

Follow-up work package P3-1-g (gateway + bridge, not part of b):
- the gateway adds `authenticatedAt` to the signed payload: the newest `amr[].timestamp` of the GoTrue access
  token, which stays fixed across refreshes;
- the bridge stamps a per-user `credentials_changed_at` on a password change, separate from
  `sessions_valid_after`, so the caller's own session survives;
- the bridge's mint (`handleBridgeSession`) refuses a payload whose `authenticatedAt` is older than that stamp
  (401 `reauthentication_required`), and refuses a payload with no `authenticatedAt` once the stamp exists.
Test: a sign-in before the change cannot mint after it; a sign-in after it can.
