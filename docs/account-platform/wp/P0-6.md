# P0-6 👹 — content-checked uploads, avatars in storage, no `data:` in responses

Repo: osionos app, branch `feat/acct-P0-6` from `feat/account-platform` **after P0-4 merges** (the
account mount seam `bridge-account-mounts.mjs`, the kv in `createBridgeServer`) **and root P1-1
merges** (`osionos_profiles.avatar_url`, CHECK `^(https://|/)`, never `data:`; the people
directory view already prefers it).

## Why (facts from the research, file:line in the app repo)
- Serving is already hardened: `servedObjectHeaders` (`scripts/bridge-storage-core.mjs:85-93`)
  sends `nosniff` and `CSP: default-src 'none'; …; sandbox`, forces `attachment` for non-inline
  types, and page types are refused 415 before a byte is stored
  (`tests/bridge/bridge-media-serve-hygiene.test.mjs:90-101`). **But the type is the declared
  `Content-Type` only** (`bridge-media.mjs:46`, `bridge-chat-media.mjs:113`, `bridge-collab.mjs:283-291`):
  no byte is ever checked.
- Avatars are `data:` URLs of up to 200 KB in `osionos_bridge_identities.profile.avatar`
  (`bridge-profile.mjs:49-52,120-134`) and ride in ~15 list projections (profile `:95,104`,
  people `:172,179`, `bridge-social.mjs:57,125,178,265`, `bridge-chat.mjs:79,95`,
  `bridge-collab.mjs:197,214`, `bridge-workspace-invites.mjs:197,241`,
  `bridge-communities.mjs:44,67`, `bridge-feed.mjs:137`, `bridge-social-core.mjs:397`): a
  200-person directory page can carry ~40 MB.
- The bridge has no image library and keeps to Node built-ins (`bridge-api.mjs:14-19`); sharp
  exists only in grobase behind `STORAGE_TRANSFORMS_ENABLED`, off by default. So **resizing happens
  in the browser** (the client already downsizes, `ImageAvatarUpload.tsx:25-42`, and
  re-encodes chat images to WebP, `src/shared/chat/mediaProcessing.ts:75-107`); **the bridge
  verifies bytes and strips metadata** — it never trusts the client to have done either.

## Contracts
1. **`scripts/bridge-mime.mjs`** — `sniffMime(buffer)` → `'image/png' | 'image/jpeg' | 'image/gif' |
   'image/webp' | 'application/pdf' | …| null` from magic bytes, and `assertBytesMatch(declared,
   buffer)`. Called **once, inside the shared writer `storagePut`** (`bridge-storage-core.mjs:138`),
   so all three upload routes are covered at the root: every type `servedObjectHeaders` would
   serve **inline** must sniff to exactly that type, else 415 `unsupported_media_type` and no
   storage write. Types served as attachments need no sniff (they are never rendered).
2. **`scripts/bridge-image-meta.mjs`** — pure functions over a Buffer, no dependency:
   `imageInfo(buffer)` → `{ type, width, height }` for PNG/JPEG/GIF/WebP (VP8, VP8L, VP8X), and
   `stripImageMetadata(buffer)` → a new Buffer without: WebP `EXIF`/`XMP ` chunks (VP8X flags and
   the RIFF size fixed); JPEG `APP1`–`APP13`, `APP15`, `COM` (keep `APP0`, `APP14`); PNG `tEXt`,
   `zTXt`, `iTXt`, `eXIf`, `tIME`; GIF comment extensions. A malformed or truncated file → throws
   (→ 415). Each format's parser bounds every length against the buffer (no infinite loop, no
   out-of-range read — the P0-3 RESP parser hung on exactly that).
3. **`scripts/bridge-avatar.mjs`** — mounted through `bridge-account-mounts.mjs`; the old
   `POST /api/profile/avatar` route is **removed from `bridge-profile.mjs`** (`:265`) so dispatch
   order cannot matter.
   - `POST /api/profile/avatar` body `{ variants: { "64": b64, "160": b64, "460": b64 } }` (cap
     512 KB): each must sniff `image/webp` or `image/jpeg`, be exactly square at its size, and fit
     its cap (24 / 80 / 300 KB); stripped, then stored in bucket `avatars` as
     `<sha>-<size>.<ext>` where `<sha>` is the sha256 of the stripped 460 variant. Then
     `asService` PATCH `osionos_profiles?user_id=eq.<me>` `{ avatar_url: '/api/media/avatars/<me>/<sha>-160.<ext>' }`
     (the role has no UPDATE on `avatar_url` by design — the bridge sets it after checking).
     `rateLimit(kv, ['avatar', userId], { limit: 10, windowMs: 3_600_000 })`.
     The **legacy body `{ dataUrl }`** (a cached old client) is still accepted: validated, stripped,
     stored once as `<sha>.<ext>`, same PATCH — no caller breaks.
   - `DELETE /api/profile/avatar` → `avatar_url` NULL, 204.
   - `GET /api/media/avatars/:userId/:key` (`key` = `<64 hex>(-(64|160|460))?.(webp|jpg|png|gif)`),
     **no session** (avatars are shown to other people; the key is content-addressed), headers
     `servedObjectHeaders` + `cache-control: public, max-age=31536000, immutable` + `etag`;
     `If-None-Match` → 304.
   - `publicAvatar(value, config)` — the ONE projection helper: `data:` → `null`; a
     `/api/media/` path → `${OSIONOS_BRIDGE_PUBLIC_URL}${path}` (absolute, because consumers put it
     straight into `<img src>` on the app origin; unset → the relative path, and the boot line
     warns); `https://` → unchanged; anything else → `null`. Apply it at every user-avatar
     projection above — find the shared projection functions and apply it there, not per call
     site (channel/community avatars are separate fields, out of scope).
4. **`scripts/bridge-migrate-legacy-avatars.mjs`** (the `bridge-` prefix puts it in the root
   image's glob) — dry-run by default, `--apply` to write. Pages identities whose
   `profile->>avatar` starts with `data:` (keyset on `user_id`, 50 per page, `bridge-paging.mjs`),
   validates (≤ 200 KB, PNG/JPEG/WebP/GIF by bytes), strips, stores `<sha>.<ext>`, then PATCH
   `osionos_profiles?user_id=eq.X&avatar_url=is.null` — a user who uploaded a new avatar meanwhile
   wins, and a re-run changes nothing. Prints counts only (scanned, migrated, already set,
   invalid by reason, failed); never a URL, email or byte. The `data:` value stays in identities
   (clearing it needs an in-SQL `profile - 'avatar'`; ledger follow-up).
5. **Frontend** — `ImageAvatarUpload.tsx` produces the three square variants with
   `canvas.toBlob('image/webp', q)`, falling back to `image/jpeg` when the blob type is not WebP,
   and posts `{ variants }`; the settings avatar (`ProfilePanel` → `Avatar` → `IconValueView`)
   must render a URL (the research found `IconValueView` renders an image only for `img:`-prefixed
   values, `packages/osionos-ui/src/atoms/IconValueView/IconValueView.tsx:36` — fix the caller,
   not the package, unless the package is the only way; say which).

## Acceptance (tests)
1. HTML bytes declared `image/png` → 415 on all three upload routes, `storage.puts` unchanged; a
   real PNG declared `image/png` → 201; a PDF declared `application/pdf` → 201; a ZIP declared
   `application/octet-stream` → 201 (attachment, no sniff needed).
2. `stripImageMetadata`: fixtures built in the test (a JPEG with an `APP1 Exif` GPS block, a WebP
   with `EXIF`+`XMP ` chunks and VP8X flags set, a PNG with `tEXt`) come out without them and
   still parse with `imageInfo`; truncated/oversized-length inputs throw within 50 ms.
3. Avatar POST: wrong size, non-square, over-cap, SVG/HTML bytes → 415/422 with no storage write
   and no PATCH; a valid set → 201, three objects, one PATCH with the 160 URL; legacy `{dataUrl}` →
   one object, one PATCH; the 11th upload in an hour → 429.
4. Serve: 200 with `immutable`, `nosniff`, sandbox CSP; ETag → 304; unknown key → 404; a key not
   matching the pattern → 404 without a storage call.
5. Every listed projection returns `null` for a `data:` avatar and an absolute URL for a stored
   one (one test per module, using its existing fixtures).
6. Migration: dry-run writes nothing; `--apply` migrates, a second `--apply` migrates 0; a row
   whose `avatar_url` was set meanwhile is not overwritten; invalid legacy data is counted.
7. e2e (offline build can't reach a bridge — use the existing bridge fakes the e2e suite already
   has, or a canvas test over the variant producer if e2e has none): the uploader posts three
   square variants of the right sizes.
