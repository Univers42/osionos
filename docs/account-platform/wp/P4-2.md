## Why

- **The VM has two ceilings and neither one counts instructions.** `VM` holds `stack`, `locals`, `max_stack` (`src/shared/notion-database-sys/src/lib/engine/src/vm.rs:49-53`) beside `MAX_STACK_SIZE = 10_000` and `MAX_CALL_DEPTH = 256` (`src/vm.rs:55-56`). The dispatch loop (`src/vm.rs:91-306`) checks the depth once per entry (`src/vm.rs:85-87`) and the stack once per opcode (`src/vm.rs:92-94`) — and nothing else. `MAX_STACK_SIZE` does not bound work either: the stack holds one `Value::Array` per level (`src/types.rs:60`), not one slot per element, so an array of 100 000 elements pushes **one** slot.
- **The work is multiplicative and unbounded by both ceilings.** `run` is re-entered for every closure call (`src/vm.rs:404`), and the array builtins re-run the closure body once per element (`src/functions/array.rs:58-84` for `map`, `:45-55` `call_closure_with` → `src/vm.rs:377-416` `call_closure`). `map` over an array of N whose closure maps another array of N costs N² closure calls; Nᵈ for d levels of nesting. `MAX_CALL_DEPTH` bounds the *nesting*, not the product, and the product is what burns the reader's CPU.
- **There is no error kind for "too expensive".** `ErrorKind` (`src/error.rs:28-57`) has `TypeError`, `DivisionByZero`, `PropertyNotFound`, `FunctionNotFound`, `ArityMismatch`, `IndexOutOfBounds`, `InvalidRegex`, `StackOverflow`, `CircularDependency` — no budget. The message table (`src/error.rs:68-103`) has no budget wording, and `StackOverflow` (`src/error.rs:98`) means *depth*, not work.
- **The TS bridge cannot tell a budget stop from a broken engine.** `evalFormula` returns `FORMULA_ENGINE_UNAVAILABLE` (`'#ENGINE_UNAVAILABLE'`, `src/lib/engine/bridge.ts:59`) for **every** `ok:false` (`bridge.ts:118-128`); `evaluateHandle` (`bridge.ts:132-142`) and `batchEvaluate` (`bridge.ts:146-171`) do the same. The wasm's `EvalResult` (`src/lib.rs:57-63`) carries only a free-text `error: String`. A formula that ran out of budget and a browser where the wasm never loaded are the same value on screen.
- **`batch_evaluate` swallows the error entirely.** `src/lib.rs:242-249`: a row that fails is pushed as `JsonValue::Empty` and the batch still answers `ok:true` — a budget stop in a batch is invisible, and the loop keeps burning CPU on the rows after it.
- **The crate has no tests at all.** There is no `#[test]` and no `#[cfg(test)]` module anywhere under `src/lib/engine/src/`, so the VM's two existing ceilings have never been exercised. That is why "cargo tests" is in the plan's scope, and why this package has to build the test rig from scratch.
- **A Rust change does nothing until `pkg/` is rebuilt.** `pkg/` is tracked in the engine repo (`git ls-files pkg` → `pkg/README.md`, `pkg/formula_engine.d.ts`, `pkg/formula_engine.js`, `pkg/formula_engine_bg.wasm`, `pkg/formula_engine_bg.wasm.d.ts`, `pkg/package.json`) and `bridge.ts:73-74` imports `./pkg/formula_engine.js` at runtime. The app's own image does not rebuild it — `docker/services/node/Dockerfile` is a plain `node:22-alpine` dev image, and the wasm-building `Dockerfile` belongs to the submodule, not to the app's build path. The committed `pkg/` **is** the shipped artifact.

## Contract

### P4-2-a — the fuel budget in the VM (do this one first)

1. **A new error kind.** `ErrorKind::BudgetExceeded { limit: u64 }` in the runtime group of `src/error.rs:28-57`. Its message (`src/error.rs:68-103`): `"Formula budget exceeded: more than {limit} instructions"`. `Caveat:` the budget counts **opcodes**, not wall-clock time and not bytes — one `repeat("x", 10000)` call is one instruction and allocates 10 000 characters (`src/functions/text.rs:295-308`), and `sort`/`unique`/`sum` over a 100 000-element array are one instruction each (`src/functions/array.rs:255-353`).
2. **A stable machine-readable code.** `ErrorKind::code(&self) -> &'static str` returns a snake_case code for every variant (`"budget_exceeded"`, `"stack_overflow"`, `"division_by_zero"`, `"type_error"`, …) and `FormulaError::code()` delegates to it. The code is the channel the TS side reads; it is never a message, and a message is never parsed.
3. **The counter lives on the VM.** `VM` (`src/vm.rs:49-53`) gains `fuel: u64` and `max_fuel: u64`, next to `const DEFAULT_MAX_FUEL: u64 = 1_000_000;` (`src/vm.rs:55-56`). `VM::new()` (`src/vm.rs:59-65`) sets both to the default; `VM::with_budget(max_fuel: u64) -> Self` sets an explicit budget (used by the tests and available to a future per-call budget).
4. **One instruction = one dispatched opcode.** In `run()` (`src/vm.rs:91-306`), **before** the `match` on `code[ip]`: if `self.fuel == 0` return `Err(FormulaError::new(ErrorKind::BudgetExceeded { limit: self.max_fuel }, None))`, else `self.fuel -= 1`. The opcode that trips the budget never executes. A `Jump`/`JumpIfFalse` costs one instruction like any other.
5. **The budget is per evaluation, not per VM instance.** `execute()` (`src/vm.rs:67-76`) does **not** refill the fuel. `eval_chunk` (`src/lib.rs:154-159`) builds a fresh `VM` per evaluation, so each `evaluate` (`src/lib.rs:201-229`) and each `eval_formula` (`src/lib.rs:313-339`) gets the whole budget. `batch_evaluate` calls `eval_chunk` per row, so every row gets the whole budget too (decision 2). The fuel is shared with nested calls because `run` takes `&mut self` (`src/vm.rs:78-84`) and `call_closure` re-enters `run` on the same VM (`src/vm.rs:404`).
6. **A budget stop is an error, never a partial value.** It propagates out of `execute` → `eval_chunk` → the wasm export exactly like `StackOverflow` does today (`src/vm.rs:85-87`).
7. **`batch_evaluate` is unchanged** (decision 2): a row over budget is `JsonValue::Empty`, and
   the batch answers `ok:true`. Add the `Caveat:` line above the `Err(_)` arm at
   `src/lib.rs:247`.
8. **The wasm surfaces the code.** `EvalResult` (`src/lib.rs:57-63`) gains `error_code: Option<String>`, filled from `FormulaError::code()` by `evaluate` (`src/lib.rs:201-229`) and `eval_formula` (`src/lib.rs:313-339`). `BatchResult` is untouched (decision 2). `CompileResult` (`src/lib.rs:49-56`) is untouched: a compile error is never a budget error.
9. **The budget is fixed and not raisable by a formula.** No opcode, builtin, property or request changes `max_fuel`. `Caveat:` the budget bounds **one evaluation**, not one page — a view with 1 000 rows evaluates the formula 1 000 times, each with its own budget.
10. **Documented.** The engine's `README.md` gets the budget next to the other limits; `CHANGELOG.md` gets an entry in the file's own format (`- **HH:MM** \`feat(vm)\` …`).

### P4-2-b — rebuild `pkg/`, surface it in the TS bridge, land the chain

1. **Rebuild `pkg/`.** Run the build above and replace the six tracked files under `src/lib/engine/pkg/`. The rebuilt `formula_engine_bg.wasm` **must** differ from the committed one — paste `sha256sum` of both. If it does not differ, the build did not pick up the change: stop and report, do not commit an unchanged artifact.
2. **`bridgeTypes.ts`** gains `error_code?: string` on `EvalResult` (`bridgeTypes.ts:27-31`). `BatchResult` is untouched (decision 2).
3. **`bridge.ts`** gains `export const FORMULA_BUDGET_EXCEEDED = '#BUDGET_EXCEEDED';` next to `FORMULA_ENGINE_UNAVAILABLE` (`bridge.ts:56-59`), and `evalFormula` (`bridge.ts:118-128`) and `evaluateHandle` (`bridge.ts:132-142`) return that sentinel when the wasm result is `ok:false` **and** `error_code === 'budget_exceeded'`. Every other failure keeps returning `FORMULA_ENGINE_UNAVAILABLE` (today's behaviour at `bridge.ts:124` and `:138`; `batchEvaluate` is unchanged). The match is on `error_code` only — never on the error text.
4. **The mapping is a pure exported function**, so it is testable without the wasm: `export function surfaceEvalResult(result: EvalResult): unknown` in `bridge.ts`, used by both call sites. Node cannot load this `--target web` wasm: `initFormulaEngine` does `await import('./pkg/formula_engine.js')` then `mod.default()` (`bridge.ts:73-74`), and the default init fetches `new URL('formula_engine_bg.wasm', import.meta.url)` — Node's `fetch` has no `file:` scheme, so the wasm never loads in a Node test and `initFormulaEngine()` always returns false there.
6. **The app needs no change, and must not get one.** `resolveFormula` (`src/shared/notion-database-sys/src/store/slices/computedSlice.ts:138-164`) calls `evalFormula` (`computedSlice.ts:150`); `formatFormulaResult` passes any non-empty string through (`src/shared/notion-database-sys/src/store/slices/storeHelpers.ts:119-126`, `:124`); `renderFormula` prints any value that is not `''`, `null` or `'#ERROR'` (`src/shared/notion-database-sys/src/components/views/table/cellRenderers/RelationCellRenderers.tsx:59`, `:62`). So the cell shows `#BUDGET_EXCEEDED` as plain text with no app-side edit. If the implementer believes the app must change, that is a deviation to report, not a file to edit.
7. **The commit chain**, in this order and nothing else:
   - the engine repo: P4-2-a's commit, then this package's engine commit (`pkg/` + `bridge.ts` + `bridgeTypes.ts`);
   - the parent repo (`notion-database-sys`): one commit that records the engine SHA in the `src/lib/engine` gitlink;
   - the app repo: one commit that records the parent's SHA in the `src/shared/notion-database-sys` gitlink.
8. **Security edge — who may call what, and what a non-owner sees.**
   - The formula is authored by whoever can edit the property; the **evaluation happens in every reader's browser** (`src/shared/notion-database-sys/src/object_database.tsx:562-564` initialises the engine in the client, `computedSlice.ts:150` evaluates per row). An expensive formula therefore burns the CPU of every reader of that database — the budget protects their tab, not the author's.
   - The budget is **deterministic**: an instruction count, not a timer. The same formula either always succeeds or always fails, for every reader, on every machine. A wall-clock budget would not be.
   - The budget is **not raisable by the author**: no formula, property or request changes `max_fuel`. A formula that fails for one reader fails for all of them.
   - What a non-owner sees: the literal text `#BUDGET_EXCEEDED` in the cell (`RelationCellRenderers.tsx:59-62`) — identical for every reader of that database. It leaks only "this formula is too expensive", nothing about the row's data.
   - What a non-owner cannot do: raise or disable the budget, or read a row they may not see. The engine only ever receives the properties of the row it evaluates (`src/vm.rs:31-33` `EvalContext`), which that reader is already allowed to see.
   - `Caveat:` the sentinel is cached like any other result (`computedSlice.ts:153`, `src/shared/notion-database-sys/src/lib/formula/formulaCache.ts:19-21` keys on expression + page + `updatedAt`), so it stays on screen until the formula or the row changes.
